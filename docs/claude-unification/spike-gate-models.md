# 検証の記録: 閉じたコンテキストの推論のゲートを Claude のモデルで判定する

- 日付: 2026-11-24 JST
- 目的: 閉じたコンテキストで高い推論が要る規則 ([rule-gates.md](rule-gates.md) の 6 節の 3 の経路) を、Codex でなく Claude Code の `claude -p` で判定した場合に、使える出力が出るかを確かめる。比べたのは Sonnet 5.5 の `medium` と `high`、Opus 5.5 の `medium` と `low` の 4 つの設定である。5 節で、同じ題材を Codex の Sol と Terra でも判定させた。

## 1. 題材

オーナーが差し戻した実際の返事を 1 つ使った。正解は、オーナーの差し戻しの文で決まっている。

- オーナーの指示: 「状況を報告し、ネクストアクションを提案せよ」
- 返事: 案 C の 2 つの検証の結果を報告し、次の手として「呼び出しの制限」と「完了判定の材料」の 2 つの検証を提案したもの (2026-11-23)。
- オーナーの差し戻し: 「検証で何を検証するのかを説明していないので判断できません。」「そのサンドボックスを動かせなかったことの原因も、それによる問題も説明できてないんだよね。っていうか、サンドボックスでやらなければいけない理由も説明できてない。」

正解は「不合格」で、提案の項目ごとに、何を確かめるのか、サンドボックスが動かない原因と起きる問題、サンドボックスが要る理由が書かれていないことが不合格の理由である。返事には、字のまま訳した「砂箱」、作業の中で付けた「担い手」「判定の口」も残っていた。

## 2. 渡し方

- 入力: オーナーの指示、返事、チェックリスト。判定の材料は、この指示と出力物の組だけにした。
- システムプロンプト: 規則ごとに `pass`・`fail`・`n/a` と、根拠の引用・理由・直し方を JSON で返すよう指示した。
- 起動: `claude -p --model <モデル> --effort <強さ> --setting-sources "" --tools "" --system-prompt <指示> --output-format json --no-session-persistence`

チェックリストを変えて 3 回比べた。

- 1 回目: 返事に当てはまる 3 の経路の規則 6 件 (7・18・19・56・101・102) を、rule-gates.json の規則の文と違反の見つけ方の 1 行で渡した。
- 2 回目: 同じ 6 件に、元になったメモリの本文を付けた。
- 3 回目: 1 回目の 6 件に、オーナーの差し戻しから書ける規則を 1 件足した。「判断を求める提案は、読み手がその返事だけで、項目ごとに採るかどうかを決められるように書く。項目ごとに、何を確かめる・何をするのか、それが要る理由 (いま何が起きていて、放っておくと何が困るか)、分かっているなら問題の原因が書かれているか。項目の中の語が、作業の記録を見ていない読み手に通じるか」。

## 3. 結果

4 つの設定とも、すべての回で指定どおりの JSON を返した。1 回の判定は 10〜46 秒だった。

### 3.1 規則の 1 行か、メモリの本文を渡した場合 (1 回目と 2 回目)

どの設定も、オーナーが差し戻した点を挙げなかった。

- 規則 19 (説明を Why → What → How の順で書く) は、1 回目の Sonnet の `medium` を除いて合格にした。返事全体の並び順だけを見て、提案の項目ごとに理由があるかは見ていない。
- 挙げた不合格は、次のとおりで、オーナーが挙げなかった点である。
  - 規則 18: 案 C の成否を決める 2 点が未検証のまま、案 C で設計に進むことを推奨している。1 回目は Sonnet の `high` と Opus の `medium`、2 回目は Sonnet の `medium` を除く 3 設定が挙げた。
  - 規則 56: 「上の検証」が段落をまたいで指している。1 回目は 3 設定、2 回目は 4 設定が挙げた。

### 3.2 読み手が判断できるかを問う規則を足した場合 (3 回目)

4 つの設定とも、足した規則を不合格にした。挙げた理由は設定で違う。

- Opus 5.5 `medium`: 項目に何を確かめるかしか書かれておらず、いま起きている問題、放っておいた場合の困りごと、原因が無いと挙げた。原因として、判定にツールの結果を渡していないこと、ミニ PC で Codex のサンドボックスが動かないこと、個人契約の呼び出しの制限を挙げた。「判定の口」「担い手」「砂箱」が通じないとも挙げた。
- Sonnet 5.5 `high`: 項目に要る理由と困りごとが無く、理由が前の節に散らばっていると挙げた。項目 2 の原因が無いことと、作業の中の呼び名が通じないことも挙げた。
- Sonnet 5.5 `medium`: 項目 2 に要る理由と原因が無いことと、「砂箱」「判定の口」が通じないことを挙げた。
- Opus 5.5 `low`: 「判定の口」「担い手」「砂箱」が通じないことと、サンドボックスが動かない原因が分かっているかが書かれていないことを挙げた。困りごとは挙げなかった。

どの設定も、サンドボックスでやる理由が書かれていないことは、はっきりとは挙げなかった。

### 3.3 費用と時間

`claude -p` の出力が示した一覧の料金での費用である。同じシステムプロンプトをキャッシュから読んだ回は安く出るので、回ごとのばらつきがある。

- Sonnet 5.5 `medium`: $0.05〜0.11、22〜26 秒、出力 1,300〜2,700 トークン
- Sonnet 5.5 `high`: $0.04〜0.06、27〜46 秒、出力 3,300〜5,200 トークン
- Opus 5.5 `medium`: $0.13〜0.23、27〜30 秒、出力 2,300〜3,000 トークン
- Opus 5.5 `low`: $0.02〜0.04、10〜19 秒、出力 700〜1,600 トークン

## 4. 分かったこと

- 判定できるかを決めたのは、モデルより規則の書き方だった。規則の 1 行の要約やメモリの本文では、どの設定も核心を挙げず、読み手がその返事だけで項目ごとに判断できるかを問う形に書くと、4 つの設定とも挙げた。チェックリストの項目は、メモリの規則を写すのではなく、読み手と単位 (返事全体か、提案の項目ごとか) を決めた問いに書き直す必要がある。
- モデルの差は、挙げる理由の網羅に出た。原因・困りごと・通じない語の 3 つをそろえて挙げたのは Opus 5.5 `medium` だけだった。
- 試したのは不合格の返事 1 件だけで、合格の返事を誤って不合格にするかは確かめていない。

## 5. Codex の Sol と Terra で判定した場合

同じ題材・同じ 3 通りのチェックリストを、ミニ PC の Codex CLI 0.172.0 で判定させた。比べたのは次の 5 つの設定である。

- `gpt-6.2-sol` の `low` と `medium`
- `gpt-6.1-terra` の `low` と `medium`
- `gpt-6.1-sol` の `low` ([rule-gates.md](rule-gates.md) の 6.2 節で 3 と 5 の経路に割り当てた設定)

起動は `codex exec - --ignore-user-config --ephemeral --skip-git-repo-check --sandbox read-only -m <モデル> -c model_reasoning_effort=<強さ> --json -o <出力>` で、判定の指示 (Claude でシステムプロンプトに渡したもの) を入力の先頭に付けて標準入力から渡した。Codex は自分の指示 (約 12,000〜15,000 トークン、キャッシュから読む) を足すので、入力は 1 回あたり約 18,000〜31,000 トークンになった。

### 5.1 結果

15 回とも指定どおりの JSON を返し、1 回は 20〜32 秒だった。約 8 分で 15 回を呼んだが、429 は返らなかった。11-23 の検証 ([spike-reply-gate.md](spike-reply-gate.md) の 5.4 節) とはログインが違う (今回は 11-24 にログインし直した `~/.codex` の側) ので、制限の数え方の違いかは分からない。

- 1 回目 (規則の 1 行): 5 つの設定とも、規則 7 (各項目に推奨とその根拠を事実で付ける) を不合格にした。理由はどれも、提案の項目と同じ箇所に、その検証を勧める根拠の事実が無く、前の節に散らばっているというもので、オーナーの差し戻しの一部 (項目ごとに理由が無い) に当たる。規則 19 (Why → What → How) も 5 つとも不合格にした。Claude の 4 つの設定は、規則 7 を全回で合格にしていた。
- 2 回目 (メモリの本文を付けた): 規則 18 は 5 つとも「対象外」にした。メモリの本文が、見本で示した要求と候補の合致を評価する場面に限っているためである。規則 7 の理由は、判断の資料を独立した Artifact にしていない、2 つの判断を束ねている、に移り、核心から離れた。規則 102 は 3 つの設定が、環境の記録を直して push した報告が依頼の対象外だとして不合格にした。
- 3 回目 (読み手が判断できるかを問う規則を足した): 5 つとも、足した規則を不合格にした。
  - `gpt-6.2-sol` `medium`: 項目ごとに、いま起きている問題、放っておいた場合の困りごと、分かっている原因がまとまっていない、と 3 つをそろえて挙げた。「Jev」が何をするものか、「砂箱」が完了判定にどう関わるかが説明されていない、とも挙げた。
  - `gpt-6.2-sol` `low`: 現状と放っておいた場合の困りごとが無いこと、「Jev」「砂箱」の役割が無いことを挙げた。原因は挙げなかった。
  - `gpt-6.1-terra` `medium`: 現状と困りごとが項目ごとにまとまっていないこと、「Jev」「完了判定」の役割が無いことを挙げた。
  - `gpt-6.1-terra` `low`: 原因が分かっていないことが項目に書かれていないこと、「規約の判定」「完了判定」「Jev」「砂箱」が通じないことを挙げた。
  - `gpt-6.1-sol` `low`: 「Jev」が何かが無いことと、完了判定の項目に現状と原因が無いことを挙げた。

### 5.2 分かったこと

- 規則の 1 行のままでも、Codex の 5 つの設定は、提案の項目ごとに根拠が無いことを規則 7 の違反として挙げた。Claude の 4 つの設定は同じ規則を合格にしていたので、違反の見つけ方の文 (「同じ箇所に書かれているか」) を字のとおりに当てるかどうかで差が出た。オーナーの差し戻しの中心 (何を確かめるのかが無い) を挙げた設定は無かった。
- 読み手が判断できるかを問う規則を足した場合の網羅は、`gpt-6.2-sol` の `medium` が Opus 5.5 の `medium` と同じ水準だった。Sol は `low` より `medium` が、Terra は `low` と `medium` で挙げる点が違うが網羅の差は小さかった。
- メモリの本文を付けると、Codex は規則の適用の範囲を本文に合わせて狭めた (規則 18 を対象外にした)。チェックリストに本文を付けるかは、規則ごとに範囲を確かめてから決める必要がある。
- Codex は個人の定額のログインで動くので、1 回ごとの従量の費用は出ない。
