# 部品の調査の計画

- 更新: 2026-11-03 JST
- 種別: 調査の計画。調査の結果と設計の結論は書かない。
- 物差し: [Claude 一本化の要件](requirements.md) の 3 節と 4 節。各項目に、根拠にした要件の番号を付ける。

## 1. この調査で決めること

設計の要素ごとに、どの既存の部品で作れるかを決める。部品は、Claude の公式の機能、公開されているスクリプト、OSS の 3 種類とする。スクラッチで全部作るのではなく、公開されている部品を使い、足りないところだけをつなぎのスクリプトで埋める (PDA の方針)。調査は、要素ごとに「使える部品」「その部品で満たせる要件」「埋めるべき隙間」を返す。

## 2. 調べる対象の 4 つの区分

オーナーが挙げた区分。1 は設計の参考にし、2〜4 は部品の候補にする。

1. 判断を委譲するツリーの設計: 上へのエスカレーション、非同期に積まれる人の判断待ち、起こした側へ結果を返す流れ。ツリーの形は要件 3.1-4 で決まっているので、形を開き直す材料にはしない。
2. Claude Code で複数のセッションを分離する実装: 公式の機能と、公開されているスクリプト。
3. ツリーの構造を実現した OSS。
4. Claude Code を内部の部品として作った OSS。

## 3. 候補を絞る条件

厳しい順に当てる。

1. 定額のログインで動く (3.3-1): 部品にできるのは、`claude` の CLI を定額のログインのまま動かすものだけ。Agent SDK を API キーで動かすものは、区分 1 の参考にとどめる。自前で claude.ai のログインを提供する OSS は、利用規約に反するので外す。調査では、実際に `claude` を起動している行を示す。
2. 画面は決まっている (3.1-1): 自前の画面 (ダッシュボード、TUI、カンバン) に価値がある OSS は、製品としては見ない。中の仕組み (起こし方、セッションごとの設定の注入、結果とエスカレーションの戻し方、状態の置き場所) だけを見る。
3. ミニ PC (Ubuntu、画面なし) で動く (3.1-2)。
4. 最後のコミットの日付は事実として記録するが、順位には使わない。

## 4. 設計の要素ごとに調べること

各要素に、答える問い、関わる区分、すでに分かっている候補、新たに探すもの、調査が返す証拠を書く。

### 4.1 入口 (3.1-1、3.1-2)

- 問い: ミニ PC で動き続ける 1 つのセッションに、Claude Desktop と Claude アプリから届き続けるには、何を使うか。長く動かす間に文脈があふれたとき、どう続けるか。
- 区分: 2。
- 分かっている候補: Remote Control のサーバーの形と、対話の形 ([入口と spawn の調査](research-entry-and-spawn.md) の V1・V4)。ミニ PC で動いている Remote Control の常駐 (`deploy/claude-remote-control/`)。
- 新たに探すもの: 長く動かす入口のセッションの文脈の扱い (compact、`--continue`、再起動の後の引き継ぎ) を書いた実践者の記事やスクリプト。
- 返す証拠: 起動の行、再起動のときに同じ会話が続く手順。

### 4.2 セッションのツリー (3.1-3、3.1-4、3.2-1、3.2-4)

- 問い: 入口が役と作業を割り当てたセッションを起こし、起こしたセッションがさらに子を起こせ、子の結果が起こした側に返り、起こした側の途中経過が入口に届くには、何を使うか。起こしたセッションは Claude のセッションとして記録に残るか。
- 区分: 2、3、4。
- 分かっている候補: `claude -p`、`claude --bg` と `claude agents`、サブエージェント、セッションの間のメッセージ (`ListAgents`、`SendMessage`)。実践者の事例のうち、Neutron の `spawn-agent.sh` (役ごとのシステムプロンプトを渡して起こす)、theptip (親の Remote Control のセッションが作業ごとに子のセッションを作る)、CommandMate (窓口・管理・ワーカー)、Instar (バックグラウンドのセッションを起こす skill)、mhaaseth の Orchestrator、Kai ([先行事例の調査](research-prior-art.md))。
- 確かめ直す事実: 起こしたセッションの最後の出力が、チャットではなく起こした側に返るか。子が親にメッセージを送れるか。`-p` で起こした子が孫を起こし、その結果を受け取れるか。Claude アプリで、サブエージェントだけでなく、起こした別のセッションも見えるか。
- 新たに探すもの: 公式の機能のうち、複数のセッションを協調させるもの (agent teams など) の今の状態。Claude Code のセッションを階層に組む OSS (確かめる候補: Gas Town、claude-squad、ccmanager、Claude Flow)。GitHub の topic (`claude-code`、`orchestrator`、`multi-agent`、`tmux`) と awesome-claude-code の一覧。
- 返す証拠: 起こす行、子に役の設定を渡す方法、結果が起こした側に戻る経路、ツリーの深さの制約。

### 4.3 判断を専門にする役と、オーナーの判断待ち (3.1-4、3.2-3)

- 問い: 入口に返ったものに判断を専門にする役が意見を出し、解決しなかったものだけがオーナーの判断待ちに非同期に積まれ、それを入口が整理するには、何を使うか。積まれたものをどこに置くか。
- 区分: 1、2、3。
- 分かっている候補: Jev (判断を関数の形にして使う判定モデル。今の運用で skill として使っている)。Claude Code の権限要求を外へ渡す仕組み (`--permission-prompt-tool`、`PermissionRequest` の hook)。
- 新たに探すもの: エージェントの非同期の承認の待ち行列 (確かめる候補: HumanLayer、LangChain の Agent Inbox)。階層型のマルチエージェントの枠組みが、結果を起こした側へ返し、判断できないものを上へ上げる仕組み (区分 1 の参考)。判断役のエージェントを置いた Claude Code の事例。
- 返す証拠: 判断待ちの置き場所の形 (ファイル、DB、セッションの中)、オーナーが後で答えたときに元の作業へ戻る経路。

### 4.4 役ごとの規約・記憶・hook と、出力の点検と直し (3.1-5、3.2-2)

- 問い: 役ごとの指示・メモリ・hook を、その役のセッションに確実に載せ、出来上がった出力を規約で点検し、外れていれば直させるには、何を使うか。
- 区分: 2、4。
- 分かっている候補: サブエージェントの定義 (`hooks`、`memory`、`skills`)、`--agents`、`--settings`、`--append-system-prompt`、`--plugin-dir`。Stop と SubagentStop の hook で出力を差し戻す仕組み。Stop の hook に LLM の判定を置いて出力を差し戻す形は、オーナーが今の Claude Code の運用で使っている。
- 確かめ直す事実: hook がどの起こし方で効き、どの起こし方で効かないか (plugin のサブエージェントは hooks を無視する、プロジェクトの `.claude/agents` はワークスペースの信頼が要る、など)。`-p` で起こしたセッションに役ごとの hook を載せる方法。
- 新たに探すもの: 役ごとに hook と規約を分けて配る公開の plugin・skill・hook 集。出力の点検に LLM を使う hook の公開例。
- 返す証拠: 起こし方ごとに、効く設定と効かない設定の一覧。

### 4.5 正本 1 か所から配る (3.3-2)

- 問い: 指示・skill・hook・MCP の正本を 1 か所に置き、すべての役のセッションに配るには、何を使うか。
- 区分: 2、4。
- 分かっている候補: plugin と marketplace、`--plugin-dir`、設定の階層。今の共通の指示 (`deploy/openclaw/common.md`)。
- 新たに探すもの: 複数の役やマシンに設定を配る公開の仕組み。
- 返す証拠: 正本を 1 か所直したときに、すべての役のセッションに届く手順。

### 4.6 会社のコネクタの経路 (3.1-6、3.2-5)

- 問い: ミニ PC の入口から、開発 PC の Claude に会社のコネクタを使う作業を頼み、結果を入口に返すには、何を使うか。開発 PC のブラウザーや画面をミニ PC から触れる形にしない。
- 区分: 2、4。
- 分かっている候補: SSH で開発 PC の `claude -p` を起こす。`claude mcp serve`。
- 新たに探すもの: 別のマシンの Claude Code を道具として呼ぶ公開の部品 (確かめる候補: claude-code-mcp)。セッションの間のメッセージがマシンをまたげるか。
- 返す証拠: 呼び出しの行、開発 PC 側で使える道具を会社のコネクタに限る方法。

### 4.7 スマホへの通知 (3.2-6)

- 問い: 入口の返事と承認待ちをスマホに知らせるには、何を使うか。
- 区分: 2。
- 分かっている候補: 今の運用の ntfy の通知。Remote Control の push 通知 (会社の組織の設定では使えなかった。個人のアカウントでは未確認)。
- 新たに探すもの: 個人のアカウントの Remote Control で push 通知が届くかの公式の記述。
- 返す証拠: 通知が届く条件。

## 5. 既にある調査の使い方

- [入口と spawn の調査](research-entry-and-spawn.md): 公式の機能の事実は、4 節の「確かめ直す事実」に挙げたものを除き、そのまま使う。
- [先行事例の調査](research-prior-art.md): 入口の画面の要件を物差しにしないまま、3 つの性質で順位を付けている。順位は使わず、各事例を 4 節の要素に振り分け、公開しているスクリプトとリポジトリを抜き出す。
- 前回の調査が外した GitHub の topic、awesome 系の一覧、plugin の marketplace、Anthropic のリポジトリを、今回は探す。

## 6. つなぎのスクリプトが要りそうなところ

調査の前の見込み。調査で部品が見つかれば消す。

- 起こしたセッションの結果を、起こした側へ返す経路 (4.2)。
- オーナーの判断待ちの置き場所と、入口がそれを整理する手順 (4.3)。
- 役ごとの設定を組み立てて子のセッションを起こす起動の行 (4.2、4.4)。
