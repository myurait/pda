# Claude 一本化の検討

- 更新: 2026-11-03 JST
- 種別: 検討の作業場所。オーナーが求めているものと、それに対する決定をこのディレクトリに置く。
- 位置付け: v0.3 の決定 ([docs/reports/v0.3-decision.md](../reports/v0.3-decision.md)) では、フロントドアに OpenClaw を選び、Claude Code と Codex を実行器にした。本件は、OpenClaw と Codex をやめて Claude Code に一本化できるかを検討する。結論が出るまで、v0.3 の決定と運用は変えない。

## 目的

Claude Code Desktop をフロントドアにし、PDA で実現したかったこと (役ごとに指示・メモリ・hook を分けて確実に効かせること) を、Claude Code CLI を包むスクリプトなどで満たせるかを確かめる。満たせるなら OpenClaw と Codex をやめる。

## 進め方

PDA の既存の書き方で、オーナーが求めているもの、それに対する決定の順に整理する。[AI-DLC Workflows](https://github.com/awslabs/aidlc-workflows) は同じ順序の先行例で、道具は入れない。

- オーナーが求めているもの: [requirements.md](requirements.md) に置く。調査と設計は、この要件を物差しにする。
- 決定: 本文書の「オーナーの判断の記録」に日付ごとに書く。

## 決まっていないこと

[solution-options.md](solution-options.md) の案Cの実現計画のうち、段階1を実装した ([design-stage1.md](design-stage1.md)、[check-stage1.md](check-stage1.md))。段階2は、2026-11-27のオーナーの指示で始めた。項目の優先度と完了条件は [plan-stage2.md](plan-stage2.md) にある。

### 2026-11-24

- 規約の判定は Jev に移す。Codex を規約の判定に使う予定はもともと無かった。
- ゲートで判定する規則は、規則が求める推論の水準で振り分け、次の 5 つの経路のどれかで処理する。経路ごとにどの AI を割り当てるかを設計で決める。
  - 機械的な検証 (決定論で判定できる)
  - 閉じたコンテキストで、高い推論能力は要らないが、決定論的ではない判定
  - 閉じたコンテキストで、高い推論能力が要る判定
  - 複数の文脈 (ハイコンテキスト) を、低い推論能力で横断して確かめる判定
  - 複数の文脈 (ハイコンテキスト) で、高度な評価を行う判定
- 発言 (原文): 「規約に対しては、規約が指示する、推論の水準みたいなものを評価する必要がある。機械的に検証できる内容か、閉じたコンテクストで評価できる内容か、それともハイテクコンテクストな内容か、この3つにと、推論的な内容については、推論的な課題としてのエフォート、必要な推論能力を、2段階程度、少ない推論能力、高い推論能力で組み合わせて評価する必要がある。」「これに対して、どのように AI を割り当てるかという問題解決になっていくはず。」「つまり検証に至る前に設計が甘い」
- ゲートは、発火させる時点 (ツール呼び出しの前後、ターンの終わり、ユーザーへの応答の前) ごとに、機械的な検証と Jev で判定できるものを分け、推論が要る場面では複数のゲートを 1 つに圧縮する。Codex はフルスペックのモデルではなく、推論の強さを絞った Sol にする。
  - 発言 (原文): 「問題は、このゲートをどのタイミングで発火させるのかということだ。」「推論で行わなければいけない場面では、その推論のゲートを複数のゲートを一つに圧縮したりなどしなければいけない。」「アストラなどのフルスペックが必要なモデルはちょっと難しいかな。クレジット的に難しいなという気がしていて、まあ、現実的なところだとエフォートを絞ったソルかなと思います。」
- 規則が当たるか (ゲートを発火させるか) の判定そのものに推論が要る場面があり、Jev が、指示と出力物の組か、指示と 1 つ前の応答で判定する。呼び出しの回数は掛け算でなく、最も多くのゲートを通る流れのシミュレーションで見積もる。Codex は規則 1 件ずつ呼ばず、チェックリストを読ませて 1 回にまとめる。前処理の Codex は外さず、どの粒度でまとめられるかを設計の論点にする。
- オーナーへの返事を書く役 (報告係) を別のモデルに分け、返事の書き方の規則は報告係の指示に吸収する。報告係の規則のうち、抽象度が高く心がけのようで検査できない規則と、判定の費用に対して出力の精度の向上を見込みにくい規則は、規則から外す印を付け、推論で扱う対象から一時的に外す。
  - 発言 (原文): 「報告係を別で分け、その報告係の規則に吸収すべき箇所がある。ただし、報告に関することは全てがそれに当たるわけではない。」「それは、今回、規則から外すべき項目として、マークしておいて、推論で取り扱う対象から一時的に除外したほうがよい」

### 2026-11-21

- 規則の遵守はメインモデルに判定させず、PDA のゲートとして吸収する。メモリの規則を判定材料で振り分けた一覧と設計の観点を [rule-gates.md](rule-gates.md) に置く。
- 小さい判定器で決まらない規則は、作業の前の推論機 (前処理) か、応答の後ろの完了判定のゲート (後処理) に振り分ける。
- 「確認なしでしてよい」という許可は、許可要求が出たときの自動承認に置き換える。応答の文で承認を求める問いも、Jev で見つけて許可済みと注入すれば同じ解き方で解ける。

### 2026-11-03

- AI-DLC は道具を入れず、PDA の既存の書き方で進める。
- 作業場所は `docs/claude-unification/` にする。
- 入口は 1 つにする。OpenAI の [Dots](https://techcrunch.com/2026/09/29/openai-launches-dots-its-bubbly-agentic-avatar/) のように、リモートに常駐するフロントドアのエージェントに複数の端末から話しかけ、そのエージェントが別のセッションを立ち上げて作業を移す形をとる。
- Claude Code での一本化もこの形にする。ミニ PC 上で長く動き続ける 1 つのセッションを、リモートのセッションか Claude Desktop から使い、そのセッションがセッションを spawn する道具で、作業と役を割り当てた別のセッションを起こす。spawn を `claude -p` のセッションの起動で行い、作業をうまく移せれば、役ごとの文脈を個別に注入できる。
- 発想は「Claude Code をどう有効に使うか」ではなく、「Claude の上に Dots のようなパーソナルエージェントを作り、1 つの入口として使い、そこにセッションを spawn する機能を持たせる」である。先行事例を含めて幅広く調べる。
- 先行事例は、公式の機能や OSS の製品ではなく、Claude でパーソナルエージェントやセカンドブレインを作った実践者の記事と実装を指す ([research-prior-art.md](research-prior-art.md))。
- 入口の画面は Claude Desktop と Claude アプリのリモートのセッションとする。
- 調査と設計の前に要件を固める。要件の正本は [requirements.md](requirements.md) とする。
