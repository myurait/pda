## 1. なぜ検討するか

PDA は v0.3 で、ミニ PC に常駐する OpenClaw を入口にし、Claude Code と Codex を実行器にした ([v0.3 の決定](../reports/v0.3-decision.md))。オーナーは PDA を補助的に使っているが、使いづらさを感じている。OpenClaw の目玉機能の Dreaming は使われておらず、使い勝手は Claude Code Desktop のほうがよい。Codex の性能にも不満がある。そこで、PDA でやりたかったことを Claude の上で満たせるなら、OpenClaw と Codex をやめて Claude に一本化することを検討する。

一本化するのは、入口 (v0.3 では OpenClaw) と、作業を行う担い手 (v0.3 では実行器の Claude Code と Codex) である。点検・ゲートの判定には、Claude 以外のモデルを差し込めるようにする (3.2-22)。Claude だけで点検すると、Claude のモデルが共通して持つ規範から外れる出力を、外から指摘できないからである。この差し込みは一本化してよいかの条件を増やすものではなく、下の条件のうち応答のライフサイクルを観測し変えられる道具 (3.3-5) の上で成り立たせる必須の要件である。

一本化してよいかの条件は、次の 3 つをすべて満たせることである。1 つでも満たせない道具は使わず、3 つを満たせる道具が無ければ一本化しない (「最終的なビジョンとして達成できるものの形が狭まるなら、それを使えない。」)。

- **応答のライフサイクルを、限りなく任意に観測し、変えられる** (3.3-5)。(「応答のライフサイクルが、限りなく任意に観測変更可能である必要がある」)
- **Claude を定額のログインで動かし、API キーの従量課金で動かさない** (3.3-1)。(問いの「どちらか一方でも満たせない道具は使えない」への答え「ok」)
- **役ごとの規約と記憶 (3.2-2) を、起動したセッションに割り当てられることが、技術的に解決している** (3.3-8)。割り当ての仕組みそのものの重みは「最終的」(3.2-2)。(「それさえできれば正直もうオープンクローを使うし必要ってあんまりないし」「要件として「それができるという技術的な問題が解決しているような選定」である必要はある」)

道具 (ハーネス、サードパーティのフレームワークやアプリ) を選ぶ条件は、上の 3 つに加えて次のとおり。

- **セッションをリポジトリやディレクトリに縛らない要求 (3.2-13) を満たせないハーネス・サードパーティは使わない** (3.3-6)。(「セッションをリポジトリやディレクトリに縛らない要求を満たせないハーネス・サードパーティは利用しない。」)
- **サードパーティのフレームワークやハーネスは、Claude や OpenAI などのモデルのランタイム側が持つ機能に、1 週間以内に追従できるものを使う** (3.3-7)。(「モデルのランタイム側が持つ機能への追従を、1週間以内に追従できるを、これをマストの要件として取り扱いたい」)

## 3. 本当に必要なもの

2 節の発言と回答から導いた要件。各項目に、根拠にした発言を付ける。要求されたことはすべて要件として書き、項目ごとに重みを付ける。項目の部分ごとに重みが違うものは、部分ごとに書く。

- **必須 (MVP)**: MVP で満たす。MVP の基準は、オーナーの「今している仕事以上のこと& 今明確に困っていることではなく、こうできたらいいなってなってる内容は MVP としては取り扱わない」「推論的自律実行の要件は MVP には入らない」。
- **できた方がいい**: 必須ではないができた方がいい。このうち「重要」としたものは、設計で先に満たす。
- **最終的**: 最終的にできるようにならなければいけない。MVP の後に満たす。道具は、これを満たせる形が狭まらないものを選ぶ (1 節)。

全体が「最終的」の項目は 3.4 に、全体が「できた方がいい」の項目は 3.5 にまとめる。入口の画面は設計で選ぶ (3.1-1) ので、画面でオーナーができることも要件として書く。

5. **役ごとに調整する対象は、指示 (コンテキスト)・メモリ・hook。** 重み: 最終的 (役の割り当ては 3.2-2)。(「各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニング」)
6. **会社のコネクタを使うことと、会社契約のアカウントでアーティファクトを作ることは、開発 PC の Claude だけが行う。** 重み: 必須。v0.3 で決めた形を保ち、会社契約のアーティファクトの作成まで広げる。作ったアーティファクトを見ることは 3.2-16。(回答「会社のコネクタの経路」、「開発 PC は、コネクタ、だったり、開発会社契約のアカウントで、作成しなければいけないアーティファクトだったりのために使う。」)
7. **開発 PC の Claude Code は、エージェントではなくモデルとして使う。** 重み: 必須。開発 PC は PDA に接続される外部接続環境の 1 つで、PDA のミラーにしない。オーナーが話しかけるのは PDA のセッションだけで、開発 PC のセッションに直接は入らない。開発 PC で作ったものも、頼んだ PDA のセッションに返る。会社のコネクタの使い方、外部に公開する作業のやり取り、権限についての規則は、開発 PC 上の閉じた会社のアカウントのナレッジとして PDA から切り離す。(「開発 PC のクロードコードはエージェントではなくモデルとして使う。つまりそれは、PDA に接続される外部接続環境の一つでしかなくて、PDA のミラーリングという扱いにはしない。」、オーナーが話しかけるのは PDA のセッションだけという読みへの答え「OK、その認識で合ってる。」、「それは、開発 PC 上の閉じた、会社権限のアカウントのナレッジとして、PDA からは切り離す想定。」)
8. **PDA は、強い推論能力を持つコアの前後に、複数のゲートをパイプラインで通す形をとる。** 重み: ゲートを積み重ねる形は必須。ゲートは役ではなく、応答の前後にミドルウェアのように置く推論の仕組み。コアは Claude で動かし、ゲートの判定には Claude 以外のモデルを差し込める (3.2-22)。(「強い推論能力を持つ Core のロジックに対して、複数の Gate や、追加の推論機構を Hook で応答の前後に仕込む形になる」「パイプラインで、ミドルウェアを通すように推論、機構を通していきたい」「複数の積層ゲートの考え方については MVP で導入した方がいい内容」)

### 3.2 機能要件

オーナーが行うこと、オーナーから見える振る舞い。

1. **頼んだ作業は、メインセッションが起動したセッションで行われ、オーナーはそのセッションに入って直接話しかけられる。** 重み: 起動したセッションで行われることと、オーナーが入って話しかけられることは必須。作業に役を割り当てることは最終的 (3.2-2)。オーナーはメインセッションに頼めば作業が進み、セッションの立ち上げと進捗の管理をメインセッションで行える。議論の深掘りのようにモデルのコンテキストを使い切る場面では、オーナーがそのセッションに入って直接操作する。(「作業割り当て、ロール割り当てをした別のセッションをスポーンさせる」「セッションを起動するのはmust」「議論の深掘りなど モデルのコンテキストをフルパワーで使わないといけない場面においては、セッションに入って操作する必要がある」)
2. **役ごとの規約と記憶。** 重み: 最終的。あわせて、これを満たせることが技術的に解決している道具を選ぶことが、一本化してよいかの条件 (1 節、3.3-8)。役ごとに定めた規約 (コミュニケーション原則のような指示) が、その役の出力に必ず効く。出来上がった出力が規約から外れていれば、点検で見つかって直る。役ごとに調整したメモリが、その役で効く。MVP で必須なのは、オーナーの規約が PDA のどのセッションでも効くこと (3.2-7) と、応答の終端のゲートで点検されること (3.2-8)。(「強制力の強い各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニングが機能する」、回答「強制力」、「別のセッションにロールなどの規則を割り当てる機構自体はmvpの外でいいが」)
3. **オーナーの判断が要るものは、作業のたびの確認ではなく、報告としてメインセッションに届く。** 重み: 報告がメインセッションに届くことは必須。判断待ちの取り扱いをメインセッションが整理することは最終的。担い手は、作業を終えるたび・進めるたびにオーナーに確認を取らない。判断の要らない手順の進行は逐一知らせず、判断が要るとき・指示が要るとき・完了したとき・未完了で止まったときに報告する。作業の成果として確定した内容 (PDA 全体のゲートを足した・消した・変えたことなど) は、完了報告の中の 1 つの議題として知らせる。メインセッションが起動したセッションの判断待ちは、起動元のメインセッションに返り、オーナーはメインセッションで受け取る。(「つどつど私に確認を取っていくのではなく、非同期的に私のジャッジが必要なものとしてスタックされていく。で、それについての取り扱いをフロントドアが整理していく」「指示に対して明確にこれをするべきとわかっている判断が不要な手順について、その進行を逐一通知することは不要」「判断が必要な状況、指示が必要な状況、完了報告、あるいは未完了で停止した状態などの「報告」は必要なまま」「報告上の一議題として扱われる」、判断待ちをメインセッションで受け取る読みへの答え「yes」)
4. **開発物の進行が、PDA のどのセッションで尋ねても分かる。** 重み: 必須。個人で受けている案件・会社の案件・PDA 自身のどれについても、今どこまで進み、次に何が要るかが、どのセッションで始めた作業か、開発 PC に頼んだ作業かを問わず分かる。メインセッションは、起動したセッションとオーナーが直接入ったセッションの進捗を把握している。会社のチケット管理ツールにしかない状態は、開発 PC の会社の Claude を通して取る。起こした先をオーナーが直接止められることは要らない。(回答「起こした先の見渡し」の自由回答「私から直接停止できることは必須ではない」、「その通り。ただここで言う開発物の進行については、会社管理のバックログとかの、チケット管理ツール上にしかない情報も存在している。」「PDA 本体ではなく PDAが、開発 PC 上の会社セッションのクロードへ接続して、そのクロードが MCP 利用でバックログに問い合わせて、その状態を取得することができる。が前提になる。」)
5. **会社のコネクタを使う作業を、PDA のセッションから頼める。** 重み: 必須。頼むと開発 PC の Claude で行われ、結果が頼んだ PDA のセッションに返る。オーナーが開発 PC への指示の出し方を作業ごとに調整しなくても、作業が通る。(回答「会社のコネクタの経路」、「開発PC に出した指示もちょっと良くなくて」「それをやっている余裕がなかったんだよね。」、この要求を記録してよいかへの答え「もちろんそれはイエス。」)
6. **オーナーが見なければいけない報告と承認待ちが、スマホに届く。** 重み: 必須。届くのは、オーナーに返す報告 (3.2-3) と承認待ちの、差し戻しを経た最後の一通だけ。メインセッションでも、オーナーが直接入ったセッションでも同じ。(回答「スマホへの通知」、「スマホの通知を最後に応答した一本に絞るができてないのが本当にストレスだね。」「私が見なければいけないという場面での通知してほしい。」)
7. **PDA のどのセッションでも、オーナーの規約 (hook・コミュニケーション規則・メモリ) が効く。** 重み: 必須。規約は読まれるだけでなく、守られたかが応答の終端のゲートで確かめられる (3.2-8)。(「開発 PC 上にあるフックやコミュニケーション規則を遵守されない状態から仕事をするっていうのがきつかった」「ルールを読んでいない。今のエージェントは。読んでても無視するか、関係ないルールとして勝手に自己判断してしまう。」)
8. **応答の終端で、複数のゲートを通す。** 重み: 必須。作業が終わったと言って終わっていなければ突き返し、オーナーへのコミュニケーション規則に外れていれば差し戻す。外れているかの判定に Claude 以外のモデルを差し込めることは 3.2-22。(「複数の、応答集端ゲートを通らせたいのよ」「そもそも作業が終わったって言って、作業が終わってなかったりしたら突き返したい」、回答「強制力」)
9. **差し戻しを何度繰り返しても、チャットに出てヒストリーに残るのは最後の一通だけ。** 重み: 必須。頭の中ですることと、口に出して言うことを区別する。差し戻しの経過はチャットとヒストリーには出さず、観測できる記録に残す (3.3-5)。(「最後の一通だけ ヒストリーに残っててほしい。し、最後の一通以外、チャットに出力してほしくない」「頭の中でやってることと、頭の中でやるべきことと、口に出して言うことの区別をつける」「応答のライフサイクルが、限りなく任意に観測変更可能である必要がある」)
10. **PDA 全体に適用するゲートを、エージェントが要否を判断して足す・消す・変える。** 重み: 必須。一般的な規則は、PDA 全体に適用するゲートで守らせる。オーナーが同じ種類の作業のたびに繰り返し出している指示も、この仕組みで覚え、言われなくても行われ、行われたかがゲートで確かめられる。オーナーはゲートを 1 つずつ承認しない。足した・消した・変えたことは、完了報告の中の 1 つの議題として知らせる (3.2-3)。このゲートはオーナーが仕組みとして指示したもので、3.3-3 の安全装置には当たらない。割り振りやフローを成果とフィードバックで書き換えることは 3.4-3 (最終的)。このゲートの判定に Claude 以外のモデルを差し込めることは 3.2-22。(「一般的な規則で吸収するものはゲートでブロックしなければいけない」「一般側側を PDA 全体に適用するゲートとして増やしていくをエージェントが主導するまでは MVP でやる」「ゲートを消すこと、変更することもAIの責任だ。ゲートの要否を自律判断しなければならない」、繰り返しの指示を覚える読みへの答え「そうだね。それも欲しい。」)
11. **作業で決まったこと・分かったことと、すべてのチャットヒストリーが PDA に集まり、どのセッションからも使える。** 重み: 必須。別のセッションで同じ案件を扱うとき、オーナーが言い直さなくても使われる。開発 PC 上のものを含むチャットヒストリーを、オーナーやセッションが尋ねると、PDA のセッションが探して読める。チャットヒストリーから要点を読み取って記憶にまとめ直すことは 3.4-2 (最終的)。(ナレッジの集約は MVP で要るという読みへの答え「合ってるよ。」、「ここでのナレッジとは全てのチャットヒストリーでもある。開発 PC 上のチャットヒストリーも PDA からは全て確認できる必要がある。」、チャットヒストリーを確かめられることは MVP という読みへの答え「ok!」)
12. **新しいセッションで案件の名前や作業の中身を話すだけで、続きから作業が始まる。** 重み: 必須。PDA がその案件のリポジトリと、前に進めていたセッションの文脈を見つける。オーナーはリポジトリやセッションを自分で指定しなくてよい。(「いつもの新規セッションを開く操作で始めても、文脈を継承できるっていうことの重要さはある」、ルーティングの段の読みへの答え「yes」、MVP に入る読みへの答え「合っているが」)
13. **セッションはリポジトリやディレクトリに縛られない。** 重み: 必須 (オーナーの指定)。
    - セッションと作業するディレクトリは切り分けられ、作業するディレクトリは後から差し替えられる。参照するパスはすべて絶対パスにする。
    - 作業の途中で割り当てのディレクトリが変わる。作ったディレクトリの中で作業しようと言えば、そのディレクトリが割り当てになる。
    - リポジトリやディレクトリによって、エージェントの動きは書き換えられない。
    - ディレクトリにある AI 向けの指示はいったん切り出し、オーナーの規範 (3.2-7) を土台にして、その上にリポジトリの都合として重ねる。
    - 3.2-12 で見つけたリポジトリも、セッションに結びつけず、差し替えられる情報として扱う。

    (「セッションがリポジトリやディレクトリに結びつくのではなく、後から差し替え可能な情報として、切り分けられている必要がある」「エージェントを求めてるのであって、そのリポジトリの中で管理されるランタイムを求めているわけではない」「ユーザー自身の規範の上にリポジトリの都合を重ねる形で設定するが正しい」「これは MVP の中に含めてほしい」、4 点の読みへの答え「はい、いいと思います。」)
14. **開発 PC で途中まで進めた作業を、PDA へ持っていって続けられる。** 重み: 必須。(「会社契約の PC の、クロード、コード上で途中まで作業していた内容を、PDA 上に持っていこうとした」)
15. **音声で話した内容が、AI が受け取る指示として正しく取り込まれる。** 重み: 必須。Claude の音声入力に近い使い心地は、できた方がいい (3.5-7)。(「それを AI が受け取る指示にすることが重要だから」「これつまり音声認識が正しく機能するっていうマストの要件なんじゃないのか。今まさに音声認識で作業してるんだけど。」)
16. **意思決定や調査の結果を受け取るアーティファクトが、PC でもスマホでも、アカウントの混線で見られなくなることがない。** 重み: 必須。会社のアカウントで作ったアーティファクトも、PC とスマホで見られる。(「会社契約の作ったアーティファクトをそのままスマホで見れないんだよね」「スマホでアーティファクトを見れないという困りごとはかなり重い」「アカウントが混線してアーティファクトが見れなくなるというのはクリティカルな開発体験の悪化になってしまう」)
17. **PC で、会社のアカウントでログインした開発 PC の Claude Code と並べて、PDA に話しかけられる。** 重み: 必須。(「クロードコードデスクトップを2つ立ち上げる必要が出てしまって、でもそんなことできないから、つなげられずに、ブラウザでやろうとしたんだけど、まあなんかあんまりブラウザでやっても使い勝手良くなかったんだよね。」)
18. **今どのセッションにいるかが分かる。** 重み: 必須。開発 PC を経由する作業でも、オーナーが話しかける相手は PDA のセッションのまま (3.1-7)。(「どのセッションに今いるのか混乱してしまったんだよね。なんでちょっとやめました。」)
19. **スマホで、PDA 上の新しいセッションを、一段深い操作なしに立ち上げられる。** 重み: 必須。(「PDA 上の別のセッションを新規で立ち上げようとしたときに、リモートデバイスの選択からそこで新規セッションをしないといけないっていう一段深掘る動きが必要になるんだよね。」)
20. **エージェントが動かしたコマンドとその出力を、会話の中で追える。** 重み: 必須。(「エージェントが動かしたコマンドとその出力を会話の中で終えることは、これは、マストにしたい。」)
21. **エージェントが示したコマンドを、ワンボタンの承認でそのまま実行に移せる。** 重み: 必須。承認のあとに、実行してよいかを尋ねる許可のポップアップで止められない。(「承認がワンボタンでできて、かつ、さらにそれを実行しますかっていうような許可ポップアップとかでブロックされないっていうことが重要になってくる」「承認即実行ができるってことは MVP の中にも含めてほしい」)
22. **オーナーの規範から外れた出力を、Claude 以外のモデルが外から指摘できる。** 重み: 応答の終端のゲート (3.2-8) と PDA 全体に適用するゲート (3.2-10) の判定に、Claude 以外のモデルを差し込めることは必須。役ごとの点検 (3.2-2) に差し込むことは、3.2-2 と同じく最終的。Claude のモデルどうしの点検では、Claude のモデルが共通して持つ規範から外れた出力が通ってしまうので、判定を行うモデルを Claude の外に置けるようにする。差し込んだゲートでは、出力がオーナーの規範から外れているかを Claude 以外のモデルが判定し、見つけた外れは 3.2-8 のとおり差し戻される。どのモデルを、どの道具を通して差し込むかは設計で選ぶ (3.7)。(「今ね、一番このクロードを使っていて不愉快なことは」「この規範から外れる内容を厳密に外から指摘することができない」「クロード同士で、まあこれはいいかとか言って、談合してすり抜けようとしてくる」「だからこれ別のモデルを注入できるようにしないといけない」)

### 3.3 オーナーの条件

機能ではないが、オーナーが要件として引き継いだもの、または指定したもの。重みはすべて必須。

1. **Claude は定額のログインで動かす。** API キーの従量課金で動かさない。個人の契約か会社の契約かは問わない。一本化してよいかの条件 (1 節)。この条件は Claude の動かし方を定めたもので、ゲートの判定に差し込む Claude 以外のモデル (3.2-22) の動かし方は定めていない。それは設計で選ぶ (3.7)。(項目「Claude を定額のログインで動かす」の回答、C11 から「個人の」を外す問いへの答え「ok!」)
2. **指示・skill・hook・MCP の正本を 1 か所に置き、PDA のすべてのセッションに配る。** 開発 PC は PDA のミラーにしない (3.1-7)。(項目「指示・skill・hook・MCP の正本を 1 か所に置き、すべての役に配る」の回答、MVP に入る読みへの答え「ok」)
3. **オーナーが指示していない安全装置を足さない。** 止める・断る仕組みは、オーナーの承認を得てから作る ([docs/process/progress-over-stopping.md](../process/progress-over-stopping.md))。3.2-8 と 3.2-10 のゲートは、オーナーが指示したもの。(項目「オーナーが指示していない安全装置を足さない」の回答)
4. **入口と作業を行う担い手を Claude に一本化し、入口としての OpenClaw と、作業を行う実行器としての Codex を使わない。** 1 節の条件が満たせる場合に限る。点検・ゲートの判定は一本化の対象ではなく、Claude 以外のモデルを差し込めるようにする (3.2-22)。差し込むモデルをどの道具を通して動かすかは設計で選ぶ (3.7)。(「クロード一本化でいいんじゃないか」「だからこれ別のモデルを注入できるようにしないといけない」)
5. **応答のライフサイクルを、限りなく任意に観測し、変えられる道具を使う。** 一本化してよいかの条件 (1 節)。応答の前後のゲート (3.1-8、3.2-8) と、最後の一通だけを出すこと (3.2-6、3.2-9) を成り立たせる前提。点検・ゲートの判定に Claude 以外のモデルを差し込むこと (3.2-22) も、この前提の上に成り立つ。(「フックの待ち受けと終端処理を行わないといけない」「応答のライフサイクルが、限りなく任意に観測変更可能である必要がある」「最終的なビジョンとして達成できるものの形が狭まるなら、それを使えない。」)
6. **セッションをリポジトリやディレクトリに縛らない要求 (3.2-13) を満たせないハーネス・サードパーティは使わない。** 道具を選ぶ条件。Claude Code それ自体の制約ではなく、運用の考え方で満たせる。(「セッションをリポジトリやディレクトリに縛らない要求を満たせないハーネス・サードパーティは利用しない。」「claude codeをどのようにランタイムで運用するかの考え方で解決できる」)
7. **サードパーティのフレームワークやハーネスは、モデルのランタイム側が持つ機能に、1 週間以内に追従できるものを使う。** 道具を選ぶ条件。1 週間は、モデルの提供元がランタイムに新しい機能を出した日から数え、その 1 週間以内に、使っているサードパーティでもその機能が使えるようになっている。(「サードパーティーのフレームワークやハーネスを使うときは、クロードやオープン API などの、うーん、モデルのランタイム側が持つ機能への追従を、1週間以内に追従できるを、これをマストの要件として取り扱いたい。」、1 週間の数え方の読みへの答え「Yes。」)
8. **起動したセッションに役などの規則を割り当てられることが、技術的に解決している道具を選ぶ。** 道具を選ぶ条件で、一本化してよいかの条件 (1 節)。割り当ての仕組みそのものは最終的 (3.2-2)。(「要件として「それができるという技術的な問題が解決しているような選定」である必要はある」)
9. **会社のアーティファクトは、組織に属するアカウントでしか見られない。** 他の人が作った会社のアーティファクトも確かめるので、ブラウザは会社契約でログインしておく。Claude のアプリを入口の画面にするなら、アプリは個人のアカウントで PDA に話しかけ、会社のアーティファクトは会社契約でログインしたブラウザで見る。(「リンクを知っている全員に共有は会社の方針的に使えないので、組織に属している必要がある」「ブラウザで、持ってる、アンスロピックのログイン自体は会社契約のものにしておかないといけないよね」「クロードアプリを使うならその前提」)

### 3.4 最終的にできるようにならなければいけない機能要件

全体の重みが「最終的」の項目。3.1-3、3.1-4、3.1-5、3.2-1、3.2-2、3.2-3 にも「最終的」の部分がある。

1. **記憶の整理。** セカンドブレインなどの別の思想の実装方法を部分的に取り込む形にする。(回答「記憶」の自由回答)
2. **古いセッションの記録を読み取り、記憶に引き継ぐ。** チャットヒストリーから要点を読み取って記憶にまとめ直すことを含む。(自由回答「機能要件としてはあるが、MVP時点の必須要件としない」、チャットヒストリーの読みへの答え「ok!」)
3. **割り振りやフローを、成果とフィードバックで書き換える。** PDA 全体に適用するゲートを足す・消す・変えることは 3.2-10 (必須)。(自由回答「記憶の整理同様。」)
4. **すべての開発物の進行とナレッジを PDA に集約し、PDA 上ですべての作業を行う。** 開発 PC は、会社のコネクタと会社契約のアーティファクトのために使う (3.1-6)。(「最終的に PDA 上にすべての開発物の進行とナレッジを集約したいからだね。」「それ以外の私の開発の主体は PDA 上に移すことが最終的な目標だから」)
5. **開発 PC 上の hook とメモリを除き、PDA 側で全部管理する。** 開発 PC に残すのは、3.1-7 の会社のアカウントの規則だけ。(「最終的に PDA 上に十分な構造が構築された暁には、開発 PC 上から、そうしたいかなるフックみたいなものも排除されて、PDA 側で全部管理できるようになっていくのが理想。」)
6. **オーナーに直接指示を求めるか、応答を返すか、質問をどこへ投げるかを、推論ゲートが決める。** 返し先は、そのゲートの戻り値の 1 つ。(「ユーザーに直接応答を返すか。応答を返す、質問を投げる先はどこかっていうような推論ゲート」、MVP に入るかへの答え「いらない。コアの機能に直結してくる内容ではない。」)
7. **頼まれた作業の範囲を決める。** 作業全体の進行を管理するコントローラーの課題に含まれる。(「作業範囲を決めることは必要だが、それはコントローラで取り扱う課題に吸収される」、MVP の外の読みへの答え「OK、それでいいよ。」)
8. **本文で返すか資料 (アーティファクト) で返すかを、判断に要る情報の粒度と密度を見て総合的に決める。** (「判断に必要な情報の流度、密度を見て、総合的に判断できるような軸を作りたいと思ってる。」、MVP に入るかへの答え「いらない。MVP からは外していい。」)
9. **プロジェクト固有の規則を、プロジェクト内のナレッジとして、エージェントが管理できる形でゲートに増やしていく。** (「PDA 全体の自己成長としてではなく、プロジェクト内での成長、ナレッジとしてゲートを増やしていく仕組みっていうのは、MVP の外に置く」「管理可能な形で、エージェントが任意に増やしていく仕組みをどう整えるかっていうのは、追加で検討していかなければいけない論点になる。」)

## 4. 判定できる受け入れ条件

3 節で重みを必須とした要件 (項目の一部を含む) ごとに、満たしたかを判定できる形で書く。

- C1 (3.1-2): PC とスマホのどちらからも、メインセッションに話しかけられる。いつもの新規セッションを開く操作で始めてメインセッションにしたとき、オーナーが前のことを言い直さずに尋ねると、前のメインセッションが起動したセッションの進捗と、返ってきた判断待ちが答えに返る。
- C2 (3.1-3、3.2-1): メインセッションに頼んだ作業が、メインセッションが起動した別のセッションで行われ、そのセッションが Claude のセッションとして記録に残る。オーナーはそのセッションに入って直接話しかけられる。
- C3 (3.1-4): 起動したセッションの報告 (判断が要るとき・指示が要るとき・完了したとき・未完了で止まったとき) が、起動元のセッションに返る。オーナーが直接入って話しかけたセッションでは、結果と判断待ちがそのセッションでオーナーに返り、メインセッションに尋ねるとそのセッションの進捗が返る。
- C4 (3.2-3): メインセッションが起動したセッションで判断が要るものが、起動元のメインセッションに報告として届き、オーナーはメインセッションで受け取れる。
- C5 (3.2-3): 担い手が判断の要らない手順を進めている間、オーナーには知らせも確認の問いも届かない。判断が要るとき・指示が要るとき・完了したとき・未完了で止まったときは報告が届く。作業の成果として確定した内容は、完了報告の中の 1 つの議題として届く。
- C6 (3.2-2、3.3-8): 選んだ道具で、起動したセッションに役ごとの指示・メモリ・hook を割り当てる方法が、公式の資料かソースで確かめられる。
- C7 (3.2-8、3.2-9): 出力がオーナーの規約から外れたとき、または作業が終わったと言って終わっていないとき、応答の終端のゲートで見つかって差し戻される。差し戻しを繰り返しても、チャットとヒストリーに出るのは最後の一通だけで、差し戻しの経過は観測できる記録に残る。
- C8 (3.2-4): 個人で受けている案件・会社の案件・PDA 自身のどれについても、PDA のどのセッションで尋ねても、今どこまで進み、次に何が要るかが返る。会社のチケット管理ツールにしかない状態も、開発 PC の会社の Claude を通して返る。
- C9 (3.1-6、3.1-7、3.2-5): PDA のセッションから頼んだ、会社のコネクタを使う作業と会社契約のアカウントで作るアーティファクトが、開発 PC の Claude で行われて作られ、結果が頼んだ PDA のセッションに返る。オーナーは開発 PC のセッションに入らず、開発 PC への指示の出し方を作業ごとに調整しない。
- C10 (3.2-6): スマホに届く通知は、オーナーに返す報告と承認待ちの、差し戻しを経た最後の一通だけ。メインセッションでも、オーナーが直接入ったセッションでも同じ。
- C11 (3.3-1): メインセッションと起動したセッションが、定額のログインで動き、API キーで課金されない。
- C12 (3.3-2): 正本の指示・skill・hook・MCP を 1 か所で直すと、PDA のすべてのセッションに届く。
- C13 (3.3-4): 入口に OpenClaw を使わず、作業を Codex に行わせない状態で、4 節のほかの条件がすべて成り立つ。
- C14 (3.3-5): 選んだ道具で、応答のライフサイクルの各段で応答を観測し変えられ、複数のゲートの判定を待ち合わせて本当の最後の応答を決められる。差し戻しを繰り返せる回数が、道具の側で限られない。
- C15 (3.1-8、3.2-10): 応答の前後に複数のゲートが置かれている。エージェントが PDA 全体に適用するゲートを足す・消す・変えると、オーナーの承認を待たずに効き、その変更が完了報告の中の 1 つの議題としてオーナーに届く。オーナーが同じ種類の作業で繰り返し出していた指示が、言われなくても行われ、行われたかがゲートで確かめられる。
- C16 (3.2-7): PDA のどのセッションでも、オーナーのコミュニケーション規則・hook・メモリが効き、守られたかが応答の終端のゲートで確かめられる。
- C17 (3.2-11): ある作業で決まったことが、別のセッションで同じ案件を扱うときに、オーナーが言い直さなくても使われる。開発 PC 上のものを含むチャットヒストリーを、尋ねると PDA のセッションが探して読める。
- C18 (3.2-12): 新しいセッションで案件の名前か作業の中身を話すだけで、オーナーがリポジトリとセッションを指定しなくても、その案件のリポジトリと前のセッションの文脈から作業が続く。
- C19 (3.2-13): セッションで作業するディレクトリを途中で差し替えられ、作ったディレクトリで作業すると言えば、そこが割り当てになる。セッションが参照するパスは絶対パスである。作業するリポジトリを替えても、セッションの動きの土台はオーナーの規範のままで、リポジトリの AI 向けの指示はその上に重なる。3.2-12 で見つけたリポジトリも、同じように差し替えられる。
- C20 (3.2-14): 開発 PC で途中まで進めた作業を、PDA のセッションで続けられる。
- C21 (3.2-15): 音声で話した依頼が、フィラーや変換ミスを含んでいても、オーナーが打ち直さずに、意図どおりの指示として作業が進む。
- C22 (3.2-16、3.3-9): PC とスマホのどちらでも、会社のアカウントで作ったアーティファクトと PDA のセッションが作ったアーティファクトを、ログインを切り替えずに開ける。リンクを知っている全員への共有は使わず、ブラウザは会社契約でログインしたまま使える。
- C23 (3.2-17): 開発 PC の Claude Code を会社のアカウントで使ったまま、同じ PC から PDA に話しかけられる。
- C24 (3.2-18): 話しかけている画面で、今 PDA のどのセッションにいるかが分かる。開発 PC を経由する作業でも、オーナーが話しかける相手は PDA のセッションのままである。
- C25 (3.2-19): スマホで、PDA 上の新しいセッションを、接続先の端末を選ぶような一段深い操作なしに立ち上げられる。
- C26 (3.2-20): エージェントが動かしたコマンドとその出力を、会話の中で追える。
- C27 (3.2-21): エージェントが示したコマンドを、ワンボタンの承認で実行でき、そのあとに許可のポップアップが出ない。
- C28 (3.3-6、3.3-7): 選んだハーネス・サードパーティで 3.2-13 が満たせる。モデルの提供元がランタイムに新しい機能を出した日から 1 週間以内に、そのハーネス・サードパーティでもその機能が使えるようになっている。
- C29 (3.1-7): PDA の正本 (3.3-2) に、開発 PC 上の会社のアカウントの規則 (会社のコネクタの使い方、外部に公開する作業のやり取り、権限) が入っていない。PDA の正本を直しても、開発 PC の Claude Code の設定は変わらない。
- C30 (3.3-3): PDA に入っている止める・断る仕組みは、どれもオーナーが指示したか、オーナーの承認の記録があるものである。応答の終端のゲート (3.2-8) と、エージェントが PDA 全体に適用するゲート (3.2-10) は、オーナーが仕組みとして指示したものに当たり、ゲート 1 つずつの承認は要らない。
- C31 (3.1-1): 入口の画面に選んだ製品で、C2・C7・C14・C22・C25・C26・C27 が成り立つ。
- C32 (3.2-22): 応答の終端のゲート (3.2-8) と PDA 全体に適用するゲート (3.2-10) で、出力がオーナーの規範から外れているかの判定を行うモデルを、Claude 以外のモデルに替えられる。Claude 以外のモデルが判定するゲートで、オーナーの規範から外れた出力が見つかり、3.2-8 のとおり差し戻される。
