# Claude 一本化の要件

- 更新: 2026-11-03 JST
- 種別: オーナー指示による要件の整理。設計・実装・製品選定の宣言ではない。
- 位置付け: Claude 一本化の検討の要件の正本で、新しい基準とする。調査と設計は、本文書の 3 節と 4 節を物差しにする。要件が変わる場合は本文書を先に改める。v0.2 の要件正本 ([docs/requirements.md](../requirements.md)) と v0.3 の要件 ([docs/plan-v0.3.md](../plan-v0.3.md) の 4 節、R1〜R14) からは、引き継ぐ項目だけを名指しで引く。
- 本文書に書くのは、オーナーが決めた形、機能要件、オーナーの条件である。仕組み・部品・製品の選び方 (実現方法) は書かず、設計と実装で扱う。

## 1. なぜ検討するか

PDA は v0.3 で、ミニ PC に常駐する OpenClaw を入口にし、Claude Code と Codex を実行器にした ([v0.3 の決定](../reports/v0.3-decision.md))。オーナーは PDA を補助的に使っているが、使いづらさを感じている。OpenClaw の目玉機能の Dreaming は使われておらず、使い勝手は Claude Code Desktop のほうがよい。Codex の性能にも不満がある。そこで、PDA でやりたかったことを Claude の上で満たせるなら、OpenClaw と Codex をやめて Claude に一本化することを検討する。

一本化してよいかの条件は、3.2 節の 2「役ごとの規約と記憶」が満たせることである (「それさえできれば正直もうオープンクローを使うし必要ってあんまりないし」)。

## 2. オーナーが求めているもの

オーナーの発言をそのまま要求として固定する。言い換えない。

2026-11-03 の発言 (オーナーの文のまま)。

- 「今、クロードコード PDA は補助的な利用しているんだが、PDA は中若干使いづらいなという気がすでにしていて、オープンクローの目玉機能である Dreaming も側の方が強くて、全然ドリーミング機能が使われてないし、使い勝手としても Cloud Code Desktop の方がいいので、PDA でやりたかったことを Cloud Code CLI にかませるラッパースクリプトで解決できるんだったらそれでいいんじゃないかなという気がしてるんだよね。」
- 「一番の問題になるのは、コミュニケーション原則みたいな、強制力の強い各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニングが機能するようにする仕組みを考えないといけないんだよね。それが、それさえできれば正直もうオープンクローを使うし必要ってあんまりないし、もうなんかコーデックスも最近正直性能がしょぼいから、クロード一本化でいいんじゃないかなって気がしてるんだけど」
- 「スマホから届く入り口と見通しについて、クロードに一本化する上で、スマホから届く入り口を一つにするためのアーキテクチャ的検討が必要だ。例えば、オープン AI が提供しているドッツは、フロントドアエージェントみたいなのが、リモート上に常駐していて、それに対してアクセスをする。複数のデバイスからドッツのエージェントに対して会話をして、ドッツのエージェントから、別のセッションを立ち上げて作業を移動するような形になる。そうしたパーソナルエージェント的な、セッションスポーンを含むエージェント環境を構築すると、一つの入り口に統一できる。」
- 「今回やりたいクロードコードでの一本化もそれで、リモートセッションまたはクロードデスクトップ上で PDA 上、ミニ PC 上の、ロングランし続ける一つのセッションを構築して、そこからセッションスポーンなどのツールで、作業割り当て、ロール割り当てをした別のセッションをスポーンさせるができると良い。それがもしセッションスポーンを、クロード -P の、CLI 上のセッションを起動して作業をうまく移乗することができれば、コンテキストを個別に注入することもできるようになるはず。」
- 「なので、発想としては、クロードコード、クロードをいかに有効活用するかというよりは、クロード上にいかにドッツのようなパーソナルエージェントを真似して構築して、それを、一つの入り口として使え、そこからセッションスポーン機能を持たせるようにするってことになる。」
- 「だからさ、クロード、デスクトップとか、クロードアプリのリモートセッションをフロントドアにするっていう要件、どっかに飛んでってないか、これ。」
- 「機能要件として私に質問してリクワイアメンツに転写する必要がある内容と、設計で吸収すべき内容、実装で吸収すべき内容が混在している。」

2026-11-03 に、要件の問い 7 件に答えた内容 (選んだ選択肢と、自由回答はオーナーの文のまま)。

- 強制力: 規約を役のセッションに必ず載せ、加えて、出来上がった出力を規約で点検し、外れていれば直させる。
- 起こした先の見渡し: 見渡し・途中で止める・途中の出力・途中の介入は、入口のセッションだけを対象にする。自由回答「入口のセッションから進捗が把握できるように中間出力が設定できれば、私から直接停止できることは必須ではない」
- 入口のアカウント: 個人。
- 会社のコネクタの経路: 入口から開発 PC の Claude に頼む経路を残す。
- 記憶: 整理の仕組みが要る。自由回答「しかし、これはセカンドブレインなどの別の思想の実装方法を部分的に取り込む形にし、初期の必須要件ではない。」
- スマホへの通知: 入口の返事や承認待ちをスマホに知らせることを要件にする。
- 既存の要件との関係: 本文書を新しい基準にし、引き継ぐ項目だけを名指しで引く。

2026-11-03 に、v0.2 と v0.3 の要件から引き継ぐ項目に答えた内容 (回答と、自由回答はオーナーの文のまま)。

- Claude を定額のログインで動かす: 引き継ぐ。
- 指示・skill・hook・MCP の正本を 1 か所に置き、すべての役に配る: 引き継ぐ。
- 起動時に読み込む道具と MCP を、役ごとに絞る: 引き継がない。自由回答「ここは"任意"。機能 要件ではなく、実装してみて、token量など次第で非機能要件の実現方法として吸収。」
- 流れが止まるときに報告を書き、成果物は報告と別に一覧できる: 未選択。自由回答「説明が意味不明。何の流れ？　何についての報告？ 一覧するのは私？」
- セッションの出来事をログストア (OpenObserve か Datadog) に流す: 引き継がない。自由回答「可視化のための実装方法であって機能要件ではない。claudeのセッションとして残る前提なら、それでも十分実現可能。」
- 使う部品が、上流の変化に追従できる: 引き継がない。自由回答「機能要件ではない。」

- 会社と個人のアカウントを、同じ一覧に並べて同じ操作で扱う: 引き継がない。
- 報告を Markdown か HTML で整形して見せる: 引き継がない。
- 古いセッションの記録を読み取り、記憶に引き継ぐ: 未選択。自由回答「機能要件としてはあるが、MVP時点の必須要件としない」

- オーナーが指示していない安全装置を足さない: 引き継ぐ。
- 判定モデル (Jev) を、判断の材料を足す使い方で使う: 引き継がない。自由回答「機能要件ではなく実現方法」

2026-11-03 に、報告の問いについて述べた内容 (オーナーの文のまま)。

- 「これは発想としては、むしろ逆で、ロールのセッションが作業を完了した、進行したで、つどつど私に確認を取っていくのではなく、非同期的に私のジャッジが必要なものとしてスタックされていく。で、それについての取り扱いをフロントドアが整理していく方式が正しいかな。で、ここで必要なのが、誰が起動したセッションかが重要であって、ここで、スタッフが自分の作業を、社長に直で上申するんですかという問題。実際はそんなことはしないと。社長が直々に、君にこの作業を任せるって言ったときは、それは社長に直で返すが、別の部署のリーダーから作業指示をもらった、その指示の結果について、まず部長が判断するよね。で、その部長で判断がつかなかったら社長にエスカレされると。」

## 3. 本当に必要なもの

2 節の発言と回答から導いた要件。各項目に、根拠にした発言を付ける。入口の画面は Claude Desktop と Claude アプリに決まっているので、画面に求める内容 (見せ方、一覧、画面からの操作) は要件にしない。

### 3.1 オーナーが決めた形

オーナーが発言で指定した形。設計はこの形の中で行う。

1. **入口の画面は Claude Desktop と Claude アプリのリモートのセッション。** それ以外のチャットのアプリや自作の画面を入口にしない。(「使い勝手としても Cloud Code Desktop の方がいい」「リモートセッションまたはクロードデスクトップ上で」「クロード、デスクトップとか、クロードアプリのリモートセッションをフロントドアにするっていう要件」)
2. **入口は、ミニ PC 上で動き続ける 1 つのセッション。個人のアカウントで動かす。** 複数の端末から、この 1 つのセッションに話しかける。(「スマホから届く入り口を一つにする」「PDA 上、ミニ PC 上の、ロングランし続ける一つのセッション」、回答「入口のアカウント: 個人」)
3. **入口のセッションが、作業と役を割り当てた別のセッションを起こし、作業を移す。** 起こした先は、Claude のセッションとして記録に残る。(「ドッツのエージェントから、別のセッションを立ち上げて作業を移動する」「作業割り当て、ロール割り当てをした別のセッションをスポーンさせる」、項目 5 の自由回答「claudeのセッションとして残る前提なら」)
4. **セッションは、オーナーを頂点に、入口が中継するツリーをなす。** 起こされたセッションの結果は、起こした側に返る。起こした側が判断し、判断がつかないものだけを一段上へ上げる。オーナーが入口に頼んだ作業の結果は、入口を通ってオーナーに返る。(「誰が起動したセッションかが重要」「社長が直々に、君にこの作業を任せるって言ったときは、それは社長に直で返す」「その部長で判断がつかなかったら社長にエスカレされる」)
5. **役ごとに調整する対象は、指示 (コンテキスト)・メモリ・hook。** (「各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニング」)
6. **会社のコネクタは開発 PC の Claude だけが使う。** v0.3 で決めた形を保つ。(回答「会社のコネクタの経路」)

### 3.2 機能要件

オーナーが行うこと、オーナーから見える振る舞い。

1. **頼んだ作業が、役を割り当てた担い手で行われる。** オーナーは入口に頼むだけで、担い手を自分で起こさない。(「作業割り当て、ロール割り当てをした別のセッションをスポーンさせる」)
2. **役ごとの規約と記憶。** 役ごとに定めた規約 (コミュニケーション原則のような指示) が、その役の出力に必ず効く。出来上がった出力が規約から外れていれば、点検で見つかって直る。役ごとに調整したメモリが、その役で効く。(「強制力の強い各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニングが機能する」、回答「強制力」)
3. **オーナーの判断が要るものは、非同期に積まれ、入口が整理する。** 担い手は、作業を終えるたび・進めるたびにオーナーに確認を取らない。(「つどつど私に確認を取っていくのではなく、非同期的に私のジャッジが必要なものとしてスタックされていく。で、それについての取り扱いをフロントドアが整理していく」)
4. **入口が起こした作業の進捗が、入口から分かる。** オーナーが入口に尋ねると進捗が分かる。起こした先をオーナーが直接止められることは要らない。(回答「起こした先の見渡し」の自由回答)
5. **会社のコネクタを使う作業を、入口から頼める。** 入口に頼むと開発 PC の Claude で行われ、結果が入口に返る。(回答「会社のコネクタの経路」)
6. **入口の返事と承認待ちが、スマホに届く。** (回答「スマホへの通知」)

### 3.3 オーナーの条件

機能ではないが、オーナーが要件として引き継いだもの。

1. **Claude は定額のログインで動かす。** API キーの従量課金で動かさない。(項目「Claude を定額のログインで動かす」の回答)
2. **指示・skill・hook・MCP の正本を 1 か所に置き、すべての役に配る。** (項目「指示・skill・hook・MCP の正本を 1 か所に置き、すべての役に配る」の回答)
3. **オーナーが指示していない安全装置を足さない。** 止める・断る仕組みは、オーナーの承認を得てから作る ([docs/process/progress-over-stopping.md](../process/progress-over-stopping.md))。(項目「オーナーが指示していない安全装置を足さない」の回答)
4. **Claude に一本化し、OpenClaw と Codex を使わない。** 1 節の条件が満たせる場合に限る。(「クロード一本化でいいんじゃないか」)

### 3.4 機能要件だが、MVP 時点の必須要件としないもの

1. **記憶の整理。** セカンドブレインなどの別の思想の実装方法を部分的に取り込む形にする。(回答「記憶」の自由回答)
2. **古いセッションの記録を読み取り、記憶に引き継ぐ。** (自由回答「機能要件としてはあるが、MVP時点の必須要件としない」)
3. **割り振りやフローを、成果とフィードバックで書き換える。** (自由回答「記憶の整理同様。」)

### 3.5 引き継がないもの

v0.2 と v0.3 の要件のうち、本件に引き継がないもの。

- 画面に求めていた内容なので要件にしない: 入口のセッションを途中で止める・途中の出力を見る・途中で指示を足す、画面から担い手を起こし止める、会社と個人のアカウントを同じ一覧で扱う、報告を Markdown か HTML で整形して見せる、成果物を報告と別に一覧して開ける。
- 機能として要らない: タスクの完了と中止をオーナーだけが記録する。
- 実現方法なので要件に置かない: 役ごとに読み込む道具を絞る (任意。実装してからトークンの量を見て扱う)、出来事をログストアに流す、上流の変化への追従、判定モデルを判断の材料に使う。

## 4. 判定できる受け入れ条件

- C1 (3.1-1、3.1-2): 個人のアカウントでログインしたスマホの Claude アプリと PC の Claude Desktop のどちらからも、ミニ PC で動き続ける同じ入口のセッションに話しかけられる。
- C2 (3.1-3、3.2-1): 入口のセッションに頼んだ作業が、役を割り当てた別のセッションで行われ、そのセッションが入口とは別の Claude のセッションとして記録に残る。
- C3 (3.1-4): 役のセッションが起こしたセッションの結果は、起こした役のセッションに返り、オーナーには直接届かない。
- C4 (3.1-4、3.2-3): 起こした側が判断できないものだけが一段上に上がり、入口まで上がったものと、オーナーが頼んだ作業の結果は、オーナーの判断待ちとして積まれる。
- C5 (3.2-3): 担い手が作業を終えたとき・進めたときに、オーナーへ確認を求める問いがその都度は届かない。
- C6 (3.1-5、3.2-2): 役ごとに定めた指示・メモリ・hook が、その役のセッションで効く。
- C7 (3.2-2): 役のセッションの出力が規約から外れたとき、点検で見つかって直され、直したことが記録に残る。
- C8 (3.2-4): 起こした先のセッションの途中経過が入口に届き、オーナーが入口のセッションに尋ねると進捗が分かる。
- C9 (3.1-6、3.2-5): 入口から頼んだ、会社のコネクタを使う作業が開発 PC の Claude で行われ、結果が入口に返る。
- C10 (3.2-6): 入口のセッションが返事をしたとき、承認を待っているときに、スマホに通知が届く。
- C11 (3.3-1): 入口と役のセッションが、個人の定額のログインで動き、API キーで課金されない。
- C12 (3.3-2): 正本の指示・skill・hook・MCP を 1 か所で直すと、すべての役のセッションに届く。
- C13 (3.3-4): OpenClaw と Codex を止めた状態で、C1〜C12 が成り立つ。

## 5. 未確定事項

以下はオーナーの判断で決まるもので、この文書では確定しない。

1. **3.1 の 4 のツリーが、オーナーの考えと合っているか。**
2. **オーナーが頼んだ作業の結果を、入口が自分で判断して片付けてよいか。** 入口が整理だけをしてオーナーの判断待ちに積むか、入口も一段として判断するか。
