# Claude 一本化の要件

- 更新: 2026-11-03 JST
- 種別: オーナー指示による要件の整理。設計・実装・製品選定の宣言ではない。
- 位置付け: Claude 一本化の検討の要件の正本で、新しい基準とする。調査と設計は、本文書の 3 節と 4 節を物差しにする。要件が変わる場合は本文書を先に改める。v0.2 の要件正本 ([docs/requirements.md](../requirements.md)) と v0.3 の要件 ([docs/plan-v0.3.md](../plan-v0.3.md) の 4 節、R1〜R14) からは、引き継ぐ項目だけを名指しで引く (5 節)。

## 1. なぜ検討するか

PDA は v0.3 で、ミニ PC に常駐する OpenClaw を入口にし、Claude Code と Codex を実行器にした ([v0.3 の決定](../reports/v0.3-decision.md))。オーナーは PDA を補助的に使っているが、使いづらさを感じている。OpenClaw の目玉機能の Dreaming は使われておらず、使い勝手は Claude Code Desktop のほうがよい。Codex の性能にも不満がある。そこで、PDA でやりたかったことを Claude の上で満たせるなら、OpenClaw と Codex をやめて Claude に一本化することを検討する。

## 2. オーナーが求めているもの

オーナーの発言をそのまま要求として固定する。言い換えない。

2026-11-03 の発言 (オーナーの文のまま)。

- 「今、クロードコード PDA は補助的な利用しているんだが、PDA は中若干使いづらいなという気がすでにしていて、オープンクローの目玉機能である Dreaming も側の方が強くて、全然ドリーミング機能が使われてないし、使い勝手としても Cloud Code Desktop の方がいいので、PDA でやりたかったことを Cloud Code CLI にかませるラッパースクリプトで解決できるんだったらそれでいいんじゃないかなという気がしてるんだよね。」
- 「一番の問題になるのは、コミュニケーション原則みたいな、強制力の強い各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニングが機能するようにする仕組みを考えないといけないんだよね。それが、それさえできれば正直もうオープンクローを使うし必要ってあんまりないし、もうなんかコーデックスも最近正直性能がしょぼいから、クロード一本化でいいんじゃないかなって気がしてるんだけど」
- 「スマホから届く入り口と見通しについて、クロードに一本化する上で、スマホから届く入り口を一つにするためのアーキテクチャ的検討が必要だ。例えば、オープン AI が提供しているドッツは、フロントドアエージェントみたいなのが、リモート上に常駐していて、それに対してアクセスをする。複数のデバイスからドッツのエージェントに対して会話をして、ドッツのエージェントから、別のセッションを立ち上げて作業を移動するような形になる。そうしたパーソナルエージェント的な、セッションスポーンを含むエージェント環境を構築すると、一つの入り口に統一できる。」
- 「今回やりたいクロードコードでの一本化もそれで、リモートセッションまたはクロードデスクトップ上で PDA 上、ミニ PC 上の、ロングランし続ける一つのセッションを構築して、そこからセッションスポーンなどのツールで、作業割り当て、ロール割り当てをした別のセッションをスポーンさせるができると良い。それがもしセッションスポーンを、クロード -P の、CLI 上のセッションを起動して作業をうまく移乗することができれば、コンテキストを個別に注入することもできるようになるはず。」
- 「なので、発想としては、クロードコード、クロードをいかに有効活用するかというよりは、クロード上にいかにドッツのようなパーソナルエージェントを真似して構築して、それを、一つの入り口として使え、そこからセッションスポーン機能を持たせるようにするってことになる。」
- 「だからさ、クロード、デスクトップとか、クロードアプリのリモートセッションをフロントドアにするっていう要件、どっかに飛んでってないか、これ。」

2026-11-03 に、要件の問い 7 件に答えた内容 (選んだ選択肢と、自由回答はオーナーの文のまま)。

- 強制力: 規約を役のセッションに必ず載せ、加えて、出来上がった出力を規約で点検し、外れていれば直させる。
- 起こした先の見渡し: 見渡し・途中で止める・途中の出力・途中の介入は、入口のセッションだけを対象にする。自由回答「入口のセッションから進捗が把握できるように中間出力が設定できれば、私から直接停止できることは必須ではない」
- 入口のアカウント: 個人。
- 会社のコネクタの経路: 入口から開発 PC の Claude に頼む経路を残す。
- 記憶: 整理の仕組みが要る。自由回答「しかし、これはセカンドブレインなどの別の思想の実装方法を部分的に取り込む形にし、初期の必須要件ではない。」
- スマホへの通知: 入口の返事や承認待ちをスマホに知らせることを要件にする。
- 既存の要件との関係: 本文書を新しい基準にし、引き継ぐ項目だけを名指しで引く。

## 3. 本当に必要なもの

2 節の発言と回答から導いた要件。各項目に、根拠にした発言を付ける。

1. **入口の画面は Claude Desktop と Claude アプリのリモートのセッション。** オーナーは、Claude Desktop と Claude アプリ (スマホ) のリモートのセッションから話しかける。それ以外のチャットのアプリや自作の画面を入口にしない。(「使い勝手としても Cloud Code Desktop の方がいい」「リモートセッションまたはクロードデスクトップ上で」「クロード、デスクトップとか、クロードアプリのリモートセッションをフロントドアにするっていう要件」)
2. **入口は 1 つで、ミニ PC 上で動き続ける 1 つのセッション。個人のアカウントで動かす。** 複数の端末から、同じ 1 つのセッションに話しかける。(「スマホから届く入り口を一つにする」「複数のデバイスから…会話をして」「PDA 上、ミニ PC 上の、ロングランし続ける一つのセッション」、回答「入口のアカウント: 個人」)
3. **入口のセッションが、別のセッションを起こして作業を移す。** 起こすセッションには、作業と役を割り当てる。(「ドッツのエージェントから、別のセッションを立ち上げて作業を移動する」「作業割り当て、ロール割り当てをした別のセッションをスポーンさせる」)
4. **役ごとに、指示・メモリ・hook を分けて機能させる。** 役ごとに、コミュニケーション原則のような指示 (コンテキスト)、メモリ、hook を分け、それが機能する仕組みを持つ。これが一番の問題である。機能するとは、規約を役のセッションに必ず載せ、加えて、出来上がった出力を規約で点検し、外れていれば直させることを指す。(「一番の問題になるのは、コミュニケーション原則みたいな、強制力の強い各ロールごとへのコンテキストチューニング、メモリチューニングやフックのチューニングが機能するようにする仕組み」、回答「強制力」)
5. **見渡しと介入は入口のセッションを対象にする。** オーナーは、入口のセッションを途中で止め、途中の出力を見て、途中で指示を足せる。起こした先のセッションについては、その中間出力を入口のセッションに届くように設定でき、入口のセッションから進捗が把握できればよい。起こした先をオーナーが直接止められることは必須ではない。(回答「起こした先の見渡し」と自由回答)
6. **会社のコネクタを使う作業は、入口から開発 PC の Claude に頼む。** v0.3 で決めた、会社のコネクタは開発 PC の Claude だけが使う形を保ち、OpenClaw の node に代わる経路を持つ。(回答「会社のコネクタの経路」)
7. **入口の返事と承認待ちをスマホに知らせる。** (回答「スマホへの通知」)
8. **Claude に一本化し、OpenClaw と Codex をやめる。** 4 が満たせることを条件にする。(「それさえできれば正直もうオープンクローを使うし必要ってあんまりないし」「クロード一本化でいいんじゃないか」)
9. **作り足しは、Claude Code CLI にかませるラッパースクリプトで済むなら、それでよい。** (「PDA でやりたかったことを Cloud Code CLI にかませるラッパースクリプトで解決できるんだったらそれでいい」)

初期の必須要件ではないもの。

- **記憶の整理。** 記憶を整理する仕組みは要る。セカンドブレインなどの別の思想の実装方法を部分的に取り込む形にし、初期の必須要件にはしない。(回答「記憶」と自由回答)

起こすセッションを `claude -p` で起動して文脈を個別に注入する形は、オーナーが「できれば」と挙げた手段の候補であり、要件ではない。

## 4. 判定できる受け入れ条件

| ID | 条件 | 要件 |
|---|---|---|
| C1 | 個人のアカウントでログインしたスマホの Claude アプリと PC の Claude Desktop のどちらからも、同じ入口のセッションに話しかけられ、同じ会話が続く | 1、2 |
| C2 | 入口のセッションがミニ PC で動き続け、オーナーが新しいセッションを作らなくても、同じ入口に話しかけられる | 2 |
| C3 | 入口のセッションに頼んだ作業が、役を割り当てた別のセッションで行われ、そのセッションが入口とは別のセッションとして記録に残る | 3 |
| C4 | 役ごとに定めた指示・メモリ・hook が、その役のセッションで効き、別の役のセッションでは効かない | 4 |
| C5 | 役のセッションの出力が規約から外れたとき、点検で見つかって直され、直したことが記録に残る | 4 |
| C6 | オーナーが、Claude アプリから入口のセッションを途中で止め、途中の出力を見て、途中で指示を足せる | 5 |
| C7 | 起こした先のセッションの中間出力が入口のセッションに届き、オーナーが入口のセッションに尋ねると進捗が分かる | 5 |
| C8 | 入口から頼んだ、会社のコネクタを使う作業が開発 PC の Claude で行われ、結果が入口に返る | 6 |
| C9 | 入口のセッションが返事をしたとき、承認を待っているときに、スマホに通知が届く | 7 |
| C10 | OpenClaw と Codex を止めた状態で、C1〜C9 が成り立つ | 8 |
