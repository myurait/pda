# 作業計画: 案Cの段階2

- 日付: 2026-11-27 JST
- 種別: 作業計画。[案の比較](solution-options.md)の5.3節の案Cの実現計画のうち、段階2の項目の優先度と、項目ごとの完了条件を決める。
- 物差し: [要件](requirements.md)の4節の受け入れ条件。
- 作成の指示: 2026-11-27のオーナーの指示「スマホでの動作確認完了。次のステップへ。優先度設定して、明確な完了条件を事前に設定し、順に自走せよ。」
- 項目ごとの設計は [design-stage2.md](design-stage2.md) に、確認した手順と結果は [check-stage2.md](check-stage2.md) に、項目に着いたときに書く。

## 1. 範囲と終点

- 範囲は、段階2の項目 (承認のワンボタンとコマンドの表示、資料の配信、音声の取り込み、開発PCのブリッジ、ヒストリーとナレッジの集約、案件の名前からの続き、ゲートの足し引き) と、オーナーの規約をセッションに載せること、定額のログインへの備えである。
- 終点は、要件の4節の必須の条件のうち、段階1で確認していないものを、3節の完了条件で確認し終えた時点とする。
- C13 (入口にOpenClawを使わず、作業をCodexに行わせない状態で、ほかの条件がすべて成り立つ) の判定と、OpenClawを止めることは、この計画に入れない。結論が出るまでv0.3の運用は変えない ([README.md](README.md)の位置付け)。

## 2. 優先度の規則

上の規則から順に当てる。

1. 満たせないと分かったら、一本化そのもの・ツール・画面の製品を選び直すことになる条件を先にする (要件の1節の一本化してよいかの条件とツールを選ぶ条件、3.7節の画面の製品を選ぶ条件)。
2. ほかの項目が前提にする項目を先にする。
3. オーナーが発言で困りごととして述べた項目を先にする。
4. 残る確認が、オーナーの端末・声・会社のログインを要るものだけの項目は後ろにする。

## 3. 項目の順と完了条件

完了条件は、要件の条件の原文と、それを判定する試験の対で書く。試験は、ミニPCの確認用の常駐プロセス (4節) で行う。

### 3.1 作業するディレクトリの差し替え (規則1)

- 条件 (C19): セッションで作業するディレクトリを途中で差し替えられ、作ったディレクトリで作業すると言えば、そこが割り当てになる。セッションが参照するパスは絶対パスである。作業するリポジトリを替えても、セッションの動きの土台はオーナーの規範のままで、リポジトリのAI向けの指示はその上に重なる。3.2-12で見つけたリポジトリも、同じように差し替えられる。
- 試験
  1. セッションの途中で、別のディレクトリで作業すると伝える。次のターンのコマンドがそのディレクトリで実行され、台帳のセッションの作業ディレクトリが替わっている。
  2. セッションの中で作ったディレクトリで作業すると伝える。試験1と同じ結果になる。
  3. AI向けの指示を持つリポジトリに替える。その指示が役の指示のあとに重なってセッションに届く。別のリポジトリに替えると、前のリポジトリの指示が届かなくなる。
  4. セッションに渡す作業ディレクトリと、台帳に残るパスが絶対パスである。

### 3.2 定額のログインへの備え (規則1)

- 条件 (C11): メインセッションと起動したセッションが、定額のログインで動き、APIキーで課金されない。
- 試験
  1. 公式の資料とCLIの説明で、`claude -p` の既定が `--bare` に替わったあとも定額のログインを使う指定があるかを確認する。あれば起動の行に入れ、その行で返信が返る。
  2. 指定が無ければ、無いことと出典を記録する。あわせて、ログインを使えずに終わった起動が、オーナーに届く返信と台帳で見分けられる。

### 3.3 資料の配信と、画面の条件の残り (規則1)

- 条件 (C22): PCとスマホのどちらでも、会社のアカウントで作ったアーティファクトとPDAのセッションが作ったアーティファクトを、ログインを切り替えずに開ける。リンクを知っている全員への共有は使わず、ブラウザは会社契約でログインしたまま使える。
- 条件 (C26): エージェントが動かしたコマンドとその出力を、会話の中で追える。
- 条件 (C24): 話しかけている画面で、今PDAのどのセッションにいるかが分かる。
- 試験
  1. セッションに資料を作らせる。資料がスレッドの中で返信の上に出て、T3 Codeの画面で、Claudeのログインを使わずに開ける。資料のURLは、tailnetの外に公開されない。(2026-11-27: [設計](design-stage2.md)の3節で、資料をT3 Codeのスレッドに付ける形を選んだので、この試験を書き直した。前は、返信に入れた資料のリンクをtailnetのURLで開く試験だった。)
  2. コマンドを実行したターンの画面で、コマンドとその出力が会話の中に出ている。
  3. メインセッションと作業のセッションのスレッドで、画面にセッションの名前が出ている。
- オーナーが要る確認: スマホで資料のリンクを開く。会社のアカウントで作ったアーティファクトは、3.8節のブリッジができてから確認する。

### 3.4 オーナーの規約をセッションに載せる、前処理のゲート (規則3)

- 条件 (C16): PDAのどのセッションでも、オーナーのコミュニケーション規則・hook・メモリが効き、守られたかが応答の終端のゲートで確かめられる。
- 条件 (C12): 正本の指示・skill・hook・MCPを1か所で直すと、PDAのすべてのセッションに届く。
- 条件 (C29): PDAの正本に、開発PC上の会社のアカウントの規則が入っていない。PDAの正本を直しても、開発PCのClaude Codeの設定は変わらない。
- 条件 (C15の前半): 応答の前後に複数のゲートが置かれている。
- 基準にする規則は [rule-gates.json](rule-gates.json) とする。オーナーの開発PCのメモリの本文は、リポジトリにコピーしない。
- 載せる規則 (2026-11-27、試験の前に決めた): rule-gates.json の規則のうち、外す印の無いものを1件ずつ見て、載せるものと載せないものに分けた。試験1の分母は、載せる規則だけにする。載せない規則は次の3種類で、規則ごとの扱いは正本のデータに残す。
  - 開発PCのツールと仕組みだけに当たる規則 (開発PCのコマンドの許可の形、サンドボックス、開発PCのメモリとhookの作り方、開発PCの画面の決まり)
  - 会社のアカウントの規則と、外部に公開する作業のやり取りの規則 (C29)
  - 凍結したバージョン (v0.1、v0.2) の進め方の規則
- 試験の結果は、規則ごとに「役の指示に載せた」「終端で判定する」「外れを差し戻す」を分けて記録する。役の指示に載せただけの規則は、C16の「守られたかが応答の終端のゲートで確かめられる」に数えない。
- 正本に置いたskill 1つとMCP 1つが、メインセッションと作業のセッションの両方に届くことを、試験2に足す。
- 試験
  1. rule-gates.json の規則のうち、外す印の無いものが、発火点ごとに、役の指示・報告係の指示・ゲートの問いのどれかに載っている。載せ先の一覧を規則のデータと照合して、載っていない規則が無い。
  2. 正本の規則を1つ直す。常駐プロセスを再起動せずに、次のターンから、メインセッションと作業のセッションの両方に届く。
  3. 依頼を受けた時点のゲートが動き、その判定が台帳に残る。
  4. 終端のゲートで、判定器ごとに、新しく載せた規則の外れが1つ以上見つかって差し戻される。
  5. 正本の中に、会社のコネクタの使い方・外部に公開する作業のやり取り・権限についての規則が無い。

### 3.5 報告の要否と判断待ち (規則2)

- 条件 (C4): メインセッションが起動したセッションで判断が要るものが、起動元のメインセッションに報告として届き、オーナーはメインセッションで受け取れる。
- 条件 (C5): 担い手が判断の要らない手順を進めている間、オーナーには知らせも確認の問いも届かない。判断が要るとき・指示が要るとき・完了したとき・未完了で止まったときは報告が届く。作業の成果として確定した内容は、完了報告の中の1つの議題として届く。
- 試験
  1. 作業のセッションに、途中でオーナーの判断が要る作業を依頼する。判断待ちの報告がメインセッションのスレッドに届き、通知はメインセッションの返信の1通である。
  2. 判断の要らない手順が続く作業を依頼する。終わるまで、通知と返信が出ない。

### 3.6 引き継ぎ、ヒストリーとナレッジ、案件の名前からの続き (規則2)

- 条件 (C1の後半): いつもの新規セッションを開く操作で始めてメインセッションにしたとき、オーナーが前のことを言い直さずに尋ねると、前のメインセッションが起動したセッションの進捗と、返ってきた判断待ちが答えに返る。
- 条件 (C17): ある作業で決まったことが、別のセッションで同じ案件を扱うときに、オーナーが言い直さなくても使われる。開発PC上のものを含むチャットヒストリーを、尋ねるとPDAのセッションが探して読める。
- 条件 (C18): 新しいセッションで案件の名前か作業の中身を話すだけで、オーナーがリポジトリとセッションを指定しなくても、その案件のリポジトリと前のセッションの文脈から作業が続く。
- 試験
  1. メインセッションに作業を移させ、判断待ちの報告を1つ返させる。新しいスレッドで「進んでいる作業と、私の判断を待っているものは」と尋ねる。前のメインセッションが起動したセッションの進捗と判断待ちが返る。
  2. あるセッションで案件について決める。別の新しいセッションで同じ案件の作業を依頼する。決めた内容が、言い直さずに使われる。
  3. 前のセッションのやり取りについて尋ねる。セッションがヒストリーを探して、該当のやり取りを答える。
  4. 新しいセッションで案件の名前だけを伝える。その案件のリポジトリが作業ディレクトリになり、前のセッションの続きから始まる。
- 開発PC上のチャットヒストリーは、3.8節のブリッジができてから確認する。

### 3.7 ゲートの足し引き (規則2)

- 条件 (C15の後半): エージェントがPDA全体に適用するゲートを足す・消す・変えると、オーナーの承認を待たずに効き、その変更が完了報告の中の1つの議題としてオーナーに届く。オーナーが同じ種類の作業で繰り返し出していた指示が、言われなくても行われ、行われたかがゲートで確かめられる。
- 試験
  1. セッションに、返信の書き方の規則を1つ足させる。次のターンから、別のセッションでその規則の外れが差し戻される。足したことが、そのターンの返信の議題に入っている。
  2. 足した規則を変えさせ、消させる。変えたあとと消したあとの判定が、次のターンから替わる。
  3. 同じ種類の作業で同じ指示を繰り返す。そのあと、指示を言わずに同じ種類の作業を依頼すると、指示の内容が行われ、行われたかの判定が台帳に残る。

### 3.8 開発PCのブリッジ (規則4)

- 条件 (C9): PDAのセッションから依頼した、会社のコネクタを使う作業が、開発PCのClaudeで行われ、結果が依頼したPDAのセッションに返る。PDAの側で作られ、T3 Codeで確認できる資料 (HTML) を、会社の中に展開するときに、開発PCのClaudeがそのHTMLのまま会社契約のアカウントのアーティファクトとして公開し、リンクが依頼したPDAのセッションに返る。オーナーは開発PCのセッションに入らず、開発PCへの指示の出し方を作業ごとに調整しない。(2026-11-28のオーナーの発言で、要件が改まった)
- 条件 (C8): 個人で受けている案件・会社の案件・PDA自身のどれについても、PDAのどのセッションで尋ねても、今どこまで進み、次に何が要るかが返る。会社のチケット管理ツールにしかない状態も、開発PCの会社のClaudeを通して返る。
- 条件 (C20): 開発PCで途中まで進めた作業を、PDAのセッションで続けられる。
- 着手したら先に、今ある経路で足りるかを確認する。開発PCに新しい常駐プロセスや外部からの接続を受け付ける仕組みを置く形が要ると分かったら、作らずに、オーナーの判断を1つ求める。
- 試験
  1. PDAのセッションから、会社のチケットの状態を尋ねる。開発PCのClaudeを通した答えが、依頼したセッションの返信で返る。
  2. T3 Codeに表示された資料を、PDAのセッションから、会社契約のアカウントのアーティファクトとして公開させる。リンクが、依頼したセッションの返信で返り、公開されたページの内容が、T3 Codeに表示された資料と同じである。
  3. 開発PCのセッションで途中まで進めた作業の続きを、PDAのセッションに依頼する。開発PCのセッションの記録を使って、続きから進む。

### 3.9 PCでの音声入力 (規則4)

- 条件 (C21): 音声で話した依頼が、フィラーや変換ミスを含んでいても、オーナーが打ち直さずに、意図どおりの指示として作業が進む。
- 試験: PCのブラウザの画面で、音声入力のボタンから文字が入力欄に入る状態になっている。
- オーナーが要る確認: PCのブラウザから声で依頼し、打ち直さずに作業が進む。

### 3.10 オーナーに届く文と資料を、Claude以外のモデルが作る (2026-11-28のオーナーの発言で足した項目)

- 条件 (C33): オーナーに届く返信と資料が、Claude以外のエージェント (試験の段階ではCodex、最終的にはGeminiのAPI) が書いた文で届く。作業するセッションは、作業の履歴と成果物についての説明を渡し、オーナーに届く文と資料のHTMLを書かない。資料は、通っていないものとして出す手順を経ずに、T3 Codeに出る。文と資料を作る係の中のエージェントを、設定で差し替えられ、差し替えても、作業するセッションとほかの部品を変えずに、返信と資料が同じ形で届く。
- 試験 (中のエージェントはCodex)
  1. 作業を依頼する。返信が、Codexの書いた文で返る。台帳に、作業するセッションが渡した内容と、Codexが書いた返信が残っている。
  2. 資料の要る依頼を送る。作業するセッションは材料だけを渡し、Codexが書いたHTMLの資料が、T3 Codeに表示される。
  3. 設定で、中のエージェントをCodexから現状のClaudeに差し替え、試験1と2を繰り返す。作業するセッションとほかの部品を変えずに、返信と資料が同じ形で届く。
- GeminiのAPIのキーが手に入ってから行うこと: Geminiの実装を足し、設定で差し替えて、試験1と2を繰り返す。
- オーナーが要る確認: Claude以外のエージェントが書いた返信と資料が、Claudeの書いたものより読みやすいこと。GeminiのAPIのキーは、オーナーが用意する。

## 4. 進め方

- 項目ごとに、設計を書き、実装し、試験で確認し、記録してから、本番の常駐プロセスに入れる。
- 試験は、本番の常駐プロセス (`pda-pipeline.service`) と別に起動した確認用の常駐プロセスで行う。確認用の常駐プロセスは、別のソケット・設定・台帳と、使い捨ての通知先を持つ。本番の常駐プロセスの設定と通知先は変えない。
- コミットはmainに入れ、originとミニPCのリポジトリにpushする。本番の常駐プロセスが使うミニPCの `~/pda` のpullと、本番の常駐プロセスの再起動は、項目の完了条件が通ったあと、進行中のターンが無いときに行う。コミットのたびに `~/pda` をpullするふだんの決まりより遅らせるのは、確認する前のコードを本番に入れないためである。
- 完了条件が通らない項目は、通らなかった試験と理由を記録して、次の項目へ進む。
- オーナーが要る確認は、項目ごとに記録し、報告でまとめて伝える。
