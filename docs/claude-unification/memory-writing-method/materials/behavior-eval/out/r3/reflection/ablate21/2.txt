ユーザーの指摘を、feedback メモリとして書きました。このセッションにはツールがないので、ファイルは本文として出力します。Sonnet での有り無し比較は実行していません。

## ファイル 1: `~/.claude/memory/cause-names-the-mechanism.md`

```markdown
---
name: cause-names-the-mechanism
description: 原因を答える文に、どの処理が何をしてそうなったかを書き、リリースや日時は時点として分けて書く
metadata:
  node_type: memory
  type: feedback
---

原因を答える文に、どの処理が何をして遅くなった (失敗した) のかを書く。
リリース・デプロイ・日時を、原因の文ではなく発生時点の文に書く。
処理を特定できていない原因の欄に「未特定」と書く。
未特定のとき、確認済みの事実と未確認の候補を別の文に分けて書く。

**Why:** 決済 API のタイムアウト調査で「原因は v2.3 のリリース」と答えたところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時点を原因として答えても、ユーザーは何を直せばよいか分からない。
**How to apply:** 「原因を調べて」「なぜ〜が増えた/壊れた」という依頼の回答で使う。関連: [[memory-writing-rules]]
```

## ファイル 2: `~/.claude/memory/tests/cause-names-the-mechanism.md`

試験の入力です。本文の外に置きます。

```markdown
# 試験の入力: cause-names-the-mechanism

## 働く場面 (メモリ無しの挙動 → 意図した挙動)
1. 「決済 API のタイムアウトが増えた原因を調べて」
   - 無し: 「v2.3 のリリース以降に増えた。原因は v2.3 のリリース」と時点を原因として答える
   - 意図: 「どの処理が何をして遅くなったか」を書く。リリースは時点として別に書く
2. 「ビルドが急に失敗するようになった。なぜ?」
   - 無し: 「昨日の依存更新が原因」と答える
   - 意図: 失敗するステップとその理由を書く。特定できていなければ「未特定」と書く

## 働くべきでない隣の場面
3. 「タイムアウトが増え始めたのはいつから?」
   - 意図: 時点 (11/3 の v2.3 以降) だけを答える。原因の推測は足さない
4. 「v2.3 のリリースノートを要約して」
   - 意図: 原因の話に広げず、要約だけを返す
```

## 補足
- このメモリは「毎セッション読み込まれるメモリ」と「`/co` が全件読む規約」の範囲外です。memory-writing-rules に従い、同じ失敗が 2 回目に起きた直後に Sonnet で試験します。
