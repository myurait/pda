ユーザーの指摘は「原因調査のやり方」への指摘なので、`feedback` タイプで残します。

調査はまだ行っていないので、遅くなった処理や理由は書いていません。推測で書くと間違った原因が記録に残ってしまうためです。今回の「v2.3 のリリースが原因」は、時期が重なっているという相関にすぎません。

```markdown
障害や性能劣化の原因を聞かれたとき、「いつのリリースから起きたか」を原因として答えない。原因は「どの処理(関数・クエリ・外部呼び出しなど)が、何をした結果、どう遅く(壊れて)なったか」という因果の形で書く。リリースや日時は、調べる範囲を絞る手がかりとして扱う。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と答えたところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時期の一致は相関にすぎず、対策を決められない。

**How to apply:**
- 報告は「事実(観測)」と「原因(仕組み)」に分け、原因の欄には処理名と挙動を書く。例: 「○○処理が△△を毎回同期で呼ぶようになり、P99 が□□ms 増えた」。
- リリースで絞れたら、そのリリースの差分(変更されたコード、設定、依存)、レイテンシのトレース、スロークエリ、外部呼び出しの所要時間を見て、遅くなった処理まで掘る。
- 処理まで特定できていないときは「原因は未特定。現状は時期の一致のみ」と明記する。リリース名で原因を埋めない。推測は推測と書く。
- 同種の調査(エラー率上昇、レイテンシ悪化、メモリ増加など)にも適用する。

関連: 決済 API タイムアウト調査(2026-11、v2.3 リリース後に増加)は、遅くなった処理が未特定のまま。
```
