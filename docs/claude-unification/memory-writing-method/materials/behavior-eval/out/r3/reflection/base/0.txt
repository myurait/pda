```markdown
障害や性能劣化の原因調査では、「いつから起きたか(リリース、デプロイ、日付)」を原因として報告しない。原因は、どの処理(関数・クエリ・外部呼び出しなど)が、何をした結果、遅く(または壊れて)なったのかという仕組みまで特定して書く。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と答えたところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時期の特定は相関にすぎず、対策を立てる材料にならない。

**How to apply:**
- リリース時期や発生開始日は、原因を絞るための手がかりとして書く。結論にはしない。
- 時期を特定したら、その差分(変更されたコード、設定、依存、クエリ)を調べる。遅くなった処理を名指しし、その処理が何をしているか(例: N+1 クエリ、同期の外部呼び出し追加、ロック競合、リトライ増加)を書く。
- 根拠を添える。レイテンシの内訳、トレース、スロークエリログ、差分の該当箇所など。
- 特定できていないときは「原因は未特定」と明記する。推測は推測と分けて書く。仮説を事実のように書かない。
- 報告は「どの処理が / 何をして / なぜ遅くなったか / 根拠」の順で構成する。
- 関連: 決済 API タイムアウト増加の件は、v2.3(11/3)以降という時期の特定までで、遅くなった処理は未特定。
```
