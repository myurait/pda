```markdown
原因調査の報告で、「v2.3 のリリース以降に増えた」「原因は v2.3 のリリース」のように、リリース・デプロイ・日時を原因として書かない。それは変化が起きた時点であり、原因ではない。原因は「どの処理が、何をして、なぜ遅くなった(壊れた)のか」の水準で書く。

**Why:** 決済 API のタイムアウト増加の調査で、「原因は 11/3 の v2.3 リリース」と報告したところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時点だけでは、次に何を直せばよいか、何を防げばよいかが分からない。

**How to apply:**
- リリースや日時で絞り込めたら、そこで終わらせない。v2.3 の差分(コミット、変更されたコード、設定、依存ライブラリ、DB クエリやスキーマ)まで掘り下げる。
- 報告は次の形で書く。「①どの処理(関数、クエリ、外部呼び出し)が、②何をして(例: N+1 クエリ、ロック待ち、同期呼び出し化、タイムアウト値やリトライ設定の変更)、③その結果どう遅くなったか」。
- ログ、メトリクス、トレース、差分など、根拠を併記する。
- 確認できていない部分は推測だと明示する。分からなければ「時点までしか特定できていない。原因は未特定」と書き、断定しない。
- 「いつから」(時点)と「なぜ」(原因)は分けて書く。

関連: 決済 API タイムアウト調査(v2.3、11/3 以降)の具体的な原因は、この時点では未特定。
```
