今回の調査では、タイムアウトが増えた時期しか特定できていません。遅くなった処理は特定できていないので、メモリにも原因は書いていません。書いたのは、調査の進め方に関するフィードバックだけです。

```markdown
障害や性能劣化の原因調査では、「いつから起きたか(リリース、デプロイ、日時)」を原因として報告しない。原因は「どの処理が、何をした結果、どう遅く/壊れたか」という仕組みのレベルまで書く。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と報告したところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。リリースは発生時期の手がかりにすぎず、再発防止や修正に使える情報になっていなかった。

**How to apply:**
- 時期の特定(リリース・設定変更・トラフィック変化)は調査の出発点として扱い、結論にしない。
- 時期が分かったら、その変更の差分(コード、クエリ、設定、依存先)を読み、遅くなった具体的な処理を特定する。例: 呼び出し箇所、追加された外部呼び出し、N+1、ロック待ち、タイムアウト値の変更など。
- 報告は「処理 → 何をしている → なぜ遅い/失敗する → 根拠(ログ、メトリクス、差分、再現結果)」の形で書く。
- 根拠をまだ確認できていない部分は推測だと明示する。分からないときは、原因が分かったとは書かずに「時期までは特定、処理は未特定」と書く。
```
