メモリは**失敗の型**で書く。事例で書かない。標語で書かない。body は「ルール本文 / Why / How to apply」の 3 部に固定し、How to apply の発火条件は実行後に観測できる事象に置く。書いたら同じ操作で索引を更新する。

**発火条件を実行後に観測できる事象へ置く規則は、メモリに限らない。** skill / hook / 規約文書など、あとから自分が読んで従うルールを書く場面すべてに適用する。

**Why:**

事例を並べたメモリは事例集になり、読み手は「今の状況はこの事例と違う」と判断して適用を見送る。逆に美徳の標語まで抽象化したメモリは、何を取り違えると何が壊れるのかを説明していないため、適用先を判断できない。機能する抽象度はその中間、すなわち失敗の型を説明する水準にある。

How to apply を内省で書くと実行されない。「〜と感じたら」「〜したくなったら」「〜で迷ったら」は、その感情や意図の発生を自分で検知できる前提に立っているが、検知自体が起きない。書いた側は対策したつもりになり、同じ失敗が繰り返される。

内省を発火条件にした行は、書き手には「判断の余地を残した親切な但し書き」に見える。この見え方があるため、観測できる事象で書く規則を知っていても、まとめの最後や前提の締めに再び現れる。

索引に載っていないメモリは読み込まれない。ルールが存在するのに機能しない状態は、ルールが無い状態より悪い。書いた本人が対策済みと認識するためである。

**How to apply:**

| 発火する事象 | 実行する操作 |
|---|---|
| 1 つのタスクについて受けた個別の指示（そのタスクの成果物に何を書く・書かないか）を、メモリとして**書いた** | そのメモリを書かない（書いたなら削除する）。個別の指示はそのタスクの中で守る。タスクを越えて当てはまる失敗の型があるときだけ、その型を書く |
| body に日付・チケット番号・ファイル名・やり取りの引用・計測値を**書いた** | 削除する。その事例が属する失敗の型を 1 文で書き直す |
| ルール本文に、何が壊れるかを書かずに望ましい態度だけを**書いた** | 何を取り違えると何が壊れるのかを構造として書き足す |
| 行に「感じたら」「したくなったら」「迷ったら」「気づいたら」「必要なら」「自問する」「先に読む」と**書いた** | その行を削除する。同じ内容を観測できる事象で書けるなら、発火条件を成果物・実行結果・ファイルの状態へ置き換え、動詞を完了形にする。置き換えられないなら書かない |
| How to apply の操作を「検討する」「確認する」で**止めた** | 検討の結果どう分岐するかまで書く。次に打つ手が一意に決まる状態にする |
| 新しいメモリのファイルを**作成した** | 該当索引を読む。同じ Why を扱うメモリがあれば、新しいファイルを削除して既存メモリへ追記する。表層的な HOW を書いたメモリがあれば、そちらを上書きして型に置き換える |
| メモリを新規作成した / `name` を変えた / 本質を書き換えた | 該当索引を同じ操作で更新する。`name` を変えた場合は他メモリからの `[[name]]` 参照もすべて直す |

配置先と索引は、そのルールが破られたときに損なわれるものが何かで決める。

- 相手への伝達が損なわれる → `~/.claude/memory/`。索引は同ディレクトリの `communication-index.md` の「型 → メモリ」表
- 成果物の正しさが損なわれ、内容がプロジェクト横断 → `~/.claude/memory/`。索引は `~/.claude/MEMORY.md`
- 成果物の正しさが損なわれ、内容がそのプロジェクト固有 → `~/.claude/projects/<プロジェクト>/memory/`。索引は同ディレクトリの `MEMORY.md`

frontmatter は次の形にする。`description` は索引での選定に使われるので、適用される状況が判別できる粒度で書く。

```yaml
---
name: <kebab-case-slug>
description: <一行要約>
metadata:
  node_type: memory
  type: feedback   # または user / project / reference
---
```

関連メモリは `[[name]]` で参照し、既存の原則体系の運用例として位置付ける。孤立した個別ルールとして置かない。
