## 1. 依頼の起点

2026-11-06、オーナーは論文 [Do Coding Agents Follow AGENTS.md? The Effect of Policy Wording on Instruction Compliance (arXiv:2611.04367)](https://arxiv.org/abs/2611.04367) を示し、Claude Code が従うメモリ・skill の書き方をこの結果に合わせて直すよう求めた。最初に「プロンプトの書き方のメモリ」(`~/.claude/memory/feedback_memory_writing_rules.md`) を直し、以後の書き換えをそれに従わせる順序だった。

論文の要点 (一次資料で確認したもの)。

- 著者: 土田陸斗・Youmei Fan・松本健一 (奈良先端科学技術大学院大学)、嶋利一真 (和歌山大学)、Raula Gaikovina Kula (大阪大学)。
- 方法: 1 つの方針 (「追加・変更したすべての Python 関数の def 行の直下に `# @tracked` を書く」) を 4 つの書き方で設定ファイルに入れ、CTXbench の 86 タスク (10 リポジトリ) で遵守率を測った。
- Claude Code での遵守率 (%):

| モデル | 言い切り | 理由付き | 条件付き | 禁止 |
|---|---|---|---|---|
| claude-sonnet-5 | 71.6 | 49.4 | 35.6 | 17.3 |
| claude-opus-5 | 78.0 | 77.2 | 64.2 | 70.7 |

- opus-5 では言い切りと理由付きに差が無く、条件付きだけが有意に低い。sonnet-5 では言い切りが他のすべてより高い。qwen-code と gpt-oss-120b の組み合わせでは理由付きが最も高い。
- 著者が挙げた限界: 書き方ごとに 1 文、方針は 1 種類、関数の変更が無いセッションを除外、10 リポジトリのみ。

## 3. 発言から読める意向

2 節の発言を項目に分けたもの。かっこ内は根拠の発言の日時。

1. 求めているのは規則の一覧ではなく、「どのようにメモリを書くかという方法論」「その水準の評価基準」「それに伴う規則」を持つ、メモリを書く上での基準を定めるための方針である (11-06 20:12)。
2. メモリには、エージェントがどうするかという方針、抽象度のある指示を書く。字面で機械的に検査できる項目は、メモリではなくリンターで検査する (11-06 19:56)。
3. 方針のメモリは、方針自身の決まりを満たす。自分で観測して内省する判断を基準にした文を置かない (11-06 19:23)。
4. 方針は、失敗への反省から書くメモリだけでなく、方法を具体的に指示されて書くメモリの型も扱う (11-06 20:28)。
5. 評価基準に「何を取り違えると何が壊れるかを書いたか」を置かない。理由を書かない論文の方向と矛盾し、それ自体に意味が無く、反省以外のメモリに合わない (11-06 20:28)。
6. 評価基準は、言い回しを変えて方法論を言い直すだけのものでは足りない。抽象を具体の文に落とす「方法論にするための方法論」を具体化し、落とすときにニュアンスが漏れることと、要らないルールが混ざることを防ぐ (11-06 22:43)。
7. 文の書き方は、提示した論文と指示に従う。主要な skill やプロンプトの書き方の事例が論文と逆の方向を勧めていても、それを根拠にしない (11-07 14:10)。
8. 書いた文の効果は試験で確かめる。Opus では差が出にくい見込みなので Sonnet で試す (11-07 14:28)。
9. メモリの書き換えに伴って、メモリを操作したときに発火する hook で書き方を検査する。軽量な判定は Jev、論理的整合性は `claude -p` で読ませる案を示し、手法の選択は任せる (11-06 09:37)。
10. この方針の作成と最適化は、PDA の Agent 環境の成果物の中で行い、そこから各環境へ展開する (11-08 07:53)。

### 4.4 段階 4: 方法論の事例の調査 (11-06 夜)

- deep-research で、GitHub 全域とそこから参照される文書・論文から、エージェント向けのメモリ・指示文・プロンプトの書き方を方法論として文書化した事例を集めた。報告書と調査メモは [materials/survey/](materials/survey/)。
- 報告書の要点。
  - 候補はおよそ 45 件、深掘り 8 件。方法論・評価基準・抽象から文を導く手順の 3 つを 1 つの出典で持つ事例は見つからなかった。方針を文に分解したうえで各文がニュアンスを保つかを照合する工程は、どの出典にも無かった。
  - 最も近い事例は [obra/superpowers の writing-skills](https://github.com/obra/superpowers/tree/main/skills/writing-skills)。指示なしで動かして失敗を観察し、その失敗を塞ぐ最小の文を書き、指示の有り無しで比べる。「Match the Form to the Failure」の節で、失敗の種類ごとに文の形 (禁止と言い訳の表・肯定の型・必須欄・観察できる条件を持つ条件付きの規則) を選ばせる。例外は但し書きにせず別の規則として切り出す。比較の数値は公開されていない。
  - [Anthropic の skill-creator](https://github.com/anthropics/skills/tree/main/skills/skill-creator) と [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) も有り無しを比べるが、規則に理由を添えることを勧める。
  - 要らない規則を削る手順: [vltansky/agents-md-evals](https://github.com/vltansky/agents-md-evals) (有り無しの A/B で差が無く、残す理由の 6 つの問いを満たさない規則を削る)、[arXiv:2604.11088](https://arxiv.org/abs/2604.11088) (規則を 1 本ずつ除いて測り、18 本のうち効いたのは 3 本)。
  - ニュアンスの欠落を防ぐ仕組みは 3 系統 (理由を添える・適合例と違反例を対で示す・観察した事例で規則を残すか決める) に分かれ、効果を第三者が測った研究は無い。
  - メモリの 3 種類 (反省・指示された方法・事実) を区別する出典は無かった。
  - 公式文書の多くと論文の数値は要約を挟んで取得しており、原文で確かめたのは writing-skills の本文だけ。
- オーナーの判定: 主要な skill やライティング系のプロンプトが論文と指示に逆行していると分かっただけで、参考にならないのではないか。

### 4.5 段階 5: 挙動を比べて文を決める方針と試験 (11-07)

- 段階 3 のセッションの説明: 調査から採るのは文の書き方ではなく、抽象から具体への橋渡しを文面ではなく挙動で確かめる手順。文の書き方は論文の結果 (言い切り) を既定にする。
  - 方法論: 書く前に、メモリが働く場面と、メモリが無いときの挙動 (反省なら観察した失敗、指示なら指示と食い違う既定の挙動、事実なら事実を知らないときの誤った前提) を書き出し、差を埋める最小の文を書く。
  - 評価基準: 働く場面で意図した挙動になる、働くべきでない隣の場面で挙動が変わらない、各文を外すと働く場面の挙動が変わる (変わらない文は削る)。
- オーナーが「やってみよう」と承認し、試験は Sonnet で行うよう指示した。
- 試験 ([materials/behavior-eval/](materials/behavior-eval/)): 反省・指示・事実の 3 種類の依頼を、方針の有り無しで 5 回ずつ Sonnet (`claude -p`) に送り、4 回改訂した。最終版は [a2319f3](https://github.com/myurait/docs/commit/a2319f3) と [51cb2db](https://github.com/myurait/docs/commit/51cb2db)。
  - 方針なしでは、どの依頼でも Why と How to apply の節・条件付きの文・禁止の文を書いた。Claude Code の既定のメモリの説明がこの形を指示しているため。
  - 「frontmatter と言い切りの文の箇条書きだけで組む」という出力の形の文を足すと、Why の節は 5 回中 0〜1 回に減った。
  - 例外を目的語の名詞句に入れて書く例を足すと、条件付きの文は 5 回中 0 回になった。
  - 文を 1 つずつ外すと効果が崩れた文は 5 つ (出力の形・例外・言い切り・場面を本文の外に残す・索引の行に description と同じ文字列を書く)。
  - コミットメッセージや README を頼む依頼 (働くべきでない場面) では、方針の有り無しで出力が変わらなかった。
  - 確かめていない点: 方針のうち「試験する」の節の 9 文、事実のメモリの文の外す試験。試験では本文全体を system prompt に入れたが、実際に毎回読まれるのは索引の行だけ。
  - 「時点は原因ではない」のメモリで試すと、メモリなしの Sonnet でも 5 回とも「相関にすぎず原因は特定できない」と答え、元の失敗 (Opus の長いセッション) を再現できなかった。
- 試験の場面と入力の置き場 (skill にするか、`memory/evals/` に置くか) を問うたところで、検討は止まっている。
