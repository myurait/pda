## 1. 結論

どの実装にも抽象が無い部分は **event stream の形式**である。Temporal の 72 種、Restate の 20 種、A2A の 2 種という閉じたイベント語彙はコードに存在するが、それが何を保証するか（どの出来事が必ず記録されるか、記録の欠落が何を意味するか）を述べた形式的定義は未発見。要件 A5・A8 が乗る不変量は、どの一次資料にも定義されていない。

どの抽象にも実装が無い部分は **異種の実行主体をまたぐプロトコル準拠の強制**である。型で準拠を強制する実装（Scribble、session_types、rumpsteak）はすべて単一言語のコンパイラ内に閉じ、複数ベンダーのランタイムが混在する場での強制は未発見。FIPA の閉じた発話種別も、JADE では字句解析器 1 か所でのみ強制され、オブジェクト API では素通りする。

両方が欠けているのは**能力の宣言に費用・到達資源・中断後に取れる state を含めた形式化**である。

採用できる対は 11 件。要件に最も近い対は **state machine replication ↔ Temporal**。ただし契約 4 項目を最も広く覆うのは A2A であり、A2A は形式的な抽象と不変量の言明を持たないため対ではない。

## 2. 対

「1 対 = 抽象・不変量・実装（強制箇所）の 3 つが揃ったもの」。以下、1 ブロック 1 対。

### 対1: tuple space（Linda） ↔ JavaSpaces / Apache River Outrigger

- **抽象**: Gelernter, "Generative Communication in Linda", ACM TOPLAS 7(1), 1985, §2.1.2。タプル空間 TS と `out` / `in` / `read` の 3 プリミティブ（1985 年原論文に `eval` は無く、第 3 プリミティブの名称は `rd` ではなく `read`）。タプルは名前と型が一致するテンプレートで取り出される。
- **不変量**: 挿入と取り出しの原子性。「The definitions require that tuples be inserted into and withdrawn from TS atomically.」(p.83–84)、競合時は「one gets it and the other does not; they cannot split it」(p.84)。生成的通信により、A が置いたタプルは「the tuple generated by A has an independent existence in TS」(p.82)。
- **実装（強制箇所）**: JavaSpaces 仕様が「Two take operations will never return copies of the same entry」(JS.2.5) を明記し、Outrigger が `_src/apache-river-3.0.0/src/org/apache/river/outrigger/EntryHolder.java:422-427` の `synchronized (handle)` ブロック内の `if (handle.removed() || handle.isProvisionallyRemoved()) return false; handle.provisionallyRemove();` で強制する。空間に置ける値の制約も規約ではなくコードで検査され、`EntryRep.java:596-599` が `if (field.getType().isPrimitive()) throw ... "primitive field, ... not allowed in an Entry"`、`EntryRep.java:345-348` が public でないクラスを拒否する。
- **契約 4 項目**: 能力の宣言=無関係。仕事の受け取り=満たす（同じ空間から `in` で取る）。成果の返却=満たす（同じ空間へ `out`、仕事と成果が同一形式）。event stream=満たさない（`notify` は登録済みテンプレートへの一致通知であり、実行中の出来事の順序付き記録ではない）。
- **A1/A2/A5/A12**: A1=満たす（取り手が誰でも渡し方が変わらない）。A2=一部（プロセスの追加は空間側の変更を要しないが、Entry は Java クラスであり別言語の実行器は追加できない。`JavaSpace.java` の各メソッドが `Entry` 型を要求する）。A5=満たさない。A12=一部（分類はテンプレート一致で決定論的、注入は同一オブジェクトのため変換不要。ただし種別の集合は Entry サブクラス全体に開いている）。
- **足りないもの**: 実行中の出来事の記録が一切無い。言語非依存の表現が無い。能力の宣言と割り振りの概念が無い。

### 対2: multiparty session types ↔ Scribble（scribble-java）

- **抽象**: Honda, Yoshida, Carbone, "Multiparty Asynchronous Session Types", POPL 2008, pp.273–284。global type、local type、射影（Definition 4.1, p.278）、coherence（Definition 4.2, p.278）。
- **不変量**: 「communication safety, progress and session fidelity are established for general n-party asynchronous interactions」(Abstract, p.273)。射影は側条件が成り立たないとき未定義（「When a side condition does not hold the map is undefined.」p.278）。
- **実装（強制箇所）**: `_src/scribble-java-master/scribble-core/src/main/java/org/scribble/core/visit/global/RoleEnablingChecker.java:51` が `throw new ScribException("Subject not enabled: " + n.subj);`、`ExtChoiceConsistencyChecker.java:70-74` が分岐ごとに有効化元が異なる場合に例外を投げる。呼び出しは `Core.java:160,174` の `runGlobalSyntaxWfPasses()` 内で、射影計算より前に走る。生成される endpoint API は状態ごとに許された操作だけを公開し、終了状態のソケットは `EndSockGen.java:43-47` で `protected void addMethods() { }` とメソッドを一切生成しない（以後の呼び出しは javac がコンパイルエラーにする）。
- **契約 4 項目**: 能力の宣言=無関係。仕事の受け取り=一部（型はメッセージの形と順序を決めるが、コンテキストの絞り込みの概念は無い）。成果の返却=満たす（ラベルと引数型が状態ごとに閉じている）。event stream=無関係。
- **A1/A2/A5/A12**: A1=満たす（同じ役割を演じる相手なら渡し方は同じ）。A2=**満たさない**（参加者を 1 つ足すと global type が変わり、全役割の射影と生成 API が変わる）。A5=無関係。A12=一部（分類は型で決定論的だが、ストアが無く成果を置く場所が存在しない）。
- **足りないもの**: 永続ストアを持たない（セッション終了後に残る構造が無い）。保証は全参加者が型検査またはモニタ下にある場合に限られ、チュートリアルも「if the endpoint program for every role is correct」という条件節でしか安全性を述べていない。

### 対3: binary session types の双対性 ↔ Rust `session_types` crate

- **抽象**: Honda, Vasconcelos, Kubo, "Language Primitives and Type Discipline for Structured Communication-Based Programming", ESOP 1998, Definition 5.1。「The co-type of a given type denotes the complementary behaviour of the original type.」
- **不変量**: 両立可能性。「Compatibility means each common channel k is associated with complementary behaviours」（Definition 5.2）。
- **実装（強制箇所）**: `_src/session-types-master/src/lib.rs:135-137` の `pub trait HasDual { type Dual; }` と `:143-149` の `Send<A,P>` ⇔ `Recv<A,P::Dual>` の相互定義。`lib.rs:209-218` の `send` は `Chan<E, Send<A,P>>` にしか実装されず、`:221-230` の `recv` は `Chan<E, Recv<A,P>>` にしか実装されない。コンパイル時強制であることは `tests/compile-fail/send-on-recv.rs:13-14` の `c.send(42).close(); //~ ERROR` が示す。
- **契約 4 項目**: 仕事の受け取り・成果の返却=一部（2 者間に限る）。能力の宣言・event stream=無関係。
- **A1/A2/A5/A12**: A1=満たす。A2=一部（2 者契約なので相手を差し替えても型は変わらないが、同一プロセス内スレッド間を前提にしている）。A5=無関係。A12=一部。
- **足りないもの**: ストア無し、プロセス境界を越えない、言語非依存性が無い。

### 対4: Kahn process network ↔ Ptolemy II PN ディレクタ

- **抽象**: Kahn, "The Semantics of a Simple Language for Parallel Programming", IFIP 1974。チャネルの履歴を c.p.o. の元とし、ノードを履歴から履歴への連続写像として解釈する。
- **不変量**: 実行順序に依存しない決定性。前提は制約 (iii) であり、著者自身が「cannot be waiting on data coming from one or another of its input lines」と言い換えている。読み出しは待つ（「The process stays blocked on a wait until something is being sent」）。チャネルの観測列が「it is called the history of the line」と定義される。
- **実装（強制箇所）**: `_src/PNQueueReceiver.java:151` の `public Token get()` が、データが無いとき `:185-193` で `_readPending = Thread.currentThread(); _director.threadBlocked(...); _director.wait();` とブロックする。複数チャネルのうち到着した方を選ぶ API を持たないことが制約 (iii) を保つ。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=一部。event stream=一部（history は順序付き列だが、実行器の外へ出す機構は `PNDirector.java:600` のリスナー登録に留まる）。能力の宣言=無関係。
- **A1/A2/A5/A12**: A1=満たす。A2=一部（グラフの変更を伴う）。A5=一部。A12=一部（チャネルごとに型は決まるが、メッセージ種別を有限タグに分類する仕組みは無い）。
- **足りないもの**: 決定性を得る代償として「どちらが先に返ってきたかで分岐する」ことを禁じる。割り振り（3.2-1）は本質的にこの分岐を必要とするため、この不変量はそのままでは採れない。

### 対5: actor モデルの隔離 ↔ Pony コンパイラ（および Erlang/OTP のコピー送信）

- **抽象**: Hewitt, Bishop, Steiger, IJCAI 1973。すべてを actor とし、相互作用をメッセージ送信のみに限る。Agha, MIT AI Lab TR, 1985 が郵便システムによる緩衝を定める。
- **不変量**: 状態を共有しないこと。「Sending a message to an actor is entirely free of side effects」(p.240)。配送は保証されるが順序は非決定。「Communications are buffered by the mail system and are eventually delivered.」(Agha, Abstract)。出来事は半順序であり、「we do not require that two arbitrary events be related by →」(Hewitt, p.240) と全順序を明示的に要求しない。
- **実装（強制箇所）**: Pony は `_src/ponyc-bare.git` の `src/libponyc/pass/flatten.c:333` で `"this parameter must be sendable (iso, val or tag)"` を出してコンパイルを止め、判定は `src/libponyc/type/cap.c:1265` の `cap_sendable` が `iso`/`val`/`tag` のみ true を返すことで行う。Erlang は `_src/erl_message.c:791-798` で送信のたびに term を `copy_shared_perform` / `copy_struct_litopt` でコピーする。Akka は `ActorRef.scala:25,32` の `trait ActorRef[-T]` と `def tell(msg: T)` でメッセージ型のみ強制し、可変状態の共有禁止はコンパイラが強制しない（規約止まり）。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=一部。event stream=一部（Akka の `EventStream.scala:24` は実在するが JVM 内に閉じる）。能力の宣言=無関係。
- **A1/A2/A5/A12**: A1=満たす。A2=一部（同一言語内では満たす。言語をまたぐと満たさない）。A5=満たさない（抽象自体が全順序を否定する）。A12=一部（Pony では behavior の集合が有限種別に対応するが、言語内に限る）。
- **足りないもの**: ストアが無い。全順序の出所が無い。要件 A5 が求める「同じ形式の event stream」は、実行器側から自然には出てこない。

### 対6: 発話種別の閉包と interaction protocol（KQML / FIPA-ACL / contract net） ↔ JADE

- **抽象**: KQML 仕様（DARPA Knowledge Sharing Initiative, 1993）の performative と BNF、FIPA ACL Message Structure (SC00061G) と Communicative Act Library (SC00037J)、Smith, "The Contract Net Protocol", IEEE Trans. Computers C-29(12), 1980。
- **不変量**: 「the only parameter that is mandatory in all ACL messages is the performative」(SC00061G §2) が「メッセージは必ず何らかの種別を持つ」に対応する。act の意味は規範的で、「The definition of a communicative act belonging to the CAL is normative.」(SC00037J §2.1)。ただし集合自体は閉じていない。KQML は「Definitions of new performatives should follow the style of the definitions in this section.」と拡張手続きを明記し、FIPA も命名審査を伴う登録簿として運用される。能力の宣言は contract net の 2 つ組で表される。「The eligibility specification is a list of criteria that a node must meet」(p.1105) と、入札側が自分の持ち物を列挙する Node Abstraction（Fig.2, p.1105）。
- **実装（強制箇所）**: `_src/jade-mirror/src/jade/lang/acl/ACLParser.jj:321-341` の字句状態が performative 名を 22 個のリテラルに固定し、未知の名前は `MESSAGETYPE` トークンとして成立しない。一方 `ACLMessage.java:460-462` の `public void setPerformative(int perf) { performative = perf; }` は検証を行わず、範囲外の値が素通りする（Javadoc の「silently initializes the message to not-understood」という記述は実装と一致しない）。プロトコルの状態遷移は `ContractNetInitiator.java:209-211` の `registerTransition(CHECK_IN_SEQ, HANDLE_PROPOSE, ACLMessage.PROPOSE);` のように、受信 performative を遷移条件にした FSM としてコードで強制される。能力の宣言は `ServiceDescription.java:33` の `implements Concept` で型付きスロットを持つが、能力の実体は `properties` の自由な key-value 列である。
- **契約 4 項目**: 能力の宣言=一部（DF に機械可読で登録・検索できるが、費用も再開可能性も語彙に無い）。仕事の受け取り=満たす。成果の返却=一部（種別は閉じるが `:content` の中身は別の content language に委ねられる）。event stream=未検証（`jade.domain.introspection` は存在を確認したのみ）。
- **A1/A2/A5/A12**: A1=満たす。A2=**満たす**（DF への動的登録で実行器を足せ、performative と protocol は不変。古典の中で A2 に最も強い）。A5=未検証。A12=一部（封筒の種別は決定論的に分類できるが、中身は分類されない）。
- **足りないもの**: 仕事と成果を置く永続ストアが無い（DF は能力の登録簿、`DataStore` はプロトコル 1 回分の一時領域）。

### 対7: state machine replication ↔ Temporal（replay 非決定性の検出）

- **抽象**: Schneider, "Implementing Fault-Tolerant Services Using the State Machine Approach: A Tutorial", ACM Computing Surveys 22(4), 1990。
- **不変量**: 「Outputs of a state machine are completely determined by the sequence of requests it processes」(p.301)。複製側は Agreement と Order、すなわち「processes the requests it receives in the same relative order」(p.303)。成立の前提は決定性・同一初期状態・同一順序の 3 つであり、論文は "Provided" 節としてこれを明示する。
- **実装（強制箇所）**: Temporal は前提の側を実行時に検査する。`_src/sdk-go/internal/internal_task_handlers.go:1581-1632` の `matchReplayWithHistory` が、リプレイで生成された command 列と保存済み history を先頭から突き合わせ、`:1616-1624` で `"[TMPRL1100] nondeterministic workflow: ..."` を返す。`internal_command_state_machine.go:1069-1076` は該当 command が無い場合に panic する。検出後の既定動作は `worker.go:542,548` の `BlockWorkflow`（失敗させず実行を止めてリトライへ回す）。静的検査は `contrib/tools/workflowcheck/` のリンターのみで、ビルド経路には組み込まれていない。
- **契約 4 項目**: 能力の宣言=満たさない。仕事の受け取り=満たす（task queue から取る）。成果の返却=満たす。event stream=**満たす**。`_src/api/temporal/api/history/v1/message.proto:1156-1160` の `HistoryEvent` が `event_id`（"Monotonically increasing event number, starts at 1."）と `event_type` を持ち、`enums/v1/event_type.proto` の `EventType` は 72 値の閉じた enum。未知種別の扱いも規定され、「If an SDK encounters an event type which it does not understand」(message.proto:1168-1170) はエラーにしなければならない。
- **A1/A2/A5/A12**: A1=満たす。A2=**満たす**（別言語のワーカーが同じ task queue を購読でき、protobuf 定義を共有する）。A5=**満たす**。A12=一部。イベント種別は閉じているが、activity の入出力は `_src/api/temporal/api/common/v1/message.proto:32-34` の `Payload { map<string,bytes> metadata = 1; bytes data = 2; }` であり、同 `:30-31` が「Serialization of the data may be user-defined.」と述べるとおり中身は分類されない。
- **足りないもの**: 能力の宣言が無い。決定性の要求が、非決定なモデルを直接ワークフロー本体に置くことを禁じる。

### 対8: journal されたステップ結果 ↔ DBOS

- **抽象**: 対7 と同系（順序付き記録に対する再実行）。公式ドキュメントが保証を言明する。
- **不変量**: 「Steps are tried at least once but are never re-executed after they complete.」（docs.dbos.dev, workflow-tutorial）。トランザクションに限り exactly-once。
- **実装（強制箇所）**: `_src/dbos-transact-py/dbos/_core.py:2297-2309` の `check_existing_result` が記録済みなら `func()` を呼ばずに保存済み出力を返す。記録先は `dbos/_schemas/system_database.py:100-118` の `operation_outputs` テーブルで、`PrimaryKeyConstraint("workflow_uuid", "function_id")` が 1 ステップ 1 行を DB 制約として強制する。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=満たす（ストアに型付きで残る）。event stream=一部。能力の宣言=満たさない。
- **A1/A2/A5/A12**: A1=一部。A2=一部。A5=一部。A12=一部。
- **足りないもの**: 保証は at-least-once であり、`_core.py` の実行（2278 行付近）と記録（2294 行付近）の間でプロセスが落ちれば外部副作用は二重に起こりうる。この限界を明言する公式文は未発見。

### 対9: journal 不一致の検出 ↔ Restate

- **抽象**: 対7・対8 と同系。
- **不変量**: ジャーナルの再生が前回と一致すること。不一致は `_src/restate/crates/types/src/errors.rs:104` の `JOURNAL_MISMATCH 570 "Journal mismatch"` として型付けされ、`crates/invoker-impl/src/error.rs:385-397` が「Detected journal mismatch. Either some code within the handler is non-deterministic」と表示する。
- **実装（強制箇所）**: 突き合わせ本体は共有コア `restatedev/sdk-shared-core`（`bcdf52777955b36bed611483abd227db03b9a09c`）の `src/vm/transitions/journal.rs:978-992` にある `check_entry_header_match` で、`if !actual.header_eq(expected, ignore_payload_equality) { return Err(CommandMismatchError::new(...)) }` が再生時の項目と記録済み項目を比較する。エラーコードへの対応は `src/vm/errors.rs:422` の `impl_error_code!(CommandTypeMismatchError, JOURNAL_MISMATCH);` と `:71` の `JOURNAL_MISMATCH: InvocationErrorCode = InvocationErrorCode(570)`。検出後の動作は `src/lib.rs:289` の `JournalMismatchRetryBehavior` を `src/vm/transitions/mod.rs:72-78` が `Pause` / `Fail` / 通常リトライへ振り分ける（SDK 側の既定は retry。`restatedev/sdk-typescript` の `packages/libs/restate-sdk/src/types/rpc.ts:626-628`）。サーバ側の扱いは `_src/restate/crates/invoker-impl/src/error.rs:282-291`。ジャーナル項目は `crates/types/src/journal_v2/command.rs:50-71` の 20 variant の `Command` enum として閉じ、ワイヤは `service-protocol/dev/restate/service/protocol.proto` で言語非依存。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=一部。event stream=一部。能力の宣言=満たさない。
- **A1/A2/A5/A12**: A2=一部、A5=一部、A12=一部。
- **足りないもの**: 比較は項目のヘッダに対して行われ、`ignore_payload_equality` によりペイロードの一致を外せる。すなわち「同じ命令を同じ順で出したか」は守るが、命令の中身まで同一であることは常に検査されるわけではない。

### 対10: workflow net の構造条件 ↔ YAWL（ロード時検証）

- **抽象**: van der Aalst, "Workflow Verification: Finding Control-Flow Errors Using Petri-Net-Based Techniques"。WF-net は「A WF-net has one input place ( i ) and one output place ( o )」(p.8)、soundness は完了可能性・適切な完了・「there are no dead transitions (tasks) in the initial state i」(p.9) の 3 条件。
- **不変量**: 上記 soundness。ただし実装が強制するのは構造条件のみ。
- **実装（強制箇所）**: `_src/yawl/src/org/yawlfoundation/yawl/elements/YNet.java:205-206` の `verifyDirectedPath(handler)` が全要素が i から o への経路上にあるかを検証し、`engine/YEngine.java:555-558` が `specification.verify(verificationHandler)` の結果にエラーがあれば `loadSpecification` を呼ばない（`ignoreErrors=true` で迂回可能）。生存性に基づく soundness（Definition 12）を計算するコードはコア engine に無い。実行時には `elements/e2wfoj/E2WFOJNet.java` の reset net 計算で OR-join の発火可能性を都度判定する。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=一部。event stream=無関係。能力の宣言=無関係。
- **A1/A2/A5/A12**: A1=無関係。A2=**満たさない**（実行器を足すにはネットを書き換える）。A5=無関係。A12=無関係。
- **足りないもの**: メッシュ状に変化するワークフロー（3.2-4）と、事前に固定されたネットの検証は両立しない。

### 対11: 順序付きログ ↔ Apache Kafka（パーティション内全順序）

- **抽象**: Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System", CACM 21(7), 1978 の全順序構成と、Schneider の Order 条件。
- **不変量**: パーティション内の全順序。Lamport は同時に「It is only the partial ordering which is uniquely determined」(p.561) と、全順序が一意でないことを明記する。
- **実装（強制箇所）**: `_src/kafka-src/storage/src/main/java/org/apache/kafka/storage/internals/log/UnifiedLog.java:123` の `private final Object lock` と `:1150` の `synchronized (lock)` がオフセット採番から追記までを直列化し、`:1158` が `logEndOffset()` を起点にオフセットを払い出す。`LocalLog.java:529-532` が単一のアクティブセグメントへ追記し logEndOffset を単調更新する。
- **契約 4 項目**: 仕事の受け取り=一部。成果の返却=一部。event stream=一部（順序は満たすが形式は強制しない）。能力の宣言=満たさない。
- **A1/A2/A5/A12**: A1=一部。A2=満たす。A5=一部（同一形式を強制する仕組みが本体に無い）。A12=**満たさない**。`ProducerRecord<K,V>` の値は `Serializer<T>.serialize()` で `byte[]` に消去され、ブローカは `Record.value()` の `ByteBuffer` しか扱わない。
- **足りないもの**: 「1 パーティションを 1 コンシューマだけが読む」は公式ドキュメントの記述（「each of which is consumed by exactly one consumer within each subscribing consumer group」）であって Fetch API の強制ではない。ブローカ側の強制はオフセットコミットの世代フェンシング（`OffsetMetadataManager.java:476` の `ILLEGAL_GENERATION`）のみ。Linda の take 原子性に当たるものが無い。

- **blackboard / Hearsay-II**（抽象のみ、不変量の言明も否定されている）: 「KSs communicate through a global database called the blackboard.」(p.218) と共有ストアの構図を定義し、「one KS can use data created by a previous KS execution」(p.235–236) と注入可能性に当たる性質も述べる。しかし論文自身が「there is no guarantee at any point that a better interpretation cannot be found」(p.236) と形式的保証を否定する。並行書き込みの排他は保証ではなく、単一スケジューラの逐次実行で回避している。実装コードは原論文に無い。

- **A2A**（実装のみ、形式的抽象と不変量の言明が無い）: 後述 4 節。スキーマの型付けは強制されるが、状態遷移の合法性を述べた形式的定義が無い。
- **GigaSpaces XAP / TSpaces / LIME**（未発見）: コアエンジンの公開ソースを確認できず、強制箇所を示せない。

## 6. 他の要素への含意

### ランタイムのラッパー

どの実行器も、要件が求める形の event stream を自分からは出さない。actor の意味論は全順序を明示的に否定し（「we do not require that two arbitrary events be related by →」）、Kahn の history はチャネルごとの列であって系全体の列ではない。A5 が求める単一形式の順序付き記録は、実行器から集めるのではなく**ログストア側が順序を与える**ものとして設計するほかない。Temporal は閉じた 72 種の enum と「未知の種別に出会った SDK はエラーにしなければならない」という規則をセットで持つ。ラッパーを作るなら、イベント語彙を閉じることと、未知種別に出会ったときの動作を先に決めることが同時に要る。

### MCP 的な自己宣言

能力の宣言を機械可読にする例は 3 つの系統がある。contract net の 2 つ組（必要条件の宣言と、自分の持ち物の列挙）、JADE の DF（型付きスロットだが能力の実体は自由な key-value）、A2A の AgentCard と MCP の `Tool.inputSchema`（必須フィールドとスキーマ型）。いずれも**費用と到達資源と中断後に取れる state を述べる語彙を持たない**。要件 3.1 の能力の宣言はこの 3 つを含むため、既製の語彙をそのまま使えない。加えて MCP の例は、スキーマを要求することと検査することが別の場所に分かれることを示す。検査を実行器側の SDK に委ねると、実行器を足すたびに検査の質が変わり A2 が崩れる。検査はコア側に置く必要がある。

### ログストア

A12 の「決定論的に分類可能」は、封筒の分類か中身の分類かで難易度が桁違いに変わる。調査した実装はすべて封筒だけを閉じている。Temporal はイベント種別を 72 種に閉じるがペイロードは `bytes data` と「Serialization of the data may be user-defined.」（`common/v1/message.proto:30-34`）、A2A は `Part` を 4 種に閉じるが `data` は `google.protobuf.Value`（`a2a.proto:233`）で任意の JSON、Kafka は `Serializer<T>.serialize()` で `byte[]` に消去する。要件が求めているのが「ある実行器の成果を、人が読み替えることなく別の実行器の仕事として注入できる」ことである以上、分類は書き込み時にストアが強制しなければならない（書いた後で監査が分類し直すのでは、実行器ごとの個別処理が発生して A5 が崩れる）。

### 共通の input/output ストア

A2A の `Task` には Linda の take 原子性に当たる操作が無い。複数の実行器が同じ仕事を取り得る構成（割り振りの失敗時の引き継ぎ、同一仕事の複数実行器での並走）を要件が含むなら、`in` の原子性は自前で用意する要素になる。Kafka はパーティション単位の排他をプロトコル規約として持つが、ブローカが強制するのはオフセットコミットの世代整合性だけである。

### 次の調査本で立てるべき問い

1. 書き込み時にスキーマを強制する順序付きログの実装はあるか（Schema Registry、Pulsar のスキーマ、Iceberg など）。強制箇所はどこか。
2. 封筒ではなく**成果の中身**の種別を閉じている実装はあるか。session types の payload 型以外に、言語をまたいでそれを行う例はあるか。
3. 中断と再開の可否（要件の「取れる state」）を機械可読に宣言する語彙は存在するか。durable execution 系はワークフロー側の再開しか扱っておらず、実行器が自分の再開可能性を宣言する形は未確認。
4. 仕事を取り合ったときに 1 つだけが取るという保証を、言語非依存のプロトコルの上で与えている実装はあるか。

### 要件への疑義

- **A2 と n 者プロトコルは両立しない。** 対2 が示すとおり、プロトコルを n 者の全体として定義すると、参加者を 1 つ足すたびに全参加者の射影が変わる。A2（コアと既存実行器を変更せずに実行器を追加できる）を満たすには、契約を厳密に 2 者（コア ↔ 実行器）に限り、実行器同士が直接話す経路を持たせない必要がある。要件 3.1 は「ランタイム間のプロトコル」と書いており、実行器同士のやり取りを含むようにも読める。どちらの意味かで設計が分岐する。
- **A12 の「決定論的に分類可能」の対象が書かれていない。** 封筒（状態・種別）の分類なら既製の実装が多数あるが、中身の分類は調査範囲では強制している実装が存在しない。どちらを指すかを要件側で確定しないと、受け入れ条件として判定できない。
- **決定性を前提にした系譜は、そのままでは使えない。** Schneider の結論（同じ順序で同じ要求を処理すれば同じ出力になる）は決定性を前提条件として明示している。実行器が LLM である以上この前提は成り立たず、順序付きログから得られるのは順序と永続性だけで、再実行しても同じ結論に至るという性質は得られない。Temporal はこの前提の破れを検出して実行を止める設計であり、非決定な推論はワークフロー本体ではなく記録される step の側に置くことが強制される。コアの設計もこの分割を避けられない。
