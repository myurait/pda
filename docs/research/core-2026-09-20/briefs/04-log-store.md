# 第4本: ログストア

- 物差し: `docs/requirements.md`（commit `cdd90e9`）3.1 契約「event stream」、コア 5 要素「ログストア」、受け入れ条件 A5・A6・A8・A9
- 形式: 第 1 本と同じ

## 問い

event stream を書き込み、可視化と監査がそこだけを読む場所について、抽象・不変量・実装の揃った対はどれか。特に次の 3 つ。

1. 書き込み時にスキーマ（イベント種別と中身の形）を強制する順序付きログの実装はあるか。強制箇所はどこか
2. 「どの出来事が必ず記録されるか、記録の欠落が何を意味するか」を形式的に定義した例はあるか（第 1 本の結論: どの実装にも抽象が無い部分）
3. 実行が終わる前から読める（追記中のログを購読できる）ことと、実行器の種類が違っても同じ形式に落ちることを、同時に満たす実装はあるか

## 起点

- event sourcing と「ログを唯一の正本にする」設計（Kleppmann 等）。第 1 本の Kafka（順序は強制するが値は `ByteBuffer` のまま。スキーマ検査は別プロダクトの Schema Registry の中だけ）の続き
- Schema Registry、Apache Pulsar のスキーマ強制、Apache Iceberg のスキーマ進化（書き込み時強制の実装）
- 分散トレーシングのスパンモデル（Dapper、OpenTelemetry）と GenAI 意味規約。異種の実行器を同じ形式に落とす既存語彙
- 監査ログの完全性（tamper-evident log、Certificate Transparency の Merkle 木、Trillian）。「欠落が検出できる」ことを不変量として持つ系譜
- Lamport / vector clock（第 1 本の続き。系全体の順序の出所）
- ワークフロー履歴の形式化（Temporal の HistoryEvent、Restate の journal。第 1 本の続き。Temporal の EventType 61 値はすべてシステムの出来事で、業務上の成果の種別を含まない）
- LLM フレームワークの実行中イベント: OpenAI Agents SDK の `RunItemStreamEvent`（11 値の有限 Literal。ツール呼び出しが独立した種別として実行中に出る）と A2A の `StreamResponse`（4 種の oneof。タスクの状態遷移と成果物の増分だけで、内部の出来事が無い）。event の粒度をどちらに置くかが可視化と監査で見えるものを決める
- 自己改変の記録と取り消し（A9）: version control の抽象（Git の DAG、CRDT の operation log）を割り振り規則やワークフロー定義の履歴に使う例

## 第 1 本から引き継ぐ問い

- 封筒ではなく成果の中身の種別を閉じる話は要件から外れた（A12 は種別の分類に限定）。ログストアが強制するのは event の種別と、種別ごとの中身の形。中身の意味内容の分類は対象外
- A12 の「注入可能」を成り立たせるには、分類は書き込み時にストアが強制する必要がある（書いた後で監査が分類し直すと実行器ごとの個別処理が発生して A5 が崩れる）
- A5 の「実行器の種類に関係なく同じ形式」を、ストアが書き込み時に強制するのか、書き手（ラッパー）が守るのかを分けて評価する。前者は Kafka + Schema Registry の構成に近づき、後者はランタイムのラッパーの責務と合流する
- Linda の著者は、共有ストアに任意の内容を置ける自由と、置かれたものを機械的に型検査できることは両立しないと書いている。ストアが強制するのを event の種別と種別ごとの中身の形に限定し、中身の意味内容は自由のままにすることで、この両立しない 2 つが分離できるかを確かめる

## 出力

要素ごとの表。列は「抽象、不変量、実装（強制箇所）、契約との対応、A5/A6/A8/A9 との対応、足りないもの」。加えて、問い 2（欠落の意味を形式化した例）は見つからなかった場合に検索語と当たった資料を明示する。
