# 第5本: 全体（異種エージェントを交換可能な実行器として扱う系）

- 物差し: `docs/requirements.md`（commit `cdd90e9`）3.1 の実行器・平等・交換可能の定義、3.2 周辺要件 1〜5（割り振り、コンテキストの絞り込み、多層の統合、メッシュ、自己改変）、受け入れ条件 A1〜A4・A9
- 形式: 第 1 本と同じ
- 前提: 第 1〜4 本の結果を入力にする。要素単位で既に評価したものは再評価しない

## 問い

異種のエージェントを交換可能な実行器として扱い、判定器が割り振り、成果を多層に統合し、成果とフィードバックで構成を書き換える系について、抽象・不変量・実装の揃った対はどれか。特に次の 3 つ。

1. 「実行器の交換可能性」を定義として持つ理論はあるか。あるなら、交換しても変わらないと保証している性質は何か
2. 割り振りを LLM ではない判定器が行い、割り振り規則自体が成果で書き換わる構造を持つ実装はあるか。書き換えの記録と取り消し（A9）をどう扱っているか
3. 非決定な実行器（LLM）を含む系で、順序付きログの再実行が保証できるものとできないものを分けて設計した例はあるか（第 1 本の含意: 非決定な推論を記録される step の側に置く分割）
4. 参加者集合が実行時に増える系を形式化した例はあるか。multiparty session types と choreographic programming は参加者集合が静的で、実行時追加の拡張（Gabbrielli ら 2019）も新ロールを受け入れる scope をあらかじめ用意する必要があった。コアと既存実行器を変更せずに実行器を追加できること（A2）を保証する形式体系があるか

## 起点

- Wooldridge, Jennings らの多エージェント系の定式化。agent の交換可能性・役割（role）と agent の分離（Gaia、AUML）
- blackboard 制御（Hearsay-II の scheduler、BB1 の control blackboard）。制御知識自体をブラックボードに置いて書き換える系譜。第 1 本では blackboard は抽象の側にしか無く、提唱者自身が概念であって計算仕様ではないと書いていると判定した。その続き
- 階層的タスクネットワーク（HTN）と task allocation の理論（contract net の続き、market-based allocation）
- メタ推論と anytime algorithm（どの推論器にどれだけ計算を割り振るかを判定する系譜）
- 自己適応システム（MAPE-K ループ、models@run.time）。実行時に自分の構成を書き換える系の形式化と、書き換えの安全性
- LLM 時代: AIOS（エージェントを OS のプロセスとして扱う）、routing/cascade の研究（FrugalGPT、RouteLLM。判定器がモデルを選ぶ構造）、mixture-of-agents、LLM エージェント間プロトコルのサーベイ（第 1 本で見たプロトコル比較サーベイは古典の形式的抽象との対応を論じていないと判定済み。不変量の軸を持つ別のサーベイがあるか）
- ワークフローの動的変更（adaptive workflow、YAWL の worklet。第 1 本の workflow net soundness の続き。改変後のワークフローが soundness を保つかを機械検査できる形にするなら、free-choice など多項式時間で検査できる部分クラスに制限する判断が要る）
