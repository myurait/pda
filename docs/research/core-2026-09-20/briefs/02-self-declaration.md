# 第2本: MCP 的な自己宣言

- 物差し: `docs/requirements.md`（commit `cdd90e9`）3.1 契約「能力の宣言」、コア 5 要素「MCP 的な自己宣言」、受け入れ条件 A2・A4・A11
- 形式: 第 1 本 `../01-store-and-protocol.v2.md` と同じ。1 対 = 抽象・不変量・実装（強制箇所の file:line）。片側だけ・未発見は別節。一次資料は日付とコミットで固定

## 問い

実行器が自分の能力を機械可読に公開し、コアがそれを根拠に割り振れる仕組みについて、抽象・不変量・実装の揃った対はどれか。特に次の 3 つを宣言できる語彙と、宣言と実態の食い違いを検出する構造があるか。

1. 費用（1 回の実行にかかる金額・時間・レート上限）
2. 到達できる資源（コネクタ権限、ファイルシステム、ネットワーク。A11 が要る）
3. 取れる state（中断されたとき再開できるのか再投入になるのか）

## 起点

- FIPA の directory facilitator と service description（第 1 本の続き。登録パラメータがすべて Optional で、仕様自身が登録内容の正しさを保証しないと書いている点を出発点にする）
- contract net の eligibility specification と node abstraction（必要条件の宣言と持ち物の列挙の 2 つ組）
- WSDL / OpenAPI / AsyncAPI（宣言と実行の分離で何を保証し何を保証しなかったか。宣言と実装の食い違いを検出する仕組みの有無）
- A2A AgentCard、MCP `Tool.inputSchema`（第 1 本の続き。A2A の proto 全文に費用・レート上限を表す語が 1 つも無いこと、スキーマを要求する場所と検査する場所が分かれる問題）
- Kubernetes の resource requests/limits と Pod の capability 宣言、Nix の derivation（能力ではなく資源を機械可読に宣言し、スケジューラが強制する例）
- 型付き effect system / capability-based security（object-capability、CHERI、Pony の参照能力）。「到達できる資源」を型や権限で閉じる系譜
- 契約による設計と型付きインタフェースの conformance checking（宣言に対する実装の準拠を機械的に検査する系譜）
- SLA / SLO の機械可読表現（費用と応答時間の宣言）

## 第 1 本から引き継ぐ問い

- 中断と再開の可否を機械可読に宣言する語彙は存在するか。durable execution 系はワークフロー側の再開しか扱っておらず、実行器が自分の再開可能性を宣言する形は未確認。実行器が宣言する state と、システムが一律に取る checkpoint は別物として扱う
- 第 1 本は MCP を「ランタイム間のプロトコル」の位置には入らないと判定した（モデル側が道具を選んで呼ぶ向きで、実行器が仕事を受け取り成果を返す向きではない）。自己宣言の側で MCP を使う場合、自己宣言だけに使うのか、プロトコルにもまたがるのかを分けて評価する

## 出力

要素ごとの表。列は「抽象、不変量、実装（強制箇所）、契約との対応、A2/A4/A11 との対応、足りないもの」。加えて、費用・到達資源・state の 3 つそれぞれについて「宣言できる語彙が既存にあるか、食い違いを検出できるか」を独立に判定する。
