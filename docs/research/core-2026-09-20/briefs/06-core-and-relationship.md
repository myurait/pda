# 第6本: コアの機能と、コアと実行器の関係

- 物差し: `docs/requirements.md` 3.1 の「フローとセル」「判定の分担」「コアの義務」「コアと実行器の関係」、3.2 の 1（割り振り）と 5（自己改変）、3.3、受け入れ条件 A13〜A18。commit は `git log -1 --format=%H -- docs/requirements.md` で取って冒頭に記録する
- 形式: 第 1 本 `../01-store-and-protocol.v2.md` と同じ
- 前提: 第 1〜5 本は実行器の側と、コアが持つ 5 要素を部品として調べた。本書はコアが主体として何をするか、実行器との間で何を約束し何を約束しないかを調べる。第 1〜5 本で既に評価した部品は再評価せず、コアの役割の側から読み直す

## 問い

コアが「フローの管理機構」であり、事前に列挙した決定論的な規則だけで判定し、指示文を書かず、セルの追加を前のセルの指示によってだけ行う、という構造について、抽象・不変量・実装の揃った対はどれか。特に次の 6 つ。

1. **フローの保持と提案ベースの変更。** 実行の経路（どのセルをどの順に通るか）を中央が保存し、変更は前段の出力に含まれる指示によってだけ起きる、という構造を持つ抽象と実装はあるか。中央が自分から経路を足さないこと（A17）を、構造として保証している例はあるか
2. **決定論的な判定への限定。** 中央の判定を事前に列挙した規則（回数、時間、フォールバック経路の条件）に限り、それ以外の判断を別の主体へ渡す構造はあるか。中央が行った判定のそれぞれについて、どの規則に該当したかを外から示せる実装（A18）はあるか
3. **指示文を書かない引き渡し。** 次段への入力が「type ごとの事前に用意した文」と「前段の出力」だけから機械的に組み立てられ、中央が文を書き足していないことを後から確かめられる（A16）構造はあるか。入力の出所を記録する系譜（provenance）と、プロンプトを版管理して実行時に引くだけにする系譜の両方を見る
4. **仕事の状態の保持と、中断・再投入。** 仕事が今どこにあり、どの状態かを中央だけが持ち（A14）、中断と再投入を規則に従って行い、再投入の形が最初の引き渡しと同じである（A15）構造はあるか。失敗をどう検知するか（応答が無いことを誰がいつ判定するか）の抽象と実装を含む
5. **形に合わない発信の不受理。** 契約の形から外れた発信を受け取らず、受け取らなかった事実を記録する（A13）構造はあるか。契約違反をどちらの側の責任として記録するかを形式化した抽象があるか
6. **関係の形。** 中央が経路を持って参加者に指示する形と、参加者が分散して規約に従う形の対比のうえで、PDA の「コアがフローを持つが、フローの変更は参加者の提案で起きる」という形はどこに位置づくか。参加者が中央の存在を知らずに（改変なしで）参加できることを、どの抽象が扱っているか

## 起点

- 実行と計画の分離。計画器が経路を作り、実行器がそれをなぞる構造（HTN 計画と実行監視、BDI の熟慮と実行の周期）。第 5 本の HTN の続き。コアがなぞる側、判定器のセルが計画する側という対応が成り立つか
- ワークフローの動的変更。実行中のインスタンスに段を足す仕組み（YAWL の worklet と ripple-down rules は第 5 本で確認済み。ほかに Temporal の子ワークフローとシグナル、Argo Workflows、Airflow の動的タスク生成）。変更の出所を前段の出力に限定している例があるか
- 自己書き換えを許す形式モデル。自己修正ネット（Valk）、グラフ書き換え系、動的トポロジを持つプロセス計算。経路の変更が「誰の出力によって」起きるかを形式に持つものがあるか
- blackboard の制御（BB1 の control plan。第 5 本で抽象側のみと判定）。制御知識を判定器のセルに置き、コアはスケジューラだけを持つ構造との対応
- 監督と再起動の規則。Erlang/OTP の supervisor の再起動回数と時間窓（第 3 本ではラッパーとして見た。ここではコアの規則として読み直す）、Kubernetes の Job の失敗回数上限と再スケジュール、Temporal の RetryPolicy。規則が一覧として読める形になっているか、規則に無い判断をどこへ逃がしているか
- 方針と機構の分離（policy/mechanism separation）。機構だけを中央に置き、方針を外に出す設計の系譜。規則エンジン（production rule、RETE）と、発火した規則の記録
- フォールバックと遮断。circuit breaker、retry budget、フォールバック経路の条件。第 5 本の routing の続き
- 失敗検知。リースとハートビート、unreliable failure detector（Chandra–Toueg）の抽象。「応答が無い」を誰がいつ判定するかの形式化
- 仕事の状態の所有。キューの可視性タイムアウト（SQS）、コンシューマグループの再割り当て（Kafka）、ジョブコントローラの状態機械（Kubernetes）。再配信の意味論（at-least-once）と再投入の同形性
- 契約と責任の帰属。高階契約と blame（Findler–Felleisen）。違反をどちらの側に帰するかを形式化した系譜と、その実装（Racket contracts）。A13 の不受理の記録と対応するか
- 入力の出所の記録。W3C PROV、noWorkflow、データ系譜（lineage）。次段の入力が前段の出力と事前文だけから成ることを、記録から確かめられる形
- プロンプトの版管理。プロンプトを登録・版管理して実行時に引く実装（Langfuse、MLflow の prompt registry）、プロンプトをコードとして型付けする系譜（DSPy の signature）。「コアが文を書かない」を構造として保証しているか
- 中央集権と分散の対比。オーケストレーションとコレオグラフィ（第 1 本の Choral の続き）。BPEL と WS-CDL。PDA の形はどちらに近く、何が違うか
- 参加者が改変なしで参加する。アダプタ層で吸収する系譜（第 3 本の OCI、LSP、ACP の続き）。ここでは「参加者が中央を知らない」ことを不変量として持つかを問う

## 第 1〜5 本から引き継ぐ問い

- 第 5 本の集約表が残した「判定器自身がコアの実行器契約に従い、差し替え可能である全体の対応は未確認」。本書では、判定器を先頭のセルとして固定する構造（エントリポイントが jev のセル）が、どの抽象に対応するかを見る
- 第 5 本の集約表が残した「自己改変を、いつ・何を根拠に・何から何へ変え、元へ戻せるかを一体で記録する対は未発見」。本書では、フローの変更が前段の出力（=根拠）に対応づけられる構造（A17）が、この空白をどこまで埋めるかを見る
- 第 4 本が指摘した「同じ形式に揃える検査をどこに置くかは要件が決めていない」は、要件側で決めた。ランタイム本体はストアに触れず、ラッパーがストアを仲介し、コアが受理で形を検査する。本書はこの配置を前提に、受理の検査（問い 5）と不受理の記録を評価する
- 第 3 本の「ラッパーが出来事を黙って落とした場合を外から検出する対は未発見」。本書では、コアの側の失敗検知（問い 4）がこれをどこまで補えるかを見る
- 第 1 本の LangGraph の観察（未知のノードへの遷移が警告だけで無視される）。経路の変更を受け付ける側が、規則に無い指示をどう扱うか（拒否するか、無視するか、記録するか）を、実装ごとに記録する

## 出力

要素ごとの表。列は「抽象、不変量、実装（強制箇所）、コアの義務 6 項との対応、A13〜A18 との対応、足りないもの」。加えて次の 2 つを別表で出す。

- 決定論的な規則だけで判定している実装について、規則の一覧が外から読める形になっているか、規則に無い事象をどこへ渡しているか（拒否、無視、別主体へ委譲）の一覧
- 経路の変更を受け付ける実装について、変更の出所（前段の出力、外部からの操作、中央自身）を区別して記録しているかの一覧

末尾に、第 1〜6 本を通した「どの抽象にも実装が無い部分」と「どの実装にも抽象が無い部分」の集約表を、第 5 本の表を更新する形で置く。
