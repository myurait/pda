決済 API のタイムアウトの原因はまだ特定できていません。これまで確認できたのは「11/3 の v2.3 リリース以降に増えた」という時期だけで、どの処理が遅くなったかは調べていません。そのため、原因を推測で書くことはしていません。メモリには、同じ誤りを繰り返さないための方針だけを残します。

## ファイル 1: `~/.claude/memory/feedback-root-cause-not-release.md`

```markdown
---
name: feedback-root-cause-not-release
description: 原因調査では「リリース/時点」を原因として報告せず、どの処理が何をして遅く/壊れたのかまで特定して書く
metadata:
  node_type: memory
  type: feedback
---

障害・性能劣化の原因を聞かれたときに、「v2.3 のリリースが原因」のようにリリースや日時を原因として答えない。リリースは変化が起きた「時点」であり、原因ではない。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と報告したところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。ユーザーが知りたいのは、メカニズムまで特定した原因である。

**How to apply:**
- 時期の特定は調査の入口として扱い、結論にはしない。時期が分かったら、その変更差分(コミット、設定、依存、DB クエリ、外部呼び出し)まで掘り下げる。
- 原因は「どの処理(関数/クエリ/外部呼び出し)が」「何をして(例: N+1、ロック待ち、同期呼び出し追加、リトライ増、タイムアウト値変更)」「なぜ遅く/失敗するようになったか」の形で書く。
- 各主張には根拠(ログ、トレース、差分、計測値)を付ける。確認できていないことは推測と明記し、確定扱いにしない。
- 特定できていない段階では「時期は分かったが原因は未特定」と正直に書き、次に確認する対象を示す。
- 例: 決済 API のタイムアウト増加は、11/3 の v2.3 以降に発生していることまでは確認済みで、原因の処理は未特定(2026-11-07 時点)。
```
