決済 API のタイムアウトについて、原因はまだ特定できていません。これまでに分かっているのは、11/3 の v2.3 リリース以降にタイムアウトが増えた、という時系列だけです。どの処理が何をして遅くなったのかは調べていません。そのため、メモリには推測を書かず、調査のやり方についての教訓だけを残します。

```markdown
障害・性能劣化などの原因調査では、「いつから起きたか」(リリース日、デプロイ、バージョン)を原因として報告しない。原因は「どの処理(関数・クエリ・外部呼び出し・設定など)が、何をした結果、なぜ遅く/失敗するようになったか」という仕組みの形で書く。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と報告したところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時系列の相関を示しただけで、原因の特定になっていなかった。

**How to apply:**
- リリース日と症状の開始時期が一致しても、それは調査の出発点として扱う。そこから該当リリースの差分(変更されたコード・クエリ・依存・設定)まで掘り下げる。
- 報告には次の 3 点を含める: (1) 該当する処理の名前と場所、(2) その処理が何を変えたか・何をしているか、(3) それがレイテンシやタイムアウトにつながる仕組み。
- 裏付け(ログ、トレース、計測値、差分)を添える。確認できていない部分は推測と明記し、事実のように書かない。
- 特定できていない場合は「時期は分かったが原因は未特定」と正直に書き、次に調べることを示す。
- 関連: 決済 API タイムアウト調査(v2.3 以降に増加)は、原因となる処理が未特定のまま。
```

## 補足

決済 API の件は、このあと調べ直す必要があります。次の順で進めるつもりです。

1. v2.3 の差分から、決済 API のリクエストパスに入った変更を洗い出す。
2. 該当エンドポイントのトレースやスロークエリのログで、遅くなっている区間を特定する。
3. 遅くなっている処理と、リリースでの変更点を突き合わせる。

調査を進めてよければ、ログや計測にアクセスできる環境か、リポジトリの場所を教えてください。
