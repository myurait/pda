直前の回答は「v2.3 のリリース以降」という時点を原因として書いており、どの処理が遅くなったのかは調べていません。そのため、具体的な原因は推測で書かず、今後の進め方のルールとしてメモリに残します。

```markdown
原因調査の報告で「v2.3 のリリースが原因」のように、リリースや日時といった時点を原因として書かない。原因として書くのは、どの処理(関数・クエリ・外部呼び出しなど)が、何をしていて、なぜ遅くなったのか(または失敗するようになったのか)までとする。

発端: 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた」「原因は v2.3 のリリース」と回答したところ、ユーザーから「リリースは時点であって原因じゃない」と指摘された。

**Why:** リリースは変化が起きたタイミングを示すだけで、対処の手がかりにならない。ユーザーが知りたいのは、何を直せば再発しないかである。

**How to apply:**
- 「いつから」が分かったら、そこで終わらせずに、その時点の変更差分(コード・設定・依存・インフラ)を調べ、遅くなった処理を特定する。
- 報告には次の3点を含める。(1) 該当する処理の場所、(2) その処理が何をしているか(例: N+1 クエリ、同期の外部呼び出し、タイムアウト値の変更、ロック待ち)、(3) それが遅延に至る根拠(ログ、メトリクス、トレースなど)。
- 根拠まで確認できていないことは、原因と断定せず「仮説」「未確認」と明記する。
- リリース時点は、原因ではなく調査の起点として書く。
```
