決済 API のタイムアウトの本当の原因は、まだ調べられていません。前回の「原因は v2.3 のリリース」は時期を示しただけで、原因の説明になっていませんでした。以下のメモリでは、どの処理が遅くなったかを推測で書かず、「未特定」と明記しています。

## メモリファイル

description: 障害や性能劣化の原因調査では「リリース/日時」を原因として報告せず、どの処理が何をして悪化したかの仕組みまで特定して書く

障害・遅延・エラー増加の原因調査で、「いつから起きたか」(リリース、デプロイ、日付)を原因として報告しない。原因として書くのは、どの処理(関数・クエリ・外部呼び出し・設定など)が、何をした結果、なぜ遅く(または壊れた状態に)なったのか、という仕組みまで。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と答えたところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時期の特定は相関を示すだけで、対処や再発防止には使えない。

**How to apply:**
- 報告は「(1) 発生時期 (2) 原因の処理 (3) その処理が何をして遅くなったか (4) 根拠」の順に分けて書く。時期は(1)だけに書く。
- 根拠は、リリース前後の差分(コード・設定・依存・スキーマ)、トレース、スロークエリログ、レイテンシの内訳など、実際に確認したものを挙げる。
- 仕組みまで特定できていない場合は「原因は未特定。現時点で分かっているのは発生時期のみ」と書き、推測で原因を埋めない。仮説は仮説と明示し、確認方法を添える。
- 「リリースが原因」「負荷が原因」のような、時点や状況だけを述べる結論で調査を終えない。

関連事例: 決済 API のタイムアウト増加(v2.3、11/3 以降)。2026-11-07 時点で、遅くなった処理は未特定。v2.3 の差分とリクエストのレイテンシ内訳から特定する必要がある。
