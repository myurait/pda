メモリのファイルと索引の行を書きます。決済 API のタイムアウトについては、実際の原因はまだ特定できていません。これまでに分かっているのは、11/3 の v2.3 リリース以降に増えたという時期だけです。そのため、メモリには原因を書かず、調査の進め方についての指摘だけを残します。原因を推測で書くと誤った情報が残るからです。

## ファイル 1: `~/.claude/memory/feedback-root-cause-not-release.md`

```markdown
---
name: feedback-root-cause-not-release
description: 障害・遅延の原因調査では「いつのリリースか」で終わらせず、どの処理が何をして悪化したかまで特定して書く
metadata:
  node_type: memory
  type: feedback
---

原因調査の報告で「原因は vX.Y のリリース」と書かない。リリースは悪化した時点を示すだけで、原因ではない。報告には、どの処理(関数・クエリ・外部呼び出しなど)が、何をして(例: 同期呼び出しの追加、N+1、インデックス不使用、リトライ増、タイムアウト値の変更)、なぜ遅くなったのかを書く。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた。原因は v2.3 のリリース」と報告したところ、ユーザーに「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時期の特定だけでは、対処も再発防止もできない。

**How to apply:**
- 時期の特定は調査の入口として扱う。次に v2.3 の差分(コード・設定・依存ライブラリ・マイグレーション)を確認する。
- 遅延の場合は、トレース、スロークエリ、レイテンシの内訳など、処理単位の計測で遅くなった箇所を絞る。
- 報告は「どの処理 → 何をしている → なぜ遅い → 根拠(ログ・計測値・差分)」の順に書く。
- 根拠が取れていない部分は推測と明記する。未確認のまま原因と断定しない。
- 特定できなかった場合は「リリース以降に増加。原因の処理は未特定」と書き、次に調べる箇所を示す。
```
