決済 API のタイムアウトの調査で、私は「v2.3 のリリースが原因」と答えました。これは発生時期を言い換えただけで、原因ではありませんでした。どの処理が何をして遅くなったのかは、まだ特定できていません。そのため、メモリには再発防止のルールだけを書き、v2.3 の具体的な原因は推測で書いていません。

**ファイル: `~/.claude/memory/feedback-root-cause-must-be-mechanism.md`**

```markdown
---
name: feedback-root-cause-must-be-mechanism
description: 障害・性能劣化の原因調査では「リリース/時期」を原因として報告せず、どの処理が何をして悪化したかの仕組みまで特定して書く
metadata:
  node_type: memory
  type: feedback
---

障害や性能劣化の原因調査で、「◯◯のリリース以降に増えた」「リリースが原因」と答えない。リリースは起きた時点を示すだけで、原因ではない。原因として報告するのは、どの処理(関数・クエリ・外部呼び出し・設定など)が、何をして(例: N+1クエリ、同期呼び出しの追加、ロック競合、タイムアウト値の変更、リトライの増加)、なぜ遅く・失敗するようになったか、という仕組みである。

**Why:** 決済 API のタイムアウト増加の調査で「v2.3 のリリースが原因」と報告したところ、ユーザーから「リリースは時点であって原因じゃない。どの処理が何をして遅くなったのかを書いて」と指摘された。時期の特定だけでは、ユーザーは修正も再発防止もできない。

**How to apply:**
- 時期の相関(リリース日、デプロイ、設定変更)は「きっかけの手がかり」として書く。そのうえで、その変更に含まれる差分(コード、設定、依存関係)まで調べる。
- 遅くなった処理を、ログ、メトリクス、トレース、コード差分などの根拠と一緒に特定する。
- 報告は「処理 → 何をしている → なぜ遅い/失敗する → 根拠」の形で書く。
- 仕組みまで特定できていないときは、原因が未特定であることを明記する。そのうえで、分かっていること、仮説、次に確認することを分けて書く。時期だけで原因と断定しない。
```
