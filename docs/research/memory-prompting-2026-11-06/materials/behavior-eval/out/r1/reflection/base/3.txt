## 1. メモリファイル

パス: `~/.claude/memory/feedback-root-cause-not-release.md`

```markdown
---
name: feedback-root-cause-not-release
description: 性能劣化や障害の原因調査では、リリースやバージョンを原因として答えず、どの処理が何をして悪化したかまで特定して書く
metadata:
  node_type: memory
  type: feedback
---

障害や性能劣化の原因を報告するときは、「v2.3 のリリースが原因」のようにリリースやデプロイを原因として書かない。原因は、どの処理(関数、クエリ、外部呼び出し、設定など)が、何をした結果、どう遅くなった(壊れた)のかという仕組みまで特定して書く。

**Why:** 決済 API のタイムアウト増加の調査で、「11/3 の v2.3 リリース以降に増えた」ことを原因として報告したところ、ユーザーから「リリースは時点であって原因じゃない」と指摘された。リリースは変化が起きた時点を示すだけで、なぜ起きたかの説明になっていない。

**How to apply:**
- リリース日時との相関は「いつから」の手がかりとして書き、原因とは分けて書く。
- 原因の欄には、次の3点を書く。
  1. どの処理か(コンポーネント、関数、クエリ、依存先など)
  2. その処理が何をしているか(変更前後の差分、追加された呼び出し、増えた待ち時間など)
  3. なぜそれがタイムアウトや遅延につながるか(ログ、メトリクス、コード差分などの根拠付き)
- リリースの変更差分(diff)、リクエスト別のレイテンシ内訳、スロークエリ、外部呼び出しの所要時間などを確認し、仕組みまで特定してから報告する。
- 仕組みまで特定できていないときは、「リリース以降に増加。具体的な処理は未特定」と書き、推測と確認済みの事実を区別する。原因が分かったかのように書かない。
```

今回の決済 API のタイムアウトについては、まだ個別の処理を特定できていません。ここまでに分かっているのは、v2.3 のリリース以降に増えたという時点だけです。そのため、メモリには具体的な原因を書いていません。
