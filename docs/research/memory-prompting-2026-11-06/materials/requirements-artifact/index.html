メモリを書く上での方針

決めてほしいこと

ご指摘を受けて、方法論と評価基準を整理し直しました。この整理を土台にして memory/feedback_memory_writing_rules.md を書き直してよいかを、3 つの項目で決めてください。

方針 ― メモリを書く上での基準を定める
方法論メモリには「どの範囲で、何をするか」を書く。範囲は元から取る。失敗への反省のメモリなら失敗の型、具体的に指示された方法のメモリなら指示された範囲。文は範囲を目的語に入れた言い切りにし、禁止の形でなく取る操作を書き、理由は付けない。
論文の結果が効くのは、この層の文の書き方
↓ 方法論で書いた物を測る
その水準の評価基準メモリの元が失敗でも指示でも、同じ 3 つで測る。
  • 範囲の一致: 範囲が元と一致するか。1 つの事例や 1 つのタスクに狭めず、指示や観察を越えて広げない
  • 行動が決まる: 読んだエージェントが取る行動が決まるか
  • 見える物で範囲を書く: 範囲を、作業中に見える物 (依頼・操作・成果物・環境) で書いたか。自分の内面の点検に頼らないか
↓ 方法論と評価基準から決まる
それに伴う規則置き場所と索引の決め方、同じ範囲を扱う既存メモリへの追記、frontmatter の形。
方針の文書の外 ― リンター・検査フック
本文の字面だけで決まる検査。frontmatter のキー、索引の行と description の一致、本文の日付、特定の語の有無。

元の版 (d25d5c3) の考え方の行き先

方法論へ失敗の型で書く。失敗への反省のメモリの範囲の取り方として残す。
評価基準へ「1 つのタスクで受けた個別の指示はメモリにしない」は範囲の一致の一例になる。「このプロジェクトでは」のように範囲が 1 タスクを越える指示はメモリにし、1 タスクに閉じる指示はしない。内省を発火条件にしない考え方は、見える物で範囲を書く基準になる。
規則へ置き場所を、破られたときに損なわれる物 (伝達か、成果物の正しさか) で決める。既存メモリへ追記する。索引を同じ操作で更新する。
捨てる何を取り違えると何が壊れるかを書く Why の節。「発火する事象 → 実行する操作」の表 (条件の形で、論文では条件付きが言い切りより低い)。
リンターへ「感じたら」「迷ったら」などの語の検出、本文の日付・チケット番号の検出、frontmatter の形。

項目 1　方針が扱うメモリの範囲

「どの範囲で、何をするか」を書く方法論に、取る行動の無い事実や状態のメモリも含めるか。

事実
既存メモリの type 欄は feedback 91 件、project 37 件、reference 10 件、user 1 件です。project と reference には、指示された方法 (例: docs リポジトリの作業では TypeSafe skill を使う) と、取る行動の無い事実や状態 (例: ミニ PC のサービス構成と接続方法) が混ざっています。

  • A　含める　事実や状態のメモリでは、範囲を「その事実が成り立つ環境と時点」とし、行動が決まる基準を「読んだエージェントが何を前提に作業するかが決まるか」と読み替える。
  • B　含めない　この方針は失敗への反省と指示された方法のメモリだけを扱い、事実や状態のメモリには規則の層 (置き場所・索引・frontmatter) だけを当てる。
  • C　枠組みが違う　自由回答の内容で整理し直す。
推奨: A　project と reference の 47 件は同じ索引から読まれ、範囲の一致 (いつの時点の状態か) は事実のメモリにも当てはまります。

項目 2　評価基準

メモリの水準を、範囲の一致・行動が決まる・見える物で範囲を書く、の 3 つで測るか。

今の状態
前の資料にあった「何を取り違えると何が壊れるかを書いたか」の基準は外しました。

事実
論文で理由を付けた書き方は、claude-opus-5 で言い切りと同じ (77.2 と 78.0)、claude-sonnet-5 で低い (49.4 と 71.6) 結果でした。外した基準は失敗への反省のメモリにしか当てはまりません。3 つの基準は、失敗への反省と指示された方法のどちらのメモリにも当てはまります。見える物で範囲を書く基準は、条件付きの書き方が見落とされる理由として論文の著者が挙げた「自分の行動が条件に当たるかをまず判断しなければならない」ことに対応します。

  • A　3 つで測る　書き直す版に、この 3 つを評価基準として書く。
  • B　足りない・違う　自由回答の内容で基準を直す。
推奨: A　3 つとも、メモリの元が失敗か指示かによらず当てはまり、理由を書かない方向と矛盾しません。

項目 3　方針の文書とリンターの線引き

当てはめに判断が要るものを方針の文書に置き、本文の字面だけで決まるものはリンターと検査フックに任せるか。

事実
baa27f7 の版の項目 (文末のかな、特定の語の有無、frontmatter のキー、索引の行と description の一致) は、どれも本文の字面だけで決まります。字面を検査するフック memory-style-gate はコミット済みで、settings.json には登録していません。

  • A　この線で分ける　baa27f7 の版の項目はメモリから外し、フックの検査項目の材料として残す。フックはこの作業では変えない。
  • B　字面の項目もメモリに残す　方針の文書に、方法論と並んで検査の一覧が載る。
推奨: A　字面の項目は、フックが書いた後のファイルから判定できます。方針の文書に並べると、方法論や評価基準の文と同じ重さで読まれます。
