# 事例: チケットのコメントの下書き (2026-11-07)

- 種別: 参考事例。メモリに書いても守られない型と、守れない型の切り分けの考え方を、1 件の訂正から整理した記録。
- 場面: 勤務先のプロダクトの障害チケットに、固着した投稿のリカバリ方法をコメントとして書く。作業は Claude Code (Opus) の 1 セッションで、調査から下書きまでを同じセッションが行った。
- 伏せたもの: お客様名、投稿の ID、勤務先のコードの識別子 (列名とその値、バッチ名、連携する外部の媒体)。

## 1. 下書きと訂正

Claude Code の下書き。

```
## 固着が残っている投稿のリカバリ

対象: <お客様名>の <ID 1> / <ID 2>

- <復旧用のバッチ>ではリカバリできません。
  - <復旧用のバッチ>は、<外部の媒体> に投稿が実在するのに DB に反映されていない場合に DB を復元するためのコマンドです。
  - 対象の 2 件は <外部の媒体> に一度も送られていないため、実行すると投稿エラーが作られるだけで、正常な状態には戻りません。
- 正常な状態は <状態の列> が承認待ち・<処理状態の列> が未処理で、承認履歴は今と同じ「申請中→承認→申請中→却下」です。今の状態とは <処理状態の列> がエンキュー済みになっている点だけが違います。
- リカバリ方法: ①（配信バッチの抽出条件の修正）を本番にリリースした後、手動の更新クエリで 2 件の <処理状態の列> をエンキュー済みから未処理に戻し、リカバリ完了とします。
  - ① のリリース前に戻すと、予約日時が過去で過去の承認履歴が残っているため、次の配信バッチで再び抽出されて固着します。
  - 2 件は <外部の媒体> に送られていないため、<処理状態の列> を戻しても <外部の媒体> 側の投稿を上書きすることはありません。
- リカバリ後、画面では却下された投稿として表示され、申請者が編集して再申請できます。
```

オーナーの訂正 (「使えない。以下のように書き直し。」)。

```
## 対象投稿のリカバリ

対象: <投稿の ID の列>: <ID 1>, <ID 2>
- リカバリ方法: ①（配信バッチの抽出条件の修正）を本番にリリースした後、手動の更新クエリで 2 件の <処理状態の列> をエンキュー済みから未処理に戻す
- リカバリ後、画面では却下された投稿として表示され、申請者が編集して再申請できるようになるため、お客様にご連絡。

※ <復旧用のバッチ>ではリカバリできません。
```

下書きの行は、オーナーが会話の中で Claude Code に尋ねた順 (復旧用のバッチは使えるか、正常な状態は何か、いつ戻せるか) の答えを積んだものだった。コメントの読み手は、データを直す開発者とお客様に連絡する人である。

## 3. 切り分け

訂正 13 か所を 4 つに分けた。3 つ目の分類は、オーナーの発言の「観点が記載されている項目」を「記載されていない項目」と読んだ。各分類の境目は次の判定で引いた。

- A (メモリを守れば直る): 観察できる事象で規則が発火し、取る操作が機械的に決まる。
- B (メモリに観点はあるが、守っても足りない): 規則の文面は削除を求めているが、実行に「この読み手にこの項目が要るか」の判断が要る。書き手はその判断で残す側に倒す。
- C (メモリに観点が無い): 観察できる事象を発火条件にした規則として書けば届く。
- D (書いても達成できない): 発火条件の形の規則が届かない語の選び方と先読み。

分類はアドバイザー (別のモデルによる第三者の検証) に通し、次の 3 点を直した: 「復旧用のバッチが使えない理由」を A から B へ移す、「B だが D 寄り」の留保を外す、対象行を法人名 (B) と区切り (D) に分けたことを明示する。

### A (2 件)

- 順序: リカバリ方法を先頭に置き、復旧用のバッチの話を末尾に下げる。「ユーザー以外の人が読む文書は、判断を動かす大きさの順に並べる」規則がある。書き手は読み手をオーナーと捉えたため、この規則が発火しなかった。
- 文体: です・ます調を、書き込み先のチケット本文と同じ常体の言い切りにする。「書き込み先の表現規約に合わせる」規則がある。

### B (6 件)

- 復旧用のバッチが使えない理由の 2 行 (削除)
- 「正常な状態は…」の行 (削除)
- 「① のリリース前に戻すと再び固着する」(削除)
- 「<外部の媒体> 側の投稿を上書きしない」(削除)
- 対象行の法人名 (削除)
- 復旧用のバッチの話を削除せず、末尾の「※」に下げて残す扱い

該当する規則は「読み手が決めない事柄の理由は消す」「落としても読み手の次の行動が変わらない事実は消す」「問われていない問いを載せない」で、どの項目も文面には当たる。書き手は「作業者の確認に使える」「安全のための警告だ」「チームの規範への先回りだ」と残す理由を作った。オーナーの言う「読み手の判断は特定できるが、何が情報の重さになるかを評価しない」はこの 6 件に当たる。

### C (2 件)

- 「リカバリ完了とします」(削除): オーナーが会話で使った言い回しを、手順の文に写していた。会話の言い回しを成果物に写さない観点は、メモリに無い。
- 「お客様にご連絡」(追加): サービス問題のコメントを、お客様が次に動けることとその連絡で終える観点は、メモリに無い。書き込み先の文書を読んで読み手の判断を推定する規則が途中までは届くので、B との境目にある。

### D (3 件)

- 見出しの「対象投稿のリカバリ」という語の選び方
- 対象の ID の区切りを「/」から「,」に変える。更新クエリに貼れる形にした、という意図は書き手の推測である。
- 「できます」を「できるようになる」に変える。今はできず、データを直すとできるようになる変化を書く。

## 4. B をメモリで扱えるか

オーナーの問い (「B は目盛りに書いたとてどうしようもないことっていうことにならないか。これは目盛りの書き方の問題なのか」) に対する、Claude Code の整理。

- B の規則は「落としても行動が変わらないか」「読み手が決めないか」の判定を書き手に求める。誤るのはこの判定そのものなので、言い回しを変えても同じ書き手が同じ判定をする。判定を書き手に任せる形の規則は、どう書いても B に効かない。
- B の 6 件は、重さで見ると判断が要るが、行の形では見分けられる。理由の形の行 (「〜ため」「〜すると〜する」)、読み手の操作を含まない状態の説明の行、懸念を打ち消す形の行 (「〜しても〜ない」)、書き込み先の本文にすでにある語。
- 案: チケットのコメントを投稿・提示する時点で、各行を「読み手の行動かその対象の行」と「理由・状態の説明・懸念の打ち消しの行」に機械的に分け、後の種類の行が残っていれば消させる検査を hook に置く (判定は Jev)。理由が必要な場面でも消すため、対象はチケットのコメントに絞る。「※」で残すべき行を見分けられるかは試していない。
- この案は、オーナーの承認を得ておらず、試作もしていない。

## 5. メモリの書き方の検討につながる点

- 書き手の判定を発火条件や操作に含む規則は、その判定を誤る型 (本件の B) には効かない。[記録の 4.1 節](../README.md#41-段階-1-言い切りの形への改訂と検査フック-11-06-午前) の、内省を要する基準の問題と同じ形をしている。
- 観点の有無 (A・B と C) と、規則の形で届くか (C と D) は別の軸である。メモリに観点を足して直るのは C だけだった。
- A の失敗は規則の欠落ではなく、発火条件の取り違え (オーナーに見せる下書きを、チームが読む文書と見なさなかった) で起きた。
