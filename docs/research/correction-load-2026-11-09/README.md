## 1. 依頼

2026-11-09、オーナーは開発 PC の Claude Code の 1 週間のセッションの仕分けを求め、続けて次を求めた。

> コンポン的に指示の出し方の問題なのか、指示を整える機構がないことが問題なのか、それ自体を目盛りとして組み込んでしまった方がいいのか、ハーネスとして取り込んで強制力を持たせた方がいいのか、実現の仕方として いろんなことが考えられるけど、何が正しくて何がコストが低くて何が長期的に運用可能で っていうところを含めて検討したいな。

比べる手当ては 4 つ。

- L1 指示の出し方（オーナーの依頼の書き方）
- L2 指示を整える仕組み（作業に入る前に範囲と終わりの条件を決める工程）
- L3 メモリ・規約（CLAUDE.md・メモリ・skill の文面）
- L4 ハーネスでの強制（hook・ゲート・外部の検査）

比べる観点は 5 つ。効くのはターンのどこか（作業の前・中・後）、失敗したときに止めるか直させるか、作業 1 件ごとのオーナーの手間、オーナーが見張らなくても保たれるか、測定で示されたこと。

## 2. 1 週間の仕分け（2026-11-02〜11-09、開発 PC）

対象は `~/.claude/projects` のセッション 59 本。自動実行（セキュリティレビューなど）を除き、分岐・始め直し・切り出しを元の作業にまとめて、オーナーが指示した作業 22 件にした。ミニ PC のセッションは含まない。

| 終わり方 | 件数 |
|---|---|
| 訂正なしで片付いた | 3 |
| 訂正を重ねて片付いた | 7 |
| 片付かなかった | 6 |
| 一問一答で返事なし | 6 |

期間内のオーナーの発言 263 回のうち、約 130 回が訂正・言い直し・やり直しの指示だった。「別セッションに切り出して」は 12 回あり、切り出した先でも同じ訂正が続いた。

失敗の型（件数はその型が出た作業の数）。

| 型 | 件数 | 例 |
|---|---|---|
| 1. 頼んだことを別の問題に置き換える | 7 | 1 行の指示（推定の時刻に試行の時刻を使う）が、設計文書の多くの箇所を書き換えた PR になった |
| 2. 頼まれていない論点・変更を足す | 7 | 図を分ける依頼で図の様式まで変えた。契約書に依頼に無い条を足して 20 条にした |
| 3. 判断・選択肢を返してくる | 7 | 文書の整理を 10 セッションの判断資料に分け、返答が付いたのは 1 つ |
| 4. 意味の通らない日本語・造語 | 8 | 「前置き」（path prefix の言い換え）、「写したキー」、「2 つに同時に当たる」（patch の直訳） |
| 5. 確かめずに「直した」「できる」と言う | 7 | 「直した」と報告したが、ほとんど直っていなかった |

型 1〜3 の訂正が、訂正の大半を占める。5 つの型すべてに、この週より前からメモリがあった（`~/.claude/memory/` の 30 ファイル・約 140KB。`/co` が毎回全件を読む）。訂正なしで片付いた 3 件は、出すものが 1 つで、何をするかをオーナーが具体的に決めていた作業だった。

## 3. 手元の測定

### 3.1 確信度を判定する Stop hook（intent-gate、11/4 設置）

`~/.claude/debug/intent-gate/` の判定の記録を全件数えた。

| 判定 | 回数 |
|---|---|
| 確信度を出して通した | 114 |
| 確信度を出して差し戻した | 6 |
| 差し戻しの直後で判定せずに通した（stop_hook_active） | 140 |
| 記録にオーナーの発言の行が無く、判定せずに通した | 58 |
| 「作業中...」で通した | 42 |
| 記録を読めず通した | 26 |
| 言い直しの途中で通した | 11 |

判定した 120 回の確信度は 72〜92% に集まっていた（85% が 37 回）。オーナーが約 2 回に 1 回訂正した週に、判定した返答の 95% を通した。オーナーが「リモートに置いていい品質じゃない」と棄却した PR を作ったセッションでは、記録に発言の行が無く、一度も判定していない。

### 3.2 指示語を点検する Stop hook（reference-gate）

差し戻しがループし、スマホへの通知が連発した（2026-11-01〜11-06 のセッションでオーナーが調査を依頼）。文書の整理のセッションでは、差し戻しの直後にオーナーが作業を止めている。

### 3.3 助言役が書いた引き継ぎ文

1 行の指示を Claude が自分の引き継ぎ文で別セッションに渡したときは、多数の箇所を書き換えた PR になった。アドバイザーが書いた引き継ぎ文で渡したときは、指示どおり 4 ファイル・6 行の変更になった。1 件だけの例で、オーナーの受け取りは記録に無い。

## 5. 4 つの手当ての比較

| | L1 指示の出し方 | L2 作業前に範囲を決める | L3 メモリ・規約 | L4 ハーネスでの強制 |
|---|---|---|---|---|
| 効く時点 | 作業の前 | 作業の前 | 作業中ずっと（文脈として） | 作業中・作業の後 |
| 失敗したとき | オーナーが書き直す | 計画の段階でオーナーが直す | 守られずに進む | 決定論的な検査なら直させる。モデルの判定はほぼ通す（3.1） |
| 作業 1 件ごとの手間 | 毎回、依頼を整える | 計画の承認 1 回 | 無し | 無し |
| 見張りなしで保たれるか | 保たれない（オーナー次第） | plan mode を既定にすれば保たれる | 量と条件付きの形で遵守が下がる | 決定論的な検査は保たれる。モデルの判定は穴がある（3.1） |
| 型 1〜3 への証拠 | 1 行の明確な指示でも範囲が広がった | 公式の手順、オーナーの「何を何に変えますって全部宣言してから変えろ」 | 5 つの型すべてにメモリがあって起きた | 確信度の hook は 95% 通した |
| 型 5 への証拠 | なし | なし | 原則 1 があって起きた | 機能の一覧と実物の検証（公式・事例） |

## 6. 測り直しの手順

同じ手順で 1 週間後に測り直せるよう、抽出のスクリプトを [materials/](materials/) に置く。

1. `python3 -I materials/extract_turns.py <git 管理外の出力先> <除外するセッション ID>` で、7 日分のオーナーの発言と直前の Claude の応答をセッションごとのダイジェストにする
2. 訂正の前に Claude が実際にした操作は `python3 -I materials/actions.py <記録の jsonl> <開始時刻> <終了時刻>` で引く
3. ダイジェストを話題ごとに分けてサブエージェントに渡し、依頼・結末（訂正なしで解決 / 訂正後に解決 / 未解決 / 不明）・訂正ごとの引用を返させる
4. 作業ごとの結末と、発言のうち訂正の割合を 2 節の表と比べる

ダイジェストと事件ごとの記録には業務の内容と同僚の名前が入るため、リポジトリには置かない（2026-11-09 の分は開発 PC の作業ツリーの git 管理外の `tmp/failure-review/` にある）。
