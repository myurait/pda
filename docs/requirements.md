# PDA v0.2 要件 — 実行器の抽象化をコアに据える

- 更新: 2026-09-22 JST
- 種別: オーナー指示による要件の整理。設計・実装・製品選定の宣言ではない。
- 位置付け: v0.2 の最初の文書であり、要件の正本。旧 PDA の資産・文書・計画は tag `v0.1-archive` に保存したうえで全破棄し、本文書の入力にしない。

## 1. なぜやり直すか

旧 PDA は、抽象化をせずに複数のツールをそれらしく繋げ、それらしく動くことを主題にしてきた。その結果、次の 2 つが起きた。

1. 大型のハーネスが、調整済みの高性能な大型モデルの能力を低下させた。ベンチマークでは、PDA より Codex Astra のバニラが圧勝した。
2. 各ツール（Claude Code desktop / CLI、Codex desktop、ChatGPT、Gemini）が別々の指示を持ち、相互に情報をやりとりする手段も、それらへ到達する動線も統一されなかった。desktop アプリや CLI は開発 PC からしか見えず、スマホで進捗を確認できない。Open WebUI と Hermes の画面を中途半端に併用した結果、仮想ターミナルの起動、コピーペーストの不能、スマホでのスタイル崩れといった体験劣化が起きた。

根本は、実行の主体を抽象化しなかったことにある。抽象化がないため、ツールを一つ足すたびに繋ぎ方が増え、体験と誠実性の両方がツールごとにばらついた。

## 2. オーナーが求めているもの

オーナーの発言をそのまま要求として固定する。言い換えない。

- コアは適切なバニラの LLM に切り替える。ハーネスでモデルの能力を落とさない。
- 報告と誠実性を外部から監査できる衛星システム。
- Codex、Claude Code、jev、Gemini など複数モデルを中立に取り扱い、タスクごとに切り替え可能な実行器として統一的に扱える UI。
- 全てを共通で触れて、かつ体験が劣化しない UI。スマホからも作業進捗を確認できる。
- 複数の環境、アカウント、エージェントを、平等で交換可能な実行器として抽象化する能力。UI/UX、可視化、自己改変も必要だが、最大のコアはこの抽象化である。
- PDA の最終形は、適切な作業を適切な実行器に割り振り、実行器ごとにコンテキストを絞った上で、最終成果をまとめ上げる多層的な統合推論機構。複数のワークフローをメッシュのように構成し、機能の成果やフィードバックに基づいてそれを自己改変する。
- 仕事の進め方、進行するワークフロー、どのモデルがどの仕事を進め、どのように相互にやりとりしたかが、ユーザーに可視化されなければならない。そのための直感的な UI/UX も PDA に含む。
- desktop アプリの現状のセッションは破棄してよい。各 desktop アプリの過去セッションはファイルとして読み取れるので、そこからのデータサルベージと統合記憶への引き継ぎを移行タスクとして持つ。
- 開発 PC に閉じる必要があるのは Notion や Datadog など一部コネクタの権限だけで、アカウント本体はその制約下にない。
- 同一ベンダーでも会社契約と個人契約のアカウント間でセッションを共有できないことが体験劣化の原因であり、実行層を切り替え可能にしたい理由の一つである。
- Gemini は API 起動のみ。個人ログインでの利用実績はない。
- コアは決定論で扱える最重要の関心だけを引き受ける。決定論的に判断可能な事項と推論的に判断可能な事項をあらかじめ定義し、「n 回実行器の起動エラーが発動したらエラー終了」「フォールバック経路上の実行器の起動エラーが発動したらエラー終了」のようなフォールバックの一部の条件だけをコアが扱う。その他の推論的ないし意味論的な判断は、判定器として別に切り出した実行器が行う。
- コアの最も重要な機能は、workflow 的な実行器の相互やりとりやパスの構造を保存、保管し、実行器からの提案ベースで追加変更できることである。
- コアは全ての作業のエントリポイントとして「タスク分解モデル選定（jev）」を持つ。jev から、タスクの複雑性と要求コンテキスト量に応じて次にタスク分解を行う最適なモデルの提案を受ける。例えば `flow: add, type: break-down, model: fable` が返れば、後続に fable のセルを追加し、作業を割り振る。
- コアはモデルに与える指示を直接記述しない。type に応じた事前に記述済みのプロンプトと、前のセルから与えられた入力（なければ初期入力）をそのまま次のセルに投入する。
- コアはフローの管理機構であり実行器の上位統括だが、コアが持つエントリ（セルないし実行器）の追加は、実行器（前のセル）からの指示によって起動される。
- 成果の中身を分類するのではなく、ワークフロー管理のメッセージなのか、次のエージェントへの入力に使う応答なのか、タスク全体への成果なのかを分類する。前の 2 つに合致しないものは成果として落とし込めばよい。後続のワークフローへ自動投入されなくなるだけで、揮発するわけではない。
- フロー変更の出所を前段に限定しなくても、フローに落とし込まれている限り影響は小さい。エージェントが破壊的に暴走することを止める必要は、運用してリスクが出たら考える。

## 3. 本当に必要なもの

2 節の要求から導いた要件を、コアと周辺に分ける。コアが成立しなければ周辺はどれも成立しない。

### 3.1 コア要件: 実行器の抽象化

**実行器とは何か。** 環境、アカウント、エージェントの組を一つの単位として扱ったものである。

- 環境: 実行が起きる場所。ミニ PC、開発 PC、ベンダーのクラウドなど。
- アカウント: その実行に使う契約や認証。会社契約の Claude、個人契約の Claude、個人契約の Codex、Gemini の API key など。
- エージェント: モデルとそれを動かすツール。Claude Code、Codex、Gemini API、jev、機械的な検証ツールなど。

同じエージェントでもアカウントが違えば別の実行器である。同じアカウントでも環境が違えば別の実行器である。判定を返す jev も、決定論的な検証を行うガードレールも、コードを書く Codex も、すべて実行器である。

**平等とは何か。** コアが特定のベンダー、モデル、ツール、環境に特権を与えないこと。コア自身の動作が特定の LLM に依存しないこと。ある実行器にしかない機能をコアの前提にしないこと。

**交換可能とは何か。** 同じ仕事を別の実行器へ渡しても、仕事の渡し方、成果の受け取り方、記憶への書き込み方、可視化のされ方、監査のされ方が変わらないこと。実行器を一つ足す、外す、差し替えるときに、コアと他の実行器を変更しなくてよいこと。

**抽象化が定める契約。** すべての実行器が同じ形で提供しなければならないものを列挙する。形の詳細は設計で決めるが、項目はここで固定する。

| 項目 | 内容 |
|---|---|
| 能力の宣言 | 何が得意か、何ができないか、費用、到達できる資源（コネクタ権限を含む）、扱える入力と出力の種類、取れる state。どの実行器も中断されうる（jev のような呼び出し型でもリクエストは切れる）。中断後に再開できるのか、再投入になるのかは、取れる state の宣言として表す |
| 仕事の受け取り | 仕事を、成果と同じプロトコルに基づくメッセージとして受け取る。中身は仕事そのものと、その仕事のために絞られたコンテキスト。実行器が全履歴を受け取る前提にしない |
| 成果の返却 | 成果を、別の実行器に注入可能で、かつ種別を決定論的に分類可能な形式で返す。種別は 3 つで、フローへの指示、次のセルへの入力、仕事全体の成果である。前の 2 つに合致しないものはすべて仕事全体の成果として扱う。成果の中身（テキスト、画像、ファイルなど）は分類しない。成果のやり取りはプロトコルに基づくメッセージとして扱う |
| event stream | 実行中に起きた出来事（受け取った指示、呼び出したツールとその結果、出した判断）を、起きた順に、実行器の種類に関係なく同じ形式で、実行が終わる前から実行器の外へ出す。可視化と監査はこの event stream だけを見る |

この契約を成立させるためにコアが持つ要素は次の 5 つである。

| 要素 | 役割 |
|---|---|
| ランタイムのラッパー | 各エージェントのランタイムを包み、上の契約の形に揃える |
| ランタイム間のプロトコル | 仕事と成果をメッセージとしてやり取りする取り決め。コアと実行器の 2 者間で定義する。実行器の発信はすべてこのプロトコルのメッセージとしてコアへ向け、実行器が自由に発話することは許容しない |
| MCP 的な自己宣言 | 実行器が能力の宣言を機械可読な形で公開する |
| 共通の input/output ストア | 仕事と成果のメッセージを置く場所。実行器はここから仕事を受け取り、ここへ成果を返す |
| ログストア | event stream を書き込む場所。可視化と監査はここを読む |

**フローとセル。** フローとは、仕事がどのセルをどの順に通るかの構造である。セルとは、フロー上の一つの実行の単位で、type と実行器の組である。type は事前に記述済みのプロンプトに対応する。セルへの入力は、その type のプロンプトと、前のセルの出力（最初のセルなら初期入力）だけから成る。コアはフローを保存・保管し、セルの出力に含まれるフローへの指示（セルの追加・変更）に従って書き換える。すべての仕事のエントリポイントは、タスク分解を行うモデルを選定する判定器（jev）のセルである。

**判定の分担。** コアが自分で行う判定は、あらかじめ列挙した決定論的な規則に限る。例として、実行器の起動エラーが n 回続いたらエラー終了する、フォールバック経路上の実行器で起動エラーが出たらエラー終了する、といったものである。次にどのモデルへ渡すか、成果が十分か、フローをどう変えるかといった推論的・意味論的な判断は、判定器として切り出した実行器のセルが行い、コアはその出力に従う。

**コアの義務。** 上の契約は実行器に求めるものである。その鏡像として、コアがすべての実行器に対して同じ形で果たすものを列挙する。

| 項目 | 内容 |
|---|---|
| 仕事の引き渡し | フローの次のセルへ、仕事をプロトコルのメッセージとして渡す。中身は type の事前プロンプトと前のセルの出力（なければ初期入力）で、コアは指示文を書き足さない。渡す形は実行器の種類で変えない |
| 発信の受理 | 実行器の発信をプロトコルのメッセージとしてだけ受け取る。形に合わない発信は受け取らず、受け取らなかった事実を event stream に残す。受理した発信を、フローへの指示、次のセルへの入力、仕事全体の成果の 3 つに分ける。指示はフローに反映し、入力は次のセルへ渡し、成果は保管する。ここに推論は含まない |
| 仕事の状態の保持 | 仕事が今どの実行器にあり、実行中か、中断されたか、再投入されたか、完了したかをコアが持つ。実行器に問い合わせなくても分かる状態にする |
| フローの保持 | フローと、その追加変更の履歴をコアが持つ。追加変更ごとに出所（前のセルの指示、人の操作、フロー定義）を記録する。コアが自分から追加変更を起こすことはない |
| 中断と再投入 | あらかじめ列挙した決定論的な規則（回数、時間、フォールバック経路の条件）に該当したときだけ、コアが中断、再投入、エラー終了を行う。再投入の形は実行器が宣言した取れる state に従う。規則に無い判断はコアがせず、判定器のセルへ渡す |
| 失敗の判定 | 応答が無い、契約の形から外れた、宣言した出力の種類と実際の種別が食い違った、といった機械的に確かめられる条件だけをコアが判定する。成果の中身の良否は判定器や監査の実行器が判定する |
| 記録 | 引き渡し、受理、不受理、中断、再投入、失敗判定、フローの追加変更を、実行器の event stream と同じログストアに同じ形式で残す |

**コアと実行器の関係。**

- 仕事の出所と成果の行き先は共通の input/output ストアである。ランタイム本体がストアに直接触れることはなく、ラッパーがストアから仕事を取り出してランタイムへ渡し、ランタイムの出力をメッセージにしてストアへ返す。
- 実行器の側にコア向けの改変を求めない。ベンダーのランタイムはそのまま使い、契約への適合はラッパーが担う。
- コアは実行器へ渡す指示文を書かない。書くのは type ごとの事前プロンプトを用意した人であり、コアは実行時にそれを引くだけである。
- コアは実行器の自己宣言を割り振りの根拠に使うが、宣言と実態が一致していることの根拠にはしない。一致は event stream と成果で確かめる。
- コアは実行器の内部に立ち入らない。推論は実行器の中で完結し、コアは引き渡し、受理、状態とフローの保持、決定論的な判定に留まる。
- コアは実行器の上位統括だが、フローへのセルの追加は前のセルからの指示で起動される。コアが自分からセルを足すことはない。

認証をどこが持つかなど、PDA が自己の機能のどの部分にオーナーシップを取るかは要件ではなく自己宣言であり、必要になった時点で ADR に書く。

### 3.2 周辺要件

コアの契約の上に載る要件である。どれも「実行器の契約が同じであること」を前提に成り立つ。

1. **割り振り。** 仕事の性質を判定し、どの実行器に渡すかを決める。判定そのものも実行器（例: jev）が行い、コアはその出力に従ってフローにセルを足す。割り振りの規則は固定せず、成果とフィードバックで変わる。
2. **コンテキストの絞り込み。** 実行器ごとに、その仕事に必要な範囲だけを渡す。全履歴の丸投げを禁じる。
3. **多層の統合。** 分割した仕事の成果を統合し、監査し、必要なら別の実行器で再確認して、最終成果をまとめる。統合の段数は仕事ごとに変わる。
4. **メッシュ状のワークフロー。** 直線の手順ではなく、複数のワークフローが相互に参照・監査・エスカレーションする構成を表現できる。
5. **自己改変。** 成果とフィードバック（ユーザーの指摘を含む）に基づき、割り振り規則、フロー、実行器の選択を書き換える。書き換えはセルからの提案としてコアに届き、記録され、元へ戻せる。
6. **可視化。** どの仕事が、どの実行器で、どの順で進み、実行器同士が何を受け渡したかを、時系列と関係の両方で見せる。ユーザーが見えない水面下のやりとりを残さない。
7. **UI/UX。** 全ての環境・アカウント・エージェントに同じ画面から到達できる。スマホで進捗の確認と判断の返答ができる。仮想ターミナルを主面にしない。コピーペーストができる。スマホでスタイルが崩れない。
8. **指示と記憶の共有。** 指示（規約・好み・禁則）と記憶の正本はコア側が一つ持ち、どの実行器にも同じ内容が届く。ベンダーごとの指示ファイルは正本から生成される派生物とする。
9. **監査。** 報告と誠実性を、実行器と独立した位置から検査する。検査は実行器の event stream と成果に対して行い、実行器自身の申告を根拠にしない。
10. **移行。** 既存の desktop アプリ・CLI・ChatGPT・Gemini のセッションファイルを読み取り、統合記憶へ引き継ぐ。移行後は旧セッションを破棄できる。

### 3.3 やらないこと

- ベンダーアプリの中継機能（リモート操作やクラウド送信）に UI を寄せない。統一の目的に反する。
- 特定のツールの画面やセッション管理をコアとして流用しない。
- コアに大型のハーネスを積み、モデルの能力を落とさない。コアは割り振りと契約の執行に留め、推論は実行器へ渡す。
- コアに推論的・意味論的な判断を持たせない。コアが指示文を書かない。事前に列挙した決定論的な規則に無い判断は、判定器の実行器へ渡す。
- 旧 PDA の資産、文書、計画を継承の前提にしない。再利用は要件を満たすと個別に示せたものだけ。
- 抽象化を後回しにして、先にツールを繋いで動かすことを主題にしない。

## 4. 判定できる受け入れ条件

要件が満たされたかを、次の観測可能な事象で判定する。すべて v0.2 の目標であり、現時点の達成ではない。

| ID | 条件 |
|---|---|
| A1 | 同じ仕事を実行器 A から実行器 B へ差し替えたとき、仕事の渡し方、成果の受け取り方、記憶への書き込み、可視化、監査の形が変わらない |
| A2 | 新しい実行器（別ベンダー、別アカウント、別環境のいずれか）を、コアと既存実行器を変更せずに追加できる |
| A3 | 同一ベンダーの会社契約と個人契約が、別の実行器として同じ一覧に並び、同じ操作で扱える |
| A4 | コアを動かすのに、どの特定の LLM も必須ではない。判定用の実行器を差し替えてもコアは動く |
| A5 | どの実行器の実行についても event stream が同じ形式で得られ、可視化と監査に実行器ごとの個別処理が要らない |
| A6 | ある仕事について、関わった実行器、順序、受け渡しの内容が、スマホの画面から一続きで追える |
| A7 | 指示の正本を一か所変更すると、全実行器に届く指示が変わる。ベンダーごとの指示ファイルを手で揃える作業が不要 |
| A8 | 監査が、実行器の申告ではなく event stream に基づいて「言っていることとやったこと」の差を検出する |
| A9 | 割り振り規則またはワークフローの自己改変が、いつ、何を根拠に、何から何へ変えたかを記録し、元へ戻せる |
| A10 | 既存の各アプリのセッションが統合記憶へ取り込まれ、取り込み後に元アプリなしで参照できる |
| A11 | 開発 PC のコネクタ権限が必要な仕事だけが開発 PC 上の実行器へ割り振られ、それ以外の仕事は環境に縛られない |
| A12 | ある実行器の成果を、フローへの指示、次のセルへの入力、仕事全体の成果の 3 つのどれかに、人が読み替えることなく決定論的に分類でき、次のセルへの入力はそのまま別の実行器の仕事として注入できる |
| A13 | 契約の形に合わない発信をコアが受け取らず、受け取らなかった事実が event stream から追える |
| A14 | ある仕事が今どの実行器にあり、実行中・中断・再投入・完了のどれかを、実行器に問い合わせずコアの記録だけで答えられる |
| A15 | 実行中の仕事を中断して別の実行器へ再投入したとき、渡す形が最初の引き渡しと同じで、再投入を決めた規則が event stream に残る |
| A16 | どのセルへの入力も、type の事前プロンプトと前のセルの出力（または初期入力）だけから成り、コアが書き足した文が無いことを event stream から確かめられる |
| A17 | フローへのセルの追加・変更のそれぞれについて、出所（前のセルの出力、人の操作、フロー定義）が event stream から追える |
| A18 | コアが行った中断、再投入、エラー終了、不受理のそれぞれについて、事前に列挙した決定論的な規則のどれに該当したかを示せる |

## 5. 未確定事項

以下はオーナーの判断か、実際に動かして観察した結果で決まるもので、この文書では確定しない。

- 実行器の粒度。プロセス単位か、セッション単位か、仕事単位か。
- ユーザーのペルソナを演じる実行器の選定基準。ベンチマークで決めるとされており、その計測方法は未定。
- 自己改変が許される範囲と、人の承認を要する境界。
- 監査の検査項目の初期集合。過去のユーザー指摘から収集するとされており、収集方法は未定。
- 統合記憶の正本の置き場所と形式。
- 実行器同士の直接経路を持たせるかどうかと、その価値。設計段階で掘り下げる。持たせる場合も、コアと実行器の間の取り決めから外れる発話は許容しない。
- コアが持つ決定論的な規則の初期集合。回数、時間、フォールバック経路の条件を、どの値で置くか。
- セルの追加が止まらなくなったときの上限（追加回数、フローの深さ）。運用してリスクが出た時点で規則として足す。
- type の一覧と、type ごとの事前プロンプトの置き場所。3.2 の指示の正本との関係。

## 6. この文書の使い方

本文書は要件の正本である。設計文書は 3.1 の契約と 4 の受け入れ条件を参照し、既製品の調査は「この契約と条件をどこまで満たすか」だけを問う。要件が変わる場合は本文書を先に改め、設計を追従させる。
