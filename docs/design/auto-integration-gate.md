- **統治正本との関係（Fact）**: 本設計は統治ADR（`docs/design/self-improvement-governance-adr.md`）D1 第1項「最終反映の承認（digest 束縛。main統合・push・デプロイ・restart・外部送信の解錠）」のうち **main統合・push を自動化する**。すなわちADR D1の現行境界と正面から衝突する。緩和しないのはD1の**残りの固定判断**（統治変更・再有効化・秘密・課金・外部公開範囲・不可逆削除・優先順位・停止指示）である。本設計の批准は2節に列挙する統治正本の改訂を伴い、改訂なしの批准では成立しない（fail-closed）。

## 1. 何を変えるか（Decision の要点）

現行の制約C5は「main統合・push・デプロイ・restart・外部送信は **カード単位の** digest束縛オーナー承認後のみ」である。本設計はこれを次へ置き換える。

> **C5'**: main統合（origin/main へのmerge・push）は、オーナーが**方針として承認した監査ゲート群**（決定論＋推論の両輪）を全通過した変更に限り自動で行う。デプロイ・restart は、観測窓・自動rollback（Phase C）に加え**非干渉検査 G8**（5節）を通過した場合に限り自動で執行できる（確定済みオーナー決定1、16節）。外部送信・統治面変更・不可逆操作は引き続きカード単位のオーナー承認（ADR D1）。オーナーは方針（本設計・Tierマニフェスト・上限値）と、その改定だけを承認対象とする。

自動化されるのは「承認の判断」ではなく「承認の**執行**」である。判断はオーナーが方針レベルで事前に行い、機械が個別インスタンスへ適用する。方針が答えられないケースは全て fail-closed でオーナーへ落ちる。

**push の位置付け（確定済みオーナー決定2、16節）**: GitHub への自動 push は条件付きで許可された。対象リポジトリが「organization によって管理される、または別の人間のユーザーが閲覧する」場合は非許可であり、その場合の統合段は agent-node local main までに縮退する。AIとオーナー個人のみが触る非公開リポジトリは許可。本リポジトリ（myurait/pda）は個人アカウント管理・オーナーとAIのみが利用する非公開リポジトリであり許可条件を満たす（オーナー確認 2026-08-29）。リポジトリの性質は方針ファイルの `auto_integration.repo_audience` へオーナーが記載し、統合実行器は値が `owner-and-ai-only` でない限り origin push を行わない（fail-closed。未記載も不許可）。

## 2. 批准に伴うオーナー作業（Phase A の entry 条件）

本設計の承認は、次の**オーナーがコミットする面**の改訂を同時に含む。いずれも `GOVERNANCE_PATHS`（`operations/improvement/scope_seed.py` ほか3実装が同一列挙を持つ機械的正本）配下または新規追加であり、実装フェーズの主体は書き込めない。改訂前に自動統合を起動してはならない。

統治正本の改訂:

- 統治ADR D1 第1項を、main統合・push の自動化を本設計のゲート群通過に条件づける形へ改訂する。ADRは自ら「この境界の変更は本ADRの改訂に固定する」と規定している（同文書13行目）。
- goal文書 C5 を C5' へ改定し、M4の運転条件へ自動統合の実測を組み込む。
- 運用細則（`docs/roadmap/autonomous-improvement-operating-rules.md`）4行目のADR D1参照を改訂後の境界へ整合させ、3節の負荷規律に自動統合パイプラインの資源契約（6節）を追記する。同細則の適用対象は現在「goal実行主体の作業運用」であり、自動統合パイプラインは対象外と読めるため、対象範囲の明記が必要。

`GOVERNANCE_PATHS` への追加（Tier G の実在化。B2/B9への対応）:

- 本設計（`docs/design/auto-integration-gate.md`）、M2設計、M3設計、`docs/operations/pda-improvement-cycle.md`、`docs/operations/worktree-lifecycle.md`。
- `schemas/` 配下（`verification-report-v1.schema.json`・`ai-invocation-audit-v1.schema.json` を含む検証・監査契約の正本）。
- `operations/backup/`、`src/pda/backup/`、`continuity/local-backup.json`（C3が「バックアップはworker/coreの書込権限外」と定める面。かつ `infra/systemd/pda-local-backup.service` の ExecStart は checkout 内のスクリプトを直接実行するため、merge + 同期だけで実行到達する）。
- `docs/status/` 配下（走行記録・反証レビュー記録・処置記録・ポストモーテム。監査可能性の証拠基盤であり、既存ファイルの改変も新規追加も自動レーンから外す）。`GOVERNANCE_PATHS` は前置一致で宣言段の拒否を行う列挙であり「既存ファイルのみ」という限定は表現できないため、この面は追加と同時に全体が Tier G になる（10節）。
- 本設計が参照する Tierマニフェスト・既知失敗リスト・G6パターン正本・回帰資産台帳（いずれも新設。パスは実装フェーズで確定し、確定と同時にオーナーが列挙へ追加する）。

方針ファイルは**新設しない**。既存の統治面ファイル `continuity/autonomous-improvement.json` に `auto_integration` 節（`enabled`、日次上限、Tier別窓、verdict有効期限、上限値）を追加する。新設すれば列挙外の面が生まれ、kill switch 面自体が自動統合可能域に入る。

契約seedの拡張（B5/B6への対応）:

- 契約seed payload（`operations/improvement/scope_seed.py` の `derive_seed_payload` / `record_seed`）へ **割当時base commit** を追加する。現在の payload は write_paths / test_paths / execution / git_write のみで、「割当時base」という値はどこにも保存されていない（Fact）。この値なしにはG1のスコープ再照合・G3のテスト浸食抽出・Tier導出の観測範囲が worker 申告の `base_sha` に依存し、検査範囲とmerge範囲が乖離する。`operations/improvement/` は統治面のためオーナーコミット。

## 3. 脅威モデル: 「自己破壊」の6軸

自動統合が守るべき対象を、実証済みの事故・実測に基づいて列挙する（各軸に対応するゲートを5節で定義）。

- **A1 行動退行**: 承認ゲートを通過した変更が本番挙動を壊す（Fact: b11e01c のstatus洪水、2026-08-22）。
- **A2 テスト浸食**: workerがテストを弱めて green を作る（Assumption: 未観測だが、実装者がテストへ書込可能な構造上、最も安価な偽装経路）。
- **A3 統治ドリフト**: 統治面への変更が通常変更に紛れる（Fact: rename によるdiff隠蔽はM1レビューで確証・修正済み。承認ゲートのdiffは `--no-renames` 取得と `changed_files` 完全一致で固定）。
- **A4 自己増幅**: 自動統合の仕組み自身（ゲート・上限・方針・検証契約スキーマ）を自動統合で弱める（憲章 C2/C4 が禁じる自己正当化）。
- **A5 品質腐敗**: 個々には無害な低品質変更の蓄積（ドキュメント腐敗・死コード・受入条件の未達・監査記録の摩耗）。
- **A6 資源暴走**: 統合パイプライン自体のAI起動・実行がクレジット/計算資源を浪費する（C6）。

## 4. パイプライン全景

カード1枚のライフサイクル（M1で実装済みの部分は「既存」と明記）。

```
起票 → ready（scope宣言必須・既存）
  → 割当: seed記録（+割当時base・2節）・隔離worktree・locked契約（既存・実運転済み）
  → 実装worker: scope内 write/test/local commit（既存）
  → 【新設 S1】worker完了合図 → 検証要求へ遷移（budget座礁時のhandoff契約を含む）
  → 【新設 S2】決定論ゲート束（5節）を封じ込め実行器で実行（6節）
  → 【新設 S3】独立検証者（推論ゲート、7節）: 読取専用clone・verified head固定
  → 【新設 S4】統合執行器（単一lease・8節）: verified head を origin/main へ統合
  → 【新設 S5】実行到達面の観測窓と自動rollback（9節、M3資産）
  → done + スレッド通知（M2要件と共通化）
```

S2〜S4 は worker の書込権限外で動く（C3）。worker は自分の成果を統合できず、検証者は自分が検証した変更の実装者になれない（C2の工程分離）。S2〜S4 が worker 著作コードを**実行**する箇所は6節の封じ込め契約に従う。

## 5. 決定論ゲート束（S2、全通過必須・fail-closed）

- **G1 スコープ再検証**: 統合候補diffが割当時契約（seed由来のwrite_paths/test_paths）の内側であることを、**割当時base（2節）から verified head まで**の全diffで再照合する。rename・mode変更・シンボリックリンク追跡を含む（M1承認ゲートの既存ロジックを流用）。worker申告の `base_sha` は入力に使わない。統治面パスは宣言段・承認段に続き第3回目の検査をここで行う（A3）。
- **G2 テスト全数**: 隔離worktreeでの focused test に加え、統合前に**スイートマニフェスト**（統治面のコミット済みファイル）が列挙する収集ルート上で全数実行する。判定規則:
  - 集合の定義: 収集ルートはマニフェスト列挙のみ。未追跡ディレクトリはGit正本に含まれないため収集対象外を明示する（`.gitignore` が `tmp/` を無視する運用がある）。ホスト依存で実行不能な収集ルート（開発PCで `hermes_cli` / `fastapi` 不在等）はマニフェストに実行ホストを併記し、実行ホストが揃わない場合は不通過。
  - 判定入力: プロセス終了コードと**収集件数・実行件数の両方**を必須にする。収集エラー・OOM kill・依存不足は「成功0失敗」と区別し、インフラ異常として不通過（自動統合しない・オーナーへ落とす）。
  - 既知失敗の扱い: 既知失敗は統治面のコミット済みリストで固定する。リスト外の失敗が1件でもあれば不通過。リスト内の失敗が消えた場合はリスト更新をオーナー作業として起票する。ベースライン比較（差分のみを見る運用）単独では、既に失敗していたテストを別要因で壊す変更を不可視にするため採らない。
- **G3 テスト資産の非弱体化**（A2）: 次を機械抽出する。
  - 収集集合の差分: 割当時baseと verified head の双方で `--collect-only` を封じ込め実行し、**収集テストID集合**を比較する。消失IDが1件でもあれば発火する。これによりテスト関数名の非 `test_` 化・parametrize候補の削減・ヘルパ/fixture側の無効化も捕捉する（assert文数の比較だけでは捕捉できない）。
  - 収集設定の変更: 収集範囲を変える設定ファイル（`pytest.ini` / `pyproject.toml` / `setup.cfg` / `tox.ini` / 任意階層の `conftest.py` / スイートマニフェスト）の追加・変更は自動統合対象外（Tier G相当・fail-closed）。Fact: 現リポジトリに pytest 設定ファイルは存在せず、収集集合は実行時引数だけで決まる。設定を新規に置く変更は「テストファイルへ触れるdiff」に該当しない。
  - テストファイル内の弱体化: skip/xfail の追加、既存テストの期待値変更、assert削減。
  - 発火時は推論ゲートS3へ「テスト変更の正当性」を必須論点として引き渡す。機械判定だけで拒否はしない（正当なテスト改修を止めない）が、S3が論点に答えない限り不通過。収集集合の消失を伴う場合はTierを1段昇格する。
- **G4 系譜と鮮度**: 統合候補が**割当時base（seed記録値）からの単一系譜**であること（他worktree混入なし）、verified head が現 origin/main へ衝突なく載ること。origin/main が進んでいればrebase後にG2の短縮版（変更影響スイート＋smoke）とG1・G3の再走を行う（rebase後のツリーは検査済みツリーと別物になるため、スコープとテスト浸食も再照合する）。
- **G5 規模上限**: Tier（10節）ごとのdiff行数・ファイル数・新規実行可能物の上限。超過は自動統合対象外（オーナー承認へ落とす）。
- **G6 秘密・資格情報スキャン**: 決定論パターンの正本は統治面のコミット済みマニフェストに置く（新規実装。`.env`系・資格情報パスの判定は既存スコープゲートの denial 規則を参照する）。マニフェストが未整備の間はG6を通過扱いにせず、自動統合そのものを開始しない（fail-closed）。
- **G7 行動回帰プローブ（縮退版）**: 回帰資産台帳（9節）が「その統合が到達する実行面」に対して宣言する最小プローブ束を、統合前に封じ込め環境でshadow実行する。台帳に登録の無い面への変更は「回帰資産なし」を明示してTierを1段昇格する（無いことを黙って通さない。M3の既存規定と同型）。M3完成後はM3の資産に置換する（A1）。
- **G8 非干渉検査**（確定済みオーナー決定1）: デプロイ・restart を伴う反映の直前に、**対象サービスに依存する進行中作業を止めないこと**を決定論的に検査する。少なくとも (a) running 状態のカード・生存worker の有無とその依存サービス、(b) オーナー直接指示で進行中の run・アクティブな対話セッション（Open WebUI 等の未終了run）の有無、(c) 統合キュー・検証者セッションの実行中有無、を確認し、干渉候補が1件でもあれば反映を延期して次の非干渉窓（または正常化窓）へ回す。merge済み・反映待ちの状態は保持したまま延期し、検査根拠と延期判断を統合記録へ残す。判定にAIを使わない。

## 6. 実行の封じ込めと資源契約（S2の前提）

**封じ込め（Fact に基づく必須要件）**: `integrations/hermes-scope-gate/scope_gate.py` は「許可されたコマンドのプロセス副作用は第一層の保証対象外であり、名前空間隔離と収集経路の静的検査はM2の必須要件（未実装）」と自ら記録し、`docs/operations/adversarial-suite.md` と2026-08-22の反証記録も同旨を固定している。統合実行器は origin への push 資格を持つ必要があるため、worker 著作コードを実行器と同じ主体で走らせるとゲート束の外側から統合が達成できる。よって次を Phase A の entry 条件とする（M2実装を待たない）。

- G2・G3・G7 が worker 著作コードを実行する箇所は、**push資格・agent-node同期資格・Kanban/承認ledger接続・秘密環境変数を一切持たない別主体**で実行する（専用の非特権ユーザー＋名前空間隔離。ネットワーク egress は既定拒否）。
- 収集経路の静的検査（マニフェスト外の収集ルート・設定ファイルの持ち込み）を実行前に行う。
- 封じ込め実行器が利用できないホストでは自動統合を開始しない（fail-closed）。統合実行器自身は worker 著作コードを自プロセスで一切実行しない。

**資源契約（M2運用細則の物理前提との整合）**: agent-node は12GiB・OOM実証済み（Fact、2026-08-22）。

- 1統合あたりの全数スイートは1回。rebase後は短縮版（変更影響スイート＋smoke）に限る。実行は常に直列・nice付きで、開始前に空きメモリ閾値を確認し、閾値未達なら統合を延期する（M2の `host_guard` を待たない最小版を Phase A で持つ）。
- 同一ホスト上のAI起動は同時1件。Tier 1以上の3レンズ反証は直列実行、または開発PC側で実行する。
- 上限値（日次統合件数・日次AI起動件数・カード当たり検証者起動上限）は方針ファイルに置き、オーナーコミットでのみ変更する。

## 7. 独立検証者（S3、推論ゲート）と来歴の束縛

- **主体分離と読取専用**: 検証者は、統合実行器が verified head から作る**読取専用clone**を読む（live worktreeへはアクセスさせない）。Fact: 同一ホスト・同一ユーザーで動くAIセッションに対する「読取専用」のプロンプト規律は強制力ではない（2026-08-22実証）。よって隔離はファイルシステム権限とセッション権限で行う: 検証者セッションはpush資格・Kanbanライフサイクル操作権限・書込可能な作業ツリーを持たない（terminal遷移claim束縛=既存も併用。Fact: review専用delegate childが保護用環境変数を自己解除して完了操作を強行した事象は2026-08-22の初回実運転で実証されたもので、2026-08-29のM1実運転で確証されたのは別の3件（budget座礁・無統制再試行・検証者未配線））。検証者向けの読取専用契約（write_paths空）を契約seed側に定義する。
- **反証スタンス**: 検証者への指示は「受け入れよ」ではなく「棄却理由を探せ」。出力は verdict スキーマ（accept / refute、根拠、確認した受入条件、G3から引き渡された論点への回答）。
- **verdict の出所固定（B4への対応）**: verdict は**統合実行器が検証者セッションの出力から直接収集して記録する**。worker が組み立てた承認metadataの `independent_verification` は自動レーンでは入力にしない（存在する場合は不通過）。Fact: 現行の検査は verifier/implementer の文字列不一致・verdict=pass・`verified_head_sha == head_sha`・checks非空のみで、実装側コメントも「別主体が検証を走らせた証明にはならない」と限界を明記している。digest承認という人間側の照合点が消えるC5'では、この自己申告レーンを閉じることが前提になる。
- **verified head の固定（B5への対応）**: 検証者へ渡す head は統合実行器が作る不変refで固定し、verdict はその commit に束縛する。S4 が統合するのは **verdict が指す commit のみ**で、branch先端が異なる場合は統合せずオーナーへ落とす（キューへ戻さない）。verdict には有効期限（方針値。初期案24時間）を置き、期限切れは再検証。Fact: M1実運転で dispatcher が同一worktreeへ第2 workerセッションを起動した実測があり、S3〜S4間にheadが動く経路は仮説ではない。
- **段階構成**: Tier 0 は単独検証者。Tier 1以上は3レンズ（正しさ／退行・互換性／セキュリティ）の反証で多数決。レンズ間で結論が割れた場合は不通過（オーナーへ落とす）。
- **C6適合と監査イベント**: 検証者の出力は統合判定に消費されるため、制限対象の「参照されない起動」に当たらない。Phase A では**統合実行器自身が**C6監査イベントの発行主体となり、`schemas/ai-invocation-audit-v1.schema.json` 準拠のイベントを `c6_audit.validate_ai_invocation` で発行前検証する（同モジュールは発行主体をM2と記すが、M2を待たない Phase A では発行経路を実行器が持たなければC6適合が検証可能な形にならない）。
- **起動回数の上限**: カード1枚あたりの検証者起動は Tier 0で1、Tier 1以上でレンズ数×1。rollback後の再実装に伴う再検証は同一カードで最大2回。以後はオーナーへ落とす。日次AI起動上限は方針値（A6。統合件数の上限は起動回数の上限ではない）。
- **検証の検証**: 検証者がaccept した変更が観測窓（9節）で rollback された場合、その検証記録を自動でポストモーテムカードへ添付し、検証プロンプト・レンズ構成の改訂対象とする（学習ループへの接続、X7）。

## 8. 統合執行器（S4）とトランザクション意味論

- **単一lease（B11への対応）**: 統合は常に1件ずつ。直列性は文書上の宣言ではなく機構で保証する。統合実行器は Kanban 上の単一lease（TTL付き・保持者記録）を取得できた場合のみ動作し、tick は前回実行中ならスキップする。TTL失効時の回収規定を持つ（回収は状態再導出後に行い、Git実状態を ground truth とする）。
- **起動経路（M6/M5への対応）**: Phase A の統合は**既存 router tick の1ステップ**として実装し、第2 dispatcher を作らない（M2設計原則P1）。したがって router timer の停止で統合も止まる。
- **正本の定義（M4への対応）**: **origin/main を唯一の正本**とする。運用細則は origin と agent-node の HEAD を別個の ground truth として扱う（Fact）ため、「現main」は origin/main を指す。統合を2段に分け、段ごとに帰結を分ける。
  - 統合段: origin から fetch → verified head を origin/main へrebase → G4/G1/G3/G2短縮版 → `merge --no-ff` → origin push。push成功で**統合済みとして確定**し、以後この段の再投入は行わない。段内の失敗はbranchを無傷のままキューへ戻す（2回失敗でオーナーへ落とす）。
  - 同期段: agent-node の checkout を ff同期。失敗は「統合済み・未同期」という別状態として記録し、同期のみ再試行してオーナーへ通知する（二重mergeを試みない）。agent-node が origin より先行している場合は ff同期が原理的に失敗するため、統合段の開始前に検査し、先行時は統合を開始しない。
  - オーナーへ落とす通知には失敗した段と到達状態を含める。
- **来歴の刻印（M3/M6への対応）**: merge commitにカードID・検証記録digest・ゲート結果digest・方針版数をtrailerとして残す。統合記録の正本は **Git（merge commit trailer）と Kanban（既存承認ledger行）の2面**とし、独立ファイルは再構築可能なキャッシュに限る（M2設計原則P3）。日次上限カウンタ・キュー滞留状態も盤面から導出し、固有永続状態を作らない。毎tickでGit trailerとledger行の突合を行い、不一致は自動統合を停止してオーナーへ通知する。Fact: ADR D3 は承認ledgerがKanban DB内にあり物理隔離が未達であることを明記している（確定済みオーナー決定4）。2面照合はこの残余に対する緩和であって解消ではない（Open Question 3）。
- **finalization契約との関係（m6への対応）**: S4の固定手順が正本。worker宣言の `finalization.steps` は自動レーンでは実行しない。`kind` / `targets` / `rollback` は Tier導出と自動rollback可否の入力としてのみ使い、宣言と実パス集合が矛盾する場合は不通過。
- **並走衝突の扱い**: 同一ファイルへ触れる複数カードが並走した場合、後続はrebase時のG4/G1/G3/G2短縮版で検出・再検証される。3回rebaseしても衝突が解けないカードは自動統合を断念しオーナーへ落とす。
- **worktree GC**: 統合成功後にworktreeとbranchを自動削除（`docs/operations/worktree-lifecycle.md` 準拠）。失敗時は保全。
- **budget座礁のhandoff契約（実測課題1の恒久対応）**: workerターンがtool budgetへ達した場合でも、(a) 完了合図1回はbudget外で常に許可する（冪等・1回限り）、または (b) 次ターンが前ターンの完了状態を機械的に回収する再開契約、のいずれかを実装する（Open Question 4）。**案(a)を採る場合の必須条件**: 非計上レーンは `docs/operations/adversarial-suite.md` が固定済み迂回クラスとして閉じた性質であり、ADR D5（統治変更を伴うリリースは次の迂回試行が遮断されることを回帰スイートで証明してからreviewへ載せる）に従い、免除レーンが class budget / tool budget で閉じること・免除経路の引数検査・run終端シグナルの契約検証を回帰スイートで先に固定する。

## 9. スケジュールと観測窓（S5）

**観測窓の接続先（B8への対応）**: 観測窓は「その統合が**実行到達する面**」に張る。merge + ff同期だけで挙動が変わらない面（installerが配備するgateway/dashboard等）の変動は当該統合と因果がなく、そこへ窓を張ると無関係な変更の誤rollbackと、実際の退行の見逃しが同時に起きる。M3設計も観測窓を「runtimeへ影響するfinalization」に紐づけている（Fact）。

- Tier 0（記録・文書のみ）: 観測窓を張らない。反映後観測が不要であることを明示する。
- checkout直接実行面（Fact: `infra/systemd/pda-local-backup.service` は checkout 内のスクリプトを直接実行する。同種のunitは統合＋ff同期がそのまま実行到達になる）: 該当面は10節で Tier 2 とし、かつC3によりバックアップ面は Tier G（2節の列挙追加）。統合後の観測窓は当該unitの次回発火を対象とし、プローブは当該面のものを使う。
- Tier 2 の反映（デプロイ・restart）: Phase C までは正常化窓でのオーナー承認執行。Phase C 以降は **G8（非干渉検査）通過を条件に自動執行できる**（確定済みオーナー決定1）。いずれも観測窓は**反映完了時点から**開き、窓の長さと閾値はM3の `risk_class` 別定義に従う。自動rollbackが成立しない面（本節の「前進のみの状態変化」）は自動執行の対象外。
- 判定は決定論のしきい値で行いAIを使わない。閾値超過で**自動rollback**: merge commit の revert のみ（force push・履歴書換・他統合の巻き添えは行わない）。M3実装までは「revert PR作成＋オーナー通知」に縮退する。

**rollback後の復帰（M8への対応）**: 自動実行してよいのは merge commit の revert に限る。宣言済み `finalization.rollback` のうち自動実行可の範囲はオーナー承認済み集合（M3の契約）に限り、両者の関係は「revertが既定、宣言手順は承認済み範囲でのみ追加実行」とする。revert 後の再統合は **割当時baseから新規branchを作り直す**（Gitはmerge済み変更を再適用しないため、同一branchの再mergeは成立しない。revertのrevertは行わない）。ファイル形式・スキーマ・ディスク生成物のように前進のみの状態変化を伴う変更は、down手順が宣言されない限り自動統合対象外（Tier昇格）。

**統合窓と日次上限**:

- Tier 0 は常時。Tier 1 は**観測完了時刻までがオーナー観測可能時間帯に収まる**よう、統合開始を 07:00-21:00 JST とする（観測窓30分を含めて22:00までに閉じる）。Tier 2 相当のデプロイ・restartは自動化せず、M2の正常化キュー（朝の正常化窓）へ積みオーナー承認で執行する。
- 自動統合は当初 **3件/日**（方針ファイルの上限値、変更はオーナーコミット）。上限到達後はキューに滞留し翌日へ持ち越す（A6）。
- **オーナーへ落とす総量の上限（m7への対応）**: 「2回失敗」「3回rebase不可」「レンズ不一致」「規模上限超過」「未分類パス」「インフラ異常」はすべてオーナーキューへ流れる。落とし物は分類別に日次1通へ集約し（M2のスレッド通知と共通化）、1日にオーナーへ提示する件数の上限を方針値に置く。超過分は滞留させ、自動レーンは停止しない。上限に達し続ける状態はゲート設計の欠陥として起票する。

**プローブの後始末・分離契約（M11への対応）**: G7・観測窓の各プローブは、M3の回帰資産台帳の宣言項目（対象surface、実行コマンド、消費クレジット目安、後始末契約=valve復元・外部通知抑止）を必須とする。加えて本番Kanban DB・承認ledger・runtimeへ接触しないこと（C7。試験用DBを使い、本番パス検出でfail-closed）。プローブが途中失敗した場合の残留状態（valve未復元・合成カード残留）を検出し、残留がある間は次の判定を行わない。

**注入演習（B10への対応）**: 演習は**専用surface・shadow branch（origin/main へのpushを伴わない）**で行い、演習であることをカードへ明示する（M3設計32行目の既存規定に従う）。本番main・本番台帳へは接触しない。演習の目的は「止まること」の実証であり、止まらなかった場合の帰結を実害にしない構成を先に用意する。

## 10. Tierマニフェスト（オーナー批准対象）

階層は**diffの実パス集合から決定論的に導出**する（workerの申告やカードの自己分類を使わない）。導出の正本は統治面の**コミット済みTierマニフェスト**（パス列挙）であり、意味カテゴリの定義文だけでは導出しない。複数階層に跨るdiffは最も厳しい側へ丸める。

- **未列挙パスの既定（M14への対応）**: マニフェストに列挙のないパスは **fail-closed でオーナーへ落とす**（推測分類をしない）。初版マニフェストで少なくとも次に置き場を与える: `schemas/`、`profiles/pda/skills/`、`docs/design/`、`docs/operations/`、`docs/status/`、`src/`、`operations/backup/`、`continuity/`、`personal_delegate_agent_plan.md`、`pda_minipc_setup_record.md`、`infra/`。
- **Tier 0 — 記録・文書の追加**（統治面を除くdocsへの**新規ファイル追加のみ**）: 自動統合可。単独検証者、G7省略可、常時窓、観測窓なし。**既存記録ファイルの変更・削除・行削除は Tier 0 に入らない**（走行評価・反証レビュー・処置記録・ポストモーテムはX6/X7の証拠基盤であり、不都合な項目の削除が最弱階層で通ってはならない）。既存ファイルへの変更はTier 1以上へ昇格する。`docs/status/` は2節の列挙追加により**全体が Tier G** となり Tier 評価に入らない（新規追加も自動レーン外。監査記録はオーナーコミット面）。Tier 0 に残る領域は統治面・`docs/status/` を除くdocsへの新規ファイル追加であり、Phase A exit の実カードもこの領域を対象とする。
- **Tier 1 — 非常駐コード**（テスト・ツーリング・runtime未接続のintegrations）: 自動統合可。3レンズ検証、G7必須、日中窓。
- **Tier 2 — 実行到達コード**（稼働gateway/dashboardが読み込む面、および**checkoutから直接実行される面**）: mergeまで自動可。デプロイ・restartは Phase C まではオーナー承認（正常化窓）、Phase C 以降は G8 通過で自動執行可（確定済みオーナー決定1）。観測窓必須。checkout直接実行面は反映操作を伴わずに実行到達するため、当該面のプローブと観測窓を必須とする。
- **Tier G — 統治面**: 自動統合**恒久不可**。集合は `GOVERNANCE_PATHS`（2節で追加した後の列挙）＋本設計＋方針ファイル＋Tierマニフェスト＋既知失敗リスト＋G6パターン正本＋回帰資産台帳＋検証者プロンプト。宣言段の拒否は**2節の列挙追加が完了して初めて成立する**（現行列挙には本設計・`schemas/`・`docs/status/`・`operations/backup/` が含まれない。Fact）。G1で第3回検査を行う。

**既存語彙との写像（M7への対応）**: Tier は既存の `risk_class`（`local-reversible` / `service-restart` / `external-visible` / `security-sensitive`）と `finalization.kind`（merge-only / merge-and-restart / apply-artifacts / no-runtime-change）を置き換えない。Tier は「自動統合の可否・検証深度・統合窓」を決め、**観測窓の長さと閾値はM3の `risk_class` 別定義に従う**。写像: Tier 0 → local-reversible / no-runtime-change。Tier 1 → local-reversible または service-restart（merge-only）。Tier 2 → service-restart / apply-artifacts。`external-visible` / `security-sensitive` は自動統合対象外。導出Tierと申告 `risk_class` が矛盾する場合は厳しい側を採り、矛盾自体を不通過事由とする。

## 11. 自己増幅の遮断（A4）と kill switch

- ゲート実装・方針ファイル・Tierマニフェスト・統合記録・検証者プロンプト・検証契約スキーマは全て Tier G に置き、workerの宣言可能域から恒久排除する（C3）。2節の列挙追加が完了するまでこの性質は成立しない。
- 統合実行器は方針ファイルの**コミット済み版**を二重確認する（routerのpolicy二重確認と同型。runtime複製の改竄では動かないことは既存の敵対テストで固定済み）。
- **kill switch と伝播（M5への対応）**: オーナーが `continuity/autonomous-improvement.json` の `auto_integration.enabled` を false でコミットすると、次の統合から全停止する（既存のサイクル停止と独立）。伝播は「統合実行器が各統合の直前に origin から fetch し、**origin/main のコミット済み版**を読む」ことで保証する（実行ホストのcheckout内容には依存しない。origin と agent-node の HEAD は別事実として扱われるため）。緊急時は router timer 停止でも止まる（8節により統合は router tick の1ステップ）。
- 方針の版数を全統合記録に刻み、方針改定前後の挙動を監査で分離できるようにする。

## 12. 実装フェーズ分割（Rollout）

- **Phase A entry（確定済みオーナー決定3: 前提を閉じてから着手）**: (1) 2節のオーナー作業（統治正本の改訂・`GOVERNANCE_PATHS` 追加・契約seedへの割当時base追加）、(2) 6節の封じ込め実行器、(3) M1実測課題2（無統制の自動再試行が同一worktreeへ第2セッションを起動する）の遮断、(4) M1実測課題1（budget座礁で完了合図が失われる。Open Question 4 の方式決定を含む）の解決、(5) M1正式完了記録（t_8aa3fd90）のclose。**全て閉じてから Phase A 実装へ着手する。**
- **Phase A**: Tier 0（新規ファイル追加）のみ・単独検証者・上限3件/日・router tick内の統合ステップ。最小構成: 検証者起動と verdict 収集＋決定論ゲート束＋単一lease統合器＋Git trailer/ledger2面記録＋C6監査イベント発行。exit: 実カード3枚がオーナー介入なしで docs 追加を統合し、注入演習1件（scope外diff・テスト弱体化・統治面接触の3種いずれか）が専用surfaceで止まる。
- **Phase B（M2オーケストレーター統合後）**: Tier 1 開放・3レンズ検証・イベント駆動キュー・スレッド通知接続。exit: 注入演習でG3（テスト浸食。収集集合の消失を含む）とG7（行動退行）の両方が機械捕捉される。
- **Phase C（M3統合後）**: 観測窓の自動rollback有効化・回帰資産のG7置換・Tier 2 のmerge自動化・Tier 2 反映（デプロイ・restart）のG8条件付き自動執行。exit: M3の注入演習（統合前または観測窓での機械捕捉・rollback実証）に加え、G8 が干渉候補（進行中のオーナー指示作業）を検知して反映を延期する実測1件。
- 各Phaseの開放はオーナー承認（実測証拠つきのgate報告）。上限値の緩和も同様。

## 13. 迂回テストの要求（ADR D5の適用）

本設計の実装は統治変更に当たるため、ADR D5 に従い、次の迂回試行が遮断されることを回帰スイートで固定してから review に載せる。固定対象は少なくとも: 封じ込め外でのテスト実行到達、収集集合の縮小（設定持ち込み・関数名変更・parametrize削減・ヘルパ無効化）、worker申告 verdict の自動レーン通過、verified head 以外の commit の統合、割当時base以外を起点にした検査、未列挙パスの推測分類、Tier 0 経由の既存記録改変、方針ファイル外の kill switch 面新設、lease 未取得での並行統合、非計上レーンの無制限化。新たに確定した迂回・欠陥は `docs/operations/adversarial-suite.md` と回帰資産台帳へ追加する（M3の学習ループ）。
