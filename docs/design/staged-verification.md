# 設計ドラフト: 段階検証と学習ループ (M3)

- Status: draft（M3 実装の設計入力。効力は M2 exit gate 通過後のオーナー承認で生じる）
- 日付: 2026-08-22
- 根拠: 2026-08-22 の実証「digest 束縛のオーナー承認を通過した成果が本番で行動回帰を起こした」（goal 文書 2.2 節）。承認は意図の確認であって挙動の保証ではない。挙動の保証は機械にやらせる。

## 構成要素

### 1. 行動回帰資産の台帳（regression asset registry）

- 既存の live probe 群（進捗表示・計画ゲート・中間表示・完了通知）を「対象 surface に紐づく行動回帰資産」としてリポジトリで台帳化する。各資産は、対象 surface、実行コマンド、消費クレジットの目安、後始末契約（valve 復元・外部通知抑止）を宣言する。
- 対象 surface に登録済み資産がある変更の finalization contract には、反映前の行動回帰検証ステップを必須で含める。検証の実行証跡（成功・失敗・出力の要約）はカードへ記録され、承認画面に表示される。
- 資産のないsurfaceへの変更は「回帰資産なし」を明示してから承認に進む（無いことを黙って通さない）。

### 2. 反映後の観測窓と自動 rollback

- runtime へ影響する finalization（restart 系・関数再インストール等）は、反映完了から risk_class に応じた観測窓を持つ。
  - 監視対象: 対象サービスの health、対象 surface のエラー・異常頻度（例: status 送出レート）、gateway ログの新規エラー。
  - 判定は決定論のしきい値で行い、AI を使わない。
- finalization contract は rollback 手順を事前宣言済み（既存契約）であることを前提に、観測窓内の異常検知で宣言済み rollback を自動実行してよい範囲をオーナーが承認する（「自動で戻してよい範囲」の確定は M3 のオーナー関与点）。
- rollback の実行・不実行はカードへ監査イベントとして残り、必ずポストモーテム起票につながる。

### 3. ポストモーテムの自動起票

- 起票契機: 自動 rollback、terminal 遷移の拒否イベント、ゲートの遮断イベント、承認の差戻し、観測窓異常。
- 起票内容: 事象・根拠イベント・影響 surface・再発防止の受入条件の雛形。idempotency key で重複起票を抑止し、未割当 triage に置く（自動実装はしない）。
- 再発防止が確定した迂回・欠陥は、敵対テストスイート（`docs/operations/adversarial-suite.md`）と回帰資産台帳へ追加する。これが学習ループの閉路になる。

### 4. 注入演習（seeded-defect drill）

- M4 の再有効化前に 1 回、既知の行動回帰を意図的に含む変更を専用の演習 surface でサイクルに流し、次のどちらかで機械的に捕捉されることを実証する: (a) 反映前の行動回帰検証で拒否される、(b) 観測窓で検知され自動 rollback される。
- 演習は本番 surface・本番台帳に触れない専用資産で行い、演習であることをカードに明示する。
- これが M3 exit gate の実証であり、以後は統治変更のたびに再演できる形で資産を残す。

## オーナー関与点

- 自動 rollback を許す範囲（risk_class 別）の承認。
- 観測窓の長さとしきい値の初期値の承認。

## 依存

- 観測窓と正常化キューの実行はM2オーケストレーターの機構を使う（`docs/design/improvement-orchestrator.md`）。
- 検証ステップの handoff への組込み形式は統治 ADR D2 の確定に従う。
