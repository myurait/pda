- 更新: 2026-09-22 JST
- 種別: 設計の提案。オーナーの決定ではない。決定が必要な事項は 10 節に列挙する。
- 物差し: `docs/requirements.md`（commit `a92a4ab`）。3.1 の契約 4 項目、コアの義務 7 項、コアと実行器の関係、4 節の A1〜A18。
- 根拠: `docs/research/` の調査 6 本。本文の「未確認」は、調査でも本提案の作成時にも一次資料で確かめていない事項を指す。

## 1. 全体像

コアにワークフローエンジンの Conductor を据える。フローは Conductor のワークフロー定義、セルは Conductor のタスク、type はタスク定義、共通の input/output ストアは Conductor のタスクキューに対応する。実行器はコンテナ 1 つに環境・アカウント・エージェントの組を閉じ込めたもので、その中のラッパーが Conductor のワーカーとしてキューから仕事を取り、ランタイムを動かし、成果を返す。実行器の能力は A2A の AgentCard を土台に欄を足した宣言ファイルで公開し、実行中の出来事はランタイムのフックから OpenTelemetry の形で外へ出す。コアの判定は Conductor のタスク定義に書く再試行・時間切れの規則と、入力スキーマの検査に限る。次に何をするかの判断は、先頭のセルである判定器（jev）が行い、その出力を Conductor の動的フォークがフローに反映する。

## 2. コア（Conductor）

### 2.1 要件の語との対応

| 要件の語 | Conductor での実体 |
|---|---|
| フロー | ワークフロー定義。実行中のインスタンスは Conductor が状態を持つ |
| セル | タスク。入力・出力・開始終了時刻・担当ワーカー・再試行回数がタスクごとに保存される |
| type | タスク定義（TaskDef）。名前、再試行、時間切れ、入出力スキーマを持つ |
| 共通の input/output ストア | タスクキュー。ワーカーが取りに来る（ポーリング）ので、要件の「ラッパーがストアから取り出す」と同じ向き |
| 仕事の状態の保持 | ワークフロー実行とタスクの状態。実行器に問い合わせず Conductor の記録だけで答えられる（A14） |
| 決定論的な規則 | タスク定義の再試行回数、再試行方式、再試行間隔、時間切れ秒数、応答時間切れ（心拍）、時間切れ時の方針、同時実行数、レート上限 |
| 発信の受理 | タスク定義とワークフロー定義に入出力スキーマを置けるが、Conductor OSS 3.32.4 は `enforceSchema` を実行系で読んでおらず検査しない（ソースで確認済み。増分 2 の評価）。検査はラッパーが入力と出力の両方で行い、合わなければ終端失敗で返す |
| 記録 | ワークフローとタスクの状態変化ごとに呼ばれるリスナー。Kafka、SQS、NATS、AMQP へ流す部品が同梱 |
| 可視化 | 同梱 UI。実行を図と時間軸で表示し、タスクごとに入力・出力・ログを見せる。実行履歴は OpenSearch か Elasticsearch に索引され検索できる |

### 2.2 フローの形

すべての仕事は同じ雛形のワークフローから始まる。

1. 判定器のセル（jev）。仕事の複雑さと必要なコンテキスト量を見て、次に走らせるセルの一覧（type と実行器）を出力する。
2. 動的フォーク。直前の判定器の出力に含まれるタスク一覧を読み、その数だけセルを生成して並列に走らせる。
3. 合流。生成したセルの出力を集める。
4. 判定器のセル。集まった出力を見て、続けるか終えるかと、続けるなら次のセル一覧を出力する。
5. 繰り返し。Conductor の DO_WHILE で 2〜4 を包み、判定器が「終える」と出すまで回す。

入れ子が要る場合は SUB_WORKFLOW で同じ雛形を子として呼ぶ。この形にすると、フローへの変更はすべて判定器のセルの出力から生まれ、Conductor は生成された子ワークフロー開始の記録に「どのタスクの完了が指示したか」を結び付けて残す。A17（変更の出所が追える）はこの記録で満たす。

### 2.3 セルへの入力の組み立て

Conductor はタスクの入力を、ワークフロー定義に書いた参照（前のタスクの出力の一部、ワークフローの初期入力の一部）から機械的に組み立てる。雛形の定義には、入力として「type の識別子」「直前セルの出力への参照」「初期入力への参照」だけを書き、プロンプトの文そのものは書かない。ラッパーが type の識別子から事前プロンプトを引く。これで「どのセルへの入力も、事前プロンプトと前段の出力だけから成り、コアが文を書き足していない」（A16）が、定義を読めば確かめられる形になる。

### 2.4 規則に無い事象

再試行回数の超過と時間切れは Conductor が決定論的に処理し、理由を状態に残す。入力スキーマ違反はラッパーが決定論的に検査し、終端失敗として Conductor に残す。ワーカー（ラッパー）が「再試行しても無駄」と判定した失敗は、終端失敗の状態で返す。それ以外の判断は Conductor に持たせず、次の判定器のセルへ入力として渡す。フォールバック経路（ある実行器が起動できなければ別の実行器へ）は、判定器のセル一覧に候補順を含めさせ、Conductor 側では失敗時に次の候補へ進むだけの分岐にする。

## 3. 実行器

### 3.1 単位

コンテナ 1 つ = 実行器 1 つ = 環境・アカウント・エージェントの組。実行器ごとに常駐のコンテナを 1 つ割り当てる。会社契約の Claude と個人契約の Claude は別コンテナで、認証情報の持ち込み先が違うだけで同じ形をとる。テスト、リンタ、ガードレールのような決定論的な検証ツールは、スクリプトを実行するホストとして 1 つのコンテナをまとめて割り当て、それを 1 つの実行器として扱う。到達できる資源はコンテナのマウントとネットワークの設定で閉じる。

最初の増分では、Conductor、ログストア、すべての実行器をミニ PC に置く。開発 PC のコネクタ権限が要る実行器を開発 PC に置くこと（A11）と、ネットワーク上にある実行器のセルへ接続する仕組みは、後の検討課題とする。

### 3.2 ラッパー

ラッパーは Conductor のワーカーであり、同時にランタイムの操作役である。1 つのラッパーが担う type の一覧は宣言ファイルと一致させる。

- Conductor のキューから仕事を取る。
- type の識別子から事前プロンプトを引き、直前セルの出力（または初期入力）と合わせてランタイムへの入力を作る。
- ランタイムを動かす。Claude Code、Codex、Gemini CLI は ACP（Agent Client Protocol）のアダプタ経由で操作する。ラッパーは ACP のクライアント側で、標準入出力越しにアダプタと話す。jev の HTTP API、Gemini の API、検証ツールは薄い専用の操作役で包む。
- ランタイムのフックと ACP の通知から出来事を拾い、閉じた種別に写して OpenTelemetry で送る。写せない種別に出会ったら、捨てずに「未知の出来事」として送る。
- ランタイムの出力を、フローへの指示、次のセルへの入力、仕事全体の成果の 3 つに分ける。前の 2 つの形に合わなければ成果とする。
- 出力を宣言した出力スキーマで検査してから Conductor に返す。Conductor はワーカータスクの出力スキーマを検査しない可能性があるため（未確認）、出力側の検査はラッパーの責務とする。
- 実行器が宣言した取れる state に従い、中断時に再開できるか再投入になるかを Conductor に返す状態で表す。

### 3.3 宣言ファイル

A2A の AgentCard の形（名前、できること、対応する通信方式、認証要件）を土台に、要件の能力の宣言に足りない欄を足す。

| 欄 | 内容 | 出所 |
|---|---|---|
| 担う type | このラッパーが受けるタスク定義の一覧 | 自作 |
| 費用 | 1 回あたりの金額の目安、時間の目安、レート上限 | SLA4OAI と OpenSLO の語彙を借りる |
| 到達できる資源 | ファイルシステム、ネットワーク、コネクタ権限の一覧 | 自作。コンテナ設定と同じ内容にする |
| 取れる state | 中断後に再開できるか、再投入になるか | 自作 |
| 環境・アカウント | どの機械で、どの契約で動くか | 自作 |

宣言は割り振りの根拠（判定器のセルへの入力）に使う。宣言と実態の一致は event stream と成果から後で確かめる。

## 4. event stream とログストア

三段で組む。ランタイムのフックと ACP の通知で拾い、OpenTelemetry のログとスパンの形で運び、出来事の種別は閉じた一覧（メッセージ出力、ツール呼び出し、ツール結果、判断、権限要求、未知、など）を自分で定める。Conductor のワークフローとタスクの状態変化も、リスナーから同じ受け口へ流す。これで可視化と監査が読む場所が一つになる（A5、A8）。

Conductor のタスクログ API を使い、セル内部の出来事の要約を各タスクに追記すると、Conductor の UI のログタブでセルごとに読める。詳細はログストア側に置く。

ログストアの実体（OpenTelemetry の受け口の後ろに何を置くか）は 10 節の決定事項。

## 5. 判定器

先頭のセルは jev。判定の種類ごとに問いの集合を用意し、jev の出力をセルの一覧（type、実行器の候補順）とフローへの指示に写す。割り振りの規則を成果とフィードバックで変える仕組みは、判定器のセルの問いの集合と事前プロンプトを更新することで実現し、更新は git の履歴に残す。

## 6. 正本と自己改変

次をこのリポジトリで版管理し、指示と規則の正本とする（3.2 の 8）。

- type の一覧と、type ごとの事前プロンプト
- タスク定義（再試行、時間切れ、入出力スキーマ）
- ワークフローの雛形
- 判定器の問いの集合
- 実行器の宣言ファイル

自己改変（3.2 の 5）は、この正本への変更として現れる。いつ、何を根拠に、何から何へ変えたかは git の履歴と、変更を提案したセルの出力の event stream で追い、元へ戻すのは git の操作で行う（A9）。

## 7. 可視化と UI

フローの層（どの仕事が、どの実行器で、どの順で進み、何を受け渡したか）は Conductor の UI がそのまま見せる。セル内部の出来事は 4 節のログストアを読む。Conductor の UI がスマートフォンで崩れないかは未確認で、崩れるならログストアを読む薄い画面を別に作る。ここは 10 節の決定事項。

## 8. 要件との対応

### 8.1 コアの義務 7 項

| 義務 | 担う部品 | 自作する部分 |
|---|---|---|
| 仕事の引き渡し | Conductor の入力組み立てとキュー | 雛形の定義 |
| 発信の受理 | ラッパーの入力検査と出力検査（Conductor は検査しない） | 3 分類の形式、ラッパーの検査 |
| 仕事の状態の保持 | Conductor | 無し |
| フローの保持 | Conductor のワークフロー定義と実行記録 | 変更の出所を event stream に写すリスナー |
| 中断と再投入 | Conductor の再試行・時間切れの規則、終端失敗 | フォールバック候補順の分岐 |
| 失敗の判定 | Conductor の時間切れ・心拍、ラッパーの形式検査 | 宣言した出力の種類との照合 |
| 記録 | Conductor のリスナーとイベント配送 | リスナーからログストアへの写し |

### 8.2 実行器の契約 4 項目

| 契約 | 担う部品 | 自作する部分 |

| 能力の宣言 | AgentCard の形、SLA4OAI と OpenSLO の語彙 | 宣言ファイルの形式と拡張欄 |
| 仕事の受け取り | Conductor のワーカー | ラッパー |
| 成果の返却 | Conductor のタスク完了 | 3 分類と出力検査 |
| event stream | ランタイムのフック、ACP の通知、OpenTelemetry | 出来事の種別の一覧と変換 |

「既存」は既存の部品だけで満たす、「一部」は既存の部品に自作を足して満たす、「自作」は自作が中心、を表す。

## 9. 自作が残る箇所

1. ラッパー。Conductor のワーカー、ACP のクライアント、フックからの出来事の変換、3 分類、出力検査を一つにしたもの。実行器の種類ごとに操作役だけが違う。
2. 宣言ファイルの形式と、それを判定器の入力に変える変換。
3. 出来事の種別の閉じた一覧と、フックと ACP の通知からの変換表。
4. Conductor のリスナーの実装。状態変化とフロー変更の出所をログストアへ写す。
5. type の一覧、事前プロンプト、雛形、問いの集合の正本と、それからタスク定義とワークフロー定義を生成する手順。
6. 監査の実行器。ログストアを読んで「言っていることとやったこと」の差を出す。
7. スマートフォン向けの画面。必要になった場合のみ。

## 10. 決定事項と未決事項

### 10.1 決定済み（2026-09-22、オーナー）

- 最初に作る範囲は、個人契約の Codex、会社契約の Claude、jev、決定論的な検証ツールの 4 実行器。移行（3.2 の 10）とペルソナ実行器の選定は範囲から外す。
- 会社契約の Claude をコンテナの中で動かしてよい。
- Conductor とログストアはミニ PC に置く。最初の増分では実行器もすべてミニ PC に置く。開発 PC への分離と、ネットワーク上の実行器のセルへの接続は後の検討課題。
- 実行器ごとに常駐のコンテナ 1 つ。決定論的な検証ツールのスクリプト実行ホストにも 1 つのコンテナを割り当て、1 つの実行器として扱う。

### 10.1.1 追加の決定（2026-09-23、オーナー）

- 会社契約の Claude は初期実装から外す。範囲は個人契約の Codex、個人契約の Claude、jev、決定論的な検証ツールの 4 実行器。会社契約は、4 実行器でコアが一連の動作をし、可視化層ができてから繋ぐ。理由は 3 つ。組織設定が確認なし実行をどの範囲で止めているかは実機でしか観測できない。ラッパーによる自動承認は組織の制御を迂回する運用になるので採らない。人が承認できる状態で待つには「ユーザー応答待ち」という状態と承認の受け皿と画面が要り、それは可視化層の仕事である。
- 個人契約の Codex と Claude は確認なし実行（全操作を許可）で動かす。権限要求が来た場合は記録だけ残す。
- 拒否するツール種別の一覧は空。仕組みは残すが原則使わない。何を避けるかは判定器が推論的に扱う。
- 作業ボリュームは全実行器で共有のまま。個人と会社の成果が混ざる懸念より、ディレクトリ境界で作業が完遂できない事故の方が初期には多いと見る。仕事ごとのサブディレクトリは、隔離ではなくセルに作業場所を渡すために切る。
- 繰り返しの上限（要件の未確定「セル追加の上限」）は、とりあえず 1 つの仕事につき判定器 10 回とし、判定器のラッパーが数えて打ち切る。

### 10.2 未決

オーナーの判断か、契約・環境の事実で決まる事項。回答が無いものは、括弧内の推奨で進める。

1. ログストアの実体。OpenTelemetry の受け口の後ろに何を置くか（推奨: 保存先を一つにし、Conductor の状態変化もそこへ写す。Conductor 自身の保存先は監査に読ませない。製品は最初の増分の設計で選ぶ）。
2. セル内部の出来事を Conductor のタスクログにも追記するか（推奨: 要約だけ追記し、詳細はログストアに置く）。
3. UI の当面の方針（推奨: Conductor の UI で進め、スマートフォン対応（A6）は表示を確かめてから決める）。
4. 決定論的な規則の初期値（推奨: Conductor の既定値で始め、セル追加の上限は運用でリスクが出てから足す）。
5. type の一覧と事前プロンプトの置き場所（推奨: このリポジトリで版管理し、指示の正本と兼ねる）。
6. 統合記憶の正本の置き場所と形式（移行の設計と一緒に決める）。

## 11. 未確認事項とリスク

- 実行器のコンテナ同士が同じポートを取り合う。ミニ PC と開発 PC のメモリ。
