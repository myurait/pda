# PDA v0.2 画面のモック（設計の成果物）

あなたはこのリポジトリで、PDA v0.2 の画面のモックを作る。この指示は完結している。質問はせず、最後まで作り、README を書いて終える。判断に迷ったら、この指示の「とりあえず」の決定に従う。指示に無いことは最も単純な選択を取り、README の「指示に無かった判断」に書く。

これは増分の実装ではない。動く製品を作るのではなく、設計を決めるために人が触って見るための静的な HTML のモックを作る。コア、ラッパー、既存の画面のコードには触れない。

## 0. 読むもの、読まないもの

作業前に次を読む。この指示と食い違う場合はこの指示を正とする。

- `docs/requirements.md` 要件の正本。語彙（タスク、実行、セル、実行器、判定器、type、報告、成果物、出来事、フロー、回）はここに従う。2 節の 2026-09-24 の発言、3.1 節の「タスクの状態」「タスクはスレッド」「オーナーの介入」、3.2 節の 6、7、11、12 が今回の画面の根拠
- `registry/executors/*.yaml` と `registry/types/*.yaml` 実行器と type の実名。見本データにはこの実名を使う
- `docs/design/increment-4.md` の 3 節と `src/pda_view/` 今ある画面。タスク、セル、出来事の中身の構造を知るためだけに読む。見た目と構成の参考にしない

次は読まない。`docs/reports/`、`docs/research/`、`docs/codex-runs/` の本指示以外のファイル、`main` 以外のブランチ。

## 1. 成果の置き場所

- 作業場所はミニ PC の `~/pda`（`origin` はミニ PC 上の `~/pda.git`）。`main` から分岐したブランチ `ui-mock` で作業する。`main` には触れない。最後に `git push origin ui-mock`
- 成果はすべて `docs/design/ui-mock/` の下に置く。この下以外のファイルを作らない、変えない。`src/`、`registry/`、`deploy/`、`tests/`、`tools/`、`docs/` の他のファイルは変更しない
- 区切りごとにコミットする。コミットメッセージは日本語で 1 文。`Co-Authored-By` 行を付けない
- `secrets/` と `deploy/.env` は Git 管理外の認証情報。読まない、写さない、変えない
- npm、ビルド工程、パッケージの追加をしない。画面の確認に Chromium を使うときは、増分 4 と同じく `uv run --no-project --with playwright` の一時環境を使い、プロジェクトの依存に足さない

## 2. 誰のための画面か

使う人はオーナー 1 人。主な端末はスマートフォンで、移動中に見て、短い指示や判断を返す。開発 PC でも同じ画面を使う。

オーナーが画面に求める見方は次の言葉のとおりで、画面全体、とくに実行器の一覧はこの視点で作る。

> リーダーがオフィスにいる部下を見渡して、席についているか、書類を書いているか、他のスタッフと議論しているか、ホワイトボードに書いていることの筋は通っていそうか、ざっくりと 30 秒で観察する。そうした視点で見通したい。

見せるのは全体像と「今何をしているか」であって、何をしたかを監査的に見ることではない。ツール利用の詳細な全出力は出さない。出来事の全列挙は画面に置かない。

## 3. 見た目の規則

- Datadog や AWS のコンソールのような、現代的で、明暗の差がはっきりした、余計な情報の少ない画面。背景と文字、状態を表す色の明暗差を大きく取る。装飾のための要素を置かない
- Unicode の絵文字をアイコンの代わりに使わない。アイコンが要るなら HTML に埋め込んだ SVG か、文字のラベルにする
- 外部の CDN、外部フォント、外部への要求を一切使わない。フォントはシステムフォント
- 文字はすべて日本語。文字の大きさは 14px 以上。文字はコピーペーストできる（画像化しない）
- 幅 375px で横スクロールが出ない。幅 1280px でも崩れない。この 2 つの幅の両方で全画面を作る
- 状態を表す語は要件の語をそのまま使う。タスクは進行中、入力待ち、完了、中止。実行は動いている、終わった、失敗した

## 4. 画面

5 つの画面を作り、画面の間をすべて実際のリンクで移動できるようにする。各画面は別の HTML ファイルにする（`index.html` はタスクの一覧）。画面の中の要素の並び順と配置は、あなたが設計して決める。ここに書くのは、各画面が見せるものとできることだけである。

### 4.1 タスクの一覧（`index.html`）

- タスクを 4 つの状態（進行中、入力待ち、完了、中止）で絞れる
- 各タスクに、指示文の先頭、状態、いまどのセルがどの実行器で何をしているか、経過時間、入力待ちならその理由（オーナーへの問いがある、自動で進める作業が無い、実行が失敗か中断で止まった）
- 新しいタスクを出す画面と、実行器の一覧と、オーナーへの問いの一覧への入口

### 4.2 指示を出す（`new-task.html`）

- 指示文の欄と、任意で作業ディレクトリの名前。回数の上限などの欄は置かない
- 出すと「受け付けた」状態が見え、そのタスクのページへ移る（モックでは見本のタスクのページへリンクする）

### 4.3 タスクのページ（`task.html`）

見せるものは 5 種。

- 報告。タスクがオーナー向けに書いた報告文。報告は必ずある。報告がまだ無い間は、何がどう進んでいるかの要約（現在の回、動いているセル、直近の中間出力の要点）
- 成果物。報告とは別の一覧。ファイル、git の所在（ブランチ、コミット）、外部への出力を、それぞれ開ける・持ち出せる形で並べる。報告の中のリンクだけを成果物への経路にしない。成果物が無いタスクもある。差分の中身をページに並べない
- オーナーへの問い。承認する・しない、選択肢から選ぶ、文で答える、の 3 形の返答の枠
- 指示の履歴。初期の指示と、重ねた指示。それぞれに、どの回から有効になったかの印
- 進行の図。回ごとの分岐と合流と、セルの箱。箱に type、実行器、状態、経過時間。箱を開くと、そのセルのプロンプト、直近の中間出力、使ったツールの一覧（名前と回数だけ）、経過時間。ツールの全出力は出さない

できることは 8 つ。モックでは実際には何も送らないが、押すとその操作が送られた状態（例: 「中断を送りました」）が画面に出ること。

- 動いている実行を中断する
- 指示を重ねる（次の回から有効。入力待ちのタスクなら、これで実行が再開する）
- セルを挿し込む（type と入力を書く）
- 動いているセルに追加入力を送る
- セルを再試行する（同じ type と入力。実行器はそのままか、選んで替える）
- 初期の指示を書き換える（「以後の回から有効」か「最初からやり直す」を選ぶ）
- 完了として記録する
- 中止として記録する

### 4.4 実行器の一覧（`executors.html`）

- 30 秒で見渡すための一枚。宣言された実行器（`registry/executors/*.yaml` の 6 つ）を並べ、生きているか、いま担っているセル（どのタスクの、何の type か）、経過時間、支える type、環境とアカウント
- 実行器を開くと、いまのプロンプト、直近の中間出力、使ったツールの一覧（名前と回数だけ）、経過時間
- 起こす・止めるの操作。押すとその操作が送られた状態が見える

### 4.5 オーナーへの問いの一覧（`inbox.html`）

- 入力待ちのタスクを横断して、問いと返答の枠を並べる。タスクのページの同じ部品を使う
- 返答すると、返答が送られた状態が見え、そのタスクのページへの経路がある

## 5. 状態の切り替え

整った状態だけのモックは評価できない。画面の端に小さな切り替えの操作を置き、次の状態を見られるようにする。切り替えの操作自体は目立たせない。

- タスクの一覧: 空、読み込み中、上流に届かない（失敗）、タスクが 50 件ある
- タスクのページ: 進行中、入力待ち（3 つの理由それぞれ）、完了、中止。報告がまだ無い。成果物が無い。指示が 5 回重なっている。回が 8 回ありセルが 30 個ある。報告文が長い（3000 字）
- 実行器の一覧: 全員が生きている。半分が止まっている。上流に届かない
- オーナーへの問いの一覧: 空、問いが 6 件

## 6. 見本データ

- 見本データは HTML から分離し、`data.js` に置いて、読み込むとグローバルの変数に値が入る形にする。JSON の別ファイルを `fetch` する形は `file://` で開くと失敗するので使わない
- `file://` で直接開いても、`python3 -m http.server` で配っても、同じに動く
- 実行器と type の実名は `registry/` のものを使う。タスクは 5 件以上で、4 つの状態と入力待ちの 3 つの理由を網羅する
- 意味の決め打ちを埋めない。「既定の実行器」「完了の基準」「しきい値」のような値を文言として書かない。見本データはあくまで見本で、差し替えられる

## 7. 要る情報の一覧（`docs/design/ui-mock/data-needs.md`）

モックと一緒に、画面ごとに、表示する要素それぞれについて次を表で書く。これが次の増分で API を設計する入力になる。

- 要る情報（1 行）
- 今の記録から取れるか。取れるなら出所を Conductor の記録、出来事の流れ、作業ディレクトリ、宣言ファイルのどれかで書く。取れないなら「新しく要る」と書く
- 更新の頻度（開いたときだけ、数秒ごと、操作したとき）

操作（4.3 の 8 つ、4.4 の起こす・止める、4.5 の返答）についても、何を送る必要があるかを 1 行ずつ書く。

## 8. 受け入れ条件

README に、次の条件を 1 つずつ合否で書く。確かめ方も書く。

- 5 つの HTML があり、画面の間の移動がすべて実際のリンクで辿れる（どの画面からもタスクの一覧へ戻れる）
- 幅 375px と 1280px の両方で、全画面で `scrollWidth` が幅を超えない（Chromium で確かめる）
- 全画面で最小の文字の大きさが 14px 以上
- 5 節に列挙した状態がすべて切り替えで見られる
- 4.3 の 8 つの操作、4.4 の起こす・止める、4.5 の返答のそれぞれで、押した後の状態が画面に出る
- 外部への要求がゼロ（Chromium のネットワークの記録で確かめる）
- Unicode の絵文字が HTML、CSS、JS、見本データのどこにも無い
- `file://` で開いたときと `http.server` で配ったときの両方で JavaScript のエラーがゼロ
- `data-needs.md` があり、5 画面の表と操作の一覧がある
