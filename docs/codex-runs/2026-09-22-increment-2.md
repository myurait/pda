## 2. 構成

`deploy/docker-compose.yaml` に次のサービスを定義する。compose のプロジェクト名は `pda-increment-2`。イメージの版はすべて固定し、報告書に列挙する。

| サービス | 内容 |
|---|---|
| conductor-server | Conductor OSS のサーバ。`conductoross/conductor:3.32.4` を使う（arm64 と amd64 の両方がある）。設定は同梱の `docker/server/config/config-redis.properties` に準じ、Redis と Elasticsearch を使う。設定ファイルはマウントで差し替える |
| conductor-redis | `redis:6.2` 系 |
| conductor-elasticsearch | `docker.elastic.co/elasticsearch/elasticsearch:7.17` 系。`ES_JAVA_OPTS=-Xms512m -Xmx1024m`。単一ノード |
| conductor-ui | Conductor の UI。`conductoross/conductor:3.32.4` のイメージには UI の静的ファイルと nginx が同梱されている。同じイメージからエントリポイントを nginx にして起動し、`/api` を conductor-server へプロキシする設定をマウントする。Java サーバは二重起動しない |
| otel-collector | `otel/opentelemetry-collector-contrib`。OTLP HTTP と gRPC を受け、`otlphttp` で openobserve へ、`file` で `/var/lib/pda/events/events.jsonl` へ出す。ファイルは 100 MB で回転。設定は `deploy/otel-collector.yaml` |
| openobserve | OpenObserve の公式イメージ。単一ノード。データは名前付きボリューム。初期ユーザーとパスワードは環境変数で与え、compose の `.env.example` に例を書く |
| exec-fake-a、exec-fake-b | 試験用の実行器。`pda_fake_agent` を ACP アダプタとして起動し、ラッパーがそれを操作する。実行器 ID は `fake-a`、`fake-b` |
| exec-tools | スクリプト実行ホスト。`pytest` と `ruff` を入れた Python イメージにラッパーを載せる。実行器 ID は `tools` |
| exec-jev | jev の実行器。実行器 ID は `jev`。`JEV_MODE=fixture` のとき API を呼ばず固定の答えを返す（8 節） |
| exec-codex-personal | Codex の実行器。`npx -y @agentclientprotocol/codex-acp` をアダプタとして起動する。認証ディレクトリを `/root/.codex` にマウントする。compose の既定では起動しない（profile `real`） |
| exec-claude-company | Claude Code の実行器。`npx -y @agentclientprotocol/claude-agent-acp@preview` をアダプタとして起動する。`CLAUDE_CONFIG_DIR=/claude-config` をマウントする。profile `real` |
| conductor-mirror | 9 節の写し |

規則。

- 実行器のコンテナはホストへポートを公開しない。公開するのは conductor-server の 8080、conductor-ui の 5000、openobserve の 5080 だけ。UI のホスト側ポートは環境変数で変えられるようにする（Mac では 5000 番を OS が使うことがある）
- 実行器ごとに内部ネットワーク（`internal: true`）を 1 つ作り、その実行器と conductor-server と otel-collector だけを乗せる。写しにも専用の内部ネットワークを作る。exec-jev、exec-codex-personal、exec-claude-company には外向きの通信のためのネットワークを別に足す。宛先ドメインの制限は Docker では掛からないので掛けない。報告書にその旨を書く
- Docker Desktop では内部ネットワークだけに乗ったコンテナのポート公開が到達しないので、公開する 3 サービスは内部でないネットワークにも乗せる
- 作業ディレクトリは名前付きボリューム `pda-work` を全実行器の `/work` にマウントして共有する
- 各実行器は環境変数 `PDA_EXECUTOR_ID`、`CONDUCTOR_URL`、`OTEL_EXPORTER_OTLP_ENDPOINT`、`PDA_REGISTRY_DIR=/registry` で設定する。`registry/` は読み取り専用でマウントする
- 実行器のコンテナは `init: true` とし、`stop_grace_period` を 20 秒にする
- 環境変数の名前にドットを使わない（エントリポイントのシェルが引き継がない）

## 3. 正本（registry）

### 3.1 `registry/types/{type}.yaml`

```yaml
type: implement
description: コードを書く、直す
prompt: prompts/implement.md
input_schema:  { JSON Schema。3.5 の共通入力に加えて type 固有の欄があれば書く }
output_schema: { JSON Schema。kind と payload と meta の形 }
task_def:
  retryCount: 3
  retryLogic: FIXED
  retryDelaySeconds: 10
  timeoutSeconds: 3600
  responseTimeoutSeconds: 600
  timeoutPolicy: TIME_OUT_WF
driver: acp        # acp | jev | tools
command: null      # driver が tools のときだけ。例: ["pytest", "-q"]
```

初期の type は 7 つ。`judge`（driver jev）、`break-down`、`implement`、`review`、`summarize`（driver acp）、`verify.test`（driver tools、command `["pytest", "-q"]`）、`verify.lint`（driver tools、command `["ruff", "check", "."]`）。

### 3.2 `registry/prompts/{type}.md`

type ごとの事前プロンプト。日本語で書く。内容は短くてよいが、次を必ず含める。「入力は `input` に与える」「出力は 1 つの JSON で、`kind` と `payload` を持つ」「`kind` は `input` か `result`」「フローへの指示は出さない（judge 以外）」。`judge.md` は jev には使わないので、判定器の役割の説明だけを書く。

### 3.4 `registry/judge/questions.json`

jev への問いの集合。問いの文面はすべて英語。state は日本語のままでよい。次の 4 問を Choice と Noul で書く。選択肢は正本から生成せず、ファイルに直接書く（type の一覧と実行器の一覧をそのまま書く）。`model` は `jev-latest`。

1. `is_complete`（Noul）: 集めた出力を見て、初期入力の仕事が完了しているか
2. `next_type`（Choice）: 次に必要な type。選択肢は break-down、implement、review、verify.test、verify.lint、summarize、none
3. `executor`（Choice）: その type をどの実行器で走らせるか。選択肢は実行器 ID の一覧。criteria に費用と到達資源を書く
4. `cell_count`（Choice）: 1、2、3

閾値は仮に置く（`is_complete` は 0.7）。実データでの検証は人が `jev-verify` で行うので、報告書に「未検証」と書く。

### 3.5 `registry/judge/fixture.json`

`JEV_MODE=fixture` のときの答え。回数は「これまでに動的セルが走った回の数」で決める（0 回目、1 回目、2 回目以降）。

- 0 回目: `then: continue`。cells は `break-down` を `fake-a` で（input_from `initial`）、`verify.test` を `tools` で（input_from `initial`）の 2 つ
- 1 回目: `then: continue`。cells は `summarize` を `fake-a` で（input_from `previous`）の 1 つ
- 2 回目以降: `then: finish`

fixture は 4 問の答えと cells の両方を直接書けるようにする（cell_count は 2 でも type は 1 つしか選べないので、fixture では cells を直接書く）。試験のために、環境変数 `PDA_FIXTURE_EXECUTOR` と `PDA_FIXTURE_TYPE` があるときは 0 回目の cells をその 1 つに差し替え、1 回目は finish にする。

### 3.6 共通入力の形

すべてのセルの入力は次の JSON。`context` の中身は自由。

```json
{"job_id": "…", "cell_id": "…", "type": "implement", "prompt_ref": {"id": "implement", "version": 1}, "input": "…", "context": {}}
```

判定器のセルだけは `input` の代わりに `initial_input` を受ける（5 節）。`context` は Conductor が省略時に null を渡すことがあるので、null は空オブジェクトとして扱う。

### 3.7 共通出力の形

```json
{"kind": "flow | input | result", "payload": {}, "meta": {"executor_id": "…", "declaration_version": 1, "trace_id": "…", "stop_reason": "end_turn"}}
```

`kind` が `flow` のときの `payload` は次の形。

```json
{"then": "continue | finish", "cells": [{"type": "…", "executor": "…", "input_from": "previous | initial"}], "dynamicTasks": [], "dynamicTasksInput": {}}
```

`then` が `continue` なら `cells` と `dynamicTasks` は 1 つ以上、`finish` なら空。これを judge の出力スキーマで強制する。

## 4. 定義の生成と登録（`tools/generate_defs.py`）

- すべての type × 実行器の組み合わせのうち、実行器の `types` に含まれるものについて、名前 `{type}.{executor_id}` のタスク定義を作る。`retryCount` などは type の `task_def` から取る
- `inputSchema` と `outputSchema` は Conductor の SchemaDef の形 `{"name": "<type>.input", "version": 1, "type": "JSON", "data": <JSON Schema>}` で埋め込む。`enforceSchema: true`
- 雛形のワークフロー定義を読み、そのまま登録する。`inputSchema` にワークフロー入力（`initial_input` は文字列必須、`context` はオブジェクト任意）を同じ SchemaDef の形で付ける
- Conductor の REST API（`GET/POST/PUT /api/metadata/taskdefs`、`GET/POST/PUT /api/metadata/workflow`）で登録する。既にあれば更新する。冪等にする
- `python tools/generate_defs.py --conductor http://localhost:8080 --registry registry/` で動く。`--dry-run` で生成物を標準出力に出す

## 5. 雛形ワークフロー

次の JSON を `registry/workflows/pda_job.json` に置く。Conductor 3.32.4 で動くことが確認されている形なので、変えない。

```json
{
  "name": "pda_job",
  "version": 1,
  "inputParameters": ["initial_input", "context"],
  "tasks": [
    {
      "name": "pda_loop",
      "taskReferenceName": "loop",
      "type": "DO_WHILE",
      "loopCondition": "$.judge['payload']['then'] == 'continue'",
      "loopOver": [
        {
          "name": "judge.jev",
          "taskReferenceName": "judge",
          "type": "SIMPLE",
          "inputParameters": {
            "type": "judge",
            "prompt_ref": {"id": "judge", "version": 1},
            "context": "${workflow.input.context}",
            "initial_input": "${workflow.input.initial_input}",
            "job_id": "${workflow.workflowId}"
          }
        },
        {
          "name": "branch",
          "taskReferenceName": "branch",
          "type": "SWITCH",
          "evaluatorType": "value-param",
          "expression": "then",
          "inputParameters": {"then": "${judge.output.payload.then}"},
          "decisionCases": {
            "continue": [
              {
                "name": "fork",
                "taskReferenceName": "fork",
                "type": "FORK_JOIN_DYNAMIC",
                "dynamicForkTasksParam": "dynamicTasks",
                "dynamicForkTasksInputParamName": "dynamicTasksInput",
                "inputParameters": {
                  "dynamicTasks": "${judge.output.payload.dynamicTasks}",
                  "dynamicTasksInput": "${judge.output.payload.dynamicTasksInput}"
                }
              },
              {"name": "join", "taskReferenceName": "join", "type": "JOIN"}
            ]
          },
          "defaultCase": []
        }
      ]
    }
  ]
}
```

Conductor の記録について分かっていること。

- 繰り返しの中のタスクは参照名に `__1`、`__2` の接尾辞が付く（`judge__1`、`c1__1`）
- 繰り返し条件の式では、ループ内タスクの出力が参照名の直下に置かれる（`$.judge['payload']`）
- 動的フォークのタスク記録は `taskType` が `FORK`、`workflowTask.type` が `FORK_JOIN_DYNAMIC`。フォークの `inputData.dynamicTasks` に展開したセルの定義が入る
- 応答時間切れは `status` が `TIMED_OUT`、`reasonForIncompletion` が「responseTimeout: 30 exceeded for the taskId: …」の形。再試行は同じ参照名で新しい `taskId` が作られ、`retryCount` が増え、`inputData` は同一
- 終端失敗は `status` が `FAILED_WITH_TERMINAL_ERROR`、`reasonForIncompletion` にワーカーが返した理由が入る

判定器のラッパーは `GET /api/workflow/{job_id}?includeTasks=true` で自分のワークフローの記録を読み、直前の回の動的フォークが生んだタスク（参照名が `c` で始まるもののうち、最も新しい回のもの。同じ参照名に複数の試行があれば `retryCount` が最大のもの。`COMPLETED` のものだけ）の出力を集めて state にする（8 節）。

## 6. ラッパー（`src/pda_wrapper/`）

### 6.1 起動とポーリング

`python -m pda_wrapper` で起動する。単一プロセス、単一スレッドの asyncio。Conductor Python SDK は使わず、httpx で REST API を直接叩く。

1. 起動時に `PDA_EXECUTOR_ID` の宣言ファイルと正本の全 type を 1 回だけ読む。以後は読み直さない
2. ループ。各タスク名を順に `GET /api/tasks/poll/{name}?workerid={executor_id}` で取る。タスクが無ければ（204 か空）次のタスク名へ。全部無ければ 500 ミリ秒待つ
3. タスクを 1 つ取ったら 6.2 で処理し、`POST /api/tasks` に TaskResult（`workflowInstanceId`、`taskId`、`workerId`、`status`、`outputData`、`reasonForIncompletion`）を送る。処理中は他のタスクを取らない（1 実行器 1 タスク）
4. 期限。取ったタスクの JSON にある `responseTimeoutSeconds` を使う（無ければ正本の `task_def` の値）。処理開始からその値の 10 秒手前（10 秒未満になるなら値の半分）でランタイムを止め（ACP は `session/cancel` と子プロセスの終了、tools は子プロセスの終了）、`FAILED` を理由 `runtime_deadline` で返す。リース延長はしない
5. 停止。SIGTERM を受けたら、処理中のタスクがあればランタイムを止め、`FAILED` を理由 `interrupted` で返し、出来事を送り切ってプロセスを終える。処理中でなければ即終える。SIGTERM 後にポーリングしない

### 6.2 1 タスクの処理

1. タスクを受け取る。`job.received` を記録する
2. 入力を type の `input_schema` で検査する。落ちれば `output.rejected`（理由 `input_schema_mismatch`）を記録し `FAILED_WITH_TERMINAL_ERROR`
3. `prompt_ref` から `registry/prompts/{id}.md` を読む。`input` と `context` と合わせてランタイムへの入力を作る。`input.assembled` に `prompt_ref` と入力の SHA-256 と `context` のキー一覧を記録する。文は記録しない
4. type の `driver` に応じた操作役（7〜8 節）でランタイムを動かす
5. 出力を分類する（6.3）。`meta` を付け、分類した種別の出力スキーマで検査する。通れば `output.classified`、落ちれば `output.rejected` を記録し、`FAILED_WITH_TERMINAL_ERROR` で返す
6. 出力の要約 1 行（kind と payload の先頭 200 字）を `POST /api/tasks/{taskId}/log` に送る
7. `COMPLETED` で返す。`outputData` は 3.7 の形そのもの

例外はすべて捕まえ、想定内（ランタイムの失敗、期限、中断）は `FAILED`（再試行あり）、想定外（ラッパー自身のバグ）は `FAILED_WITH_TERMINAL_ERROR` で返す。どちらも `unknown` の出来事に理由を残す。

### 6.3 分類

ランタイムの出力（文字列）を次の順で判定する。

1. JSON として読め、`kind` が `flow` で 3.7 の flow の形に合う。ただし type が `judge` でない実行器からの `flow` は拒否（`output.rejected`、理由 `flow_from_non_judge`）
2. JSON として読め、`kind` が `input` か `result` で、`payload` を持つ。そのまま採用
3. JSON として読めるが `kind` が無い。`{"kind": "result", "payload": <そのJSON>}` に包む
4. JSON として読めない。`{"kind": "result", "payload": {"text": <文字列>}}` に包む

jev と tools の操作役は自分で 3.7 の形を作るので、分類は 1 と 2 だけ通り、3 と 4 は拒否する。

### 6.4 出来事（event stream）

OpenTelemetry の Python SDK を使う。トレース ID は `sha256(job_id)` の先頭 128 ビット、スパンはタスク 1 つに 1 つで、スパン ID は `sha256(task_id)` の先頭 64 ビット。出来事はログレコードとして送り、属性に必ず `pda.event.kind`、`pda.job_id`、`pda.cell_id`（task の reference name）、`pda.task_id`、`pda.executor_id`、`pda.type` を付ける。送り先は `OTEL_EXPORTER_OTLP_ENDPOINT`（HTTP）。同じ内容を標準出力に JSON 1 行で出す。

種別と追加属性は次の表に限る。表に無い出来事を作らない。写せないものは `unknown` に元のデータを `pda.raw`（JSON 文字列、10 KB で切る）として入れる。

| 種別 | 出所 | 追加属性 |
|---|---|---|
| job.received | ラッパー | Codex の実行器では pda.agent_mode（起動時の権限モード） |
| input.assembled | ラッパー | pda.prompt_id、pda.prompt_version、pda.input_sha256、pda.context_keys |

## 7. ACP の操作役（`drivers/acp.py`）

ACP の Python SDK（PyPI `agent-client-protocol`、0.12 系）のクライアント側を使う。`acp.spawn_agent_process(client, command, *args, env=..., observers=[...])` が子プロセスの起動と接続を提供する（`observers` は接続へそのまま渡される引数）。JSON-RPC を自前で書かない。

1. 宣言ファイルの `adapter.command` を子プロセスとして起動する。環境変数は `adapter.env` を足す。作業ディレクトリは `/work`
2. `initialize` を送る
3. `session/new` を `cwd=/work` で送る
4. `session/prompt` で、事前プロンプトと入力を連結した 1 つのテキストブロックを送る
5. `session/update` の通知を受けるたびに 6.4 の表に写す。SDK の型検査より前に生の通知を受け取り（observer）、知らない `sessionUpdate` は `unknown` にする
6. `session/request_permission` が来たら、宣言ファイルの `permissions` に従って答える。`default: allow_once` なら `allow_once` に当たる選択肢を選ぶ。`deny_kinds` に該当するツール種別なら `reject_once`。該当する選択肢が無ければ cancelled で答える。答えた内容を `permission.response` に記録する
7. 応答の `stopReason` を `turn.end` に記録し、`meta.stop_reason` に入れる
8. `agent_message_chunk` のテキストを連結したものをランタイムの出力とする
9. 期限か中断が来たら `session/cancel` を送り（2 秒待つ）、子プロセスを終了する。`turn.end` を `cancelled` で記録する
10. 1 セッションは 1 タスクで使い捨てる。子プロセスはタスクごとに起動して終了する
11. 子プロセスの標準エラーは出来事にしない。ラッパーの標準出力にログとして流す。ランタイムが失敗したときだけ、末尾 20 行を失敗の `unknown` の `pda.raw` に含める

Codex のアダプタは起動時の `INITIAL_AGENT_MODE` で権限モードを決める。`session/request_permission` が来るかどうかは不明なので、来たら 6 のとおり答え、来なくても `job.received` の属性に `pda.agent_mode` を入れる。

### 7.4 試験用エージェント（`src/pda_fake_agent/`）

ACP のエージェント側を Python SDK で実装する。`session/prompt` を受けると次を順に行う。`agent_thought_chunk` を 1 つ、`tool_call`（kind `read`、title `read /work/README`）と `tool_call_update`（status `completed`）を 1 組、`agent_message_chunk` で応答本文、`stopReason: end_turn` で終える。応答本文は環境変数 `FAKE_MODE` で切り替える。

- `echo`（既定）: `{"kind": "input", "payload": {"text": "<受け取ったプロンプトの末尾 100 字>"}}`
- `invalid`: `kind` が `bogus` の JSON。A13 の試験に使う
- `slow`: 応答前に `FAKE_SLEEP_SECONDS`（既定 700）秒待つ。`session/cancel` を受けたら待ちを打ち切り `stopReason: cancelled` で返す。期限と中断の試験に使う
- `permission`: 応答前に `session/request_permission` を 1 回送る

## 8. jev の操作役（`drivers/jev.py`）

TypeSafe の jev API を呼ぶ。送信の形は次のとおり。手元の `~/.claude/skills/jev-judge/scripts/jev_judge.py` が読めれば照合し、食い違えば手元のスクリプトを正として報告書に書く。

- `POST https://api.typesafe.ai/v1/systemone`、ヘッダ `Authorization: Bearer <API キー>`、`Content-Type: application/json`
- 本文は `{"state": <state>, "model": "jev-latest", "questions": <questions.json の questions>}`
- 応答は `{"answers": {"<問いの ID>": {"noul": 0.8} または {"choice": "…", "confidence": 0.9}, …}}`
- API キーは環境変数 `TYPESAFE_API_KEY`、無ければ `/secrets/typesafe_credentials` の `API_KEY=` 行

処理。

1. `job_id` のワークフローを `GET /api/workflow/{job_id}?includeTasks=true` で読む。直前の回の `c` で始まる参照名のタスクの `outputData` を集める（5 節の規則）。無ければ空。これまでに動的セルが走った回の数も数える
2. state を作る。`{"initial_input": …, "context": …, "previous_outputs": [ {cell_id, type, executor, kind, payload} ], "executors": [宣言ファイルの一覧], "types": [type の一覧]}`
3. `registry/judge/questions.json` の 4 問を送り、答えを読む。`JEV_MODE=fixture` なら API を呼ばず fixture の答えを使う（3.5 節）
4. `is_complete` が閾値以上、または `next_type` が `none` なら `then: finish`、`cells: []`。そうでなければ `then: continue` で、`cell_count` の数だけ `{type: next_type, executor: executor, input_from: previous}` を並べる（前の回が無ければ `input_from: initial`）。fixture は cells を直接与える
5. `cells` の各要素について、type が正本にあり、実行器が宣言されていて、その実行器の `types` に type が含まれることを確かめる。外れていれば `FAILED`（理由 `judge_selected_unsupported_pair`）
6. `cells` から `dynamicTasks` と `dynamicTasksInput` を生成する。参照名は `c1`、`c2`…、name は `{type}.{executor}`、type は `SIMPLE`。入力は 3.6 の形で、`input` には `input_from` が `previous` なら前の回の出力の `payload` を参照名の順（`c1`、`c2`…）に JSON 文字列にして改行で連結したもの、`initial` なら `initial_input`
7. `then` が `continue` で `cells` が空なら `then` を `finish` に変え、`judge.answer` に `pda.question_id: next_type`、`pda.answer: finish:empty_cells` を残す
8. 4 問それぞれの答えを `judge.answer` に記録する
9. `{"kind": "flow", "payload": {...}}` を返す。`meta` はラッパーが付ける

## 9. tools の操作役と写し

### 9.1 tools（`drivers/tools.py`）

type の `command` を、`input` が JSON で `workdir` を持てばそこで、無ければ `/work` で走らせる。6.1 の期限で打ち切る。`command.run` を記録し、`{"kind": "result", "payload": {"passed": <exit_code == 0>, "exit_code": …, "stdout_tail": <末尾 4000 字>, "stderr_tail": <末尾 4000 字>}}` を返す。

### 9.2 写し（`src/pda_mirror/`）

3 秒ごとに Conductor を読み、前回との差分を出来事にする。

1. `GET /api/workflow/running/pda_job` で実行中のワークフロー ID を得る。加えて、前回実行中だったが今は無い ID を 1 回だけ読む（最終取得）。最終取得が HTTP エラーなら次回に持ち越す
2. 各 ID を `GET /api/workflow/{id}?includeTasks=true` で読む
3. ワークフローの `status` が変わっていれば `engine.workflow`（pda.status、pda.reason に `reasonForIncompletion`）
4. タスクごとに `status`、`retryCount` が変わっていれば `engine.task`（pda.status、pda.retry_count、pda.reason に `reasonForIncompletion`、pda.worker_id、pda.task_def_name）
5. 動的フォークが生んだタスク（参照名が `c` で始まる）には pda.origin_cell に、生んだ判定器の参照名を入れる。同じ回のフォークの `inputData.dynamicTasks` と判定器の `outputData.payload.dynamicTasks` が一致することで辿る。辿れなければ `unknown`
6. 最終取得を終えたワークフローの記録（状態とタスクの状態）は捨てる。記録を持ち続けない

トレース ID とスパン ID の作り方は 6.4 と同じにし、ラッパーの出来事と同じトレースに並ぶようにする。写しの出来事の `pda.executor_id` は、タスク定義の名前が `{type}.{executor}` ならその実行器、それ以外は `engine`。

## 10. 部品ごとの受け入れ条件

報告書に、次の条件を 1 つずつ合否で書く。確かめ方も書く。

- 正本: 7 type、6 実行器、4 問、fixture 3 段、雛形が揃い、すべての JSON Schema が Draft 7 として有効
- 定義の生成と登録: 19 のタスク定義と 1 つのワークフロー定義が生成され、2 回続けて登録して両方成功する。`--dry-run` が Conductor 無しで動く
- ラッパーの起動とポーリング: 起動時に正本を 1 回だけ読む。宣言した type のタスク名だけをポーリングする。SIGTERM 後にポーリングの HTTP 要求が出ない（単体試験で httpx のモックか子プロセスで確かめる）
- ラッパーの期限: `responseTimeoutSeconds` を 30 にしたタスク定義で slow の実行器を動かすと、20 秒でランタイムが止まり、タスクが `FAILED` 理由 `runtime_deadline` になり、`turn.end` が `cancelled` で残る
- ラッパーの停止: 処理中に SIGTERM を受けると、`session/cancel` が送られ、タスクが `FAILED` 理由 `interrupted` になり、プロセスが 20 秒以内に終わる
- 分類とスキーマ検査: 6.3 の 4 段と拒否 2 種（`flow_from_non_judge`、`invalid_kind_or_missing_payload`）が単体試験で通る。judge の出力スキーマが `continue` で空の cells を拒否する
- 出来事: 表の全種別が単体試験で生成でき、表に無い種別を渡すと `unknown` になる。トレース ID とスパン ID が sha256 から決定的に出る
- ACP の操作役: 試験用エージェントの 4 モードすべてと実際に往復する単体試験が通る。子プロセスの標準エラーが出来事に入らない
- jev の操作役: fixture の 3 段が state の回数で切り替わる。API の要求の形（URL、ヘッダ、本文のキー）がモックで確かめられる。未対応の type と実行器の組を拒否する
- tools の操作役: 終了コード 0 と非 0 の両方で `passed` が正しく、`workdir` が入力から取れる。期限で子プロセスが止まる
- 試験用エージェント: 4 モード。slow が `session/cancel` で打ち切られる
- 写し: 差分だけを出来事にする。最終取得を 1 回だけ行い、その後記録を捨てる。origin_cell を辿る
- compose: 実行器のポートが公開されていない。実行器のネットワークが分離されている（fake-a のコンテナから openobserve に到達できないことを確かめる）

## 11. 試験

`tests/unit/` に 10 節の単体試験。`tests/e2e/` に compose を使う試験。e2e は `PDA_E2E=1` のときだけ動く。

e2e の筋書き。`docker compose up -d`（profile `real` は上げない）、`generate_defs.py` を実行、次を順に確かめる。

1. `POST /api/workflow` で `pda_job` を `initial_input: "README を要約せよ"` で開始する。fixture により 0 回目に `break-down.fake-a` と `verify.test.tools`、1 回目に `summarize.fake-a` が走り、2 回目に finish して `COMPLETED` になる。`summarize.fake-a` の `inputData.input` が、0 回目の 2 セルの出力の `payload` を JSON 文字列にして改行で連結したものと一致する（A12）。判定器が 3 回（`judge__1`〜`judge__3`）走る
2. `/var/lib/pda/events/events.jsonl`（compose のボリュームから読む）に、この job_id について `job.received`、`input.assembled`、`tool.call`、`tool.result`、`turn.end`、`output.classified`、`command.run`、`judge.answer`、`engine.task`、`engine.workflow` が 1 件以上ずつあり、動的セルの `engine.task` に `pda.origin_cell` が判定器の参照名で入っている（A17）。すべて同じトレース ID
3. OpenObserve の検索 API に SQL で問い合わせ、同じ job_id の行が返る
4. `FAKE_MODE=invalid` の exec-fake-b に向けたセル（`PDA_FIXTURE_EXECUTOR=fake-b`、`PDA_FIXTURE_TYPE=implement`）が `FAILED_WITH_TERMINAL_ERROR` 理由 `invalid_kind_or_missing_payload` になり、`output.rejected` が残る（A13）
5. ワーカーが消えた場合の応答時間切れ。`implement.fake-b` のタスク定義を試験用に `responseTimeoutSeconds: 60`、`retryCount: 1`、`retryDelaySeconds: 1` に更新し、`FAKE_MODE=slow` の exec-fake-b に向けたセルを開始し、タスクが `IN_PROGRESS` になったら `docker compose kill exec-fake-b` で止める。Conductor が `TIMED_OUT` にした後、exec-fake-b を `FAKE_MODE=echo` で起動し直し、再試行が `COMPLETED` になる。1 回目と 2 回目の `inputData` が同一で、`engine.task` に `retry_count` の増加と `reason` が残る（A15、A18）。終わったらタスク定義を元に戻す
6. ラッパーの期限。同じ試験用定義（`responseTimeoutSeconds: 60`）で `FAKE_MODE=slow` の exec-fake-b を止めずに動かす。50 秒でラッパーがランタイムを止め、1 回目のタスクが `FAILED` 理由 `runtime_deadline` になり、`turn.end` が `cancelled` で残る。確かめたらワークフローを `DELETE /api/workflow/{id}` で終わらせ、タスク定義を元に戻す
7. スキーマの強制。`initial_input` を欠いた入力で `POST /api/workflow` を呼び、応答の HTTP 状態と本文を記録する。受け付けられた場合は、ワークフローが `COMPLETED` にならないことを確かめる
8. `docker stats --no-stream` の結果を保存する

証拠の分量。`docs/reports/evidence/increment-2/` に置くのは抜粋だけ。ワークフローの記録は `workflowId`、`status`、`reasonForIncompletion` と、各タスクの `referenceTaskName`、`taskDefName`、`taskType`、`status`、`retryCount`、`reasonForIncompletion`、`responseTimeoutSeconds`、`workerId`、`iteration`、`inputData`、`outputData` だけを残す。出来事はその job_id の行だけ。1 ファイル 300 行まで。
