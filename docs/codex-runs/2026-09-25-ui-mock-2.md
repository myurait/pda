# PDA v0.2 画面の UX 設計とモック（作り直し）

あなたはこのリポジトリで、PDA v0.2 の画面の UX 設計を行い、その設計を実際に触れるモックとして作る。この指示は完結している。質問はせず、最後まで作り、README を書いて終える。判断に迷ったら、この指示の決定に従う。指示に無いことは、1 節のシステムの目的と 3 節のユースケースに照らして最も素直な選択を取り、設計書の「指示に無かった判断」に理由と一緒に書く。

これは増分の実装ではない。コア、ラッパー、今ある画面のコードには触れない。作るのは、オーナーが触って体験し、画面の設計を決めるためのモックと、その設計書である。

見た目を整えることが仕事ではない。この画面を使う人が何をしたくて来るのかを解釈し、それを画面と動線と操作に分解することが仕事である。要素を並べただけのページはデザインではない。

## 1. このシステムは何のためにあるか

PDA は、オーナー 1 人のための、AI への仕事の指令所である。

オーナーは Codex、Claude Code、jev など複数の AI を、会社と個人の複数のアカウント、ミニ PC や開発 PC など複数の環境で使っている。PDA はそれらを「実行器」という同じ形に揃え、タスクを適切な実行器に割り振り、実行器同士の受け渡しを組み立て、最終的な成果をまとめる。次に何をするか、どの実行器に渡すかは判定器（jev）が判断し、コアはそれに従ってフローにセルを足す。

旧 PDA が失敗したのは、ツールごとに画面と指示がばらばらで、仮想ターミナルの画面を主にし、スマートフォンでは崩れ、実行器同士が何をやりとりしたかが見えなかったからである（要件 1 節）。v0.2 の画面は、その逆を実現する。

オーナーがこの画面でしたいことは次の 5 つである。

1. どこからでも（主にスマートフォンから）タスクを出す
2. 30 秒で全体を見渡し、誰が何をしているか、おかしなことが起きていないかを掴む
3. 意図しないモデルが意図しない仕事をしていたら、止める、指示を足す、書き換える、セルを足す、やり直させる
4. 実行器や判定器からの問いに、文脈を見たうえで答える
5. タスクの結果を、実行器が書いた読める報告として受け取り、成果物に辿り着き、完了か中止かを自分で記録する

オーナーが画面に求める見方は、次の言葉そのままである。画面全体、とくに概観と実行器の画面はこの視点で作る。

> リーダーがオフィスにいる部下を見渡して、席についているか、書類を書いているか、他のスタッフと議論しているか、ホワイトボードに書いていることの筋は通っていそうか、ざっくりと 30 秒で観察する。そうした視点で見通したい。

見せるのは全体像と「今何をしているか」である。何をしたかを監査的に見る画面は作らない。ツールの全出力、出来事の全列挙は画面に出さない。

## 2. 語と概念（画面の情報の形）

語は `docs/requirements.md` に従う。画面の情報は次の概念の組で表す。モックの見本データもこの形で持つ。

- タスク。オーナーが出した指示から始まる 1 つの仕事。状態は 4 つ（進行中、入力待ち、完了、中止）。進行中と入力待ちは自動で決まり、完了と中止はオーナーが記録する。入力待ちの理由は 3 つ（オーナーへの問いがある、自動で進める作業が無い、実行が失敗か中断で止まった）。報告を書く実行器をタスクごとにオーナーが指定する
- 実行。タスクのフローの 1 回の走行。機械の状態（動いている、終わった、失敗した、中断した）を持つ。初期の指示を「最初からやり直す」で書き換えると、同じタスクに新しい実行が積まれ、前の実行は中断として残る
- フロー。セルと、セルの間の受け渡しの図。回の単位で進む。1 回は、判定器のセルが次の仕事を決め、分岐して複数のセルが並行に動き、回の終わりで合流して次の判定器に入る
- セル。フロー上の 1 つの実行の単位で、type と実行器の組。種類は次のとおり
  - オーナーの指示。初期の指示、重ねた指示、書き換えた指示は、すべてオーナーを実行器とするセルとしてフローに置かれ、次の判定器の入力になる。指示をフローと別の一覧として持たない
  - 判定器。次にどの type をどの実行器で何個動かすか、自動で進める作業が残っているかを決める
  - 作業のセル。break-down、implement、review、summarize、verify.test、verify.lint など
  - オーナーへの問い。実行器や判定器がオーナーに問う場面。オーナーを実行器とするセルで、返答が届くまで入力待ちになる。返答もオーナーのセルとしてフローに残る
  - 報告。実行の最後にオーナー向けの報告を書くセル。実行は報告を出して終わる。中断された実行にも報告がある
- セルと実行の状態の語は画面の語である。Conductor の状態との対応は、9 節の `data-needs.md` の中で示す
- セルが持つ情報。type、実行器、状態（待機、動いている、終わった、失敗した、中断した、返答待ち）、経過時間、出所（フロー定義、前のセルの指示、オーナーの操作）、プロンプト（type の事前プロンプトと入力）、直近の中間出力、使ったツールの一覧（名前と回数だけ）、試行の履歴
- 報告。Markdown か HTML の文書。見出し、表、コード、リストを含む長い文書でありうる。整形して見せ、平文で読ませない。報告が書かれる前は、途中の要約（いまの回、動いているセル、直近の中間出力の要点）を「途中」と分かる形で見せる
- 成果物。報告とは別の一覧。ファイル（作業ディレクトリの中）、git の所在（リポジトリ、ブランチ、コミット、変更ファイル数）、外部への出力（公開先の名前と所在）。それぞれ開ける、持ち出せる。報告の中のリンクだけを成果物への経路にしない。差分の中身を並べない。成果物が無いタスクもある
- 実行器。宣言ファイルの実行器。生きているか（生きている、止まっている、不明）、支える type、環境、アカウント。1 つの実行器は複数のセルを同時に担う。担っているすべてのセルが見える。起こす、止めるの操作がある

オーナーの介入は次の 8 つで、どれもフロー上に結果が現れる。

- 実行を中断する。動いているセルが中断になり、タスクは入力待ち（中断）になり、中断の報告が付く
- 指示を重ねる。オーナーの指示のセルがフローに加わり、次の回から有効になる。入力待ちのタスクなら実行が再開する
- セルを挿し込む。type と入力を指定する。次の回に分岐として置かれ、その回の終わりで合流する。出所はオーナーの操作
- 動いているセルに追加入力を送る。そのセルにオーナーからの入力として付く
- セルを再試行する。同じ type と入力で起こす。実行器は同じか、その type を支える別の実行器に替える。試行の履歴に残る
- 初期の指示を書き換える。「以後の回から有効」なら書き換えた指示のセルが加わる。「最初からやり直す」なら新しい実行が始まる
- 完了として記録する
- 中止として記録する。動いている実行があれば止める

オーナーへの問いに返答すると、返答のセルがフローに加わり、タスクは進行中に戻る。

## 3. ユースケース

設計書の中心はここである。各ユースケースについて、オーナーがどの画面のどこを見て、何を押し、どうなれば成功かを設計し、モックでその通りに辿れるようにする。

- UC1 朝や移動中に 30 秒で見渡す。スマートフォンで開き、最初の画面だけで次が分かる。自分の入力を待っているものが何件あり、それぞれ何か。いま進行中のタスクはどれで、どの実行器が何をしているか。止まっている、失敗している、長く動き続けているなど、おかしなものはあるか。報告が届いたタスクはどれか。そこから 1 回の操作で対象に移れる
- UC2 新しいタスクを出す。長い指示を貼り付けて書ける。任意で作業ディレクトリを指定する。報告を書く実行器を選ぶ（前回選んだものが最初から選ばれている）。出すと受け付けた旨が出て、そのタスクのページに移り、フローに初期の指示のセルと判定器のセルが現れている
- UC3 進行中のタスクの様子を掴む。タスクのページでフロー図を見て、いまどこにいるか（動いているセルが目で分かる）、何本に分岐しているか、どの実行器が担っているか、どこで合流するかが分かる。セルを押すと、そのセルのプロンプト、直近の中間出力、使ったツール、経過時間が見える
- UC4 意図しない実行を止める。実行器の画面かタスクのページで、意図しない実行器が意図しない作業をしているのに気づき、その場から実行を中断する。中断前に何が止まるかが示される。止めた後、フローで中断されたセルが分かり、中断の報告が付き、タスクは入力待ちになる
- UC5 途中で指示を足す。タスクのページから指示を重ねる。送るとフローにオーナーの指示のセルが「次の回から有効」として現れる
- UC6 初期の指示を書き換える。書き換え、「以後の回から有効」か「最初からやり直す」を、それぞれ何が起きるかの説明を見て選ぶ。やり直しでは新しい実行が始まり、前の実行は中断として同じタスクの中で見られる
- UC7 セルを挿し込む。フロー図の上で、次の回に足すセルの type と入力を書く。挿したセルが次の回の分岐としてすぐ図に現れ、オーナーの操作で足したことが分かる
- UC8 動いているセルに追加入力を送る。フロー図で動いているセルを押し、追加の入力を送る。そのセルに付いたことが分かる
- UC9 失敗したセルをやり直させる。入力待ち（失敗）のタスクで、失敗したセルと理由がすぐ分かり、実行器を選び直して再試行する。試行の履歴が残る
- UC10 問いに答える。入力待ちの一覧から問いを開くと、問いの横に文脈が見える（タスクの初期の指示、問いを出したセルが何をしていたか、そこまでのフローの流れ、その時点の報告か途中の要約、関わる成果物）。承認する・しない、選択肢から選ぶ、文で答える、のどれかで返答する。返答すると次の問いに移れる。フロー図でその問いのセルを開く経路もある
- UC11 結果を受け取る。自動で進める作業が無くなったタスクで、報告を整形された文書として読む（見出しで移動できる）。成果物を報告とは別の一覧から開き、持ち出す。完了として記録するか、指示を重ねて続けさせる
- UC12 実行器を見渡し、起こし、止める。実行器の画面で、各実行器が生きているか、同時にいくつのセルを担っているか、それぞれどのタスクの何をしているか、誰から受け取り誰に渡すのかが分かる。担っているセルを開くと、プロンプト、直近の中間出力、使ったツール、経過時間が見える。止まっている実行器を起こし、動いている実行器を止める。止めるときは、担っているセルが中断されることが示される

## 4. 情報設計と動線

- アプリの外枠は、上端の帯と左の画面の一覧と本文から成る。上端の帯には製品名「PDA」、「新しいタスク」のボタン、入力待ちの件数を置く。左の画面の一覧は「概観」「タスク」「入力待ち」（件数付き）「実行器」の 4 つ。スマートフォンでは左の一覧を畳み、上端から開く
- 詳細の画面にはパンくずを置く
- 操作の受付は、画面上部の通知の帯に出し、操作した場所にも結果が現れる
- 画面は URL で直接開ける（ハッシュ方式のルーティング）。タスク、セル、問い、実行器はそれぞれ URL で指せる。タスクのページでセルを選んだ状態も URL に載る
- 各画面の設計では、画面を開いたとき最初に目に入るもの、次に見るもの、の順を決め、その順に視線が流れる配置にする（視点の誘導）。設計書に画面ごとにこの順を書く

## 5. 画面の設計の方向

以下は必須である。ここに書いていない細部は、3 節のユースケースが速く辿れるように設計し、設計書に理由を書く。

### 5.1 概観（最初の画面）

UC1 のための画面。30 秒で見渡せることがすべて。上から、自分の番（返答待ちの問い、届いた報告、失敗や中断で止まったもの）、動いているタスク（タスクごとに動いているセルの 1 行ずつの「いま何をしているか」）、実行器の見渡し（実行器ごとに、生きているか、担っているセルの数と中身の要点）、の順に視線が流れるようにする。数字だけを並べた表示にしない。どの項目からも 1 回の操作で対象に移れる。

### 5.2 タスクの一覧

表の画面。状態（すべて、進行中、入力待ち、完了、中止）で件数付きの絞り込み、文字での絞り込み、並べ替え、ページ送り。列は、タスク（指示の先頭）、状態、いまの動き（例: 「implement を codex-personal、ほか 2 セル」）、入力待ちの理由、関わる実行器、経過時間、最終更新。スマートフォンでは表をカードの並びに替える。

### 5.3 タスクのページ

このページは構造を見せるページである。主役はフロー図で、AWS の Step Functions の実行画面のような図表で見せる。文章や箇条書きでフローを表さない。

- 上部に、タスクの指示の先頭（全文は開ける）、状態、報告を書く実行器、作業ディレクトリ、経過時間と、ページ全体の操作（中断、完了として記録、中止として記録、初期の指示を書き換える）。その下に、いまの状態を 1 文で言う帯（例: 「第 3 回。2 セルが動いている」「報告が届いています」「問いに返答が必要です」）
- 本文はタブで「フロー」「報告」「成果物」に分ける。最初は「フロー」
- フロー図
  - 2 節のセルの種類ごとに、形と印を変える。オーナーのセル（指示、返答）、判定器、作業のセル、オーナーへの問い、報告が、一目で見分けられる。分岐と合流は Step Functions の並列の表現のように、分かれて再び一つになる線で表す
  - セルの箱には type、実行器、状態、経過時間を載せる。動いているセルは控えめな動きで目立たせる。状態は色と語の両方で表す
  - オーナーの操作で足したセル、再試行したセル、書き換えた指示は、箱の印で分かる
  - 配置は自動で行う。PC では左から右、スマートフォンでは上から下
  - 拡大、縮小、全体表示、「いま動いているところへ」の移動、PC では縮小図。回が多いときは、終わった回を畳んで 1 つの箱にでき、開ける。8 回 30 セルでも読める
  - やり直しで実行が複数あるときは、実行を切り替えて見られる。前の実行は中断として見える
  - 凡例を開ける
- セルを押すと、PC では右、スマートフォンでは下からの詳細の枠が開く。詳細には、状態、出所、経過時間、いまの作業（直近の中間出力。整形して表示）、プロンプト（畳んである）、使ったツール（名前と回数の表）、試行の履歴。セルの種類と状態に応じた操作を、その枠の中に置く。動いているセルには追加入力、終わったか失敗したセルには再試行（実行器は、その type を支える実行器から選ぶ）、問いのセルには返答の枠（文脈と一緒に）、報告のセルには報告のタブへの経路
- 指示を重ねる入力欄は、フローのタブの下端に常に置く。送るとフローにオーナーの指示のセルが現れる
- セルを挿し込む操作は、図の上の次の回の位置から始められ、挿したセルがすぐ図に現れる
- 初期の指示の書き換えは、専用の対話の枠で、書き換える文と、「以後の回から有効」「最初からやり直す」の選択と、それぞれで何が起きるかの説明を見せる
- 報告のタブ。Markdown と HTML を整形して表示する（見出し、表、コードの区画とその複写、リスト、リンク）。HTML は安全のため無害化してから表示する。長い報告には見出しの目次を付ける。書いた実行器と時刻を示す。報告がまだ無いときは途中の要約を「途中」と分かる形で見せる。過去の実行の報告も実行を切り替えて読める
- 成果物のタブ。ファイル、git の所在、外部への出力を分けた一覧。ファイルは名前、所在、大きさ、更新時刻、「開く」（文書は整形、画像は画像として、枠の中で見る）と「持ち出す」。git はリポジトリ、ブランチ、コミット、変更ファイル数。外部への出力は名前と公開先へのリンク。無いときは無いと示す

### 5.4 入力待ち

UC10 のための画面。タスクをまたいで、オーナーの入力を待っているもの（問い、届いた報告、失敗か中断で止まったもの）を並べる。PC では左に一覧、右に選んだものの詳細を置く。スマートフォンでは一覧から詳細の画面に移る。

問いの詳細では、返答の枠と同時に、問いに至った文脈を見せる。タスクの初期の指示、問いを出したセルが何をしていたか、そこまでのフローの流れ（問いのセルに至る部分の小さなフロー図）、その時点の報告か途中の要約（整形）、関わる成果物。文脈なしに返答させる画面にしない。返答したら、その問いは一覧から外れ、次の問いに移る操作がある。フロー図でその問いのセルを開く経路も置く。

### 5.5 実行器

UC12 のための画面で、オフィスを見渡す視点で作る。実行器ごとに 1 つの区画を置き、生きているか、環境とアカウント、同時に担っているセルの数を示し、担っているセルを 1 つずつ並べる。各セルには、どのタスクの何の type か、経過時間、いま何をしているかの 1 行、受け取り元と渡し先（どのセルから受け取り、どのセルが待っているか）。何も担っていない実行器は控えめに、止まっている、不明の実行器は目立つように。セルを押すと、プロンプト、直近の中間出力、使ったツール、経過時間が開き、フロー図のそのセルへ移れる。起こす、止めるの操作を実行器ごとに置き、止めるときは担っているセルが中断されることを確認の枠で示す。生きている、止まっている、動いているで絞り込める。

### 5.6 新しいタスク

指示の欄（長文を貼れる。Markdown の見た目を確かめられる）、作業ディレクトリ（任意）、報告を書く実行器（前回選んだものが最初から選ばれている）。回数の上限などの欄は置かない。出すと通知の帯に受け付けた旨が出て、そのタスクのページに移る。

## 6. 見た目の規則

- 明るい配色だけで作る。暗い配色を作らない、切り替えも置かない。構成を読む画面なので、白と明るい灰色の地に、濃い文字と細い区切り線で組む
- AWS のコンソールや Datadog のように、現代的で、情報の密度が高く、余計な装飾が無い画面。色は状態（動いている、終わった、失敗した、返答待ち、待機、中断）と主な操作だけに使い、それ以外は無彩色
- 状態の色は画面全体で 1 つの対応に揃える。色だけに頼らず、語か形を必ず添える
- 本文、操作、表の文字は 14px 以上。補助の注記だけ 12px まで下げてよい。日本語の書体は端末の書体（ヒラギノ、Noto Sans JP など）を使い、外部の書体を読み込まない
- Unicode の絵文字をアイコンの代わりに使わない。アイコンは部品集のアイコンか、SVG で描く
- 文字は選択して複写できる
- 幅 390px（スマートフォン）で画面全体が横にはみ出さない。フロー図は図の中で動かせればよい。幅 1440px でも間延びしない
- 前回の見本で起きた次のことを繰り返さない。暗い配色を勝手に選んだ。画面を文章の段落と要素の羅列で組み、動線と視点の誘導が無かった。フローを箇条書きと線で表した。指示をフローと別の区画にした。報告を平文で出した。実行器が 1 つのセルしか担わない前提で作った。問いを文脈なしに答えさせた

## 7. 技術の決定

- `ui-mock/` の下に、Vite、React、TypeScript の独立した小さなプロジェクトとして作る。リポジトリの Python のプロジェクトとは依存を混ぜない
- 画面の部品は AWS の公開の設計部品集 Cloudscape（`@cloudscape-design/components`、`@cloudscape-design/global-styles`）を使う。外枠（上端の帯、左の画面の一覧、パンくず、詳細の枠）、表、状態の表示、通知の帯、対話の枠を、この部品集で組む。AWS の商標、ロゴ、製品名は使わない
- フロー図は React Flow（`@xyflow/react`）で描き、自動配置は ELK（`elkjs`）の層状の配置で行う
- 報告の整形は `react-markdown`、`remark-gfm`、HTML には `rehype-raw` と `rehype-sanitize` を使う
- ルーティングは `react-router` のハッシュ方式
- 依存は `ui-mock/package.json` と `ui-mock/package-lock.json` に記録する。`node_modules/` はコミットしない（`ui-mock/.gitignore`）。全体へのインストールをしない
- ビルドの出力先は `ui-mock/site/`（`dist` ではない）。相対パスで動くようにし、`python3 -m http.server --directory ui-mock/site` で配って開ける。`site/` はコミットする
- 実行時に外部への要求を一切しない。部品、アイコン、書体はすべてビルドに同梱する

## 8. モックの振る舞いと見本データ

- 見本データは `ui-mock/src/mock/` に TypeScript で置き、2 節の概念の形で持つ。画面のコードに文言や値を埋め込まない
- 操作はモックの中の状態を実際に変える。指示を重ねればフローにセルが増え、中断すればセルが中断になりタスクが入力待ちになり、返答すれば問いが一覧から消えてタスクが進行中に戻る。受付の表示を出すだけで何も変わらない作りにしない。外部へは何も送らない
- 画面の隅に目立たない「見本の操作」の枠を置き、次ができる。見本の場面を切り替える。見本を初期に戻す。「1 歩進める」で模擬的に時間を進める（判定器が次のセルを決める、セルが終わる、分岐が合流する、報告が書かれる、問いが出る）。オーナーが進行の変化を体験できるようにする
- 見本のタスクは 8 件以上、実在しそうな日本語の内容（例: 画面の API を実装する、判定器の問いを見直す、旧アプリのセッションを取り込む）で、次を網羅する。2 本以上に分岐して動いている。問いの 3 形それぞれで返答待ち。報告が届いて自動で進める作業が無い（見出し、表、コード、長いリストを含む 3000 字以上の Markdown の報告）。セルが失敗して止まっている。中断されて中断の報告がある。最初からやり直して実行が 2 つある。8 回 30 セルある。完了。中止。オーナーが挿したセル、再試行したセル、書き換えた指示を含む
- 実行器は宣言の 6 つ。1 つの実行器が 2 つのタスクにまたがって 3 セルを同時に担う場面を含める。止まっている実行器、何も担っていない実行器を含める
- 見本の場面として、次も切り替えで見られる。タスクが 1 件も無い。読み込み中。上流に届かない。タスクが 60 件ある。入力待ちが 0 件。実行器が不明

## 12. 作業の規則

- 作業場所はミニ PC の `~/pda`（`origin` はミニ PC 上の `~/pda.git`）。`main` から分岐したブランチ `ui-mock` で作業する。`main` には触れない。最後に `git push origin ui-mock`
- 区切りごとにコミットする。コミットメッセージは日本語で 1 文。`Co-Authored-By` 行を付けない
- `secrets/` と `deploy/.env` は Git 管理外の認証情報。読まない、写さない、変えない
- Playwright は `ui-mock/` の開発用の依存として入れるか、`uv run --no-project --with playwright` の一時環境で動かす。リポジトリの Python の依存に足さない
- 重い処理（npm の取得、ビルド、ブラウザでの確かめ）は `nice` を付けて直列に行う。ミニ PC の RAM は 12 GiB で、他のコンテナも動いている
- 画面の公開や配信の設定はしない。オーナーが見る経路は設計側が用意する
