# v0.3 候補の OSS のセットアップと試用 (共通の指示)

あなたは、このマシン (ミニ PC。Ubuntu Server 24.04、画面なし、利用者 `user`、sudo 不可) に、PDA v0.3 の候補の OSS を 1 本入れ、決まった試用を行い、起きたことを報告書にまとめる。対象の製品は、この共通の指示と一緒に渡された製品ごとの指示ファイルに書いてある。この指示は完結している。質問はせず、最後まで進め、報告書を push して終える。

## 0. 何のためか

PDA v0.3 は、オーナーがどこからでも Claude Code と Codex に仕事を頼み、進み具合を見渡し、途中で止められる口を、既製の OSS で作れるかを選んでいる (`docs/plan-v0.3.md`)。この走行の仕事は、1 本の製品について、このマシンに常駐し、Claude Code と Codex を動かし、途中の出力が見え、途中で止められるかを事実で確かめることである。製品の良し悪しは書かない。起きたことと証拠だけを書く。

## 1. 読むもの

- `docs/plan-v0.3.md` の 4 節 (要件)、5.2 節 (標準シナリオ)、5.4 節 (セットアップの規律)。
- 製品ごとの指示ファイル。
- 製品の README と公式文書のうち、インストール、セルフホスト、サーバとしての起動、認証、停止に当たるもの。

`docs/reports/` の他の製品の報告と `docs/research/` は読まない。

## 2. 決まり

### 2.1 場所

- 作業ディレクトリ `~/pda-v03a` (このリポジトリ) には、報告書と証拠だけを書く。
- 製品は `~/v03/<製品>/` に入れる。`<製品>` は製品ごとの指示ファイルの名前。
- 試用で製品のエージェントに作業させる使い捨てのリポジトリは `~/v03/work/<製品>/scratch/` に作る。`~/pda`、`~/pda-v03a`、`~/pda.git` を製品やエージェントの作業場所にしない。
- ブランチは `main` から `v0.3/setup-<製品>` を切る。

### 2.2 権限と道具

- sudo を使わない。apt での導入や root の権限が要る手順に当たったら、その手順を報告書の「人の手順」に書く。その手順が無いと進めない試用は「root が要るため未実施」と書き、先へ進む。root が要ることは失敗に数えない。
- 道具は利用者の権限で入れてよい。npm、npx、uv、`pip install --user`、rustup、公開されている実行ファイル (release の成果物) を使える。docker と docker compose を使える。
- このマシンにあるもの: Node 24.18、npm 11.16、Python 3.12、uv 0.11、tmux 3.4、git、curl、jq、docker 29.6。go と cargo は無い。
- 既に動いているもの: OpenObserve (5080 番) と otel-collector (4317、4318 番)。これらと 22、44105、22037 番を使わない。止めない、変えない。

### 2.3 認証

- 秘密情報のファイルを読まない、表示しない、写さない、変えない。対象は `/home/user/pda/secrets/` の下すべて、`~/.claude`、`~/.codex`、`~/pda/deploy/.env`。
- 製品を動かすプロセスの `HOME` を `/home/user/v03/agent-home` にする。ここには、認証の複製のディレクトリへの symlink `.claude` と `.codex` が置いてある。Claude には、これに加えて環境変数 `CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude` で場所を渡す。Codex には `CODEX_HOME` を渡さず (unit では書かず、手で起こすときは `env -u CODEX_HOME` で外す)、HOME の `.codex` から読ませる (`CODEX_HOME` が HOME の `.codex` と違う文字列だと、認証を自分の場所へ写す製品があった)。`PATH` の先頭に `/home/user/.local/bin` を置く。
- Claude Code と Codex は `/home/user/.local/bin` の `claude` (2.1.274) と `codex` (0.156.1) を使う。製品が自分用に別の Claude Code や Codex を入れる場合は、それを使ってよく、版を記録する。
- API キーは入れない。製品がログイン画面や API キーの入力を求める場合は、製品の文書にある「既存の CLI のログインを使う」設定を探して使う。見つからなければ、その事実と画面の文言を報告書に書き、その試用は未実施とする。
- 認証の複製を増やさない。上の 2 つのディレクトリだけを使う。製品が認証のファイルを自分の場所に作ったら、その場所とファイル名をメタデータ (`ls -l`) だけで記録し、写さずに動かす設定を探す。作られたファイルは消さない。

### 2.4 常駐と待ち受け

- この走行は、他の製品の走行と同時に動かさない。始める前に、他の `v03-*.service` が止まっていることを確かめる。
- 製品を systemd の user unit `v03-<製品>.service` で動かす (このマシンは linger が有効)。製品が docker compose で動くなら、compose を user unit から起こしてよい。
- 待ち受けは `127.0.0.1` と、製品ごとの指示ファイルのポートにする。ポートや待ち受けの住所を変えられない製品は既定のまま使い、そのことを記録する。
- 製品のコードは変えない。設定ファイル、環境変数、製品の用意した skill と hook の仕組みだけを使う。

### 2.5 やり直しの上限

- 1 つの手順が失敗したら、原因を調べてもう 1 回だけ試す。それでも失敗したら、その手順を失敗として記録し、次の手順へ進む。
- 導入そのものができずに先へ進めなくなったら、そこまでを報告書に書いて終える。

## 3. 事前の準備

1. 使い捨てのリポジトリ `~/v03/work/<製品>/scratch/` を作る。`git init` し、`README.md` (`# scratch` の 1 行) と `hello.py` (`print("hello")` の 1 行) をコミットする。
2. Claude Code と Codex は、初めて開くフォルダで信頼の確認を出す。製品の中で確認が出て止まらないように、使い捨てのリポジトリを両方で信頼済みにしておく。tmux の中で、上の環境変数と `HOME` を付けてそのリポジトリで `claude` を 1 回起動し、信頼の確認に答えて終了する。`codex` も同じようにする。設定ファイルを自分で書き換えず、それぞれの CLI に書かせる。やったことを報告書に書く。

## 4. 試用

証拠は `docs/reports/evidence/v0.3-<製品>/` に置く。ファイル名は下の番号のとおり。証拠に秘密の値 (トークン、パスワード、認証ファイルの中身) を書かない。

- **T1 導入と常駐。** 製品の版 (release のタグか、コミット) を決めて入れ、unit を起こす。証拠: `01-install.txt` (実行したコマンドと出力の要点)、`01-unit.txt` (`systemctl --user status v03-<製品>.service` の出力と unit ファイルの中身。秘密の値があれば伏せる)、`01-listen.txt` (`ss -ltnp` の該当行と、画面の URL への `curl -sS -o /dev/null -w '%{http_code}'` の結果)。
- **T2 Claude Code に頼む。** 製品の画面、API、CLI のどれかから、使い捨てのリポジトリで Claude Code に次を頼む。「hello.py に、名前を引数で受け取って挨拶する関数を足し、README.md に使い方を 1 行書き足してください。何をしているかを短く書きながら進めてください。」 製品に権限の確認を省く設定があれば使ってよい。途中の出力が流れてくる様子を、時刻付きで記録する。製品の API のストリーム、WebSocket の受信、画面の 10 秒おきのスクリーンショット、のどれでもよい。画面しか無い製品では Playwright の Chromium を headless で使ってよい (`npx playwright` で入れる)。証拠: `02-claude-stream.txt` または `02-claude-*.png`、`02-claude-result.txt` (使い捨てのリポジトリの `git diff`)。
- **T3 Claude Code を途中で止める。** T2 と同じ依頼をもう一度出し、途中の出力が出始めたら、製品の停止の操作 (停止ボタン、中断の API、埋め込みの端末への Ctrl-C や Esc) で止める。止まったこと (claude のプロセスが終わったか、製品の表示が止まった状態になったか) と、止めてから止まるまでの秒数を記録する。証拠: `03-claude-stop.txt` (と画面なら `03-claude-stop.png`)。
- **T4 Codex に頼む。** T2 と同じ依頼を Codex に出す。証拠: `04-codex-stream.txt` または `04-codex-*.png`、`04-codex-result.txt`。
- **T5 Codex を途中で止める。** T3 と同じことを Codex で行う。証拠: `05-codex-stop.txt`。
- **T6 起動のされ方。** T2 と T4 の実行中に `ps -eo pid,ppid,etime,args --forest` を取り、claude と codex がどの親プロセスから、どの引数で起動されたかを残す。判定はしない。証拠: `06-ps-claude.txt`、`06-ps-codex.txt`。
- **T7 資源。** T2 の実行中の、製品と子プロセスのメモリ (`ps` の RSS、docker なら `docker stats --no-stream`)。証拠: `07-resources.txt`。
- **T8 別の端末からの開き方。** 画面の URL (パスを含む)、待ち受けのポート、画面にログインが要るならその手順 (トークンやパスワードの置き場所か、出すコマンド。値は書かない) を報告書に書く。開発 PC からの到達は設計側が SSH のポート転送で確かめるので、ここでは行わない。
- **T9 Claude Code と Codex の間で仕事を渡す。** 製品に、あるエージェントから別のエージェントへ仕事を渡す機能 (委譲、worker、伝言、引き継ぎ) があれば、それを使って Codex から Claude Code へ T2 と同じ依頼を渡し、渡した先の途中の出力が製品の画面か API で見えるかを記録する。逆向き (Claude Code から Codex) も行う。そうした機能が製品に無ければ「製品の機能には無い」と書いて先へ進む。skill や MCP で補うことはこの走行ではしない。証拠: `09-handoff.txt`。

試用が終わったら `systemctl --user stop v03-<製品>.service` で止める。docker compose なら `stop` にし、`down` はしない。入れたものは消さない。

## 5. 報告書

`docs/reports/v0.3-<製品>-codex.md` に、次の節をこの順で書く。

1. 結論: T1〜T5 のうち、通ったものと通らなかったもの (1〜2 文)。
2. 版と導入: 製品の版、入れた場所、unit の名前、ポート、画面の URL、製品が同梱する Claude Code と Codex の有無と版。
3. 試用の結果: T1〜T9 を 1 つずつ、「やったこと」「起きたこと」「証拠のファイル名」の 3 行で。失敗したものは、エラーの文と試した回数。
4. Claude Code と Codex の起動のされ方: T6 から読める事実 (親プロセスと引数)。
5. 認証: 認証の渡し方 (環境変数、HOME)、製品がログイン画面や API キーを求めたか、それにどう対応したか。
6. 人の手順: root が要った手順。Tailscale Serve での公開の手順を `/home/user/.local/bin/tailscale-pda serve --bg --https=<番号> http://127.0.0.1:<ポート>` の形で (番号は製品ごとの指示ファイル)。画面のログインの手順。
7. 分からなかったこと。

良し悪しの評価、推奨、感想は書かない。

## 6. 終わり方

- 報告書と証拠を 1〜2 コミットで入れる。コミットメッセージは日本語の短い 1 文。
- `git push origin v0.3/setup-<製品>` で終える。
- 最終メッセージは、結論の 1〜2 文と報告書のパス。
