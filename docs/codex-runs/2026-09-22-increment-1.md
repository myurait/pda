## 2. 構成

`deploy/docker-compose.yaml` に次のサービスを定義する。イメージの版はすべて固定し、報告書に列挙する。

| サービス | 内容 |
|---|---|
| conductor-server | Conductor OSS のサーバ。公式配布のイメージがあればそれを使い、無ければ conductor-oss/conductor の `docker/server/Dockerfile` でビルドする。設定は同梱の `docker/server/config/config-redis.properties` に準じ、Redis と Elasticsearch を使う |
| conductor-redis | `redis:6.2` 系 |
| conductor-elasticsearch | `docker.elastic.co/elasticsearch/elasticsearch:7.17` 系。`ES_JAVA_OPTS=-Xms512m -Xmx1024m`。単一ノード |
| conductor-ui | Conductor の UI。公式配布があればそれを使い、無ければ同梱の `docker/ui/Dockerfile` でビルドする |
| otel-collector | `otel/opentelemetry-collector-contrib`。OTLP HTTP と gRPC を受け、`otlphttp` で openobserve へ、`file` で `/var/lib/pda/events/events.jsonl` へ出す。ファイルは 100 MB か 1 日で回転。設定は `deploy/otel-collector.yaml` |

| exec-codex-personal | Codex の実行器。`npx -y @agentclientprotocol/codex-acp` をアダプタとして起動する。認証ディレクトリを `/root/.codex` にマウントする。compose の既定では起動しない（profile `real`） |

規則。

- 実行器のコンテナはホストへポートを公開しない。公開するのは conductor-server の 8080、conductor-ui の 5000、openobserve の 5080 だけ
- 実行器は compose の内部ネットワークで conductor-server と otel-collector にだけ到達できるようにする。exec-jev だけは外向きの通信（`api.typesafe.ai`）を許す。exec-codex-personal と exec-claude-company は各ベンダーの API への外向き通信を許す。docker の network の分離で実現できる範囲でよく、できない部分は報告書に書く
- 作業ディレクトリは名前付きボリューム `pda-work` を全実行器の `/work` にマウントして共有する
- 各実行器は環境変数 `PDA_EXECUTOR_ID`、`CONDUCTOR_URL`、`OTEL_EXPORTER_OTLP_ENDPOINT`、`PDA_REGISTRY_DIR=/registry` で設定する。`registry/` は読み取り専用でマウントする

## 3. 正本（registry）

### 3.1 `registry/types/{type}.yaml`

```yaml
type: implement
description: コードを書く、直す
prompt: prompts/implement.md
input_schema:  { JSON Schema。3.5 の共通入力に加えて type 固有の欄があれば書く }
output_schema: { JSON Schema。kind と payload の形 }
task_def:
  retryCount: 3
  retryLogic: FIXED
  retryDelaySeconds: 10
  timeoutSeconds: 3600
  responseTimeoutSeconds: 600
  timeoutPolicy: TIME_OUT_WF
driver: acp        # acp | jev | tools
command: null      # driver が tools のときだけ。例: ["pytest", "-q"]
```

初期の type は 7 つ。`judge`（driver jev）、`break-down`、`implement`、`review`、`summarize`（driver acp）、`verify.test`（driver tools、command `["pytest", "-q"]`）、`verify.lint`（driver tools、command `["ruff", "check", "."]`）。

### 3.2 `registry/prompts/{type}.md`

type ごとの事前プロンプト。日本語で書く。内容は短くてよいが、次を必ず含める。「入力は `input` に与える」「出力は 1 つの JSON で、`kind` と `payload` を持つ」「`kind` は `input` か `result`」「フローへの指示は出さない（judge 以外）」。`judge.md` は jev には使わないので、判定器の役割の説明だけを書く。

### 3.3 `registry/executors/{executor_id}.yaml`

```yaml
executor_id: fake-a
name: 試験用エージェント A
version: 1
agent: fake
runtime: acp
account: none
environment: minipc
types: [break-down, implement, review, summarize]
adapter:
  command: ["python", "-m", "pda_fake_agent"]
  env: {}
capabilities: {streaming: true, cancel: true}
cost: {currency: JPY, per_run_estimate: 0, per_run_seconds_estimate: 5, rate_limit: {requests: 1000, per: hour}}
resources: {filesystem: ["/work"], network: [], connectors: []}

permissions: {default: allow_once, deny_kinds: []}
```

6 ファイル書く。`fake-a`、`fake-b`（同じ内容で ID と名前だけ違う）、`tools`（runtime tools、types は verify.test と verify.lint）、`jev`（runtime jev、types は judge）、`codex-personal`（agent codex、adapter.command は `["npx", "-y", "@agentclientprotocol/codex-acp"]`、adapter.env に `INITIAL_AGENT_MODE: agent`、network は `["api.openai.com", "chatgpt.com"]`、types は break-down、implement、review、summarize）、`claude-company`（agent claude、adapter.command は `["npx", "-y", "@agentclientprotocol/claude-agent-acp@preview"]`、network は `["api.anthropic.com", "claude.ai"]`、types は同じ）。

### 3.4 `registry/judge/questions.json`

jev への問いの集合。問いの文面はすべて英語。state は日本語のままでよい。次の 4 問を Choice と Noul で書く。選択肢は正本から生成せず、ファイルに直接書く（type の一覧と実行器の一覧をそのまま書く）。

1. `is_complete`（Noul）: 集めた出力を見て、初期入力の仕事が完了しているか
2. `next_type`（Choice）: 次に必要な type。選択肢は break-down、implement、review、verify.test、verify.lint、summarize、none
3. `executor`（Choice）: その type をどの実行器で走らせるか。選択肢は実行器 ID の一覧。criteria に費用と到達資源を書く
4. `cell_count`（Choice）: 1、2、3

閾値は仮に置く（`is_complete` は 0.7）。実データでの検証は人が `jev-verify` で行うので、報告書に「未検証」と書く。

### 3.5 共通入力の形

すべてのセルの入力は次の JSON。`context` の中身は自由。

```json
{"job_id": "…", "cell_id": "…", "type": "implement", "prompt_ref": {"id": "implement", "version": 1}, "input": "…", "context": {}}
```

判定器のセルだけは `input` の代わりに `initial_input` を受け、`join.output` は受けない（5 節）。

### 3.6 共通出力の形

```json
{"kind": "flow | input | result", "payload": {}, "meta": {"executor_id": "…", "declaration_version": 1, "trace_id": "…", "stop_reason": "end_turn"}}
```

`kind` が `flow` のときの `payload` は次の形。

```json
{"then": "continue | finish", "cells": [{"type": "…", "executor": "…", "input_from": "previous | initial"}], "dynamicTasks": [], "dynamicTasksInput": {}}
```

### 3.7 `registry/workflows/pda_job.json`

5 節の雛形をそのまま置く。

## 4. 定義の生成と登録（`tools/generate_defs.py`）

- すべての type × 実行器の組み合わせのうち、実行器の `types` に含まれるものについて、名前 `{type}.{executor_id}` のタスク定義を作る。`retryCount` などは type の `task_def` から、`inputSchema` は type の `input_schema` から取り、`enforceSchema: true`。`outputSchema` も登録し、強制は付けない
- 雛形のワークフロー定義を読み、そのまま登録する。`inputSchema` にワークフロー入力（`initial_input` は文字列必須、`context` はオブジェクト任意）を付ける
- Conductor の REST API（`POST /api/metadata/taskdefs`、`PUT /api/metadata/taskdefs`、`POST /api/metadata/workflow`、`PUT /api/metadata/workflow`）で登録する。既にあれば更新する。冪等にする
- `python tools/generate_defs.py --conductor http://localhost:8080 --registry registry/` で動く。`--dry-run` で生成物を標準出力に出す

## 5. 雛形ワークフロー

`docs/design/increment-1.md` の 5 節の JSON を土台にする。ただし判定器のタスクの `inputParameters` から `input: "${join.output}"` を外し、次だけにする。

```json
{"type": "judge", "prompt_ref": {"id": "judge", "version": 1}, "initial_input": "${workflow.input.initial_input}", "context": "${workflow.input.context}", "job_id": "${workflow.workflowId}"}
```

判定器のラッパーは `GET /api/workflow/{job_id}?includeTasks=true` で自分のワークフローの記録を読み、直前の回の動的フォークが生んだタスク（`taskReferenceName` が `c` で始まるもののうち、最も新しい回のもの）の出力を集めて state にする（8 節）。

とりあえずの決定と代替。

- まず DO_WHILE の中に判定器、SWITCH、動的フォーク、JOIN を置く形（設計文書の JSON）で登録し、試験用実行器で 2 回以上回ることを確かめる
- 動かない場合（登録が拒否される、2 回目の参照が解決しない、SWITCH の式が評価されない、のいずれか）は、次の代替に切り替える。`pda_job` を 1 回分（判定器、SWITCH、動的フォーク、JOIN）だけのワークフローにし、判定器のラッパーが `then` が `continue` のときに `POST /api/workflow` で次の回を開始し、`correlationId` に `job_id`（最初のワークフロー ID）を入れる。判定器の `job_id` には `correlationId` があればそれを、無ければ自分のワークフロー ID を使う
- どちらで動いたか、動かなかった場合の Conductor の応答を報告書に書く
- SWITCH は `evaluatorType: value-param`、`expression: then`、`inputParameters: {then: "${judge.output.payload.then}"}` で書く。動かなければ `javascript` の評価方式に変える
- 動的フォークには空の一覧を渡さない。判定器のラッパーは `then` が `continue` のとき `cells` が 1 つ以上あることを保証し、無ければ `then` を `finish` に変えて `judge.answer` の出来事に理由を残す

## 6. ラッパー（`src/pda_wrapper/`）

### 6.1 起動

`python -m pda_wrapper` で起動する。`PDA_EXECUTOR_ID` の宣言ファイルを読み、`types` の各 type について `{type}.{executor_id}` のタスク名で Conductor のワーカーを登録し、ポーリングを始める。Conductor の Python SDK（PyPI `conductor-python`）の `worker_task` と `TaskHandler` を使う。`lease_extend_enabled=True`。

### 6.2 1 タスクの処理

1. タスクを受け取る。`job.received` を記録する
2. `prompt_ref` から `registry/prompts/{id}.md` を読む。`input` と `context` と合わせてランタイムへの入力を作る。`input.assembled` に `prompt_ref` と入力の SHA-256 と `context` のキー一覧を記録する。文は記録しない
3. type の `driver` に応じた操作役（7〜8 節）でランタイムを動かす
4. 出力を分類する（6.3）。分類した種別の出力スキーマで検査する。通れば `output.classified`、落ちれば `output.rejected` を記録し、Conductor には `FAILED_WITH_TERMINAL_ERROR` で返す（Python SDK では `NonRetryableException` を投げる）
5. 出力の要約 1 行（kind と payload の先頭 200 字）をタスクログに追記する
6. `COMPLETED` で返す。`outputData` は 3.6 の形そのもの

例外はすべて捕まえ、想定内（ランタイムの失敗、時間切れ）は `FAILED`（再試行あり）、想定外（ラッパー自身のバグ）は `FAILED_WITH_TERMINAL_ERROR` で返す。どちらも出来事に残す。

### 6.3 分類

ランタイムの出力（文字列）を次の順で判定する。

1. JSON として読め、`kind` が `flow` で 3.6 の flow の形に合う。ただし type が `judge` でない実行器からの `flow` は拒否（`output.rejected`、理由 `flow_from_non_judge`）
2. JSON として読め、`kind` が `input` か `result` で、`payload` を持つ。そのまま採用
3. JSON として読めるが `kind` が無い。`{"kind": "result", "payload": <そのJSON>}` に包む
4. JSON として読めない。`{"kind": "result", "payload": {"text": <文字列>}}` に包む

jev と tools の操作役は自分で 3.6 の形を作るので、分類は 1 と 2 だけ通る。

### 6.4 出来事（event stream）

OpenTelemetry の Python SDK を使う。トレース ID は `sha256(job_id)` の先頭 128 ビット、スパンはタスク 1 つに 1 つで、スパン ID は `sha256(task_id)` の先頭 64 ビット。出来事はログレコードとして送り、属性に必ず `pda.event.kind`、`pda.job_id`、`pda.cell_id`（task の reference name）、`pda.task_id`、`pda.executor_id`、`pda.type` を付ける。送り先は `OTEL_EXPORTER_OTLP_ENDPOINT`（HTTP）。

種別と追加属性は次の表に限る。表に無い出来事を作らない。写せないものは `unknown` に元のデータを `pda.raw`（JSON 文字列、10 KB で切る）として入れる。

| 種別 | 出所 | 追加属性 |
|---|---|---|
| job.received | ラッパー | なし |
| input.assembled | ラッパー | pda.prompt_id、pda.prompt_version、pda.input_sha256、pda.context_keys |
| message.output | ACP agent_message_chunk | pda.chars |
| reasoning | ACP agent_thought_chunk | pda.chars |
| tool.call | ACP tool_call | pda.tool_call_id、pda.tool_kind、pda.tool_title、pda.raw_input |
| tool.result | ACP tool_call_update | pda.tool_call_id、pda.tool_status、pda.raw_output |
| plan | ACP plan | pda.items |
| permission.request | ACP session/request_permission | pda.tool_call_id、pda.options |
| permission.response | ラッパー | pda.option_id、pda.policy |
| usage | ACP usage_update | gen_ai.usage.input_tokens、gen_ai.usage.output_tokens |
| turn.end | ACP の応答 | pda.stop_reason |
| output.classified | ラッパー | pda.kind、pda.schema_id |
| output.rejected | ラッパー | pda.reason |
| command.run | tools | pda.command、pda.exit_code、pda.duration_ms |
| judge.answer | jev | pda.question_id、pda.choice、pda.confidence |
| unknown | ラッパー | pda.raw |

## 7. ACP の操作役（`drivers/acp.py`）

ACP の Python SDK（PyPI `agent-client-protocol`）のクライアント側を使う。SDK がクライアント側の標準入出力接続を提供しない場合は、JSON-RPC 2.0 を標準入出力で自前に実装する（改行区切り JSON）。どちらにしたかを報告書に書く。

1. 宣言ファイルの `adapter.command` を子プロセスとして起動する。環境変数は `adapter.env` を足す
2. `initialize` を送る
3. `session/new` を `cwd=/work` で送る
4. `session/prompt` で、事前プロンプトと入力を連結した 1 つのテキストブロックを送る
5. `session/update` の通知を受けるたびに 6.4 の表に写す。知らない `sessionUpdate` は `unknown`
6. `session/request_permission` が来たら、宣言ファイルの `permissions` に従って答える。`default: allow_once` なら `allow_once` に当たる選択肢を選ぶ。`deny_kinds` に該当するツール種別なら `reject_once`。答えた内容を `permission.response` に記録する
7. 応答の `stopReason` を `turn.end` に記録し、`meta.stop_reason` に入れる
8. `agent_message_chunk` を連結したテキストをランタイムの出力とする
9. タスクの中断（プロセスへの SIGTERM）を受けたら `session/cancel` を送り、子プロセスを終了する
10. 1 セッションは 1 タスクで使い捨てる。子プロセスはタスクごとに起動して終了する

Codex のアダプタは起動時の `INITIAL_AGENT_MODE` で権限モードを決める。`session/request_permission` が来るかどうかは不明なので、来たら 6 のとおり答え、来なければ `job.received` の属性に `pda.agent_mode` を入れる。

### 7.4 試験用エージェント（`src/pda_fake_agent/`）

ACP のエージェント側を Python SDK で実装する。`session/prompt` を受けると次を順に行う。`agent_thought_chunk` を 1 つ、`tool_call`（kind `read`、title `read /work/README`）と `tool_call_update`（status `completed`）を 1 組、`agent_message_chunk` で応答本文、`stopReason: end_turn` で終える。応答本文は環境変数 `FAKE_MODE` で切り替える。

- `echo`（既定）: `{"kind": "input", "payload": {"text": "<受け取ったプロンプトの末尾 100 字>"}}`
- `invalid`: `kind` が `bogus` の JSON。A13 の試験に使う
- `slow`: 応答前に `FAKE_SLEEP_SECONDS`（既定 700）秒待つ。A15 の試験に使う
- `permission`: 応答前に `session/request_permission` を 1 回送る

## 8. jev の操作役（`drivers/jev.py`）

TypeSafe の jev API を呼ぶ。リクエストと認証の形は、ユーザーのホームにある `~/.claude/skills/jev-judge/scripts/jev_judge.py` と `~/.claude/skills/jev-verify/scripts/jev_call.py` を読んで、その送信部分をこのパッケージに移植する（読めない場合は報告書に書き、`JEV_MODE=fixture` だけで進める）。API キーは環境変数 `TYPESAFE_API_KEY`、無ければ `/secrets/typesafe_credentials` の `API_KEY=` 行。

1. `job_id` のワークフローを `GET /api/workflow/{job_id}?includeTasks=true` で読む。直前の回の `c` で始まる reference name のタスクの `outputData` を集める。無ければ空
2. state を作る。`{"initial_input": …, "context": …, "previous_outputs": [ {cell_id, type, executor, kind, payload} ], "executors": [宣言ファイルの一覧], "types": [type の一覧]}`
3. `registry/judge/questions.json` の 4 問を送り、答えを読む
4. `is_complete` が閾値以上、または `next_type` が `none` なら `then: finish`、`cells: []`。そうでなければ `then: continue` で、`cell_count` の数だけ `{type: next_type, executor: executor, input_from: previous}` を並べる（同じ type と実行器の繰り返しでよい。前の回が無ければ `input_from: initial`）
5. `cells` から `dynamicTasks` と `dynamicTasksInput` を生成する。reference name は `c1`、`c2`…、name は `{type}.{executor}`、type は `SIMPLE`。入力は 3.5 の形で、`input` には `input_from` が `previous` なら前の回の出力の `payload` を JSON 文字列で連結したもの、`initial` なら `initial_input`
6. 4 問それぞれの答えを `judge.answer` に記録する
7. `{"kind": "flow", "payload": {...}, "meta": {...}}` を返す

`JEV_MODE=fixture` のとき、API を呼ばず `registry/judge/fixture.json` の答えを返す。fixture は 1 回目「continue、break-down を fake-a で 1 つと verify.test を tools で 1 つ」（cell_count は 2 だが type は 1 つしか選べないので、fixture では cells を直接書けるようにする）、2 回目「finish」を返す形にする。回数は state の `previous_outputs` が空かどうかで決める。

## 9. tools の操作役と写し

### 9.1 tools（`drivers/tools.py`）

type の `command` を、`input` が JSON で `workdir` を持てばそこで、無ければ `/work` で走らせる。600 秒で打ち切る。`command.run` を記録し、`{"kind": "result", "payload": {"passed": <exit_code == 0>, "exit_code": …, "stdout_tail": <末尾 4000 字>, "stderr_tail": <末尾 4000 字>}}` を返す。

### 9.2 写し（`src/pda_mirror/`）

3 秒ごとに Conductor を読み、前回との差分を出来事にする。

1. `GET /api/workflow/running/pda_job` で実行中のワークフロー ID を得る。加えて、前回実行中だったが今は無い ID も 1 回だけ読む
2. 各 ID を `GET /api/workflow/{id}?includeTasks=true` で読む
3. ワークフローの `status` が変わっていれば `engine.workflow`（属性 pda.status、pda.reason に `reasonForIncompletion`）
4. タスクごとに `status`、`retryCount` が変わっていれば `engine.task`（属性 pda.cell_id、pda.task_id、pda.status、pda.retry_count、pda.reason に `reasonForIncompletion`、pda.worker_id、pda.task_def_name）
5. 動的フォークが生んだタスクには、`engine.task` の属性 pda.origin_cell に、生んだ判定器の reference name を入れる（フォークの入力に含まれる `dynamicTasks` の出所から辿る。辿れなければ `unknown`）

トレース ID とスパン ID の作り方は 6.4 と同じにし、ラッパーの出来事と同じトレースに並ぶようにする。

## 10. 試験

`tests/unit/` に分類、スキーマ検査、フローの指示の生成、出来事の写しの単体試験。`tests/e2e/` に compose を使う試験。e2e は `PDA_E2E=1` のときだけ動く。

e2e の筋書き。`docker compose up -d`（profile `real` は上げない）、`generate_defs.py` を実行、次を順に確かめる。

1. `POST /api/workflow` で `pda_job` を `initial_input: "README を要約せよ"` で開始する。fixture の判定器により、1 回目に `break-down.fake-a` と `verify.test.tools` が走り、2 回目に finish して `COMPLETED` になる。5 節の代替に切り替えた場合は、`correlationId` でつながった 2 つのワークフローが両方 `COMPLETED` になる
2. `/var/lib/pda/events/events.jsonl`（compose のボリュームから読む）に、この job_id について `job.received`、`input.assembled`、`tool.call`、`tool.result`、`turn.end`、`output.classified`、`command.run`、`judge.answer`、`engine.task` が 1 件以上ずつある
3. OpenObserve の検索 API に SQL で問い合わせ、同じ job_id の行が返る
4. `FAKE_MODE=invalid` の exec-fake-b に向けたセル（fixture を切り替える環境変数で `implement.fake-b` を選ばせる）が `FAILED_WITH_TERMINAL_ERROR` になり、`output.rejected` が残る（A13）
5. `FAKE_MODE=slow` で、`responseTimeoutSeconds` を試験用に 30 秒に下げたタスク定義を使い、再試行が起きて `engine.task` に `retry_count` の増加と `reason` が残る（A15、A18）。再試行後の入力が 1 回目と同じであることを Conductor の記録で確かめる
6. `docker stats --no-stream` の結果を保存する
