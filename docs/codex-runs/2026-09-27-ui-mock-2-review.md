# PDA v0.2 画面モック：レビュー後の修正指示

整理日：2026-09-27。対象は [2026-09-25-ui-mock-2.md](2026-09-25-ui-mock-2.md) に基づく画面モックと、2026-09-25〜26 にオーナーが送ったブラウザーコメント・追加説明である。

本書は修正要求をまとめた追補指示書である。元の指示と異なる箇所は本書を優先する。後から訂正された内容は最新の指示に統合した。ここに変更のない要件は元の指示を引き継ぐ。以下のユースケースは、コメントの具体例と既存の見本タスクを使って操作手順・成功条件を整理したものである。

実装・検証の記録は [review-comments.md](../../ui-mock/docs/review-comments.md)、現行の画面設計は [ux-design.md](../../ui-mock/docs/ux-design.md)、必要な情報と出所は [data-needs.md](../../ui-mock/docs/data-needs.md) を参照する。

## 1. 元の指示から変更する前提

| 対象 | 修正後の指示 |
|---|---|
| タスクと実行 | タスクは一つのフローと報告群を持つ。「実行 n」はユーザー応答へ戻るまでの抽象概念であり、独立した状態・引数・選択ドロップダウンにしない。やり直しも同じタスクのフローに記録する |
| 次の回 | フローは進行に応じて追記する。抽象的な「次の回」を仮セルとして先に描かない。未合流の状態で合流ノードを先置きしない |
| セルの追加 | 「次の回に挿し込む」操作をやめ、選択したセルの「この次にセルを追加」「並列するセルを追加」とする |
| 報告担当 | タスクごとに選ばない。報告担当・判定器・タスクオブザーバーという role ごとに、利用する実行器・モデル・注入プロンプト・skill を個別設定する |
| タスクの入口 | デフォルトは「報告」タブ。報告がまだないときは途中の要約を示す |
| 入力待ちの入口 | inbox は一覧だけを持ち、選択後はタスクの報告タブへ移動する。左ナビの独立項目と inbox 内の詳細ページは不要 |
| 初期の指示 | 最初のユーザー指示もオーナーのセルである。初期指示の書き換えは、そのセルの詳細から行う |
| 時間 | タスクの時間は「実行時間」「待機時間」に分け、ページを開いた時点の値を表示する |

## 2. 画面別の修正指示

### 2.1 概観・入力待ち・状態表示

1. セルの「動いている」という表記は「動作中」にする。タスク自体の状態「進行中」とは区別する。
2. 通常の入力待ちに warning の黄色三角を使わない。判断を求めること、次の指示を待つことは正常なステップとして表示する。中断による入力待ちと中断セルには黄色三角を使う。
3. 入力待ち理由は次の文言にする。

   | 以前の文言 | 修正後 |
   |---|---|
   | 報告に問いがあります | 判断を求めています |
   | 自動で進める作業がありません | 次の指示を待っています |
   | コアの規則で実行が止まりました | タスクが中断されています |

4. 「再試行で立て直し中」「オブザーバーから立て直し中」「長時間の作業」などの黄色い補助バッジは、どの場面にも出さない。UI が独自に長時間かどうかを判定しない。
5. 概観の「自分の番を確認して、いまの仕事を見渡す。」を削除する。作業行の実行時間は右上に配置する。実行器カードの `implement / review / implement` のような type の列挙は不要。
6. 上端の入力待ち入口は、inbox と分かるアイコンと件数を表示する。PC・スマートフォンとも一覧からタスクの報告タブへ移動する。
7. 入力待ちカードには、通知から何分経過したか、状態・待ち理由、短い報告文を載せる。この短いサマリは報告担当が一覧掲載用に出力する。
8. 「見本の操作」は場面の切り替え・初期化・模擬進行のためのモック操作として維持する。

### 2.2 タスク一覧・時間

1. 一覧は「タスク」「状態」「実行時間」「待機時間」「最終更新」の5列にする。スマートフォンのカードも同じ情報構成にする。
2. 以前の「状態」「いまの動き」「入力待ちの理由」を「状態」列にまとめる。「報告が届いています」という重複説明は削除し、進行中なら現在の作業、入力待ちなら具体的な待ち理由を示す。
3. 「関わる実行器」の列を削除する。
4. 最終更新は日付と時刻を二段に分ける。
5. 待機時間は、タスクが待ち状態になってから放置されている時間とする。実行時間は、最終指示から現在まで、入力待ちの場合は最終指示から待ち状態になるまでの時間とする。
6. タスク詳細・一覧・入力待ちカードの時間は、ページを開いた時点の値を表示すればよい。秒ごとの自動更新は不要。タスク詳細の「経過時間」は「実行時間」に変更する。

### 2.3 タスク見出し・報告・返答

1. 状態バッジはタイトルのすぐ下に置き、少し大きくする。状態を繰り返す説明欄を削除する。操作ボタンは右上、狭い画面ではタイトル・状態・操作の順に折り返す。
2. 指定された作業ディレクトリに加え、作業ブランチがある場合は表示する。「完了として記録」「中止として記録」のボタン表記は「完了」「中止」とし、記録操作であることはホバー説明で示す。
3. ヘッダーの「初期の指示を書き換える」ボタンは削除する。初期指示セルを選んで編集する。
4. 報告本文の上に、報告生成前の最後のユーザー入力を折りたたみで表示する。過去の報告には当時の入力を対応させる。
5. 複数報告を確認できる見本を用意する。ドロップダウンに加えて「戻る」「進む」で切り替えられるようにする。「報告を選ぶ」という表示ラベルは不要。
6. 報告の目次は縦並びにする。「持ち出す」ボタンは削除する。コードの複写はアイコンだけにし、操作を識別できる読み上げ名・説明を付ける。
7. 返答前の注意文は不要。問いごとの送信は行わず、すべての問いへの返答を一つの「送信」で送る。「まとめて」の表記は不要。
8. 承認・選択式の問いにも、必ず「それ以外」と自由入力欄を設ける。選択肢だけで回答を制限しない。
9. 「判断の文脈」に初期指示本文だけの独立セクションは置かない。実際に失敗したセルの最終応答とオブザーバーの判断を、それぞれ折りたたみで表示する。
10. 判断の文脈のフロー図には、最初のユーザー指示をセルとして含める。当該報告に関係するオーナーの指示も確認できるようにする。初期指示の独立セクションを削除する指示は、初期指示セルを削除する意味ではない。

### 2.4 報告のための成果物

1. 「関わる成果物」は「報告のための成果物」に変更し、問いより上に置く。
2. ここには、報告担当が「これを確認しなければユーザーの判断・追加指示が難しい」と判断した成果物を載せる。タスクの全成果物とは区別する。
3. ユーザーが挙げた具体例は、モックアップの URL、報告用の HTML、議題となる成果物ファイルである。これらを開いてから問いに答えられるようにする。
4. ファイルは、実体の `ファイル名.拡張子` をリンクにし、その下に作業ディレクトリからの相対パスを表示する。実体と異なる表示名、フルパス、更新日時、サイズ、「開く」ボタンは出さない。

### 2.5 フロー・セル詳細・介入

1. 初期の指示、追加指示、書き換え、返答をオーナーのセルとして表す。オーナーセルの外観と詳細項目は、その役割に合わせ、指示本文・操作の出所・適用範囲が分かるようにする。
2. セル詳細は下から開くスティッキーパネルで表示し、不要なグラバーを削除する。`review · claude-personal` などの見出しをリンクにし、押すとフロー上の該当セルへ移動する。「フロー図のこのセルへ」という別ボタンは不要。
3. 各試行に実際に与えられた入力を確認できるようにする。セルに指示を追加できるようにする。
4. 完了・合流済みのセルへ指示を追加する場合は、次の確認を表示する。

   > 後続のセルの成果を破棄し、このセルからやり直しますか？

5. 確認を取り消した場合は変更しない。確定後は対象セルからやり直し、その成果に依存する後続セル・報告・成果物を破棄する。独立した並列セルを巻き込まない。試行の入力・出力は履歴として確認できるようにする。
6. 「この次にセルを追加」「並列するセルを追加」は、選択したセルを基準として type・入力を指定し、追加結果と接続がフローに現れるようにする。
7. 初期指示の書き換えで「現在の作業を続ける／以後の回から有効」と「最初からやり直す」を選べるようにする。どちらも同じタスクのフローに記録し、実行の切り替え画面は作らない。

### 2.6 実行器・role・skill・利用状況

1. 実行器の担当セルを押すと、タスクのフローの該当セルへ移動し、セル詳細のスティッキーを展開する。担当セルの「受け取り元／渡し先」は削除する。
2. role 設定は一覧と下から開く編集スティッキーにする。現在の3 role だけを前提とする大きな固定フォームの並びにしない。
3. 設定を持つのは role であり、実行器が報告担当を持つ構造ではない。各 role が利用する実行器・モデル・注入プロンプト・skill を個別に設定する。
4. skill 登録ページを設ける。role の skill は登録済みのものからポップアップで選択する。
5. 契約クレジット残量・従量課金額などの利用状況を表示する。取得するスクリプトは実行器ごとに個別設定する。
6. 応答 JSON の `title` と `value`、任意の `limit` と `alert` を表示する。割合・金額・単位を UI で固定しない。警告かどうかも UI で計算せず、応答の `alert` に従う。前節までの黄色い補助バッジの削除とは別の指定である。

ユーザーが提示した応答例を、有効な JSON 配列として整理すると次の形になる。

```json
[
  {"title": "5時間制限", "value": "75%", "limit": "100%", "alert": "warning"},
  {"title": "週制限", "value": "95%", "limit": "100%", "alert": "critical"},
  {"title": "クレジット利用額", "value": "1$"}
]
```

## 3. 修正後の具体的なユースケース

### UC1：移動中に、判断待ちと中断を見分ける

1. 場面：スマートフォンで概観を開く。「判定器の問いと保存範囲を見直す」「画面 API の実装結果を受け取る」「検証用実行器の起動を確認する」が入力待ちになっている。
2. 操作：待ち理由・通知からの時間・短いサマリを見る。上端の inbox から一覧を開き、保存範囲のカードを選ぶ。
3. 成功条件：通常の判断待ち・次の指示待ちは警告表示にならず、中断だけ黄色三角になる。一覧選択から対象タスクの報告タブへ直接移動できる。長時間や立て直しの黄色い補助バッジは出ない。

### UC2：新しいタスクを出す

1. 場面：画面 API の実装を長文で依頼し、作業ディレクトリを指定したい。
2. 操作：「新しいタスク」から指示・任意の作業ディレクトリを入力して送る。報告担当はここでは選ばない。
3. 成功条件：タスクの報告タブに途中の要約が表示される。フローには最初のユーザー指示セルと判定器セルがあり、role 設定に基づく担当が使われる。

### UC3：タスク一覧から進行と時間を確認する

1. 場面：保存範囲の判断待ちと、動作中の画面 API 実装を見比べたい。
2. 操作：タスク一覧の「状態」を読み、実行時間・待機時間・二段の最終更新を見る。タスクを開き、フローの作業セルから入力・中間出力・ツール・時間を確認する。
3. 成功条件：状態と理由が一つの列で読め、重複する報告到着文や実行器列はない。表示時間はページを開いた時点で固定され、待機時間と実行時間を区別できる。

### UC4：意図しない実行器の作業を止める

1. 場面：実行器一覧で意図しない作業に気づく。
2. 操作：担当セルを押してタスクのフローと開いた詳細へ移動する。タスクの「中断」で止まるセルを確認し、理由または次の指示を任意で添える。
3. 成功条件：中断したセルと、その後の判定器の判断が同じフローで分かる。実行器画面から詳細を開き直す手間がなく、中断は黄色三角で識別できる。

### UC5：作業を続けるための条件を足す

1. 場面：API 実装の途中、または結果の報告を読んだ後に、追加の条件を伝えたい。
2. 操作：フロー下端で指示を重ねる。
3. 成功条件：オーナーの追加指示セルに本文・出所・適用範囲が残る。入力待ちなら作業が再開する。将来の「次の回」という仮セルを操作する必要はない。

### UC6：初期指示を確認して書き換える

1. 場面：保存範囲の報告を読み、最初に出した依頼の前提を修正したい。
2. 操作：報告の判断の文脈で「初期の指示」セルを選ぶ。元のセルの詳細から書き換え、現在の作業を続けるか最初からやり直すかを選ぶ。
3. 成功条件：初期指示をセルとして確認・編集できる。書き換え前後の指示は同じタスクのフローで確認でき、実行を選び直すドロップダウンはない。

### UC7：特定セルの次または並列に確認作業を足す

1. 場面：API 実装にレビューを続けたい、または独立した確認を並列に行わせたい。
2. 操作：基準となるセルを選び、「この次にセルを追加」または「並列するセルを追加」で type と入力を指定する。
3. 成功条件：選んだ位置にオーナーが追加したセルと接続が現れる。次の回だけに挿す仕組みや、未実行の合流ノードを使わない。

### UC8：セルの入力を確認し、指示を追加する

1. 場面：作業セルの解釈を修正したい。対象は動作中の場合と、完了・合流済みの場合がある。
2. 操作：セル詳細で当該試行の入力を読み、指示を追加する。完了・合流済みの場合は、後続成果の破棄を伴う確認を読む。
3. 成功条件：動作中なら当該セルへの入力として反映される。完了済みなら確認を取り消した場合は変化せず、確定した場合だけ依存する後続成果を破棄して対象から再開する。以前の試行入力・出力と独立した並列作業は保持される。

### UC9：失敗からの立て直しを追う

1. 場面：接続が途切れた取り込み処理、または検証環境の不足から再開した作業を確認したい。
2. 操作：失敗セル、判定器の再試行／オブザーバー選択、オブザーバーの判断、再開した作業セルをたどる。必要なら対応する実行器を選んでセルを再試行する。
3. 成功条件：補助バッジがなくてもフローとセルの入力・出力から経緯が分かる。実際に行われた分岐・合流だけが描かれ、試行履歴が確認できる。

### UC10：報告と成果物を読んで、すべての問いに答える

1. 場面：「保存範囲と取り込み先の確認」に、保存対象・取り込み先・守る条件の問いがある。判断にはモックアップ URL、報告用 HTML、議題となるファイルを確認する必要がある。
2. 操作：inbox から報告を開き、最後のユーザー入力、本文、問いより上の「報告のための成果物」を読む。必要に応じて失敗セルの最終応答・オブザーバー判断を展開する。既定の選択肢で答えられない問いは「それ以外」に記入し、全問を「送信」する。
3. 成功条件：判断に必要な資料を回答前に開ける。返答はまとめて一つのオーナーセルになり、入力待ちから進行中に戻る。最初の指示は文脈のフロー図から確認できる。

### UC11：過去の報告と成果物を見て、完了か続行を決める

1. 場面：同じタスクに異なる日時の報告が3件あり、最新と過去を見比べたい。
2. 操作：報告タブの「戻る」「進む」またはドロップダウンで移動する。それぞれの直前入力、縦の目次、本文、成果物リンクを読む。「完了」で記録するか、指示を重ねて続ける。
3. 成功条件：報告ごとに当時のユーザー入力が表示される。ファイルは実ファイル名と相対パスで特定できる。完了・中止の意味はホバー説明で分かる。

### UC12：同時に動く実行器の担当を確認する

1. 場面：`codex-personal` が2タスクにまたがって3セルを担っている。
2. 操作：実行器の生死・担当数と各担当セルを見る。担当セルを押し、フロー上の位置と開いた詳細を確認する。起こす／止める操作は元の指示どおりに行う。
3. 成功条件：全担当セルを確認でき、セルの選択でタスクの詳細へ直行する。type の重複列挙や受け取り元／渡し先の説明はない。

### UC13：role ごとにモデル・プロンプト・skill を設定する

1. 場面：報告担当と判定器に異なるモデル・プロンプト・skill を指定したい。
2. 操作：skill 登録画面で登録する。role 一覧から対象を選び、下部の編集スティッキーで実行器・モデル・注入プロンプトを設定し、ポップアップで登録済み skill を選んで保存する。
3. 成功条件：設定は role ごとに保持され、新しく動く該当 role のセルに使われる。タスク作成ごとに報告担当を指定する必要がない。

### UC14：実行器ごとの契約残量・利用金額を確認する

1. 場面：ある実行器は5時間・週の制限を割合で返し、別の実行器は従量課金額を金額で返す。
2. 操作：実行器ごとに利用状況取得スクリプトを設定し、応答の `title`・`value`・`limit`・`alert` に対応する表示を確認する。モックではスクリプトパスと応答見本を保存して表示を試す。
3. 成功条件：`75% / 100%`、`95% / 100%`、`1$` のような異なる形式を表示できる。UI が単位や閾値を決めず、`alert` がない値には独自に警告を付けない。
