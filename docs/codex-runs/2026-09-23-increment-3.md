# PDA v0.2 増分 3 の実装

あなたはこのリポジトリで PDA v0.2 の増分 3 を実装する。この指示は完結している。質問はせず、最後まで実装し、報告書を書いて終える。判断に迷ったら、この指示の「とりあえず」の決定に従う。指示に無いことは最も単純な選択を取り、報告書の「指示に無かった判断」に書く。

増分 3 は、`main` にある増分 2 の成果を入力として、2 節に列挙した変更を加えるものである。列挙に無い部分は変えない。

## 0. 読むもの、読まないもの

作業前に次を読む。この指示と食い違う場合はこの指示を正とする。

- `docs/requirements.md` 要件。語彙はここに従う
- `docs/design/basic-design-proposal.md` 基本設計。10.1.1 の決定が今回の変更の根拠
- `docs/design/increment-1.md` 設計
- `main` の `src/`、`registry/`、`tools/`、`deploy/`、`tests/` の現状。これが入力

次は読まない。`docs/reports/` の既存ファイル、`docs/codex-runs/` の本指示以外のファイル、`main` 以外のブランチ。

## 1. 成果の置き場所

- 作業場所はミニ PC の `~/pda`（`origin` はミニ PC 上の `~/pda.git`）。`main` から分岐したブランチ `increment-3` で作業する。`main` には触れない。最後に `git push origin increment-3` でブランチを `origin` に送る（外部のサービスへは送らない）
- 認証ファイルは `secrets/codex/auth.json`、`secrets/codex/config.toml`、`secrets/claude/.credentials.json` に置いてある。`deploy/.env` も置いてある。どちらも Git 管理外で、読まない、写さない、変えない
- Python 環境は `.venv` に `uv sync --frozen` 済み。試験は `.venv/bin/pytest`、`.venv/bin/ruff` で走らせる。重い処理は `nice` を付け、e2e の前に `free -h` で空きメモリを見る。この機械では他のコンテナ（firecrawl、openwebui、bp-*）が動いているので、それらを止めない
- `docs/requirements.md`、`docs/design/`、`docs/research/`、`docs/process/`、`docs/reports/` の既存ファイル、`docs/codex-runs/` は変更しない
- 区切りごとにコミットする。コミットメッセージは日本語で 1 文。`Co-Authored-By` 行を付けない
- 秘密情報をリポジトリに入れない。`secrets/` と `deploy/.env` は Git 管理外
- 手順書は `docs/runbook/increment-3.md` に全体を書き直し、`docs/runbook/increment-2.md` は削除する
- 報告書は `docs/reports/increment-3-codex.md`（形式は 7 節）。証拠は `docs/reports/evidence/increment-3/` に抜粋だけ（増分 2 と同じ規則。1 ファイル 300 行まで）
- コードにコメントを書くのは、読んでも分からない理由があるときだけ。指示の文脈、経緯、代替案をコメントに書かない。使わないコードを残さない

## 2. 変更

### 2.1 出来事の送出の作り直し（`src/pda_wrapper/events.py`）

送出部分を作り直す。閉じた種別の表、必須属性、標準出力への JSON 1 行の写し、トレース ID とスパン ID の作り方（`sha256(job_id)` の先頭 128 ビット、`sha256(task_id)` の先頭 64 ビット）は変えない。

- OpenTelemetry Python SDK の公開されたエクスポータ `OTLPLogExporter` と `OTLPSpanExporter`（`opentelemetry-exporter-otlp-proto-http`）を、`BatchLogRecordProcessor` と `BatchSpanProcessor` で使う。自前の送信キューと HTTP 送信を書かない
- `opentelemetry` の名前に `_internal` を含むモジュールを import しない。単体試験で `src/` 全体を grep して `_internal` が無いことを確かめる
- タスクの処理が終わるごと（結果を Conductor に返す前）と、プロセス終了時に `force_flush` する。終了時の待ち上限は 5 秒
- 送り先が無い（環境変数が空）ときはエクスポータを付けず、標準出力の写しだけにする

### 2.2 実行器の入れ替え（会社契約の Claude を外し、個人契約の Claude を入れる）

- `registry/executors/claude-company.yaml` を削除し、`registry/executors/claude-personal.yaml` を作る。`executor_id: claude-personal`、`name: Claude Code 個人契約`、`agent: claude`、`runtime: acp`、`account: personal`、types は break-down、implement、review、summarize、adapter.command は `["npx", "-y", "@agentclientprotocol/claude-agent-acp@preview"]`、adapter.env に `CLAUDE_CONFIG_DIR: /claude-config`、network は `["api.anthropic.com", "claude.ai"]`、cost.per_run_estimate は null。permissions は `{default: allow_once, deny_kinds: []}`
- `registry/judge/questions.json` の executor の選択肢から claude-company を外し claude-personal を足す。criteria に費用不明と到達資源を書く
- compose の `exec-claude-company` を `exec-claude-personal` に置き換える。profile `real`。`${CLAUDE_AUTH_DIR:-../secrets/claude}:/claude-config` を読み書きでマウントし、加えて `./executors/claude-settings.json` を `/claude-config/settings.json` に読み取り専用でマウントする。`deploy/executors/claude-settings.json` の中身は `{"permissions": {"defaultMode": "bypassPermissions"}}`
- Codex は確認なし実行にする。`registry/executors/codex-personal.yaml` の adapter.env を `INITIAL_AGENT_MODE: agent-full-access` にする。このモードはアダプタが毎ターン承認方針 `never` とサンドボックス `danger-full-access` を Codex に渡す（[codex-acp の README](https://github.com/agentclientprotocol/codex-acp/blob/main/README.md) と `src/AgentMode.ts`）ので、Codex 本体の `config.toml` に承認とサンドボックスの設定は要らない。`config.toml` は認証のファイル保存 `cli_auth_credentials_store = "file"` の 1 行だけ（[公式資料](https://learn.chatgpt.com/docs/auth)）
- Codex の認証ディレクトリは、コンテナが非 root で動くので `/root/.codex` ではなく `/codex-home` にマウントし、compose の環境変数 `CODEX_HOME=/codex-home` を実行器に与える。アダプタは環境をそのまま Codex に渡すので、Codex はそこを見る。`.env` の `CODEX_AUTH_DIR` の既定は `../secrets/codex` のまま
- 実行器のコンテナはすべて非 root で動かす。Claude Code は root では確認なし実行を拒否する（[公式資料](https://code.claude.com/docs/en/sandbox-environments)「On Linux and macOS, Claude Code refuses to start with this flag when running as root」）ため、また作業ボリュームの所有者を揃えるため、`deploy/executors/Dockerfile` の base で UID 1000 のユーザー `pda` を作り、`/work` と `/app` の所有者にして `USER pda` で動かす。全実行器と写しが同じ UID になる。手順書に、`secrets/` 配下と `.env` で指すディレクトリの所有者を UID 1000 にする手順を書く
- Claude Code のアダプタが権限モードをどう決めるかを [アダプタの README と docs](https://github.com/agentclientprotocol/claude-agent-acp) で確かめる（settings.json を読むのか、起動時の引数か環境変数か）。とりあえず settings.json の `permissions.defaultMode: bypassPermissions` を置き、アダプタ側に別の指定手段があればそれも宣言の adapter.env か adapter.command に足す。確かめた内容を報告書に書く
- 権限要求が来た場合の扱いは変えない（宣言に従って答え、`permission.request` と `permission.response` を記録する）

### 2.3 作業場所の受け渡し

- 共通入力（3.6 の形）に `workdir`（文字列、必須）を足す。値は `/work/jobs/{job_id}`。判定器のラッパーが `dynamicTasksInput` に入れる。judge 自身の入力には要らない
- 全 type の `input_schema` に `workdir` を足す（judge 以外は必須）
- ランタイムへ渡す入力の JSON（事前プロンプトの後ろに付ける `input` と `context`）に `workdir` も入れる
- ラッパーはタスク受け取り後に `workdir` を作る（存在すればそのまま）。ACP の操作役は子プロセスの cwd と `session/new` の cwd に `workdir` を使う。tools の操作役は `workdir` で走らせる。`input` を JSON として読んで作業ディレクトリを取り出す処理は削除する
- 事前プロンプト（`registry/prompts/*.md`、judge 以外）に「作業ディレクトリは `workdir` に与える。ファイルの読み書きはその中で行う」を足す
- `command.run` の出来事に属性 `pda.workdir` を足す。`job.received` にも `pda.workdir` を足す（judge は空文字）
- 試験用エージェントの echo モードは、応答の前に cwd に `note.txt` を書き、その内容を受け取ったプロンプトの末尾 100 字にする。invalid、slow、permission の各モードは変えない

### 2.4 結果送信の意味論

- ラッパーが `POST /api/tasks` に失敗したら、タスクを受け取ってから `responseTimeoutSeconds` が経つまで 1 秒間隔で再送する。それでも送れなければ `unknown` の出来事に理由 `result_delivery_failed` を残して諦める。Conductor 側で応答時間切れになり、再試行で同じセルが再び動くことを受け入れる（少なくとも 1 回の意味論）。報告書にこの意味論を 1 行で書く

### 2.5 Collector のファイル出力の分離

- `deploy/otel-collector.yaml` で、ログは `/var/lib/pda/events/events.jsonl`、トレースは `/var/lib/pda/events/traces.jsonl` に分ける。回転は両方 100 MB、バックアップ 5

### 2.6 定義の登録をコンテナから行えるようにする

- `deploy/executors/Dockerfile` の base で `tools/` も `/app/tools` に複製する。ミニ PC には uv を入れないので、定義の登録は `docker compose -f deploy/docker-compose.yaml run --rm --no-deps exec-tools python /app/tools/generate_defs.py --conductor http://conductor-server:8080 --registry /registry` で行う。この形で動くことを e2e の登録で使って確かめる（ホストの Python からの実行も残す）

### 2.7 繰り返しの上限

- `registry/judge/questions.json` に `limits: {max_rounds: 10}` を足す。判定器のラッパーは、これまでに動的セルが走った回の数が上限以上なら、答えに関わらず `then: finish` にし、`judge.answer` に `pda.question_id: next_type`、`pda.answer: finish:round_limit` を残す。fixture でも同じ

### 2.8 試験の追加

単体試験は 2.1〜2.7 の各項目に対応するものを足す。e2e は増分 2 の 8 項目を `workdir` に合わせて直し（e2e 1 は `command.run` の `pda.workdir` が `/work/jobs/<job_id>` で、そのディレクトリに `note.txt` があることを `docker compose exec exec-tools` で確かめる）、次を足す。

9. 宣言の追加だけで実行器が増える（A2）。試験の中で `registry/executors/fake-c.yaml`（`fake-a.yaml` の executor_id と name だけ変えたもの）をリポジトリの `registry/` に書く（compose が既にマウントしている場所）。`generate_defs.py` を実行し、`*.fake-c` の 4 定義が増え、既存の定義が変わらないこと（実行前後の `GET /api/metadata/taskdefs` を比較）を確かめる。判定器は正本を起動時に 1 回しか読まないので、`exec-jev` を再作成する。`docker compose run --rm -d -e PDA_EXECUTOR_ID=fake-c exec-fake-a` で実行器を起動し、fixture の差し替えで `implement.fake-c` を 1 つ動かして `COMPLETED` を確かめる。終わったら（失敗しても）コンテナを止め、`fake-c.yaml` を消し、`*.fake-c` の定義を `DELETE /api/metadata/taskdefs/{name}` で消し、`exec-jev` を再作成する。宣言の追加に判定器の再作成が要ることを報告書に書く
10. 実 Codex。認証ファイルは `secrets/codex/auth.json` と `secrets/codex/config.toml` に置いてある（Git 管理外。中身を読まない、写さない）。profile `real` の `exec-codex-personal` を起動し、fixture の差し替えで `implement.codex-personal` を 1 つ、`initial_input` は「作業ディレクトリに hello.py を作り、実行すると hello と表示するようにせよ。作ったファイル名を報告せよ」で動かす。`COMPLETED`、`/work/jobs/<job_id>/hello.py` の存在、`job.received` の `pda.agent_mode`、`permission.request` の有無、`turn.end` の `stop_reason`、出来事の種別の集合を記録する
11. 実 Claude。認証ファイルは `secrets/claude/.credentials.json` に置いてある。10 と同じことを `implement.claude-personal` で行う
12. 同じ仕事を 2 実行器で（A1）。10 と 11 の出来事の種別の集合と Conductor の記録の欄の集合を比べ、差を報告書に書く

10〜12 は必須。認証ファイルが無い、またはアダプタが認証に失敗したときは、その応答（アダプタの標準エラーの末尾）を証拠に残して失敗として報告する。認証操作は行わない。実 Codex と実 Claude は外部の API に接続し費用が掛かるので、10〜12 のそれぞれで仕事は 1 つだけ動かす。

## 3. 部品ごとの受け入れ条件

報告書に、次の条件を 1 つずつ合否で書く。確かめ方も書く。増分 2 で合格した部品も、変えていないことを含めて再確認する。

- 出来事の送出: `_internal` の import が無い。公開エクスポータと Batch プロセッサを使っている。出来事が OpenObserve とファイルに届く。トレース ID とスパン ID が決定的。プロセス終了時に未送信が残らない（終了直前の出来事がファイルに現れる）
- 実行器の宣言: claude-company が無く claude-personal がある。19 のタスク定義が生成される（実行器 6、組み合わせは増分 2 と同数）
- Codex と Claude の権限: 宣言の env と設定ファイルが確認なし実行になっている。値の根拠が報告書にある。実行器のコンテナが非 root（UID 1000）で動く（`docker compose exec exec-fake-a id -u` が 1000）
- 作業場所: 全セルの入力に `workdir` があり、ラッパーが作り、操作役がそこで動く。`command.run` と `job.received` に `pda.workdir`
- 結果送信: 送信失敗時に `responseTimeoutSeconds` まで再送し、諦めたら `result_delivery_failed` を残す（単体試験でモック）
- Collector: ログとトレースが別ファイル
- 繰り返しの上限: 上限に達した判定器が finish を返し、理由を残す（単体試験で fixture を上限回数だけ continue にして確かめる）
- ラッパーの起動、期限、停止、分類とスキーマ検査、ACP・jev・tools の操作役、試験用エージェント、写し、compose: 増分 2 の受け入れ条件を満たしたまま
- 試験: e2e 1〜9 が通り、10〜12 は条件により実施か未実施が明記される
