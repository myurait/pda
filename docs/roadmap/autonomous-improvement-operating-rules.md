# 自律改善再設計 運用細則

- Status: active（2026-08-22 オーナー指示。フォークでの律速分析に基づく）
- 位置付け: `docs/roadmap/autonomous-improvement-goal.md` と `docs/design/self-improvement-governance-adr.md` に**従属する**運用細則。C1-C9 および ADR D1 の「オーナー固定判断」（統治変更・再有効化・秘密・課金・外部公開・不可逆削除）は一切緩和しない。
- 適用対象: goal 実行主体（外部Fableサイクル）の作業運用。

## 1. 承認は gate 単位に限定する

- オーナーへの承認要求は各マイルストーン exit gate でのみ行う。gate 報告に「次 gate までに実行する反映操作の一覧」（main統合、パッチ適用・再起動、台帳操作、worktree GC 等）を含めて一括承認を得る。
- 承認済み一覧内の操作は以後、個別確認なしで実行してよい。
- 一覧外の操作が必要になったら、単発の承認要求を投げずに gate まで貯める。進行のブロッカーになる場合のみ即時エスカレーションする。

## 2. サブエージェント / Workflow を標準投入する

- **設計の敵対レビュー**: Hermes本体・統治・本番に触れる変更は、実装着手前に複数レンズ（正しさ／upstream慣行との適合／互換性／迂回可能性）の並列反証レビューを通す。高コストな実機検証より先に机上で欠陥を潰す。
- **検証パイプライン**: フルスイート実行 → 失敗名diff → 失敗1件ごとの単独再現と分類（flaky／変更起因）は、失敗1件=1エージェントの pipeline で自動化し、本体は判定と修正だけを行う。
- **並列実装**: 相互依存の薄い実装項目は、worktree 分離つきの並列実装＋実装者とは別の独立検証者ステージで進める（M2 の運用モデルの先取りを兼ねる）。探索・機械的編集の Sonnet 委譲は維持する。
- 出力が成果物に消費される AI 起動は C6 の制限対象ではない。

## 3. ミニPC負荷規律

- agent-node 上のフルスイートは常に**直列・nice付き**で実行し、変更をバッチして gate 直前に原則1回にまとめる。実行前に `free -h` を確認する。
- 並列化してよいのは開発PC側の分析エージェントのみ（agent-node は 12GiB・OOM 実証済み。2026-08-22）。

## 4. 権限ブロックの扱い

- ハーネス権限分類器にブロックされた操作は、代替経路の試行を**2回まで**とする。
- 通らなければ「オーナー実行用コマンド＋settings.json allowlist 追記案」として gate 報告に集約し、手を止めずに他項目へ進む。

## 5. 再開時の実状態検証

- セッション再開・compaction 後は、記録上「実行済み」の操作を信用せず、ground truth（origin / agent-node の HEAD、ライブ Hermes の HEAD、盤面、承認 ledger）から実状態を再導出してから続行する。

## 6. 報告規律

- オーナー向け報告は承認シート artifact の更新＋チャット数行に限る。
- 操作単位の逐次報告・実装者語彙の報告はしない。オーナーが行動に使う識別子（カードID・リンク・対象名）は省略しない。
