# V2-M2再定義 — 単純に復帰できる本体を選ぶ

更新日: 2026-09-08 JST。追跡正本: default board / pda-improvement / `t_ec4c52b9`。関連: 全体 `t_395213b7`、M3 `t_0a0c6ad7`。

状態: 既存の委任とオーナー訂正に基づく課題定義の修正。旧試作品はNO-GOのまま。新候補の選別・実証は未実施で、製品採用、本番反映、自律dispatcher再開を意味しない。

## 1. 結論と変更の効力

M2を「復旧・制御基盤を先に作り、その上に本体を選ぶ」段階から、「単純な復帰で活動を継続できる本体候補を選別し、隔離実証する」段階へ変更する。M3に置いていた本体の予備比較をM2の先頭へ移す。M2→M3の依存は残すが、M3開始の前提を独自controlの完成にしない。

これは自己完全性の先送りでも、停止・作用整合の要求緩和でもない。失敗時の応答・修復能力の回復と、個別の仕事の再開資格・外部結果確認を分け、後者の未確定をPDA全体の不通へ連座させない。本体が戻れば全ての仕事が完了したことにもならない。

本書は、旧自走計画（2026-09-07_104307-pda-v2-autonomous-milestones.md）のM2/M3の実行順、M1 state-custody実装の継承必須条件、旧NO-GO報告の「次の境界」を置換する現行の実行仕様である。旧版とレビューは履歴として残す。憲章、明示停止、情報境界、本番作用の許可条件は変更しない。M1の原因証拠・反例は再利用するが、そこで選んだDBOS＋独自controlという解決案と800行上限を要件へ昇格させない。

根拠は[PDA憲章](../../pda_charter.md)第六条・第七条と、オーナーの「復旧にAIも複雑なサービスも必要ない。複雑な復旧機構を要求するなら、そもそもその本体機能それ自体に問題がある」という訂正である。

## 3. 何を残し、何をやめるか

| 既存の論点 | 残す要求・具体的ケース | 新しい担当と実現方針 | やめる仕事 |
|---|---|---|---|
| 起動元消滅・作業残留 | 担当消滅後に旧作業が残り、新担当と競合しない | M2で候補標準の監督・再起動と仕事の記録を実機確認。不足なら本体・実行の持たせ方を変更または棄却 | 旧launcher用の独自watchdog追加 |
| 作業領域の枯渇 | 一件の作業出力増大で応答・保存済み状態・復帰まで壊さない | M2で候補の標準的な資源制限と永続状態の保全を確認。全ホスト枯渇を実際に起こす試験はしない | 旧試作の保存構成を維持するための独自容量管理系 |
| 停止と送信の競合 | 停止済み仕事を再起動で再開しない。開始済み操作の取消を偽らない | M2は停止の永続保持・旧仕事の非自動再送を確認。M3では実際に採る活動・送信先について停止と実行の意味を実接続で検証する | 全runtime・全外部APIを支配する新しい汎用送信proxy |
| 外部作用の結果不明 | 完了不明を消さず、再送による二重作用を避け、確認可能なら確認を続ける | M2は未確定記録を残したまま本体が戻ることを確認。M3で実活動の安定ID・対象照会・重複防止など既存能力を比較し、M4で実証済み方式を統合する | 旧DBOSのuncertainを救うための独自汎用照合サービス |
| 記録・復元・更新 | 記憶、仕事、停止を保ち、正常版復元で利用可能状態へ戻る | M2で実在する候補の保存・復元・rollbackを試す。M3で全体の移行・退出と照合する | 旧control DBとDBOS DBの構造を全候補へ継承すること |
| 指示の効力 | 局所的な障害対応へ注意が移っても、低保守負担という指示が案の棄却に作用する | M2の採否記録とM3の注意・記憶評価に、過去指示→今回の選択→実際に作らなかったものを残す | 指示の再引用や追記を合格とすること、新しい指示監視サービス |

要求をどの部品へ置くかは比較結果で決める。単純さを部品数・行数だけで判定せず、停止時に必要な依存関係、独自に保守する責任、更新・復元の操作と実測時間で判断する。既製品の寄せ集めでも復帰経路が複雑なら失格。独自コードを接続層と呼び替えて存続させない。

## 4. 新M2の一回の自走単位

入力は旧M1/M2の失敗証拠、上記要求、既存の広域比較調査、現在のowner委任。PDA自身が直列で、調査→候補選別→隔離試験→棄却・修正→証拠整理まで進める。subagentは起動しない。時間・クレジットを理由に途中の再承認を求めない。新規課金契約・認証操作・情報区分拡張・対象外本番作用や明示停止の解除を自動的に許可されたと解釈しない。

最初の比較は、Hermesの最小標準構成を対照に、現行Lettaの公式構成、運用負担をサービス側へ移す管理型／混成の代表。これらの実現性・利用条件・標準復帰範囲を一次資料で更新する。名称や機能表だけで優劣は決めない。候補が自身の正常復帰にAI診断やPDA独自の複雑な制御連携を必要とするなら、周辺部品を作る前に棄却する。許可された認証・送信条件がない管理型候補は未検証として残し、性能で負けたことにしない。

資料選別を通った最小候補を隔離環境で実行し、主プロセス停止、起動不能の更新、記憶・モデル接続障害、担当消滅、限定した資源上限、停止中・外部結果不明での再起動を試す。復帰に使うのは標準監督、事前に用意した正常版・互換データの復元等の決定的手段。AIが原因を調べて修理してから戻る成功例は、この復帰試験の合格に数えない。標準手段を結ぶ小さな設定・宣言は許容するが、新しい業務状態機械や復旧service群を作り始めない。

単なるHTTP正常では足りない。モデルが利用可能なら、復帰後のPDAが保存済みの依頼・記憶・停止・未確定操作を読み、継続できる仕事と保留すべき仕事を区別できるところまで確認する。モデル停止中の状態表示を、自然言語応答の完全復旧と報告しない。仕事の全面自動再開もM2だけでは合格にしない。

Exitは、実証済みの候補、対応できる故障範囲、復帰時間、保持できる状態、未確認事項、PDAが将来保守するもの、棄却した構成と理由を示す判定資料。既存の状態表示2分・正常版復帰5分の目標を維持し、結果を見て合格閾値を緩めない。対象試験でオーナー救出、保存済み状態の喪失、停止済み仕事の誤再開、未確定操作の盲目的再送は0を要求する。対応しないホスト全損・全provider断を明示する。

合う候補がなければM2はNO-GO。別の本体方式・管理型・責任範囲を検討し、勝手に汎用復旧基盤の自作へ戻らない。低保守の候補に実証見込みがない場合だけ、要求と実現性の本当の衝突をオーナーへ提示する。

## 5. M3以降と現在の未完了

M3はM2で単純復帰が成立した候補について、注意切替、部分的忘却、休眠skill再発見、活動UI、実仕事の停止・結果照合・引継ぎ、更新・退出を同じ活動で比較する。これらの必須条件が未実証ならM4統合へ進めない。M2が限定成功でも、個別仕事を永久保留して「自己完全性完成」とはしない。

M3では、過去指示を検索・説明できたかに加え、今回のような追加部品の誘惑がある問題で、低保守負担の指示を適用して棄却・選択できるかを試す。これはF19等の制約保持を判断行動まで追跡する評価であり、新しい常駐gateの実装依頼ではない。

M4〜M7の全体統合、shadow、canary、限定常用は目標として残る。採用構成に依存する実装詳細はM3 exitで更新し、旧M1/M2のcontrol実装をそのまま必須条件として継承しない。各本番適用の既存承認境界、明示停止、データ所有条件は維持する。

今回検証したのは、課題定義・証拠・依存順の整合である。新構成の単純復帰、将来の指示遵守、M2/M3の合格を実証したわけではない。
