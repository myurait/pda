# 開発の進め方: リメイクのサイクル

- 更新: 2026-09-22 JST
- 種別: 開発の進め方の取り決め。PDA の開発で使い、PDA 完成後も開発タスクの主要な進め方とする。

## 役割の区切り

- 設計側（Fable）は、思想と抽象を「とりあえず」の設計に落とし込み、実装に渡す指示を書く。片づいていない問いは、指示の中で「とりあえずこれで実装」と決めて閉じる。開いた問いを実装側に渡さない。
- 実装側（Codex）は、新規チャットで、指示だけを入力に、ロングランのワンショットで可能な限り実装する。会話のコンテキストに頼らず、完全な指示形式で受ける。
- 評価は設計側で行う。作ってみてどうだったか、どこが不確定だったかを、実装の成果から読み取る。

## サイクル

1. 設計側が、すべてを具体化した指示を 1 本書く。自由度の高い問いが残っていると実装の品質が下がるので、残さない。
2. 実装側が新規チャットからワンショットで実装する。
3. 設計側が成果を評価する。部品ごとに、完成しているか、直す量がどれだけかを見る。
4. 直す量が 25% 以上の部品と成果は捨てる。完成している部品だけを残す。
5. 反省点を、成果物ではなく設計と決定と指示に反映する。
6. 直した指示で、もう一度ワンショットを回す。良いものができるまで抽選する。

## 理由

成果物に対して改善を重ねるより、指示だけを改善して良いものができるまでワンショットを引き直す方が、費用が安く、最終の品質が高い。非決定論的な成果は再抽選する。「保守・改善」ではなく「リメイク」を回す。

## 指示の書き方

- 実装側が読むべき正本（要件、設計）を列挙し、指示と食い違う場合は指示を正とすると書く。
- 未確認の事項ごとに「とりあえずこう作る」と決めて書く。動かなかった場合の代替も、判定の基準と一緒に書く。
- 成果の置き場所、ブランチ、コミットの単位、報告書の形式を固定する。
- 実装側が確かめるべきことを列挙し、確かめた結果を報告書に書かせる。設計側はその報告書から不確定部分を拾い、指示に反映する。
- 人でなければできない手順（認証、機器への配置）は、実装側に手順書として書かせ、実行は人が行う。

## 捨てる基準

- 直す量が 25% 以上の部品・成果は捨てる。境目は厳しめに判定する。
- 捨てた成果からは、反省点だけを設計と指示に持ち帰る。コードは持ち帰らない。
- 残すのは、単体で完成し、次のワンショットの入力（既存の部品）として渡せるものだけ。
