## 不備と割り当て

直さず（リメイク）

- ラッパーの起動と停止。Conductor Python SDK の多重プロセスのワーカー機構と噛み合わず、中断後に旧ワーカーが再試行を受け取らないよう、シグナル処理で強制終了している。触る関数は起動、シグナル処理、タスク受け取りの 3 つで、この部分の関数のほぼ全部。次の指示で、SDK のワーカー機構を使わず Conductor の poll と update の API を直接叩く単一プロセスのループとして作り直す。契約処理と操作役は入力として渡す。

直す（1 回の追加指示、汚染なし）

- 写しが、最終取得を終えた仕事のタスク記録を捨てない。長期運転で記録が増え続ける。1 関数内の数行。
- 写しが jev 用の内部ネットワークに乗って Conductor と Collector に到達している。compose に写し専用の内部ネットワークを足す。設定項目の追加。
- パッケージ名が「増分 1」を含む。値の差し替え。

直さない（負債。4 部品に及ぶため、増分全体の一括リメイクの根拠）

- ラッパーの契約処理: タスクごとに正本のファイル全部を読み直す。
- ACP の操作役: アダプタの標準エラーの全行を `unknown` の出来事にする。実 Codex や実 Claude では npm の出力が雑音として大量に入る。
- jev の操作役: 数値の問い（is_complete）の出来事で、確信度の欄にその数値そのものを入れている。
- compose: 外向き通信の宛先制限が Docker のネットワーク分離だけでは掛からず、jev、Codex、Claude の実行器は許可した宛先以外にも到達できる。ミニ PC で閉じている間は受け入れる。

## 設計の見落とし（次の指示の範囲）

- 応答時間切れは再試行をキューに入れるだけで、動いているランタイムを止めない。リース延長が有効な限り、生きて詰まったワーカーでは応答時間切れ自体が起きない。ラッパーが type の規則から期限を持ち、期限でランタイムを止める。
- ACP の `usage_update` はコンテキストの占有量と容量で、トークン数ではない。費用は宣言の見積り値で扱い、実測はベンダー側の記録を後で当てる。
- Conductor の入力スキーマの強制は登録が通ったことしか確認していない。合わない入力での挙動を e2e に加える。
- kind が `input` の出力を次のセルへ渡す経路（A12）は、fixture の 2 回目が finish を返すため未通過。fixture に 3 回目を足す。
- 部品ごとの受け入れ条件を指示に書いていなかった。
- 証拠として Conductor の記録全文（2 万行）が入った。次の指示では抜粋の範囲を指定する。

## 設計側の誤り

- 雛形の繰り返し条件。設計文書は `$.judge['output']['payload']['then']` と書いたが、Conductor はループ内タスクの出力を参照名の直下に置く。実装側が `$.judge['payload']['then']` に直して通した。設計文書を直した。
- 設計文書の雛形 JSON に、本文で外すと決めた `join.output` の参照が残っていた。直した。
