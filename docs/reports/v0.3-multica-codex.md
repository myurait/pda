```text
systemd --user (1274)
└─ multica daemon start --foreground --no-auto-update --no-auto-reload --max-concurrent-tasks 1 (265474)
   ├─ T2: /home/user/.local/bin/claude (266282)
```

T2 と T4 は順番に実行した。図の二つの枝は同時実行を表さない。

固定版の [server/pkg/agent/claude.go:36](https://github.com/multica-ai/multica/blob/v0.6.1/server/pkg/agent/claude.go#L36) は Claude CLI を起動する実装で、同ファイル 78 行で command を作り、1078 行以降で上記引数を組み立てる。[server/pkg/agent/launch.go:112](https://github.com/multica-ai/multica/blob/v0.6.1/server/pkg/agent/launch.go#L112) は Go の `exec.CommandContext` を呼ぶ。採取した Claude 経路は利用者の CLI の直接起動であり、`@anthropic-ai/claude-agent-sdk` や ACP adapter を読み込んで起動する経路ではない。

## 5. 認証

unit と手動準備では HOME を `/home/user/v03/agent-home`、CLAUDE_CONFIG_DIR を `/home/user/pda/secrets/claude` とし、PATH の先頭を `/home/user/.local/bin` にした。unit に CODEX_HOME の値は設定せず、`UnsetEnvironment=CODEX_HOME` を指定。手動起動は `env -u CODEX_HOME` とした。既設の `.claude` / `.codex` symlink を利用し、AI プロバイダーの API キーや新たな CLI ログインは求められなかった。

実際の子プロセスでは Multica 自身が PATH の先頭へ製品 CLI のディレクトリを加え、Codex の CODEX_HOME を task ごとの `runtime/.../codex-home` に設定していた（[daemon.go:8495](https://github.com/multica-ai/multica/blob/v0.6.1/server/internal/daemon/daemon.go#L8495)）。[codex_home.go:17](https://github.com/multica-ai/multica/blob/v0.6.1/server/internal/daemon/execenv/codex_home.go#L17) と 194 行以降には認証を symlink、設定をコピーする実装がある。実測でも `auth.json` は既設の `/home/user/v03/agent-home/.codex/auth.json` への symlink で、通常ファイルの認証複製は検出しなかった。内容は読まず、[08-auth-metadata.txt](evidence/v0.3-multica/08-auth-metadata.txt) と終了時の `ls -l` に記録した。

Multica 自身の Web ログインは必要だった。[公式のログイン手順](https://multica.ai/docs/self-host-quickstart#4-log-in-and-create-a-workspace) に従い、ローカル backend が出す確認コードを使った。デーモンは製品自身の PAT で接続し、その保存場所は最終的に `/home/user/v03/multica/state/config.json`（0600）。これは Claude / Codex の認証情報とは別である。値は報告・証拠に保存していない。

終了時には次を行った（[10-cleanup.txt](evidence/v0.3-multica/10-cleanup.txt)）。

- `systemctl --user stop v03-multica.service` で停止。4 コンテナは Exited、5101 / 19514 の待ち受けなし。Compose は `stop` を使い、コンテナ・volume・導入物は残した。
- 共用 HOME に新規作成された `.multica` を製品の `state/` へ rename し、unit が起動時だけ symlink を置く設定にした。変更後に起動・`/readyz`・同じ daemon ID・実行中 task 0 を確認し、再度停止。終了時に共用 HOME の `.multica` はない。
- Codex が使用した task 別 `auth.json` symlink 4 本を削除した。参照先の認証本体には触れていない。
- 今回の CLI 起動で作られた `/home/user/pda/secrets/claude/backups/.claude.json.backup.*` 6 個を、内容を読まず削除した。各ファイル名と削除結果は証拠にある。
- 専用の `tmux -L v03-multica` server を終了。採取用のブラウザと API 接続も終了した。

認証本体の `.credentials.json` / `auth.json` / `.claude.json` と共有の `settings.json` / `config.toml` は実装側で直接読み書き・削除していない。信頼設定は指示どおり各 CLI に保存させた。製品による共有設定への MCP・hook・plugin の新規登録は観測しなかった。終了時の `claude mcp list` は `claude.ai Claude Docs`、`codex mcp list` は `No MCP servers configured yet` だった（[10-mcp-after.txt](evidence/v0.3-multica/10-mcp-after.txt)）。製品が各 task に用意する説明・標準 skill は専用の作業場所に残っており、独自の連携 skill / MCP は追加していない。

## 6. 人の手順

root が必要となる未実施の導入手順はなかった。終了時は停止しているので、再度開く際は他の試用サービスが停止していることを確認し、次を実行する。

```bash
systemctl --user list-units 'v03-*.service' --all --no-pager
systemctl --user start v03-multica.service
curl -fsS http://127.0.0.1:5101/readyz
```

ローカル画面は `http://127.0.0.1:5101/login`。Tailscale Serve の公開操作は今回実行していない。人が実行するコマンドは次のとおり。

```bash
/home/user/.local/bin/tailscale-pda serve --bg --https=19101 http://127.0.0.1:5101
```

Serve が示すホスト名を使い、公開 URL は `https://<ホスト名>:19101/login`、試用結果は `https://<ホスト名>:19101/pda-multica-trial/issues/PDA-6`。公開時には `/home/user/v03/multica/trial/server.env` の非秘密設定 `FRONTEND_ORIGIN` と `MULTICA_APP_URL` を `https://<ホスト名>:19101` に合わせて `systemctl --user restart v03-multica.service` を行う。`MULTICA_DAEMON_SERVER_URL` はローカルの `http://127.0.0.1:5101` を使う構成である。gateway の `/ws` と `/api/daemon/ws` は backend へ転送済み。[公式の単一 origin 構成](https://multica.ai/docs/self-host-quickstart#remote-access) に対応する。

ログインは次の手順で行う。

1. `/login` で `pda-multica-trial@example.invalid` を入力し、`Continue` を押す。
2. メール送信サービスは未設定なので、ミニ PC 上で次のコマンドから最新のコードを取り、画面へ入力する。コードの値を報告書やチャットへ貼らない。

   ```bash
   docker logs v03-multica-backend-1 2>&1 \
     | rg 'Verification code for pda-multica-trial@example.invalid' | tail -1
   ```

3. この試用アカウントは onboarding を完了済み。別の初回アカウントでは onboarding が出る。既存 workspace がある場合は `I've done this before` で進めた。
4. `PDA Multica Trial` の Issues を開く。PDA-1 / 3 は通常実行、PDA-2 / 4 は停止、PDA-5 / 6 は双方向引き継ぎの記録。issue 右側の Execution log から run を開ける。

デーモン用の製品 PAT が失効・取り消しされた場合は、稼働中の Web の `Settings → API Token` で新しく発行し、次の CLI のプロンプトへ入力する。[公式 CLI 認証文書](https://github.com/multica-ai/multica/blob/v0.6.1/CLI_AND_DAEMON.md#authentication) にある headless の経路である。

```bash
env -u CODEX_HOME HOME=/home/user/v03/agent-home \
  CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude \
  PATH=/home/user/.local/bin:/home/user/v03/multica/bin:/usr/local/bin:/usr/bin:/bin \
  /home/user/v03/multica/bin/multica login \
  --server-url http://127.0.0.1:5101 --token=
```

確認後の停止は `systemctl --user stop v03-multica.service`。この unit は `docker compose stop` を呼ぶ。公開を終える際は人が追加した Serve 設定も人が戻す。
