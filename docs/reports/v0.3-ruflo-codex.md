## 1. 結論

T1 は CLI/MCP の常駐に成功し Web UI の導入は失敗、T2 は権限拒否で差分なし、T4 は編集を完了したが途中の本文は出なかった。T3/T5 は製品の公開 JavaScript API でそれぞれ 0.538 秒／0.018 秒で停止したが、本文の途中出力が始まった後に止める条件は満たせず、T1〜T5 の全条件を通過した項目はない。

## 3. 試用の結果

証拠はすべて `docs/reports/evidence/v0.3-ruflo/`。本文の「途中出力」は Claude/Codex の文やツール出力を指し、製品の `worker:started` という通知と区別した。失敗後の同一手順は最大1回だけ再試行した。

### T1 導入と常駐

やったこと: npm 導入2回、Docker build 2回、公式 `ruflo mcp start --transport http --host 127.0.0.1 --port 5121` を user unit で起動1回。\
起きたこと: npm 初回は `No matching version found for @claude-flow/codex@3.0.3.`、再試行成功。Docker 初回は `"/.env": not found`、再試行は `Error: OPENAI_BASE_URL not set`。HTTP MCP は active、`/health` 200、`/` 404。Web 画面は未提供。\
証拠のファイル名: `01-install.txt`、`01-npm-install.txt`、`01-docker-build.txt`、`01-docker-build-retry.txt`、`01-unit.txt`、`01-listen.txt`。

### T2 Claude Code に頼む

やったこと: 指定文を scratch で `dual run --worker claude:coder:…` に1回送信。差分がなく、CLI が本文を表示しない実装を調査し、同じ製品の公開 API で最終返値を取得する形で1回再試行。\
起きたこと: 初回は `SUCCESS`、Claude 子プロセス19.3秒、差分なし。再試行は12.2秒で「権限が未許可のため、ツールが拒否されました。許可いただければ編集を続けます。承認をお待ちします。」と返り、製品の status は `completed`／`success:true`、差分なし。起動と完了の通知の間に本文イベントはなかった。利用した worker 設定・引数組立てには権限省略フラグの項目がなかった。計2回。\
証拠のファイル名: `02-claude-stream.txt`、`02-claude-result.txt`、`02-claude-retry-stream.txt`、`02-claude-retry-result.txt`、`02-claude-retry-request.json`。

### T3 Claude Code を途中で止める

やったこと: 同じ依頼をもう1回送信し、`worker:started` から3秒後に製品の `stopAll()` を呼んだ。本文の途中出力は公開されないため、その表示を停止の契機にはできなかった。\
起きたこと: 停止要求 21:14:38.907、子プロセス close 後の失敗通知 21:14:39.445 JST、0.538秒。`Worker coder exited with code 143:`。製品の停止APIによる終了を確認した。本文表示後の停止条件は未達。1回。\
証拠のファイル名: `03-claude-stop.txt`、`03-claude-stop-stream.txt`、`03-claude-stop-request.json`。

### T4 Codex に頼む

## 4. Claude Code と Codex の起動のされ方

T2 初回は Node の Ruflo CLI PID 339615 → Claude PID 341016。再試行は Node の公開 API 呼出し PID 341497 → Claude PID 341637。T4 は Node の公開 API 呼出し PID 342302 → Codex PID 342424。cwd はすべて scratch だった。

[dual-mode/orchestrator.ts の206〜281行](https://github.com/ruvnet/ruflo/blob/caf5078be6627c6496fa2497a63b72e80a0bcf14/v3/@claude-flow/codex/src/dual-mode/orchestrator.ts#L206) は `child_process.spawn` で実行器を起動する。Claude は `-p <prompt> --output-format text`、Codex は `exec --sandbox workspace-write --skip-git-repo-check <prompt>`。stdout/stderr は文字列に蓄積し、close 時に返す。CLI の `printResults()` は本文を表示せず、公開 API では完了時に `workers[].output` を取得できる。`stopAll()` は [666〜671行](https://github.com/ruvnet/ruflo/blob/caf5078be6627c6496fa2497a63b72e80a0bcf14/v3/@claude-flow/codex/src/dual-mode/orchestrator.ts#L666) で子に SIGTERM を送る。

指示ファイルの手がかりにあった [`headless-worker-executor.ts:1397`](https://github.com/ruvnet/ruflo/blob/caf5078be6627c6496fa2497a63b72e80a0bcf14/v3/@claude-flow/cli/src/services/headless-worker-executor.ts#L1397) の `claude --print --output-format json` も存在するが、今回の指定タスクに使った経路は上記 dual-mode だった。実行した経路では Agent SDK／ACP adapter を介していない。T3/T5 はローカルプロセス内の JavaScript API 呼出しであり、Web画面やHTTP RPCからの停止を観測したものではない。

## 5. 認証

手動起動には `/home/user/v03/ruflo/run-env` を使い、環境を限定して `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude`、PATH の先頭 `/home/user/.local/bin` を渡した。`CODEX_HOME` は設定せず `env -u CODEX_HOME` で外した。unit も同じ HOME・PATH・ラッパーを使用した。API キーは投入していない。認証・設定の秘密ファイルを開かず、既存の `.claude`／`.codex` symlink を CLI に使わせた。

試用前に tmux で両 CLI を起動し、scratch の信頼確認に答えた。Claude は Claude Pro の通常入力画面、Codex は GPT-6-Astra の通常入力画面まで到達した。信頼の記録は各 CLI が書き、設定ファイルを手で編集していない。実行中にログイン画面や API キー入力を求められた事実はない。Claude の失敗はツール権限の拒否という返答だった。

Web UI は起動前にビルドで止まり、画面上の認証要求を観測していない。公式の RuVocal 手順は OpenAI 互換 endpoint とキーを例示する。橋渡し実装の [`/chat/completions`](https://github.com/ruvnet/ruflo/blob/caf5078be6627c6496fa2497a63b72e80a0bcf14/ruflo/src/ruvocal/mcp-bridge/index.js#L1815) は provider のキーがなければ `No API key for provider: …` を401で返す構造だった。この直接API経路を実行せず、既存CLIのログインをWebチャットに使用する設定は今回確認できなかった。

終了時の `claude mcp list` は開始時と同じ既存の `claude.ai Claude Docs` のみ、`codex mcp list` は登録なしだった。製品の MCP／hook／plugin を追加する初期化コマンドは実行していない。共有 HOME の `settings.json` と `config.toml` は、内容を読まず比較したサイズ・更新時刻が開始前と一致した。認証の複製ファイルは新規作業領域のメタデータ調査で見つからなかった。

`systemctl --user stop v03-ruflo.service` 後、5121番の待受が消えた。別に残った Ruflo の worker daemon PID 347361 は scratch で製品の `daemon stop` を実行して停止した。試用用 tmux は終了済み。共有 HOME に新規作成された `.claude-flow/update-state.json` と空ディレクトリ、複製された Claude 設定の `backups/.claude.json.backup.*` のうちこの走行中に生成され現存していた5件を、メタデータのみ確認して削除した。認証本体・設定本体には手を加えていない。導入物と scratch は保持した。詳細は [10-auth-metadata.txt](evidence/v0.3-ruflo/10-auth-metadata.txt)、[10-cleanup.txt](evidence/v0.3-ruflo/10-cleanup.txt)。

作業場所の規律からの逸脱が1回あった。最後の共有メモリ読出しコマンドで cwd 指定を落とし、製品が報告リポジトリ直下に未追跡の `ruvector.db` を作った。生成時刻と開始時に無かったことを確認して削除した。Claude/Codex の仕事はすべて scratch で実行し、最終的に報告リポジトリに残した変更は報告書と証拠だけである。

## 6. 人の手順

ホストで root が必要となる必須手順はなかった。Dockerfile 内部の apt 以外に apt／sudo を実行していない。Codex はホストの bubblewrap 不在を通知したが、同梱版を使って T4 を完了した。

HTTP MCP を再開する手順:

```sh
systemctl --user start v03-ruflo.service
curl -sS http://127.0.0.1:5121/health
/home/user/.local/bin/tailscale-pda serve --bg --https=19121 http://127.0.0.1:5121
```

Tailscale のホスト名は `/home/user/.local/bin/tailscale-pda status` で確認する構成。公開時の対応パスは `https://<ホスト名>:19121/health` と `/rpc`。この走行では Serve を実行していない。現在の unit は MCP サーバであり、チャット画面はない。画面のログイン手順・トークンの置き場所は未確認で、入力する値は記載しない。

使い終わったときは `systemctl --user stop v03-ruflo.service`。Web UI の再ビルドはこの走行での上限に達しており未実施。ビルド時の `OPENAI_BASE_URL` 設定と、その先の起動可否が未確認である。

## 7. 分からなかったこと

- Web UI の起動、画面上のログイン・途中出力・停止。Docker build の2回目で終了したため。
- dual-mode で Claude のツール権限を製品設定から許可して同じ依頼を完了できるか。公開 worker 設定と引数の組立てに権限省略の指定は見当たらず、T2 は2回で打ち切った。
- `stopAll()` が孫プロセスまで必ず止めるか。今回確認したのは直接の Claude/Codex 子プロセスの close である。T9中に起動された別の Ruflo daemon は後片付けで明示的に停止した。
- Tailscale 経由・別端末・スマホからの到達。指示されたローカル確認のみを行った。
