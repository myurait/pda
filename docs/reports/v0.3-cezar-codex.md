## 5. 認証

製品プロセスの `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude`、PATH の先頭を `/home/user/.local/bin` にした。HOME の `.claude` と `.codex` は用意済みの認証ディレクトリへの symlink のまま使用した。unit の Environment に `CODEX_HOME` は設定せず、`UnsetEnvironment=CODEX_HOME` で継承も外した。手で起動した CLI も `env -u CODEX_HOME` を使用した。

`CEZ_CLAUDE_BIN` / `CEZ_CODEX_BIN` で既存 CLI の絶対パスを指定した。`CEZ_AGENT_MODELS_LOCKED=1` は [公式の環境変数の説明](https://github.com/open-mercato/cezar/blob/1b13522dd3642a4ea8331629b3680838164d2a2e/docs/reference.md#how-it-runs-agents) に従い、認証とモデル選択を既存 CLI に任せる設定として使用した。profile は両方 `default`。既定 profile では環境変数を追加しない実装を `core/agent-profiles.ts` と `workspace/agent-profiles.ts` でも確認した。

API キーは追加せず、unit では `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`OPENAI_API_KEY` も unset した。CLI の事前信頼画面以外にログインや API キー入力は求められず、T2・T4・T9 は既存のログインで完了した。製品アカウントの追加・ログイン・設定ファイルの seed API は呼んでいない。

秘密情報のファイルは内容を読まず、表示・転記・手動変更していない。cezar の state と scratch の worktree で既知の認証ファイル名をメタデータだけ探索したところ、`auth.json`、`.credentials.json`、`credentials.json`、`secure_credentials.json` は0件だった。これは全ファイルの不存在証明ではない（`08-auth-metadata.txt`）。

## 6. 人の手順

今回の導入・試用で root が必須になった手順はない。公式の `cezar-cli server-install --platform ubuntu-vps` の既定経路を別途使う場合は、nginx の導入、`/etc` 以下の nginx vhost と htpasswd の作成、必要に応じて ufw・certbot の設定が root の作業になる。今回はその wizard を実行せず、既に有効な linger と user unit を使用した。

再び開く際は、他製品の `v03-*.service` が止まっていることを確認して、次を実行する。

```bash
systemctl --user start v03-cezar.service
/home/user/.local/bin/tailscale-pda serve --bg --https=19103 http://127.0.0.1:5103
```

Tailscale Serve が表示する HTTPS URL の `/tasks` を開く。T2 のタスクは `/tasks/ee1356dc-d174-4d9c-a694-2f7ce4ac76af`、T4 の差分は `/tasks/afd2f2fb-7b22-416b-bdd5-7127a6f450f5/changes`。この走行では Serve 設定と別端末からのアクセスは未実施。

cezar 自体の画面ログインはないため、cezar 用トークンやパスワードを出す操作はない。上記の公開経路では Tailscale 側のアクセス権を使う。公式 wizard の nginx 経路を使う場合だけ、wizard で設定した Basic 認証のユーザー名とパスワードをブラウザに入力する。今回、その認証ファイルは作成していない。

閲覧・試用が終わったら停止する。

```bash
systemctl --user stop v03-cezar.service
```

## 7. 分からなかったこと

- PC・スマホからの到達、Tailscale Serve 公開、ブラウザ上の描画と停止ボタン操作、再起動後の復帰は、この走行では確認していない。途中出力と停止は製品 API で確認した。
- 停止時間の「状態変更」は cancel API 後の最初の GET で確認した時点。「プロセス消失」は採取した全子孫の `/proc/<pid>` がなくなった時点で、主タスク単独の正確な終了時刻は分離していない。
- T4 の費用値は SSE に出ず、実際の請求額も調べていない。Claude の費用は製品が通知した値として記録した。
- Codex 配下にあった既存の `cccc mcp` の登録元は、秘密ディレクトリ内の設定を読まないため不明。引き継ぎでは cezar の dispatch を使い、取得したイベントに CCCC ツールの呼び出しはなかった。
