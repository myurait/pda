## 5. 認証

unit と手動実行に `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude` を設定した。既設の HOME の `.claude` / `.codex` symlink を使用した。unit に `CODEX_HOME` は書かず、手動実行は `env -u CODEX_HOME` とした。実行中の両 CLI でも `CODEX_HOME` が無いことを確認した。API キーを設定していない。

unit の PATH の先頭は `/home/user/.local/bin`。製品は子端末の PATH にさらに `/home/user/v03/pane/data/bin` を先頭追加した。このディレクトリにあったのは `runpane` と `runpane.cjs` で、`claude` / `codex` の別バイナリは無かった。実際の環境は [06-process-environment.txt](evidence/v0.3-pane/06-process-environment.txt)。

Claude は既存の Claude Pro ログイン、Codex は既存の CLI ログインで動作し、追加ログインや API キー入力は求められなかった。Claude に更新通知は出たが、試用前後の `claude --version` はともに2.1.274、Codex は0.156.1だった。

Pane のブラウザ接続には CLI のログインとは別に `pane-remote://` の接続コードが必要だった。コード発行時の出力は値を伏せ、ブラウザ入力に使用したコードも保存しなかった。製品の `data/config.json` には Pane 自身のペアリング設定が残る。これは CLI の認証複製ではない。ブラウザ認証の観測結果は T8 のとおり。

グローバルな Pane skill / MCP 登録とリポジトリの `AGENTS.md` 書換えは、製品設定で無効にした。終了後の `claude mcp list` に Pane は無く、`claude.ai Claude Docs` の接続表示のみだった。`codex mcp list` は登録なし。Pane による追加登録の解除操作は不要だった。製品専用データ内に生成された同梱 skill / agent ファイルは導入物として残し、共有 HOME への追加は見つからなかった。

## 6. 人の手順

今回 root が必要になった手順は無い。以下は公開・再接続用の手順であり、Tailscale Serve の実行と開発 PC / スマホからの到達確認は行っていない。ブラウザの認証成功も本試用では確認できていない。

ローカル転送で試す場合は、ホストで次のように新しい接続コードを発行する。値は端末に一度出るので、ブラウザへ貼り付けるために扱い、報告書には転記しない。停止中に設定してから起動するこの順序は、今回の稼働中の設定変更とは異なり、未検証である。

```sh
systemctl --user stop v03-pane.service
env -u CODEX_HOME \
  HOME=/home/user/v03/agent-home \
  CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude \
  PATH=/home/user/.local/bin:/home/user/v03/pane/cli/node_modules/.bin:/usr/local/bin:/usr/bin:/bin \
  PANE_DIR=/home/user/v03/pane/data \
  /home/user/v03/pane/squashfs-root/pane \
  --ozone-platform=headless --disable-gpu --remote-setup \
  --label 'PDA pane' --listen-port 5116 --prefer-tunnel ssh \
  --no-install-service --no-tailscale-serve
systemctl --user start v03-pane.service
```

開発 PC で `ssh -N -L 5116:127.0.0.1:5116 user@<ミニPCのSSH接続先>` を実行し、`http://127.0.0.1:5116/app/` を開く。`Connect with a code` → `Connection Code` に出力されたコード全体を入れ、`Import & Connect` を押す。今回は開発 PC 側の操作は実施していない。

Tailscale Serve の公開コマンドは指定どおり次の形となる。

```sh
/home/user/.local/bin/tailscale-pda serve --bg --https=19116 http://127.0.0.1:5116
```

画面の URL は `https://<ミニPCのTailscale DNS名>:19116/app/`。接続コード内の API 接続先も同じ HTTPS origin にするため、コード発行コマンドの `--prefer-tunnel ssh` を `--prefer-tunnel manual --base-url 'https://<ミニPCのTailscale DNS名>:19116'` に置き換える。`--listen-port 5116`、`--no-install-service`、`--no-tailscale-serve` と環境変数は同じにする。公開後は同じ tailnet の端末で画面を開き、コードを入力する。[公式手順](https://runpane.com/docs/remote-daemon)の接続方法と [固定版の setup オプション](https://github.com/greenfield-inc/Pane/blob/ec2a558468481301d73d9d671b4a3a203834147d/main/src/daemon/setupRemoteHostCli.ts#L146-L162)を参照。

試用後の停止は `systemctl --user stop v03-pane.service`。現在も停止状態である。

## 7. 分からなかったこと

- 稼働中に発行した接続コードが403になった根本原因。1回目の画面待機 timeout 後、設定反映の待機を入れた2回目でも認証が成立せず、上限のため終了した。停止中のコード発行と再起動で変わるかは試していない。
- ブラウザ認証後の端末操作、開発 PC / スマホからの SSH / Tailscale 経由の到達、再起動後の復帰。API/CLI で確認した編集・停止・引き継ぎの結果から、これらの成功は推定していない。
- RSS は T2 実行中の1時点だけであり、継続運転時や同時実行数を増やした場合の使用量は測っていない。

必須証拠と終了処理の照合結果は [11-verification.txt](evidence/v0.3-pane/11-verification.txt)。
