## 4. Claude Code と Codex の起動のされ方

Gateway は systemd user manager PID `1274` の下で PID `203946` として起動した。T2 の Claude は PID `204970`、PPID `203946`。実行引数は次のとおり（セッション UUID と一時設定の可変パスだけ省略）。

```text
/home/user/.local/bin/claude
  --disallowedTools ScheduleWakeup,CronCreate,Bash(run_in_background:true),Monitor
  --strict-mcp-config --mcp-config /tmp/openclaw-cli-mcp-<一時名>/mcp.json
  --effort high --print --input-format stream-json --output-format stream-json
  --verbose --include-partial-messages --replay-user-messages
  --permission-prompt-tool stdio --permission-mode default --setting-sources user
  --model claude-sonnet-5 --allowedTools mcp__openclaw__* --session-id <UUID>
```

これは [claude-cli backend](https://docs.openclaw.ai/gateway/cli-backends) の経路で、未改変の Claude Code 実行ファイルを直接起動したもの。`mcp__openclaw__sessions_spawn` は製品が標準で供給する Gateway ツール橋渡しであり、この走行で MCP サーバを追加したものではない。設定では `acpx.enabled=false`。プロセスにも acpx は出なかった。

Codex は PID `204355`、PPID `203946`、実行引数は `/home/user/.local/bin/codex app-server --listen stdio://`。T2 中にもこのプロセスが存在し、T4/T5 で同じ PID が使われた。T4 ではその下に `codex-code-mode-host` PID `205523`（0.156.1 の実行ファイルのディレクトリ）が現れた。[Codex harness](https://docs.openclaw.ai/plugins/codex-harness) の app-server 経路である。T5 の中断は app-server の終了ではなく、対象 run の停止として観測した。

## 5. 認証

Gateway の実環境は `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude`、`PATH=/home/user/.local/bin:/usr/local/bin:/usr/bin:/bin`。unit に `CODEX_HOME` はない。手動 CLI 用の既存 `oc` ラッパーは `env -u CODEX_HOME` と API キー類の unset を行う。tmux の信頼確認でも同じ指定を使った。

`.claude` / `.codex` の symlink は既存の認証複製先を指すものを使った。Claude は上の `CLAUDE_CONFIG_DIR` を継承した。Codex plugin は `appServer.homeScope=user` を使用し、実際の app-server 子プロセスでは製品により `CODEX_HOME=/home/user/v03/agent-home/.codex` が設定されていた。HOME の `.codex` と同じ文字列である。子プロセスの PATH は製品により Node のディレクトリ等が先頭に加わったが、起動された Claude/Codex は指定の絶対パスだった。

このログイン経路は [Codex の認証と homeScope](https://docs.openclaw.ai/plugins/codex-harness-reference/auth) と同梱公式文書で照合した。API キーの入力、OpenClaw への OAuth インポート、再ログインは行っていない。両 CLI の準備と T2/T4 は既存ログインのまま進み、認証入力を求めるエラーは出なかった。

保護対象の認証ファイルは読まず、表示・複製・編集していない。製品 state のファイル名検査では `auth.json`、`auth-profiles.json`、`.credentials.json`、`credentials.json` は見つからなかった。これはファイル名による確認で、状態 DB の中身を検査した結果ではない。DB と既存 fingerprint key は `ls -l` のメタデータのみ記録した。

Gateway 自体の認証は既存の `auth.mode=none`。API クライアントはその接続用にメモリ内で device identity を作り、ローカル pairing を経て接続した。返された device token 等は証拠保存時に伏せ、CLI の認証情報をクライアントへ渡していない。

## 6. 人の手順

root が必要になった導入・試用の手順はなかった。試用後のサービスは停止中なので、同じミニ PC の `user` で次を実行して起動する。

```bash
systemctl --user start v03-openclaw.service
```

開発 PC から SSH ローカル転送を用いる場合の画面 URL は `http://127.0.0.1:5114/`。転送先はミニ PC の `127.0.0.1:5114`。現在の設定には画面用の共有トークン・パスワードはない。[画面の接続・pairing 手順](https://docs.openclaw.ai/web/control-ui/connect-and-pair) では、直接 loopback のブラウザ device identity はこの認証方式で自動 pairing される。画面が `pairing required` になった場合は、タブを開いたままホストで次を実行する。

```bash
/home/user/v03/openclaw/oc devices list
/home/user/v03/openclaw/oc devices approve <requestId>
```

Tailscale Serve の公開はこの走行では変更していない。指定の操作は次のとおり。

```bash
/home/user/.local/bin/tailscale-pda serve --bg --https=19114 http://127.0.0.1:5114
```

公開後の URL は `https://<ミニPCのTailscale DNS名>:19114/`。別 origin を使うため、必要な Control UI origin を設定する操作は次の形になる。これはこの走行では未実施であり、Serve 経由の接続と pairing は設計側の確認対象。

```bash
/home/user/v03/openclaw/oc config set gateway.controlUi.allowedOrigins \
  '["https://<ミニPCのTailscale DNS名>:19114"]' --strict-json
systemctl --user restart v03-openclaw.service
```

今回 `gateway.tailscale.mode=off` なので、外部の `tailscale-pda serve` と製品自身が管理する Tailscale 認証を同じ動作とは扱っていない。Serve の設定だけでブラウザの認証・pairing が完了するかは未確認。

## 7. 分からなかったこと

- ブラウザにおける実際の表示、スマホ・別端末からの到達、SSH 転送、Tailscale Serve の接続・pairing は試していない。途中出力と停止の結果は、画面が使う Gateway API での観測である。
- 停止所要時間の 0.0136 秒 / 0.0033 秒は、採取クライアントの停止要求開始から `aborted` イベント受信まで。OS プロセスの終了時刻そのものではない。Claude の今回の PID 消滅は約2.2秒後の確認、Codex app-server は再利用のため残った。
- T9 の親子間では、依頼先の途中出力は子セッションを API で購読して見えた。親の画面だけで同じ出力が見えるかは確認していない。
- Codex→Claude の T9 で README に残った使用例は `python`、実行確認は `python3` だった。このマシンには `python` コマンドがなく、この例をそのまま実行できることは確認していない。生成物は修正せず証拠に残した。
- 常駐はこの試用時間内の確認で、再起動後の自動復帰や長時間運用は試していない。状態 DB 内の認証データの有無も、秘密を読まない条件のため調べていない。
