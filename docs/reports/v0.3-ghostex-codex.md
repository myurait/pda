## 4. Claude Code と Codex の起動のされ方

T2 採取時は `claude` PID 299354 の親が bash PID 299343、その親が `zmx run S2d-P6xce-G3rty -d --initial-command /bin/bash -lic …` PID 299342 だった。T4 採取時は `codex --no-daemon` PID 300534 の親が bash PID 300522、その親が `zmx run S2d-P6xce-G5tq8 …` PID 300521 だった。両方の zmx daemon の PPID は user systemd の 1274。gxserver PID 299018 の子には `zmx watch-title` と WebSocket のための `zmx attach --require-existing` があった。長い shell 初期化引数は ps の証拠に省略せず保存した。

実行ファイルの解決先は `/proc/<pid>/exe` のメタデータで Claude 2.1.274 と Codex 0.156.1 の実体に一致した。Ghostex の [helpers.rs:37](https://github.com/maddada/Ghostex/blob/85e925a9e9c8527d2f05e58e3a3df9fef65b28ab/server/src/agents/helpers.rs#L37) は既定のコマンドを `claude` / `codex` とし、[launch_plan.rs:439](https://github.com/maddada/Ghostex/blob/85e925a9e9c8527d2f05e58e3a3df9fef65b28ab/server/src/agents/launch_plan.rs#L439) が端末に渡す起動文字列を組み立てる。[同:543](https://github.com/maddada/Ghostex/blob/85e925a9e9c8527d2f05e58e3a3df9fef65b28ab/server/src/agents/launch_plan.rs#L543) では Codex に `--no-daemon` を付ける。今回の Claude はこの端末 CLI 経路であり、Claude Agent SDK や ACP adapter を経由していない。

途中出力の証拠は製品の端末 WebSocket の受信フレームを JSON Lines にし、受信時刻を付けたもの。ANSI 制御列は JSON のエスケープとして保持した。捕捉を終える際のソケット close に続く `error` イベントも記録しており、実行途中のストリーム停止とは区別した。T2 の chat API には `messages: []`、`status: starting`、`working: true` が返った時点があり、Claude の会話 ID はセッション一覧でも未設定だった。一方、端末 API では途中説明と完了まで読めた。

## 5. 認証

製品、子エージェント、準備用 CLI の `HOME` は `/home/user/v03/agent-home`。用意済みの `.claude`、`.codex` symlink を利用した。Claude には `CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude` を渡した。Codex には `CODEX_HOME` を渡しておらず、手動起動用 `gx-env` は `env -u CODEX_HOME`、unit にその変数の設定はない。実プロセスでも未設定を確認した。`PATH` の先頭は `/home/user/.local/bin`。製品のデータは XDG 環境変数で `/home/user/v03/ghostex/xdg/` にまとめた。

Claude / Codex の再ログインや API キー入力は求められなかった。両 CLI の認証本体と設定ファイルの中身は直接読まず、表示・複製・手編集もしていない。フォルダの信頼設定は 3 節の CLI 操作による。T9 の Codex Full Access は、その受信・送信セッション内の操作であり、最後にそのセッションを閉じた。

gxserver は自身の API 認証用に `xdg/state/ghostex/gxserver/auth/token`（0600、44 bytes）を作った。これは Claude / Codex の認証のコピーではない。値は記録していない。API を使う試用プログラムは製品の `gxserver endpoint` の出力をメモリ内で接続に使い、証拠には token を含めなかった。Web は `/api/webBootstrap` から同じ認証を取得し、入力画面を経ずに接続処理を始めた。

終了時に `ghostex kill` で `G3rty`、`G5tq8`、`G97hi` を閉じ、最終構成の確認後に `systemctl --user stop v03-ghostex.service` を実行した。専用 tmux サーバにセッションが残っていないこと、製品プロセスと待ち受けが残っていないことを確認した。ビルド用 sccache の daemon も停止した。削除したものは次のとおり。

- gxserver が作った API 認証 token。次回の起動時は製品が再生成する。
- 今回新しくできた `/home/user/pda/secrets/claude/backups/.claude.json.backup.` に続く `1791111330454`、`1791111394013`、`1791111951529`、`1791112136112`、`1791111826992` の 5 ファイル。内容を読まず、メタデータだけ記録して削除した。
- scratch に試用でできた `__pycache__/`。

`.credentials.json`、`auth.json`、`.claude.json`、`settings.json`、`config.toml` を後片付けのために変更・削除していない。Ghostex の MCP、hook、plugin、skill の登録は行っていない。終了時の `codex mcp list` は登録なし、`claude mcp list` は cloud 側の `claude.ai Claude Docs` を表示した。製品、ビルド道具、scratch と実行時データは残した。[10-cleanup.txt](evidence/v0.3-ghostex/10-cleanup.txt)、[10-claude-mcp-list.txt](evidence/v0.3-ghostex/10-claude-mcp-list.txt)、[10-codex-mcp-list.txt](evidence/v0.3-ghostex/10-codex-mcp-list.txt) を参照。

## 6. 人の手順

今回 root が必要になった手順はない。sudo、apt、既存サービスの設定変更は行っていない。

再度起動する場合は、このマシンで次を実行する。

```sh
systemctl --user start v03-ghostex.service
```

Web の URL は `http://127.0.0.1:5118/`。画面配信と bootstrap は応答したが、このマシンの headless Chromium では前述の描画停止が残っている。ログイン値を入力する操作はなく、製品の bootstrap がローカルの API token を取得する。SSH クライアント用の接続情報が必要なら、次の製品コマンドで出せる。出力には秘密の値が含まれるので、報告書には値を記載していない。

```sh
/home/user/v03/ghostex/gx-env /home/user/v03/ghostex/bin/gxserver endpoint
```

指定された Tailscale Serve の公開コマンドは次のとおり。この走行では実行していない。

```sh
/home/user/.local/bin/tailscale-pda serve --bg --https=19118 http://127.0.0.1:5118
```

このコマンドが転送するのは画面側の 5118 である。実測した bootstrap の `baseUrl` は絶対 URL `http://127.0.0.1:58744` だった。そのため、別端末のブラウザでは 5118 だけを転送しても API 接続経路は揃わない、という推定になる。設計側が SSH で確認する際は、画面の 5118 と API の 58744 を両方転送し、ローカルで上記 URL を開く経路を確認する必要がある。HTTPS 公開下の HTTP API 接続、Host / Origin 条件を含め、Tailscale Serve だけでブラウザ操作が成立するかは未検証である。

公式の別端末用アプリの経路は、Ghostex の `Settings > Remote > Remote machines > Add a machine` で SSH 情報または Easy Connect を登録し、gxserver に接続する手順。[公式 guide](https://github.com/maddada/Ghostex/blob/85e925a9e9c8527d2f05e58e3a3df9fef65b28ab/skills/ghostex-help/references/features.md#L1653) に記載されている。この走行で用意した HOME と XDG 環境を使うには上記 `gx-env` の環境が必要であり、アプリの自動導入がこの配置をそのまま使えるかは試していない。CLI の端末表示は、その環境で `ghostex sessions` と `ghostex attach <selector>` を使う手順である。現在は試用セッションを閉じている。

確認を終えたら次で停止する。

```sh
systemctl --user stop v03-ghostex.service
```

## 7. 分からなかったこと
