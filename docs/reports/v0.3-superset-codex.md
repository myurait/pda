## 5. 認証

製品の unit と手動起動の環境は次のとおり。`SUPERSET_HOME` はインストーラの導入先指定であり、製品の実行時データには別の `SUPERSET_HOME_DIR` を使った。

| 設定 | 値・扱い |
|---|---|
| `HOME` | `/home/user/v03/agent-home` |
| `CLAUDE_CONFIG_DIR` | `/home/user/pda/secrets/claude` |
| `CODEX_HOME` | unit に記載せず、手動起動では `env -u CODEX_HOME` で除外 |
| `PATH` 先頭 | `/home/user/.local/bin` |
| `SUPERSET_HOME_DIR` | `/home/user/v03/superset/state` |
| 既存 symlink | HOME の `.claude` → `/home/user/pda/secrets/claude`、`.codex` → `/home/user/pda/secrets/codex`。メタデータのみ確認 |

製品はログイン要求を CLI のエラーとして表示した。[認証 middleware](https://github.com/superset-sh/superset/blob/e15ae8cfacfdb08f5706a8a018672dc327b62d19/packages/cli/src/commands/middleware.ts#L5) が先に [resolveAuth](https://github.com/superset-sh/superset/blob/e15ae8cfacfdb08f5706a8a018672dc327b62d19/packages/cli/src/lib/resolve-auth.ts#L21) を呼び、通常のローカル起動では Superset の API key か OAuth を求める。さらに [start](https://github.com/superset-sh/superset/blob/e15ae8cfacfdb08f5706a8a018672dc327b62d19/packages/cli/src/commands/start/command.ts#L39) は Superset API から組織を取得する。Claude／Codex の既存ログインをこの認証に使う設定は見つからず、共通指示2.3に従って後続試用を未実施とした。API key の入力、Superset のログイン、認証の複製は行っていない。

`state/config.json`、host の manifest、HOME の `.superset` は生成されなかった。エラーの位置とソースから、host 起動時の agent hook／wrapper 登録処理には到達していないと確認した。製品による MCP・hook・plugin の登録はなく、解除コマンドの対象はなかった。秘密ファイルの内容は読まず、証拠にも写していない。

試用後に `systemctl --user stop v03-superset.service` を実行し、失敗出力を証拠に保存した後で当該 unit の failed 状態を解除した。Claude は `/exit` で終了。Codex に `/exit` を送った後も専用 session が残ったため、`tmux -L v03-superset kill-server` で終了した。終了後は専用 tmux server がなく、scratch にいるプロセスと Superset 配布実行ファイルのプロセスは0件、5122番の待ち受けもない。

信頼設定用に起動した Claude が作った `.../.claude/backups/.claude.json.backup.1791117619858` と `.claude.json.backup.1791117687228` の2件を、名前・mtime・`ls -l` だけで確認し、内容を開かず削除した。ここで `...` は `/home/user/v03/agent-home`。認証本体、`settings.json`、`config.toml` は手編集・削除していない。HOME 内の既存 `.local/bin/claude` は mtime だけ変わり、symlink の対象は前後とも既存の `2.1.289` で同一だった。指定 PATH の CLI は終了時も `2.1.274` のままで、既存リンクと導入物は保持した。証拠: [10-cleanup.txt](evidence/v0.3-superset/10-cleanup.txt)。

## 6. 人の手順

今回、root が必要になった手順はない。常駐を阻害したのは Superset のログインである。

以下は今回未実施の、Superset 自体へのログイン手順。製品の [CLI Getting Started](https://docs.superset.sh/cli/getting-started) と固定版 [auth.ts:270–400](https://github.com/superset-sh/superset/blob/e15ae8cfacfdb08f5706a8a018672dc327b62d19/packages/cli/src/lib/auth.ts#L270) に基づく。CLI が表示する URL をブラウザで開き、Superset アカウントで認証する。固定版にはブラウザから返されたコードを CLI に貼り付ける経路もある。ログイン時の URL・コード・トークンの値は報告書や証拠に保存しない。

```bash
cd /home/user/v03/work/superset/scratch
env -u CODEX_HOME \
  HOME=/home/user/v03/agent-home \
  CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude \
  PATH=/home/user/.local/bin:/home/user/v03/superset/bin:/usr/local/bin:/usr/bin:/bin \
  SUPERSET_HOME_DIR=/home/user/v03/superset/state \
  /home/user/v03/superset/bin/superset auth login
systemctl --user start v03-superset.service
systemctl --user status v03-superset.service --no-pager
```

認証の保存先は `/home/user/v03/superset/state/config.json`。起動できた場合の endpoint とローカル認証情報の manifest は `/home/user/v03/superset/state/host/<organizationId>/manifest.json`。今回はどちらも未生成で、値は未取得。

指定された Tailscale Serve の公開コマンドは次のとおり（今回未実行）。

```bash
/home/user/.local/bin/tailscale-pda serve --bg --https=19122 http://127.0.0.1:5122
```

今回の状態では転送先が起動していない。このコマンドで standalone host にブラウザ用 IDE が追加されるわけではなく、開ける画面 URL は未確認。[Remote Access の公式手順](https://docs.superset.sh/remote-access)は Superset のホストを desktop app／CLI から扱う構成を説明する。iPhone は公式文書上 Superset Pro、iOS 26 以降、ホストの Remote Access が必要。画面側も Superset へのログインが必要で、既存 Claude／Codex の認証だけでの画面ログインは確認していない。

再試用後は user unit を停止する。実際に host／端末を起動した場合は、同じ HOME と `SUPERSET_HOME_DIR` の環境で `superset stop --terminals` を実行するのが公式の全端末停止手順。今回の host は起動前に終了したため、この追加停止操作は不要だった。
