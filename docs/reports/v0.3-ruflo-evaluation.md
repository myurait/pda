## 結論

棄却する。必須の条件 R13 (途中の出力が見える) を満たさない。製品の作りが、エージェントの出力を終わるまで溜めてまとめて返す形で、設定やセットアップの不備ではない。

- 根拠: Claude Code と Codex に仕事を渡す製品の部分 (dual-mode) は、`claude -p <依頼> --output-format text` と `codex exec ...` を `child_process.spawn` で起こし、標準出力を文字列に溜めて、プロセスが終わったときに返す ([v3/@claude-flow/codex/src/dual-mode/orchestrator.ts の 206〜281 行目](https://github.com/ruvnet/ruflo/blob/caf5078be6627c6496fa2497a63b72e80a0bcf14/v3/@claude-flow/codex/src/dual-mode/orchestrator.ts#L206))。CLI の結果の表示も本文を出さない。
- 試用でも、T2、T4、T9 のどれでも、起動と完了の通知の間に本文の途中の出力は 1 件も届かなかった。
- 指示の手がかりにあった別の経路 (`headless-worker-executor.ts` の `claude --print --output-format json`) も、終わったときに 1 つの JSON を返す形である。

- 画面 (RuVocal) は、公式の Dockerfile でのビルドが、OpenAI 互換の API の接続先 (`OPENAI_BASE_URL`) が無くて失敗し、出せなかった。棄却の根拠にはしていない。
- T2 は、Claude Code に編集の権限を渡す設定が製品の起こし方に無く、編集が拒まれて差分が出なかった。
- T3、T5 は、製品の JavaScript の API の `stopAll()` で、Claude は 0.538 秒、Codex は 0.018 秒で子のプロセスが止まった。
- T9 は、共有のメモリを通す受け渡しを両方向に試したが、Claude Code がメモリの読み書きの承認を得られず、どちらも渡せなかった。
