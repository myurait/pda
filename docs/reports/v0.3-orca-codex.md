## 5. 認証

unit には指定の `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude`、`CODEX_HOME=/home/user/pda/secrets/codex` と、先頭が `/home/user/.local/bin` の PATH を設定した。`LIBGL_ALWAYS_SOFTWARE=1`、`ORCA_TELEMETRY_DISABLED=1`、`DO_NOT_TRACK=1` も設定し、DISPLAY は渡していない。Orca の Claude/Codex の managed account 選択はどちらも null、登録アカウントは0件だった。`account add`、API キーの投入、再ログインはしていない。

事前の tmux 起動では、Claude の `Yes, I trust this folder` と Codex の `Trust and continue` を選び、CLI 自身に信頼を保存させて終了した。秘密情報のファイルや CLI の設定ファイルを、この走行の操作側から読み書きしていない。

Claude の Orca 端末では `WARNING: Claude Code running in Bypass Permissions mode` が表示され、`Yes, I accept` を選んだ。Codex は `permissions: YOLO mode` と表示され、追加同意の画面は出なかった。両者とも、試用依頼の前にログインや API キーを求めなかった。

**指示の想定と異なった点:** 初回起動の Orca は、指定した CODEX_HOME を custom home と判定し、自分の `codex-runtime-home` へ認証を複製した。`/home/user/v03/agent-home/.config/orca/codex-runtime-home/` 内の `home/auth.json`、`system-default-auth.json`、`shared-runtime-auth-provenance.json` が通常ファイルとして生成されていることをメタデータだけで確認した。内容は取得していない。製品が生成したこれらは削除・変更していない。

その後、unit に `ORCA_CODEX_HOME=/home/user/pda/secrets/codex` を追加した。[custom home 判定](https://github.com/stablyai/orca/blob/v1.4.218/src/main/codex/codex-real-home-path.ts) と [PTY の環境処理](https://github.com/stablyai/orca/blob/v1.4.218/src/main/ipc/pty/host-env/codex-home.ts) が両変数の一致を扱うことを確認したためである。この追加後の Codex プロセスでは `CODEX_HOME` と `ORCA_CODEX_HOME` が除去され、`HOME=/home/user/v03/agent-home` の既設 `.codex` symlink を通して指定の認証先を使った。これはソースで確認した内部環境変数の利用で、公式手引きの手順ではない。

hooks の開始状態、終了前状態、`agent hooks off --json` とその後の状態は [10-hooks.txt](evidence/v0.3-orca/10-hooks.txt) に記録した。off は `appliedBy=runtime` / `enabled=false` で成功した。直後の status は設定保存前の `enabled=true` を返したが、両 CLI の hook は既に `not_installed` / `managedHooksPresent=false`。保存待ち後の再確認で `enabled=false` と両方の hook 不在を確認した。off の再実行はしていない。状態表示のための製品自身による設定更新は、指示ファイルの承認範囲で行わせた。操作側は認証先の settings / hooks / config / `.claude.json` の内容を開いていない。

## 6. 人の手順

この走行で root を必要とする作業はなかった。導入物を残し、15:53 JST に unit を停止した。全端末が0件になった後、別 scope の terminal daemon も停止し、Orca 実行ファイルの残存 PID と5113番の待ち受けがないことを確認した。既存の OpenObserve / otel-collector は稼働を継続している（[11-shutdown.txt](evidence/v0.3-orca/11-shutdown.txt)）。以下の遠隔接続と Tailscale Serve は未実施の手順である。

### 起動とブラウザ

```bash
systemctl --user start v03-orca.service
orca_pid=$(systemctl --user show v03-orca.service -p MainPID --value)
journalctl _PID="$orca_pid" -o cat --no-pager |
  jq -Rr 'fromjson? | select(.type == "orca_server_ready") | .pairing.webClientUrl'
```

このコマンドを利用者の端末で実行して最新の URL を取り出し、同じ tailnet のブラウザで開く。形は `http://100.69.167.33:5113/web-index.html#pairing=<符号>`。値は報告書・証拠に載せていない。通常のユーザー名 / パスワード入力ではなく、起動時の pairing capability を渡す方式。画面ファイルの HTTP 200 までを実測し、ブラウザでの pairing 完了は未確認。

### Mac の Orca app

上記 jq の最後を `.pairing.url` に替えて、runtime 用のリンクを手元で取得する。Mac で **Settings → Remote Orca Servers → Add Server** を開き、名前とそのリンクを入力して Add Server。Disconnected なら Connect を押す。この手順は [Remote Orca Servers](https://github.com/stablyai/orca/blob/v1.4.218/docs/site/content/docs/remote-servers.mdx) による。

### スマホの Orca app

スマホ用は unit の `ExecStart` に `--mobile-pairing` を追加して起動する。

```text
/home/user/v03/orca/squashfs-root/AppRun serve --port 5113 --pairing-address 100.69.167.33 --mobile-pairing --json
```

unit の環境はそのままにし、編集後は `systemctl --user daemon-reload`、`systemctl --user restart v03-orca.service`。最新の `.pairing.url` を取得して、同じ tailnet 上の Orca Mobile の **Pair** に貼る。`--json` なしの前景起動なら公式手引きの QR 表示を使える。headless server のプッシュ通知は試していない。

### Tailscale Serve

unit の `--pairing-address` を **`https://pda-web.tailaff53a.ts.net:19113`** に変更する。明示した proxy 側のポートを含む URL を渡し、Orca に `wss://pda-web.tailaff53a.ts.net:19113` を広告させる。[公式の reverse proxy の説明](https://github.com/stablyai/orca/blob/v1.4.218/docs/reference/headless-linux-server.md) に基づく。

```bash
systemctl --user daemon-reload
systemctl --user restart v03-orca.service
/home/user/.local/bin/tailscale-pda serve --bg --https=19113 http://127.0.0.1:5113
```

最新の起動 JSON から URL を取り直す。ブラウザ URL の形は `https://pda-web.tailaff53a.ts.net:19113/web-index.html#pairing=<符号>`。Mac には runtime 用、スマホには `--mobile-pairing` で生成したリンクを使う。待ち受け自体は引き続き `0.0.0.0:5113`。

再試用で hooks を使う場合は、unit 起動後、unit と同じ HOME・認証環境を付けた同梱 CLI で `agent hooks on --json`。終了時は `agent hooks status --json` → `agent hooks off --json` → `agent hooks status --json` の順に確認してから `systemctl --user stop v03-orca.service` とする。

## 7. 分からなかったこと

- T3 の内部停止時刻は取得できていない。22.434秒は、停止した画面を最後に確認した上限。
- T7 は処理中の単一時点の RSS で、全期間のピーク RSS は取得できていない。
- 追加した内部環境変数による Codex の直接参照が、別版でも同じになるかは未確認。
- 初回に Orca が複製した認証の内容・元ファイルとの一致は確認していない。認証ファイルを読まない条件のため、メタデータと製品ソースで記録した。
- 再起動後の terminal handle の継続性、再起動時の自動常駐復帰、スマホの中断操作は試していない。
