## 5. 認証

unit と事前準備の CLI に次を渡した。API キーは設定していない。

```text
HOME=/home/user/v03/agent-home
CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude
CODEX_HOME=/home/user/pda/secrets/codex
PATH=/home/user/.local/bin:/home/user/v03/cccc/bin:/usr/local/bin:/usr/bin:/bin
```

既設の `agent-home` の symlink を前提に起動した。認証ファイルの内容は読み出し・表示・複製せず、直接編集していない。`cccc setup --runtime codex` は製品側から `codex mcp add cccc -- /home/user/v03/cccc/bin/cccc mcp` を実行し、既存の `CODEX_HOME` の設定に MCP 登録を追加した。`cccc setup --runtime claude` は `injected_per_session` / `ready` と返した。

事前準備は専用 tmux socket `v03-cccc` の中で行った。Codex は scratch の `Trust this folder?` で `Trust and continue` を選び、通常の入力待ち画面に到達して終了した。信頼の設定は CLI に書かせた。

Claude は初回起動でテーマ選択後に `Select login method:` を表示した。同じ環境の `claude auth status --json` から非秘密フィールドだけを取り出すと `loggedIn=true`、`authMethod=claude.ai` だった。公式 CCCC 文書にある bypass-mode の事前操作に合わせ、`claude --dangerously-skip-permissions` で1回だけ再試行したが、subscription を選ぶと `Browser didn't open? Use the url below to sign in (c to copy)` と `Paste code here if prompted >` が出た。追加ログインは行わず終了し、scratch の信頼確認と bypass disclaimer の受諾は完了していない。認証 URL は証拠から除いた。

CCCC の localhost 画面はログインや API キーを求めなかった。Codex の製品内実行も既存ログインで依頼を処理した。Claude の製品内実行は認証の成否を試す前に版要件で止まった。

## 6. 人の手順

今回、root が必要な導入手順はなかった。試用後は停止しているため、画面を開くときはミニ PC の利用者 `user` で次を実行する。

```bash
systemctl --user start v03-cccc.service
```

開発 PC からの SSH ポート転送で localhost の画面を開く確認は設計側で行う。画面のパスは `/ui/`、選択する Group は `cccc scratch`。直接 localhost として開いた画面ではログイン不要。Group の Actor は試用終了時に stopped であり、unit を起こすことと仕事を開始することは別の操作になる。

Tailscale 経由の公開に先立ち、localhost 画面の **Settings → Web Access** で **Admin Access Token** を作成し、値を保管する。今回トークンは作成していない。remote で初回設定する場合のホスト確認コードの場所は `/home/user/v03/cccc/state/web_bootstrap_token` であり、今回その内容は読んでいない。詳細は [公式の認証手順](https://chesterra.github.io/cccc/guide/web-ui#security)を参照する。

ミニ PC で実行する公開コマンドは次のとおり。今回、このコマンドは実行していない。

```bash
/home/user/.local/bin/tailscale-pda serve --bg --https=19109 http://127.0.0.1:5109
```

別の端末では `https://<このミニPCのTailnet DNS名>:19109/ui/` を開き、Sign in のフォームに作成した Admin Access Token を入力する。公式文書では LAN / reverse proxy 越しの API 利用にはこの認証が必要とされている。token の値を URL や報告書には入れない。

Claude を再試用する場合、[公式 runtime 文書](https://chesterra.github.io/cccc/guide/runtimes#managed-codexclaudegrokopencodekilo-sessions)が要求する `2.1.259` 以降と、同じ `CLAUDE_CONFIG_DIR` での初回確認完了が前提になる。この走行では指定された既存 `2.1.205` を更新していない。

## 7. 分からなかったこと

- Claude Code の既存ログインで実際に編集・途中出力・途中停止ができるか、およびその作業中の資源。版要件でセッション開始前に止まった。
- Claude の `auth status` がログイン済みと表示する一方で、初回 UI がログイン方法を要求する理由。認証内容や設定ファイルを調べる方法は取っていない。
- PC / スマホからの到達、Tailscale Serve 越しのログイン、OS 再起動後の復帰。今回の指定範囲では実施していない。
- `headless` WebSocket ではセッション開始・切断・停止のイベントを受信したが、今回の Codex の turn / text delta は得られなかった。途中出力として確認できたのは、`ledger` で実行中に届く Codex の進捗メッセージと、T5 で同時受信した native terminal WebSocket の出力。peer runtime を visible にする設定を行っても、観測中の turn / text delta は得られなかった。

初回 T4 が誤った作業先に作成した `/home/user/v03/cccc/hello.py` と `/home/user/v03/cccc/README.md` は残した。製品の `source/` と `bin/cccc` は変更していない。T4 の成功時の差分は証拠に保存し、T5 のため scratch を初期状態へ戻した後、編集前に停止したため、終了時の scratch の `git status --short` は空だった。
