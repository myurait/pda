## 4. Claude Code と Codex の起動のされ方

`codexia-web` PID 329314（親は user systemd PID 1274）の子として次が起動した。

```text
PID 329732, PPID 329314:
claude --output-format stream-json --verbose --input-format stream-json --permission-mode bypassPermissions

PID 329331, PPID 329314:
/home/user/.local/bin/codex app-server
```

Claude の実体は `/home/user/.local/share/claude/versions/2.1.274`。採取した引数に `-p` / `--print` は無い。Codex の実体は `/home/user/.codex/packages/standalone/releases/0.156.1-x86_64-unknown-linux-musl/bin/codex`。いずれも cwd は scratch だった。T4 終了時には Codex の子 `codex-code-mode-host` PID 330151 も存在した。

ソースでは [CCState が Rust の ClaudeClient を生成](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/crates/cc/src/state.rs#L69) し、[message_service が接続](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/crates/cc/src/services/message_service.rs#L36) する。依存 crate は [PATH 上の claude を探索](https://github.com/milisp/claude-agent-sdk-rs/blob/1d9bbaed097740c19f2f136d324dd0f54d5ca335/src/internal/transport/subprocess.rs#L153) し、[Command に引数を設定して spawn](https://github.com/milisp/claude-agent-sdk-rs/blob/1d9bbaed097740c19f2f136d324dd0f54d5ca335/src/internal/transport/subprocess.rs#L707) する。この経路で npm の `@anthropic-ai/claude-agent-sdk` や ACP adapter は使用していない。Codex は [app_server.rs の103〜131行](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/crates/codex/src/app_server.rs#L103) で `app-server` を引数に起動する。

## 5. 認証

unit と事前信頼確認では `HOME=/home/user/v03/agent-home`、`CLAUDE_CONFIG_DIR=/home/user/pda/secrets/claude`、PATH の先頭を `/home/user/.local/bin` とした。Codex の `CODEX_HOME` は unit に書かず、手動 CLI は `env -u CODEX_HOME` で起動した。unit プロセスの該当環境変数だけを確認し、`CODEX_HOME` が未設定であることも記録した。既設の `.claude` / `.codex` symlink を使った。

API キーは入力していない。Claude の init は `apiKeySource=none`、Codex の account API は `accountType=chatgpt` を返した。localhost の製品画面・API から再ログインは要求されなかった。tmux では両 CLI の信頼確認に答え、設定は CLI 自身に保存させた。

認証ファイルの内容は読まず、表示・複写・手編集もしていない。製品が生成した独自の端末認証ファイル `/home/user/v03/agent-home/.codexia/device-token` は `ls -l` のみ記録し、試用後に削除した。CLI 認証の複製 `codexia-accounts/` は生成されなかった。CodexAuth 画面には [アカウント snapshot を自動保存する処理](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/src/components/codex/CodexAuth.tsx#L93) があり、その画面は開かず既存ログインを API から利用した。

この走行で新規にできた `/home/user/pda/secrets/claude/backups/.claude.json.backup.1791114310165` と `.claude.json.backup.1791114460431` をメタデータ確認後に削除した。試用で生成した Chromium 設定・shader cache・scratch の Claude CLI cache も削除した。認証本体、`.claude.json`、`settings.json`、`config.toml` には手を加えていない。製品の `cache.db` と通常の CLI セッション履歴、導入物、unit は残した。

この走行で永続 MCP・hook・plugin を追加する操作は行っていない。T2 init の `mcp_servers` と `plugins` は空だった。終了確認で `codex mcp list` は設定なし、`claude mcp list` は既存の `claude.ai Claude Docs` を表示した。この既存コネクタは削除していない。証拠は [10-cleanup.txt](evidence/v0.3-codexia/10-cleanup.txt)。

## 6. 人の手順

root が必要だった手順は無い。導入物は残してあるので、他製品の試用 unit が停止していることを確認してから起動する。

```sh
systemctl --user start v03-codexia.service
/home/user/.local/bin/tailscale-pda serve --bg --https=19120 http://127.0.0.1:5120
```

ローカル画面のパスは `/`。設計側が SSH 転送で確認するときは、転送先の `http://127.0.0.1:<ローカル転送ポート>/` を開く。初回は `Select a project` の `Add new project` から `/home/user/v03/work/codexia/scratch/` を選ぶ画面がある。localhost では端末トークンの入力は不要だった。

Tailscale Serve の公開 URL は `https://<このマシンの MagicDNS 名>:19120/`。実際の転送はこの走行では設定していない。製品は [接続元と Host の両方が loopback の場合だけ認証を省略](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/web/src/auth.rs#L172) するため、上記 Serve コマンドだけでブラウザの保護 API まで開けるとは確認していない。

端末トークンが必要な場合、起動後の格納先は `/home/user/v03/agent-home/.codexia/device-token`。利用者自身が取得するコマンドは次のとおり。値を報告書や証拠に貼らない。

```sh
curl -fsS http://127.0.0.1:5120/api/pairing | jq -r .token
```

製品のネイティブ iOS/Android 画面には `Pair desktop` でホスト・ポート・トークンを入力する導線がある。ただし [通常の Web ブラウザでは isPhone() が false](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/src/hooks/runtime.ts#L95) で、[その導線は表示条件外](https://github.com/milisp/codexia/blob/9220b196d88f3b9d8b631228aa58db6167998d29/src/components/layout/AppSidebar.tsx#L146)。今回の127.0.0.1待ち受けと Serve を組み合わせた、通常の Web 画面でのトークン入力手順は確認できなかった。API は Bearer ヘッダか `token` クエリを受け付ける。

確認を終えたら `systemctl --user stop v03-codexia.service` で停止する。現在は停止済みで、次回起動時には削除した端末トークンが再生成される。

## 7. 分からなかったこと

- 開発 PC・スマホ・Tailscale Serve 経由の実到達と、そのブラウザでの端末トークン認証。指示によりこの走行では外部到達確認をしていない。
- T9 の受け手の途中出力と結果の返却。指定された Claude/Codex の経路を Bot の実行先にできず、両方向とも未実施。
- 中断時間は同一マシンの API 要求から終了イベント受信までの1回の計測。モバイル画面の停止操作、通信遅延、OS プロセス終了までの時間は測定していない。
- 画面閲覧中の journal に `500: File does not exist or is a directory` が2回と `500: General D-Bus Error` が1回残った。画面表示と T1〜T5 は上記のとおり確認したが、これらの内部要求が画面の全機能に与える影響は確認していない。
