# 画面が要る情報と操作の入力

これは次の増分で API を設計するための一覧である。モックは通信しない。確認対象は `docs/requirements.md`、`docs/design/basic-design-proposal.md` の Conductor の構成、`registry/executors/*.yaml`、`registry/types/*.yaml`、`src/pda_wrapper/events.py` の出来事の種別一覧に限定した。現行 API がすでに返すという意味ではない。

「取れる」は、基本設計で保存が明記された Conductor の記録、実在する宣言、または列挙された出来事に必要な材料があるという意味である。出来事の payload の実装や全フィールドは調査していない。記録間の関係、専用の意味フィールド、オーナー操作の永続化が必要なものは「新しく要る」と明記する。本文にイベント全件やツールの全出力は出さない。

## 1. 状態と言葉の対応

以下は表示側の対応案。Conductor の機械状態をタスクの完了・中止へそのまま変換しない。

| 対象 | 画面の状態 | Conductor の記録からの対応 | 追加の意味 |
|---|---|---|---|
| セル | 待機 | `SCHEDULED` | 次の回に予約した未生成セルも待機。予約記録は新しく要る |
| セル | 動いている | `IN_PROGRESS` | 担当実行器と開始時刻を関連付ける |
| セル | 終わった | `COMPLETED` | 作業の終了。タスクの完了ではない |
| セル | 失敗した | `FAILED`、`FAILED_WITH_TERMINAL_ERROR`、`TIMED_OUT` | 失敗理由を保持し、後続の判定器 A に関連付ける |
| セル | 中断した | `CANCELED` | オーナー中断か実行の終了かを出所と理由で区別 |
| セル | 終わった／注記あり | `COMPLETED_WITH_ERRORS`、`SKIPPED` | 成功と同一視せず「任意セルの失敗」「実行を省略」を別注記。今回の見本では使用しない |
| 実行 | 動いている | Workflow `RUNNING` | 一つのタスクに複数の実行を関連付ける |
| 実行 | 終わった | Workflow `COMPLETED` | 報告が書けたか、次の自動作業があるかは別の意味フィールド |
| 実行 | 失敗した | Workflow `FAILED`、`TIMED_OUT` | 規則停止の理由と報告を関連付ける |
| 実行 | 中断した | Workflow `TERMINATED` | 再開始前の実行を履歴に保持する |
| 実行 | 中断した／一時停止 | Workflow `PAUSED` | ワーカー中断完了とは断定しない。一時停止の注記とセルの個別状態を併記する。見本では未使用 |
| タスク | 進行中 | 機械状態だけでは決めない | 動作中または次の作業が予約されている。新しく要る：タスク集約状態 |
| タスク | 入力待ち | `COMPLETED` や `FAILED` だけからは決めない | 報告があり、問い／自動作業なし／コア規則停止の理由を持つ。新しく要る |
| タスク | 完了・中止 | 対応なし | オーナーが記録した状態・時刻。新しく要る |

機械状態名の照合資料：[Conductor Task lifecycle](https://conductor-oss.github.io/conductor/devguide/architecture/tasklifecycle.html)、[Workflow API](https://conductor-oss.github.io/conductor/documentation/api/workflow.html)。参照日は 2026-09-25。表はこれらの状態を要件の表示語へ写す設計上の判断であり、使用中の Conductor 版との接続検証は次の増分で行う。

## 8. 送る必要がある情報

すべての操作に対象 ID、操作の識別子、オーナー由来であること、入力時刻が必要。以下は API の入出力項目案であり、URL や HTTP メソッドは定めない。現在の完了・中止記録とオーナーセルの永続化契約は新しく要る。

| 操作 | 送る情報 | 受け付けたあと画面が必要とする情報 |
|---|---|---|
| 1. 実行を中断 | taskId、runId、任意の理由／次の指示 | 中断対象の cellId 全件、受理状態、判定器 A の cellId、中断理由の参照 |
| 2. 指示を重ねる | taskId、runId、指示原文 | ownerCellId、適用する次の roundId、入力待ちから再開した状態 |
| 3. セルを挿し込む | taskId、runId、type、入力原文 | cellId、次の roundId、branchId、合流先、出所=オーナーの操作 |
| 4. 動いているセルへ追加入力 | taskId、runId、cellId、入力原文 | inputId、対象セルでの受理状態、セルへの参照 |
| 5. セルを再試行 | taskId、runId、元 cellId、選んだ executorId、元の type と入力への参照 | 新しい cellId、元セルとの関係、試行履歴、出所=オーナーの操作 |
| 6. 初期の指示を書き換える | taskId、runId、新しい指示、適用方法（以後／最初から） | 以後なら ownerCellId と適用回。最初からなら新 runId と旧実行の中断状態 |
| 7. 完了として記録 | taskId、現在の runId、状態=完了 | オーナーの記録時刻、タスク状態、動作セルがあれば終了対象 |
| 8. 中止として記録 | taskId、現在の runId、状態=中止 | オーナーの記録時刻、タスク状態、止めた実行とセル |
| 実行器を起こす | executorId、操作=起動 | 生死、観測時刻、操作の受付と完了の区別 |
| 実行器を止める | executorId、操作=停止、確認時点の担当セル ID 群 | 中断された全セル、各判定器への関連、実行器の生死 |
| 問いへの返答 | taskId、runId、reportId、questionId、回答（真偽／選択肢 ID／文字列） | 回答済みの問い、残数、全回答時の ownerCellId と次の judgeCellId、入力待ちからの除外 |
| 新しいタスク | 指示原文、任意 workdir、reporterExecutorId | taskId、runId、初期 ownerCellId、先頭 judgeCellId、受付時刻 |

同一操作の再送と、確認後に対象が変わったことを識別するため、操作 ID と対象の版を API 設計時に検討する。回数上限などの入力欄は加えない。

## 9. モックで代用しているもの

型は `src/mock/model.ts`、宣言の写しと見本は `seed.ts`、段階進行と介入は `actions.ts` にある。ブラウザのローカル保存は実サーバの状態を表さない。経過と時刻、稼働、出力、問い、成果物は見本。1 歩ごとの遷移は判定器やオブザーバーへの実呼び出しを行わない。宣言にない observe/report は summarize 対応実行器に模擬的に担わせる。オブザーバーは指示だけを出し、作業は別の作業セルが行う。
